# «Ё» — клавиатура, где у Ё есть место (дорожка KB)

Новый продукт, лендинг L1: механическая 65 % (68 клавиш), алюминиевый корпус (пескоструй), латунная плита 408 г в дне,
PBT с двумя раскладками, у Ё — левый верхний угол и единственный цвет. Три страницы с одинаковыми текстами и сеткой —
различается только источник 3D:

| Страница | Что за 3D | Открыть |
|---|---|---|
| `a-code/` — **A, код на максимуме** | three r186, модель целиком кодом по паспорту (колпачки Cherry кольцами, атлас canvas шрифтом страницы, пластина с вырезами, свитчи — инстансы простых форм), N8AO на десктопе; постер и запасные кадры сняты с её же рендера, у постера ГРИП кодом по камере Blender | `serve_br.py a-code 8783` |
| `b-blender/` — **B, Blender (предрендер)** | только кадры Cycles, 0 КБ three: постер H2v2, набор (кадр + 4 кадра «нажато» в обводах клавиш), оборот 36 × 10° на каждую расцветку (телефон 24 × 15°), разборка 4 станциями | `serve_br.py b-blender 8783` |
| `c-hybrid/` — **C, гибрид** | постер Cycles (как у B) + живое 3D на GLB из Blender: инстансы колпачков + атлас надписей (WebP), расцветки `KHR_materials_variants`, разборка слоями-узлами, тень пола запечена в Cycles; ввод, пружины, разборка — кодом | `serve_br.py c-hybrid 8783` |

Общее для трёх: первый экран — постер = LCP (`<picture>` AVIF/WebP, отдельный портрет для телефона); «Напечатайте что-нибудь»
— нажатия с настоящей клавиатуры посетителя (`event.code` → клавиша, `event.key` → буква его раскладки RU/EN), крупная строка
напечатанного, «ё» — акцентом и подпись «Ё набрана одной клавишей»; на телефоне — касание клавиш на картинке в окне левой
половины раскладки (клавиша ≈ 44 CSS px), полоса листается вбок, кнопка «Правая половина →», RU/EN и Shift; «Три цвета» — фон
раздела плавно меняется под расцветку (Снег #EDEFF0, Графит #141619, Лён #EFE8DC), поворот только перетаскиванием/кнопками/
стрелками; «Как устроена» — одна сцена ≤ 150vh; reduce → кадры, three не грузится; один WebGL-контекст, рендер по требованию
(0 кадров в покое); three (A, C) — после `load` и только по намерению: первое нажатие/касание/клик или остановка ≥ 2,5 с на
разделе с 3D — до этого разделы показывают кадры и уже отвечают на нажатия.

## Рецепт: `KHR_materials_variants` из Blender 5.2.2 до three r186 (три условия)

Проверено в фазе 1 на 12 колпачках (`04-variants/`) и в фазе 2 на полной модели (26 примитивов, 19 с вариантами, 3 расцветки);
на странице C — переключение чипами, живое 3D (`src/model_c.js`), кадры `gallery/c-khr-variants.webp`.

1. **Экспорт (glTF-IO 5.2.40).** Расширение пишется, только если в процессе включено предпочтение аддона
   `bpy.context.preferences.addons['io_scene_gltf2'].preferences.KHR_materials_variants_ui = True` (без него
   `primitives.py:336` молча пропускает варианты; в `-b --factory-startup` это настройка только в памяти). Варианты —
   `bpy.data.scenes[0].gltf2_KHR_materials_variants_variants` (именно `scenes[0]`, не `context.scene`); у меша —
   `mesh.gltf2_variant_mesh_data` (слот, материал, индекс варианта) + `gltf2_variant_default_materials`. Привязка — на меш:
   связанные дубликаты (инстансы) получают её все сразу.
2. **Постобработка.** `gltf-transform optimize` — только с `--join false` (шаг `join` склеивает примитивы и выбрасывает
   привязки: 7 → 3 примитива, у двух вариантов нет); flatten и palette варианты не трогают. Нативный `gltfpack` 1.2 варианты
   держит (`-cc`, и с KTX2 `-tc`, и с WebP `-tw`), но имена узлов/материалов и extras — только с `-kn -ke -km`; для страницы,
   которая ищет узлы по имени, — ещё `-vpf` (без узлов деквантования). Валидатор — 0 ошибок.
3. **three r186.** Расширение — в `gltf.userData.gltfExtensions`, у меша — в `mesh.userData.gltfExtensions`; переключение —
   `parser.getDependency('material', mapping.material)` + назначение материала (как `webgl_loader_gltf_variants`). Если меши
   собираются в `InstancedMesh`, отображения вариантов переносятся с исходного меша; свой патч шейдера (UV ячейки атласа) —
   на каждый материал варианта (`customProgramCacheKey`).

Цена: варианты — это целые материалы (у колпачков — свой полноцветный атлас на расцветку: WebP 2048 — в GLB 159 КБ br целиком,
телефон WebP 512 + упрощение -si 0.4 — 84,5 КБ br); переключение мгновенное, материалы и текстуры варианта грузятся по первому требованию.
Условие применимости: у вариантов должна быть одна геометрия (меняется только материал); если расцветка меняет форму — не
подходит. Обход без стандарта: `material.color` по имени материала из JS — 0 КБ, но чужие просмотрщики не увидят расцветок.

**Грабли атласа надписей (KB3):** KTX2 ETC1S (`gltfpack -tc`) сдвигает почти-серые PBT в сиреневый (модификаторы #D3D6D8,
белые колпачки; `-tq 10` не лечит — `99-raw/experiments/KB/10-check/kb3_atlas_ktx2_q8_q10_webp.jpg`) и тянет транскодер Basis
(212 КБ br: js 13 + wasm 199). WebP-атлас: цвет как у A и B, GLB 159 против 176 КБ br, итого −229 КБ br на десктопе
(`12-metrics/kb3_atlas_webp_vs_ktx2.json`). Правило: плоские цвета + текст — WebP/PNG; KTX2 — для фото-текстур и памяти GPU.

## Итоги фазы 2 — для базы (что сработало, цена, условия, слабые места)

Пути вида `12-metrics/…`, `10-check/…`, `09-capture/…` — от `99-raw/experiments/KB/`.

Числа — таблицы ниже и `numbers.json` → `phase2`; кадры — `judge/`, `gallery/`. Время агента: KB 19 мин + KB2 86 мин + KB3
(ночь 26.09) — см. строку «Время» ниже; машина — журнал очереди (`numbers.json` → `phase2.queue`, `phase2.queue_KB3`).

**Окупается ли живой ввод — да, но окупается механика, а не обязательно живое 3D.** Сама механика (`event.code` → клавиша,
`event.key` → буква раскладки посетителя RU/EN, строка напечатанного, «Ё набрана одной клавишей», касание на телефоне) — общий
`page.js`, 3,6 КБ br, одинаково работает у A, B и C, в том числе у B без three. Живое 3D поверх неё (ход 3,8 мм пружиной,
шток свитча, свечение Ё) стоит A 127/208 КБ br JS (three + модель + сцена, телефон/десктоп с N8AO) и C 139/220 КБ br JS + GLB 84,5/159 КБ br, запуск по
намерению: готово через 1,2 (C) – 1,6 (A) с, первый кадр 1,4–1,8 с (десктоп); у B то же впечатление даёт 5 кадров Cycles (кадр «все вверх» + 4 «нажато», 5 × 33 КБ AVIF) и `clip-path`
по обводам клавиш, спроецированным из Blender. Разница видна в движении (пружина, перелёт 0,3 мм), не в статике — отсюда
записи `typing-10s.webm` A/B/C для слепого сравнения. Вывод для базы: живой ввод как механику брать всегда (дёшево, это и
есть «вау»-ход: своя клавиатура печатает Ё); живое 3D под него оправдано, когда тот же рендерер обслуживает ещё и расцветки без
наборов кадров и непрерывную разборку (у C одно 3D на три раздела), для одного набора хватает кадров B.

**A против C (одна `stage3d.js`, разное — только модель): по виду в живых сценах почти равны, по цене — разные вложения.**
Свет, камеры, экспозиция и пост у A и C общие, поэтому разница = вклад ассета Blender. В одной камере с Cycles: оборот A−B
ΔL* −1,6, C−B −1,1; разборка +0,4 / +1,1 (`12-metrics/abc_after_fix.json`) — одинаково далеко от кадра B. C выигрывает
деталью, которая уже есть в Blender-модели (свитчи со штоком, стабилизаторы, фаски корпуса, латунь — без переписывания),
и стандартом расцветок; A — байтами (0 КБ ассетов против GLB 84/159 КБ br, JS на 12 КБ br меньше, на телефоне 15 вызовов
против 27; треугольники после упрощения телефонного GLB C сравнялись — 46 против 43 тыс.) и полным контролем (атлас canvas
шрифтом страницы). Цена по агенту
(отдельного хронометража у KB/KB2 нет — по объёму кода): A — вся модель кодом, `model_a.js` 381 строка (генератор колпачков
Cherry кольцами, корпус лофтом, пластина с вырезами, атлас canvas); C — `export_web.py` 297 + `make_web_atlas.py` 68 + `pack.sh` 13 +
`model_c.js` 173 строки поверх готовой Blender-модели (`_lib/kbb.py`), которая всё равно нужна для B. Правило: есть
Blender-модель ради предрендера → C даёт живое 3D той же модели малой добавкой; нет модели и предмет параметрический (ряды
одинаковых деталей) → A.

**B против C (предрендер против гибрида).** B — лучший вид там, где хватает заготовленного ракурса: макро Ё с ГРИП, матовый
пескоструй, контактные тени, латунная плита в разборке; вес мал (постер 9 КБ, оборот ≈ 0,45 МБ на расцветку, JS 4,6 КБ br).
Предел B: набор — кадры «нажато» (без пружины, одна расцветка, один ракурс), оборот — 36 положений, расцветки — только
заготовленные. C — тот же постер, что у B, плюс живое 3D, но свет three — «другое распределение» (медиана |ΔL*| 5–14 к Cycles),
металл холоднее.

**Что сработало (и почему).** (1) Один паспорт в метрах → общие камеры и обводы клавиш A/B/C (кадр кода совпал с Cycles по
пикселям, обводы Blender подошли к three без правок). (2) Телефон, набор касанием: окно левой половины кадра T через
`setViewOffset` (A/C) и CSS-обрезку полного кадра 1600 px (B) — клавиша 20 → 44 CSS px без нового рендера, буква на отпускании
(свайп не печатает) — проверено касаниями «ёлка» на A/B/C (`10-check/mt_*/mob_touch.json`). (3) 3D по намерению: длинные кадры
фазы прокрутки C 843 мс (4,2 %) → 0 (`12-metrics/kb3_loaf_probe.json`). (4) ГРИП кодом для постера A: радиус кружка по тонкой
линзе камеры Blender + выборка с порядком по глубине (`gallery/a-dof-gather.webp`). (5) Поправка экспозиции three по сцене по
ΔL* к Cycles. (6) Сведение кадров B на цвет раздела (вычесть «серый пол» ловца теней) — фон кадра к странице ΔE ≈ 0,8.

**Что не сработало / пределы.** Нажатие у A/C в статике малозаметно: ход 3,8 мм в кадре T — 3–5 px; KB3 добавил подсветку
верха по глубине хода (эмиссия 0,09 → +2,4…3,6 L* по клавише, как оверлей у B), в движении у A/C есть пружина и перелёт, у B —
нет. EEVEE-RT для секвенций (нет ловца теней — корпус чёрный, −14,5 L*); BokehShader three как есть
(ореол резкого переднего плана на размытом фоне); KTX2 ETC1S для атласа надписей (оттенок); на телефоне «Три цвета» и
«Как устроена» — альбомный кадр 16:10, клавиатура 2,75:1 по ширине экрана (≈ 330 px) — отдельной портретной камеры нет
(для B это ещё 3 × 24 + 4 кадра рендера); C на телефоне был 107 тыс. треуг. (3D не в первом экране, бюджет героя 50 тыс. формально
не нарушен; KB3 упростил телефонный GLB `gltfpack -si 0.4` до 42,8 тыс., глазами без разницы); металл A местами «хром»
(PMREM-студия), свитчи A — простые формы; разборка A/C площе кадра Cycles: N8AO затемняет только щели (≈ 1 % пикселей), дно
корпуса не темнеет — тени слоёв и AO радиусом 4,5 см у A/C пробованы и откачены, глазами без разницы
(`12-metrics/kb3_n8ao_probe.json`).

**Доработка после отсева ИИ-судьи (26.09, 06:30–06:50):** на станциях разборки B тень доходила до нижнего и правого края
кадра — на фоне раздела была серая плашка с прямой кромкой. `07-b/encode.py comp()`: тень гаснет по расстоянию от предмета
(полная ближе 4 %, ноль дальше 20 % меньшей стороны кадра) + растушёвка к краю 12 % (было 5 %), AVIF 4:4:4. Край кадра на

(кромка сред. 1,1–1,8 → 0,5–0,9). B и C пересобраны (у C эти кадры — reduce и «до намерения»), `judge/b-blender__*` десктоп
