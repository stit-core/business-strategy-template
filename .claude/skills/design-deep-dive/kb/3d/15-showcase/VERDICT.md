## 1. Коротко

Два решающих голоса заказчика, 26.09: **слепое голосование по кадрам** (06:53, 31 из 32 пар в двух порядках — блок §5,

Они отвечают на разные вопросы и друг другу не противоречат (§5.1).

1. **Главный вывод:** по неподвижным кадрам вслепую сильнее чистый Blender (главный кадр «Звена» B > A > C, «Сдано» B > A во всех
   четырёх парах); страницу целиком вживую заказчик выбрал **гибридную во всех трёх предметах** — «Звено» C, клавиатура C, «Сдано» C
   (фонарик): ответ на ввод кодом плюс модель и материал Blender («где-то код лучше, где-то Blender, а гибрид прямо самое то»). Дуэль
   Velmora — равны и вслепую (4 ничьи из 4), и вживую.
2. **Уровень:** лучший вариант каждого продукта держится на уровне якоря класса — первые экраны «Звена» и клавиатуры вровень с hubtown и
   Apple AirPods Pro по идее и ремеслу, Velmora выиграла у Shopify Editions по идее и вровень по ремеслу: правило L2 плана проходят все три.
   Годность — у всех 11 страниц ворота без провалов (§6). Одна машина, 0 ₽.
3. **Blender (Cycles) — кадр и постер:** вслепую B выигрывает кадр; но первый экран клавиатуры кодом с ГРИП вровень с Cycles (A = B), а
   «изнутри» сустава код выиграл (A > B). Секвенции Cycles на прокрутке («Звено» B) в движении не уступили живому гибриду (B = C) при
   TBT 0 / 28 мс и 0 КБ JS 3D, но без ответа на ввод.
4. **Код — ввод и вес:** код v3 выиграл у базы v2; живой набор клавиатуры в движении (гибрид C: модель Blender, ввод кодом) выиграл
   и у кода A, и у кадров B — единственная
   «живая» пара голосования совпала с оценкой вживую. «Звено» A — 0 КБ ассетов, кадр 4,72 мс, ворота 0 FAIL (`zveno/a-code/README.md`).
5. **Гибрид по правилу плана** (доля побед C над A по кадрам) — **0,40 → «по бюджету»**, на нижней границе («не нужен» < 0,4): это ремесло
   неподвижного кадра («Звено» C проиграл по кадру и A, и B — свет three при детали Blender), а ценность гибрида — в живой странице; её
   вслепую меряет второй тур «живой проход», которого ещё не было. **Нейросеть** — 4 ничьи из 4 с Blender за 0 ₽: оправдана только скоростью.
6. **Слабое:** судья один; оценка вживую — не вслепую и без пар; 0,40 по 5 парам — 95 % интервал Уилсона ≈ [0,12; 0,77] (накрывает все
   три зоны правила), для 70/30 нужно 50–70 голосов; ничьи — расхождение порядков, а не «равно»; `z-motion-bc` и `s-beam-bc` сравнивали
   разные состояния; до голосования ИИ-отсев снял 7 негодных пар (§5); реальные телефоны и Safari/WebKit не проверены; скрабы держат

## 3. Когда Blender, когда код, когда гибрид, когда нейросеть

| Задача страницы | Бери | Доказательство |
|---|---|---|
| Продукт **отвечает на ввод** (курсор, касание, клавиши; прокрутка ведёт механику) | **код** (A или C) | IK за курсором — 0,5 КБ br, ≈ 0,2 мс CPU, 0 кадров в покое; у кадров и видео Blender этого слоя нет (`14-code-3d/README.md` п. 3; `zveno/judge/a-code__hero-ik.png`); **люди:** набор клавиатуры в движении — живое C > кадры B и > код A (§5) |
| Ввод есть, но хватает **заготовленных состояний** (набор, расцветки, повороты) | **кадры Blender + механика кодом без three** | клавиатура B: набор = 5 кадров Cycles + обводы клавиш из Blender, JS страницы 4,6 КБ br; «живое 3D видно в движении, не в статике» (`keyboard/README.md` «Окупается ли живой ввод») |

**Не помогло или помогло с поправкой:**

- **Числа не выбирают красоту**: у всех дорожек «шум» и «блик» по умолчанию мерили не то (рёбра, надписи, широкие белые зоны); пороги KIT §4.5

- **«Ключ 30–45° к главной грани»** — верно для выпуклого товара, не для рельефа (KB — скользящий ключ), разреза (SD — солнце 83°) и брифа с
  контровым ключом (VD).
- **Объёмная дымка на весь кадр** — муть и ×2 времени (VD S3, Z S3); ореол за силуэтом — своей лампой или экранным градиентом.
- **EEVEE для финала и секвенций** — нет ловца теней (−14,5 L*), GI и анизотропии; Cycles 20–40 спп + OIDN дороже в ×3, но годен.
- **Этюд без выравнивания экспозиции** сравнивает экспозицию, а не свет (SD, первый прогон).
- **ИИ-судья** — только отсев брака, не выбор красоты: по базе он «выбирает богаче» (J/02: 3 из 4 — брак). В испытании (AJ, 05:00–06:30)
  он ловил то, что пропускают числа ворот: одинаковые кадры в паре, подписанный вариант на кадре, отсутствующий у одной стороны объект
  сравнения (итог — §5).
- **Итог метода по людям:** лучший вариант каждого продукта прошёл правило L2 против якоря класса (ничьи по идее и ремеслу у «Звена» и
  клавиатуры, победа по идее у Velmora), «Сдано» B выиграл у базы 4 из 4 — метод довёл продукты до уровня якорей для одного судьи; но
  гибрид «Звена», собранный тем же методом, по ремеслу кадра проиграл и коду, и Blender (свет three при детали Blender), хотя вживую
  заказчик выбрал гибрид во всех трёх предметах — голосование кадрами мерит ремесло неподвижного, а не живую страницу (§5.1): протоколу
  оценки нужен второй тур «живой проход».

**Воспроизводимость** (критерий дайджеста 04 F: ≥ 2 из 3 свежих прогонов по рецепту проходят ворота и L2) — **не проверена**: рецепты 13–17
написаны ночью (`12-recipes/13…17`), свежими агентами не прогонялись.

**Главные новые правила** (подробно — рецепты 13–17 и `14-code-3d/`):

1. **Тёмные тона под Khronos Neutral** — «носок» x − 6,25x² давит тёмное в 5–10 раз: фон, туман, мир — через обратную кривую (Z, CD).
2. **Мир для лучей камеры = CSS-градиент страницы** (обратная кривая Neutral) — фон кадра совпадает со страницей, ΔE 1,7–1,9 (Z).
3. **Свет предмета — только на предмет** (light linking): пол со своим «солнцем», у ленты и крышки флакона свои лампы (Z, VD).
4. **Облучённость, а не мощность** — точечная лампа у лака «розовит» сустав при любой мощности (Z).
5. **three по намерению** и **ворота варианта — одной задачей «тишины»** (KB, оркестратор v2.1).
6. **`KHR_materials_variants` из Blender 5.2.2 — три условия** (настройка аддона, `scenes[0]`, постобработка без `join`) (KB → рецепт 17).
7. **Анизотропия в three требует TANGENT**, а `gltf-transform optimize` без `--prune-attributes false` его выбрасывает (Z).
8. **Для орто-изометрии хранить высоту, а не глубину**; тени фонаря — по карте высот сверху (SD2 → SD3).
9. **ГРИП кодом под Cycles** — радиус кружка по тонкой линзе камеры Blender, выборка с порядком по глубине (KB3).
10. **Живой ввод — механикой** (3,6 КБ br), 3D под ним — только если то же 3D обслуживает ещё расцветки и разборку (KB).
11. **Контровой свет в дымке кодом** (+0,37 мс, 1,8 КБ br) отделяет силуэт, как объём Cycles (CD3).
12. **Вес приёма — только сборкой с `--define`**; **ворота — только в тишине** и парой с эталоном (CD).
13. **Порог памяти очереди — по реальному пику процесса** (VD `peak.py`: пик 1,6–1,7 ГБ → порог 3000 МБ, кадр 2560 — 4,4 ГБ → ≥ 4500; Z: пачки секвенций 4000 вместо 6000).
14. **Предрендер по прокрутке — Blob-кэш + окно декодированных ImageBitmap + отрисовка только смены номера**; постер = кадр 0 той же секвенции (Z3).
15. **Скан сустава: резать только корпус, начинку показывать цельной** — сечение всей начинки читалось «ящиком с брусками» (Z3).
16. **Атлас надписей и плоских цветов — WebP, не KTX2 ETC1S** (KB3; сходится с крюком CD3 для «Звена»).
17. **У скраба постер ≥ площади видео и холста** — иначе LCP-элементом становится видео (VD3).
18. **Молчание агента > 30 мин без живых процессов = зависание**: смотреть хвост транскрипта (`tool_use` без `tool_result`); `ffmpeg` в циклах — только
    с `-nostdin` и `timeout` (оркестратор после SD3; `ctx_watch.py` v2, событие HUNG).
