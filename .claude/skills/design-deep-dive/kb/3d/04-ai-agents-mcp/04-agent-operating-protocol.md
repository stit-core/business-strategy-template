## Выжимка для агента

1. **Цикл**: бриф → уточнение → паспорт стиля и паспорт ассета → источник геометрии → один идемпотентный `build(P)` →
   исполнение → аудит и утверждения → рендер (камера + 4 ракурса + глина) → критика по рубрике → правка (≤2–3 визуальные
   итерации) → экспорт → сжатие → проверка в браузере. → §1 `[проверено]`
2. **Уточни бриф до кода**: назначение на странице, размер в кадре, фон страницы, стиль серии, бюджет, анимация. Чистое ТЗ
   снижает невалидные решения Claude с 56,6 до 11,8 %, уточняющий вопрос — брак с 14,6 до 0,9 % (ProCAD, по C2). → §2
   `[исследование]`
3. **Паспорт стиля серии фиксируется один раз** (камера, свет, материалы, палитра hex, кадр, поля, фон, тон-маппинг) и
   хранится в файле рядом со скриптом, а не в промте. → §3.1 `[практика, ui-research §6.2]`
4. **Паспорт ассета — части с размерами в метрах реального объекта**: у трёх моделей «с первой попытки» кружка 1,4–2,2 м,
   телефон 1–2,9 м (×10–25). → §3.2 `[проверено]`
5. **Координаты частей вычисляй от опорной детали** (стык = габарит соседа), модель задаёт только отношения («ручка на
   стенке, между 30 % и 80 % высоты»). → §3.3 `[проверено: 12; исследование: SceneCraft, L3GO по C2]`
6. **Источник геометрии**: стилизованные и продуктовые формы — кодом; HDRI и PBR-текстуры — Poly Haven; органика и
   «похожая вещь» — библиотека/генератор по разрешению; ассет чужого стиля в серию не ставить. → §4 `[мнение C1, 12]`
7. **Один идемпотентный `build(P)`, а не цепочка шагов**: после ошибки, смены параметра и потери сцены он приходит к тому же
   состоянию; пошаговый код дал дубли `Ceramic.001`, `Mug.001` и `KeyError`. → §5.1 `[проверено: 05]`
8. **Скрипт живёт в файле рабочей папки**; MCP или `blender -b` — только исполнитель; в контекст модели — текущий скрипт
   целиком (без него объект «уплывает», LL3M по C2). → §5.2 `[исследование + практика]`
9. **Две коллекции**: `ASSET_<id>` (экспортируется) и `STAGE` (свет, камера, фон); `build` сносит только свою коллекцию. → §5.3 `[проверено: 12]`
10. **Материалы — по имени с переиспользованием (только в своём фоновом файле; в сцене человека — по тегу, `../02-blender-workflow/01-scene-organization-naming-units.md` §2)**, Principled — поиск по `type`, входы — по имени сокета; цвет из hex —
    через `Color.from_srgb_to_scene_linear()`. → §5.4 `[проверено: 12]`
11. **Слоты материалов до индексов граней**: `materials.clear()` и `pop()` в 5.2.2 обнуляют `material_index`. → §5.4 `[проверено: 12]`
12. **Фаска + сглаживание по углу** на всём, что не low-poly: `Mesh.shade_smooth()` + `set_sharp_from_angle`,
    модификатор Bevel с `harden_normals`. → §5.4 `[проверено: 12]`
13. **Камеру не ставь углами Эйлера «на глаз»**: haiku — объект вне кадра 3/3, sonnet — кадр режет объект 7/8; камера
    считается по габаритам и FOV, направление — `to_track_quat('-Z', 'Y')`. → §5.5 `[проверено: 11, 12]`
14. **После каждого исполнения — аудит JSON и утверждения по паспорту** (габариты ±5 %, зазоры ≤1 мм, треугольники); это
    ловит парящие детали числом. → §6 `[проверено: 10, 16]`
15. **Исполнилось ≠ годится**: все 8 скриптов sonnet прошли без исключений, годен один. Проверка вида — рендер из камеры,
    4 ракурса и глина, а не снимок вьюпорта. → §6.3 `[проверено: 11]`
16. **Ошибка исполнения → traceback целиком → исправление → не больше 2 повторов** (исполнимость 0,70 → 0,97 на Blender
    5.0, по C2); одинаковая ошибка дважды → смена подхода или справка 5.2. → §6.1 `[исследование]`
17. **Проверки кодом сильнее VLM-судьи** (F1 0,962 против 0,549 по C2): числа сцены — утверждениями, взгляд — на
    композицию, стиль и материалы. → §6 `[исследование]`
18. **Критика по рубрике и вопросами да/нет из брифа**, сравнение с прошлой версией попарно в двух порядках; «оба хуже» —
    допустимый ответ. → §7 `[исследование по C2, практика]`
19. **Визуальных итераций 2–3, с откатом**: после ~2 правок улучшений почти нет, слабые критики ломают (по C2); держи
    лучший вариант в отборе. → §8 `[исследование]`
20. **При неопределённой форме — 2–4 варианта параллельно и отбор**, а не длинная цепочка: 3 пути по 1 итерации лучше 3
    по 5 (ShapeCraft), 10 кандидатов — брак 16,8 → 0,3 % (CAD-Recode), по C2. → §8 `[исследование]`
21. **Сохраняй контрольную точку** `save_as_mainfile(copy=True)` после каждого принятого шага; undo через MCP нет. → §10.2 `[проверено: 04]`
22. **Экспорт**: только коллекция ассета, модификаторы применены, затем `gltf-transform optimize` (meshopt + WebP),
    `gltf_check.py`, `web_view.py`; 119,5 → 20,7 КБ у кружки, 29 → 3 вызова отрисовки у комнаты. → §9 `[проверено: 15]`
23. **Процедурные материалы в веб не доходят**: градиент экрана из ColorRamp, thin film — теряются; для сайта — цвета
    Principled или запечённые текстуры (агент E). → §9 `[проверено: 11, 12]`
24. **MCP или фон**: фоновый `blender -b --python` — детерминированные пересборки, серии, рендеры; MCP — пошаговая работа
    рядом с человеком в его Blender или с официальным сервером без окна. → §10.1 `[мнение C1 на основе 04, 09]`
25. **Остановка**: все утверждения зелёные + рубрика ≥ порога → экспорт; 3 итерации без улучшения, повтор одной ошибки,
    исчерпан бюджет времени → вопрос человеку или смена стратегии. → §8.3 `[практика, исследование]`
26. **Журнал**: каждый исполненный скрипт, stdout, трассировка, флаги аудита, пути рендеров — в папку задачи (как в
    3DCodeBench); это же — регрессионный набор. → §10.3 `[практика]`

## 1. Цикл целиком

```text
бриф ─► уточнение ─► паспорт стиля (1 раз на серию) + паспорт ассета (части, метры, бюджет)
     ─► источник геометрии (код / библиотека / генератор)
     ─► build(P) в файле ─► исполнение (blender -b или MCP) ─┬─ ошибка → traceback → правка (≤2) ─┐
                                                             └─ ок → аудит + утверждения ─ красное → правка кода
                                                                     └ зелёное → рендер камера + 4 ракурса + глина
     ─► критика: рубрика + вопросы да/нет + сравнение с прошлой версией ─ хуже → откат
     ─► правка (tweak/leap, одна вещь) ≤2–3 раза или 2–4 варианта параллельно
     ─► экспорт коллекции ASSET → gltf-transform → gltf_check → web_view → отчёт
```

| Шаг | Артефакт | Проверка | Стоп-сигнал |
|---|---|---|---|
| 1. Бриф | текст задачи | есть назначение, место на странице, фон, стиль, бюджет | нет места/фона → спросить |
| 2. Паспорт стиля | `style.json` серии | поля §3.1 заполнены | стиль противоречит бренду → спросить |
| 3. Паспорт ассета | `P = dict(...)` в скрипте | размеры в метрах, опорная деталь, отношения, бюджет | размеры неизвестны → взять справочные, записать допущение |
| 4. Источник | решение с причиной | §4 | нужен платный генератор → разрешение |
| 5. `build(P)` | `<id>.py` | исполняется без исключений | 2 одинаковые ошибки → справка 5.2 / смена приёма |
| 6. Аудит | строка AUDIT JSON | флаги §6.2 объяснены | неустранимые флаги → записать в отчёт |
| 7. Утверждения | строка ASSERT JSON | `ok: true` | парящие части, габарит ±5 % |
| 8. Рендеры | PNG камера, `sheet.png` 4 ракурса, глина | рубрика §7 | «оба хуже» дважды → откат, другой вариант |
| 9. Экспорт | `<id>.glb`, `<id>_opt.glb` | валидатор 0 ошибок, бюджет §9 | превышен бюджет → упростить |
| 10. Браузер | `web_sheet.png`, `web_stats.json` | вид совпадает с рендером, ошибок консоли нет | расхождение цвета → тон-маппинг/материал |

## 2. Бриф и уточнение

Минимум, без которого код не пишется (по ProCAD: уточняющий вопрос снижает брак 14,6 → 0,9 %, `03 §3`):

| Вопрос | Зачем | Если не ответили |
|---|---|---|
| Где на странице и какого размера в пикселях | детализация, бюджет, ракурс | hero 800–1200 px по ширине |
| Статика (рендер PNG/WebP) или интерактив (GLB в three.js) | бюджет треугольников, запекание, pivots частей | рендер, GLB — по запросу |
| Фон страницы (hex, светлая/тёмная тема) | цвет мира и циклорамы, прозрачность | прозрачный PNG + светлая тема |
| Стиль серии (clay, low-poly, реалистичный пластик, стекло) | материалы и свет | взять из паспорта серии |
| Референсы (картинки) | направление, не размеры | текст важнее: картинка вместо текста ухудшает код у 4 из 5 моделей (`03 §2.2`) |
| Анимация/интерактив (вращение, открытие крышки) | части и точки вращения | без анимации, части — одним мешем |
| Бюджет: вес файла, треугольники | §9 | 150–300 КБ после сжатия для hero |

Референс-картинку использовать вместе с текстовым брифом, не вместо него; из неё снимать направление, а не размеры
(`../../ui-research/12-ai-generated-ui/01 §частые ошибки`).

## 3. Паспорта

### 3.1. Паспорт стиля серии (фиксируется один раз)

Поля — из паспорта 3D-серии ui-research (`12-ai-generated-ui/01 §6.2`), дополнены полями для веба. Хранить в
`style.json` рядом со скриптами; `build` читает его, а не держит числа в голове модели.

| Поле | Пример значения | Где проверяется |
|---|---|---|
| камера | перспектива 60–85 мм для предметов, орто для изометрии (35,264° / 45°), `frame_camera(az, el, margin)` | аудит `frame`, рендер |
| свет | key 45° слева-сверху (тёплый #FFF4E5), fill 30 % (холодный #E8F0FF), rim 80 % сзади; мощность от размера ассета | рендер |
| мир и фон | цвет фона страницы (hex), сила мира 0,35; циклорама того же цвета или прозрачный фон | рендер, браузер |
| материалы | матовый пластик roughness 0,4–0,5; керамика 0,25–0,3 + coat 0,35; металл 1,0 / 0,25–0,35 только на акцентах | аудит `materials` |
| палитра | 6–10 hex бренда; акцент ≤ 15 % площади | рендер |
| тон-маппинг | для бренда и товара — Khronos PBR Neutral, look None; на сайте — `THREE.NeutralToneMapping` (ΔE к hex 1,8–1,9, D2 `../06-materials-lighting-render/03-render-engines-color.md` §2.3); AgX — только атмосферный hero без брендового hex | браузер `--tone neutral` |
| кадр и поля | 1200 × 900 / 1000 × 1000; поля 8–12 % | аудит `frame` (площадь 0,3–0,7) |
| тень | контактная, мягкая; на прозрачном фоне — ловец теней (только рендер) | рендер |
| именование | `ASSET_<id>`, части `<Id>_<Part>`, файлы `<id>.glb`, `<id>_cam.png` | аудит `default_names` |
| бюджет | hero GLB ≤ 300 КБ сжатого, ≤ 50 000 треуг., ≤ 8 материалов, ≤ 10 вызовов отрисовки | утверждения, gltf_check |

3D оправдан, только если конвейер воспроизводим: сцена, свет, материалы и камера сохранены в файле и переиспользуются;
разовая генерация даёт серию, которая «разваливается на третьей картинке» (`07-iconography-imagery/02 §5.2`).

### 3.2. Паспорт ассета

```python
# Blender 5.2.2 — [проверено] — фрагмент laptop.py: паспорт = параметры build
P = dict(W=0.304, D=0.212, base_t=0.012, lid_t=0.006, corner=0.012, open_deg=110,      # метры и градусы
         alu="#C9CCD1", keys="#1F2023", pad="#B9BCC2", bezel="#08090B", screen="#0B1322", glow="#4C7BE8",
         bg="#ECEEF2")                                                                   # sRGB hex из паспорта стиля
```

Что обязательно в паспорте: список частей с размерами в метрах (из справочника или брифа), **опорная деталь** (основание,
корпус, пол), отношения частей («клавиши лежат на основании», «крышка на петле по заднему краю», «ручка входит в стенку»),
материалы по частям, бюджет треугольников и материалов, какие части двигаются на сайте (им нужен свой pivot).
Справочные размеры (от них не отступать без причины): кружка Ø 80–85 мм × 95 мм; смартфон 71,5 × 147 × 7,8 мм; ноутбук
13" 304 × 212 мм; комната 3 × 3 м, стены 2,4–2,8 м; дерево для сцены 1–4 м.

### 3.3. Отношения → координаты кодом

Модель формулирует отношения, код вычисляет числа: прямые координаты LLM в раскладке не лучше случайных (MRR 0,364 против
0,369), отношения + решатель — 0,706 (`03 §6`). В C1/12 все стыки вычислены от опорной детали: торцы ручки кружки — внутри
толщины стенки (`x = R − wall·0,45`), клавиши — `z = base_t + h/2`, крышка ноутбука — поворот вокруг оси петли
`(y = D/2, z = base_t)`; утверждения C1/16 подтвердили зазоры 0 / 0,49 / 0,2 мм. У «первой попытки» sonnet те же отношения
заданы числами наугад: экран в 0,451 м от основания, блок камеры телефона вне корпуса [проверено: 11, 16].

## 4. Источник геометрии

| Ситуация | Источник | Почему | Цена |
|---|---|---|---|
| Стилизованный предмет, иконка, продукт из простых тел (кружка, телефон, ноутбук, ракета, логотип) | **код** (`bmesh`, тела вращения, скруглённые пластины, текст → меш) | точные размеры, стиль серии, лёгкая сетка, воспроизводимость | 1 скрипт 60–120 строк; C1/12 — 1–4 итерации |
| Изометрическая комнатка, витрина из многих предметов | код + функции-заготовки (box, cylinder, lathe) | единый стиль, контроль бюджета | 29 → 3 вызовов отрисовки после сжатия |
| Абстрактная форма, узел, органика по формуле | код (кривая с толщиной, SDF, параметрические поверхности) | параметры = вариации | тяжелее по треугольникам (15 552 у узла) |
| Освещение окружения, фото-фактуры (дерево, металл, ткань) | **Poly Haven** (CC0, без ключа) | качество фото-текстур, HDRI | 1k текстура = 2,27 МБ до сжатия, 326 КБ после |
| Сложная органика (животное, еда, растение крупно), «такая же как на фото» | генератор 3D (Rodin, Hunyuan, …) **по разрешению** или библиотека (Sketchfab, Poly Pizza) | код с такими формами не справляется (худшие категории 3DCodeBench — вилка, ложка, ваза, по C2) | деньги, лицензии, ретопология и доводка (агент G) |
| Много однотипных предметов в сцене | код + инстансы / Array | вызовы отрисовки | — |

Промт `asset_creation_strategy` mcp-for-blender предлагает обратный порядок («сначала библиотеки и генераторы») — для
hero-объектов серии это неверно: чужой стиль, тяжёлая триангулированная сетка, лицензии (`01 §3.14`).

## 5. Код: частями или одним идемпотентным скриптом

### 5.1. Что показал эксперимент

C1/05, мост без окна, одна сцена (кружка, ручка, блюдце, материал, свет, камера) и три возмущения — опечатка на полпути,
смена высоты 0,095 → 0,110 м, потеря сцены [проверено]:

| | Код частями (как пишет модель в чате) | Идемпотентный `build(P)` |
|---|---|---|
| вызовов / ошибок | 9 / 2 | 5 / 1 |
| отправлено кода | 3 585 символов | 13 036 (×3,6) |
| после ошибки и повтора | `Ceramic` и `Ceramic.001`, у кружки два слота | чистая сцена: 5 объектов, 1 материал |
| после смены параметра | две кружки друг в друге (`Mug`, `Mug.001` без материала), ручка на старой высоте | высота 0,110, ручка и камера пересчитаны |
| после потери сцены | `KeyError: 'Mug' not found` | та же сцена |

Частичное состояние после ошибки бывает у обоих подходов (у `build` остались объекты и материал-сирота) — поэтому `build`
начинается с уборки своей коллекции. Цена идемпотентности — объём кода в контексте; решение — хранить скрипт в файле и
отправлять целиком только при изменении, а в фоне запускать файл (`blender -b --python build.py`). Исследования говорят
то же: передавать текущий скрипт при каждой правке (LL3M), держать «последний скрипт = состояние» и короткую историю
(VIGA) (`03 §8.1`).

### 5.2. Правила скрипта

- Скрипт = паспорт `P` + `build(P)` + студия + камера + рендер-настройки; вызов `build(P)` в конце; итог — одна строка JSON.
- Никаких опор на переменные прошлых вызовов, выделение, активный объект, открытое окно.
- Геометрия — через `bmesh` и `bpy.data` (операторы — только если нет альтернативы, с `temp_override` и проверкой
  `{'FINISHED'}`, агент B `../03-bpy-api/01 §4`).
- Трансформации — в вершинах (`mesh.transform(M)`) или в `matrix_world` объекта с масштабом 1; не оставлять
  неприменённый масштаб. Если часть будет двигаться на сайте — отдельный объект с pivot на оси движения.
- Не больше ~150 строк на объект; повторяющиеся детали — функции-заготовки (см. §5.4).

### 5.3. Состояние в сцене

- `ASSET_<id>` — всё, что уйдёт в GLB; `STAGE` — свет, камера, фон, ловец теней (не экспортируются).
- `fresh_collection(name)` сносит коллекцию вместе с данными-сиротами и создаёт заново (идемпотентность).
- Custom property `asset_id`, `passport_hash` на корне ассета — чтобы следующий вызов нашёл «свои» объекты.
- Контрольные точки: `<work>/<id>/checkpoint_NN.blend` (`copy=True`), исходные файлы пользователя — только копии.

### 5.4. Проверенные заготовки

Полная библиотека — `99-raw/experiments/C1/12-protocol-objects/proto_lib.py` (все функции использованы в 8 объектах
C1/12; без `bpy.ops`, совместима с фоном). Ключевые фрагменты:

```python
# Blender 5.2.2 — [проверено: 99-raw/experiments/C1/17-doc-snippets; полная версия — 12-protocol-objects/proto_lib.py]
import bpy, bmesh, math
from mathutils import Vector, Color

def srgb(hexstr, alpha=1.0):                     # hex дизайнера (sRGB) → линейный цвет для Principled
    h = hexstr.lstrip("#")
    lin = Color((int(h[0:2], 16) / 255, int(h[2:4], 16) / 255, int(h[4:6], 16) / 255)).from_srgb_to_scene_linear()
    return (lin.r, lin.g, lin.b, alpha)

def fresh_collection(name):                      # идемпотентность: снести свою коллекцию и построить заново
    old = bpy.data.collections.get(name)
    if old:
        datas = [ob.data for ob in old.all_objects]
        for ob in list(old.all_objects):
            bpy.data.objects.remove(ob, do_unlink=True)
        bpy.data.collections.remove(old)
        for d in datas:                          # данные-сироты (меши, лампы, камеры) тоже убрать
            if d is not None and d.users == 0:
                for coll in (bpy.data.meshes, bpy.data.curves, bpy.data.lights, bpy.data.cameras):
                    if coll.get(d.name) == d:
                        coll.remove(d); break
    c = bpy.data.collections.new(name); bpy.context.scene.collection.children.link(c)
    return c

def material(name, hexcolor, rough=0.5, metal=0.0, **inputs):   # переиспользовать по имени, Principled по type
    m = bpy.data.materials.get(name) or bpy.data.materials.new(name)
    p = next(n for n in m.node_tree.nodes if n.type == "BSDF_PRINCIPLED")
    p.inputs["Base Color"].default_value = srgb(hexcolor)
    p.inputs["Roughness"].default_value = rough
    p.inputs["Metallic"].default_value = metal
    for k, v in inputs.items():                  # Coat_Weight=0.35 → вход «Coat Weight»
        p.inputs[k.replace("_", " ")].default_value = srgb(v) if isinstance(v, str) else v
    m.diffuse_color = srgb(hexcolor)             # цвет во вьюпорте Solid = цвет рендера
    return m

def assign(ob, *mats):                           # materials.clear() обнуляет material_index — сохранить и вернуть
    me = ob.data
    idx = [0] * len(me.polygons)
    if idx:
        me.polygons.foreach_get("material_index", idx)
    me.materials.clear()
    for m in mats:
        me.materials.append(m)
    if any(idx):
        me.polygons.foreach_set("material_index", [min(i, len(mats) - 1) for i in idx]); me.update()

def smooth(ob, angle=35.0):                      # вместо удалённого use_auto_smooth
    ob.data.shade_smooth()
    ob.data.set_sharp_from_angle(angle=math.radians(angle))

def look_at(ob, target):
    ob.rotation_euler = (Vector(target) - ob.location).to_track_quat("-Z", "Y").to_euler()
```

Камера по габаритам (не углами «на глаз»):

```python
# Blender 5.2.2 — [проверено] — упрощённая frame_camera из proto_lib.py
import bpy, math
from mathutils import Vector

def world_bbox(objs):
    dg = bpy.context.evaluated_depsgraph_get()
    pts = [o.evaluated_get(dg).matrix_world @ Vector(c) for o in objs for c in o.evaluated_get(dg).bound_box]
    return (Vector((min(p.x for p in pts), min(p.y for p in pts), min(p.z for p in pts))),
            Vector((max(p.x for p in pts), max(p.y for p in pts), max(p.z for p in pts))))

def frame_camera(objs, az=30.0, el=18.0, lens=70.0, margin=1.2, res=(1200, 900)):
    lo, hi = world_bbox(objs)
    c, r = (lo + hi) / 2, max((hi - lo).length / 2, 1e-3)          # центр и радиус описанной сферы
    cd = bpy.data.cameras.new("Camera"); cd.lens = lens; cd.sensor_fit = "AUTO"
    cam = bpy.data.objects.new("Camera", cd); bpy.context.scene.collection.objects.link(cam)
    s = bpy.context.scene; s.render.resolution_x, s.render.resolution_y = res
    half = math.atan(cd.sensor_width / 2 / lens) * (min(res) / max(res))   # половина FOV по короткой стороне
    a, e = math.radians(az), math.radians(el)
    cam.location = c + Vector((math.sin(a) * math.cos(e), -math.cos(a) * math.cos(e), math.sin(e))) * (r / math.sin(half) * margin)
    cam.rotation_euler = (c - cam.location).to_track_quat("-Z", "Y").to_euler()
    cd.clip_start, cd.clip_end = r * 0.01, r * 50
    s.camera = cam
    return cam
```

Азимут 0 — вид спереди (камера на −Y смотрит на +Y), как в `render_views.py`; в glTF передний вид Blender −Y становится +Z.

### 5.5. Свет и фон

Три area-источника, мощность и размер — от радиуса ассета (`900 Вт × (d / 7 м)²` при дистанции `d = 4r` — калибровка

## 6. Проверки после каждого исполнения

### 6.1. Исполнимость

Ошибка → тип, сообщение, строка `<string>` → одно исправление → повтор; не больше двух повторов на одну ошибку. По
3DCodeBench (Blender 5.0) два повтора по traceback поднимают исполнимость 0,702 → 0,974, ~90 % отказов — несовпадения
API версии; трассировку давать целиком, длинную — 70 % начала + 30 % конца (`03 §2.2`). В C1/11 все 8 падений haiku —
ровно такие: `scene.render.samples`, вход `Emission`, выдуманные `bpy.math` и `ShaderNodeValRamp` (агент B, `03-bpy-api/04`).

### 6.2. Аудит сцены

`../../scripts/3d/scene_audit.py` — самодостаточный код (проходит безопасный режим mcp-for-blender),

|---|---|---|

## 7. Критика по рубрике

Сначала числа (§6), потом взгляд. Рубрика hero-ассета для сайта (каждый пункт — да/нет по рендеру камеры и листу 4
ракурсов; «нет» → правка с конкретной причиной):

| # | Критерий | «Да», если | Типичная правка |
|---|---|---|---|
| 1 | Силуэт читается в 300 px | объект узнаётся по уменьшенному рендеру | ракурс, отделение частей тоном |
| 2 | Пропорции по паспорту | утверждения ok, соотношения частей как у референса | параметры `P` |
| 3 | Детали на местах и касаются | нет парящих, провалившихся, проросших частей | стыки от опорной детали |
| 4 | Края | фаски ловят блик, нет «компьютерных» острых рёбер и гранёных кругов | Bevel, `set_sharp_from_angle` |
| 5 | Материалы | цвет из палитры, шероховатость различает материалы, нет серого по умолчанию | `material(...)` |
| 6 | Свет | есть key/fill/rim, объём читается, нет пересветов и провалов | мощности, цвет ламп |

| 8 | Фон | совпадает с фоном страницы или прозрачный; нет линии горизонта | циклорама, мир |
| 9 | Стиль серии | тот же свет, камера, материалы, что у соседних ассетов | паспорт стиля |
| 10 | Готовность к вебу | бюджеты §9, нет процедурных материалов, pivots для анимации | упрощение, запекание |

Вопросы да/нет по брифу («у кружки есть ручка справа?», «экран светится синим?») — надёжнее целостной оценки: 88,7–91,5 %
согласия против 72,8 % (Eval3D); оценку «1–10» не использовать — Pearson 0,17–0,37 с людьми (`03 §7`). Сравнение
«новая версия против прошлой» — попарно, в двух порядках, засчитывать только согласованный ответ; не больше 2 картинок за
вызов; «оба хуже» — разрешённый ответ (судьи его почти не дают: 0–3 % против 15,6 % у людей).

## 8. Правка и остановка

### 8.1. Как править

- Одна причина — одна правка: сначала числа в `P` (tweak), структура — только если числа не помогают (leap);
  чередование tweak/leap и участие текущего лучшего в отборе — BlenderAlchemy (`03 §2.5`).
- Правка — в файле скрипта, затем полный `build(P)`; не «доделывать» сцену отдельными вызовами.
- Приоритет исправлений: отсутствующее → парящее/пересекающееся → пропорции → края → материалы → свет → кадр.

### 8.2. Параллельные варианты

Когда форма неочевидна (абстрактная скульптура, стилизация), строить 2–4 варианта `P` сразу (в фоне — отдельными
процессами по очереди, в одной сцене — разными коллекциями), отбирать утверждениями и попарным сравнением. Исследования:
3 пути по 1 итерации — IoGT 0,535 за 3,7 мин против 0,431 за 18 мин у 3 путей по 5; дерево 4×8 лучше 32 правок подряд;
10 кандидатов — брак 16,8 → 0,3 % (`03 §8.1`).

### 8.3. Критерии остановки

| Условие | Действие |
|---|---|
| утверждения ok + рубрика без «нет» | экспорт |
| 2–3 визуальные итерации без улучшения по попарному сравнению | остановиться на лучшем, описать остаток в отчёте |
| одна и та же ошибка исполнения дважды | справка 5.2 (`bpy_probe.py`, `bpy_api_lookup Type.prop`), затем смена приёма |
| форма не даётся кодом (органика) | предложить библиотеку/генератор, спросить разрешение |
| время вызова > 30 с или рендер > 60 с | уменьшить разрешение/сэмплы, разделить работу |
| Blender закрылся/заглох (§10.2) | восстановить из последней контрольной точки |

## 10. Режимы работы, состояние, восстановление

### 10.1. MCP или фоновый скрипт

| Задача | Режим | Почему |
|---|---|---|
| пересборка ассета «с нуля по параметрам», серия ассетов, пакетные рендеры, CI | `blender -b --factory-startup --python build.py` через `blender_run.py` | детерминизм, изоляция, нет 180-секундного предела, свои логи |
| пошаговая работа в Blender пользователя (он смотрит в окно) | MCP (mcp-for-blender с окном) | правки видны сразу; человек может вмешаться |
| агент без окна с MCP-клиентом | официальный MCP Blender Lab (`--command blender_mcp`) или мост C1 | штатный фон / все инструменты mcp-for-blender |
| поиск HDRI и текстур Poly Haven | MCP mcp-for-blender (инструменты) или прямой API Poly Haven из скрипта | готовые материалы и атрибуция |
| проверка вида | рендер в PNG (любой режим) | снимок вьюпорта не годится (`01 §3.5`) |

Разница с исследованиями: они меряют сходство с эталоном; наш критерий — «годится в hero серии», поэтому к их циклу
добавлены паспорт стиля, бюджет веба и проверка в браузере. Сильная модель «с первой попытки» (opus в C1/11) уже даёт
верную композицию и присоединённые части — у неё остаются масштаб, экспортируемость и тяжесть; значит, для сильной
модели протокол экономит не на форме, а на проверках масштаба, бюджета и веба.

## Частые ошибки

1. **Писать код до паспорта** — размеры «на глаз» (кружка 1,8 м у sonnet, 2,2 м у opus) [проверено: 11].
2. **Камера углами Эйлера** — объект вне кадра или обрезан (haiku 3/3, sonnet 7/8) [проверено: 11].
3. **Числа стыков наугад** — парящие детали (телефон, ноутбук sonnet) [проверено: 11, 16].
4. **Цепочка мелких вызовов с состоянием в голове** — дубли `.001`, лишние слоты, `KeyError` после перезапуска [проверено: 05].
5. **«Скрипт отработал — значит готово»** — без рендера и утверждений [проверено: 11].
6. **Проверка снимком вьюпорта** — чужой ракурс, в фоне серые материалы [проверено: 04].
7. **Бесконечная доводка по картинке** — >3 визуальных итераций без попарного сравнения и отката (по C2 после ~2
   итераций улучшений нет).
8. **Смена стиля между ассетами серии** — свет, камера и материалы заново для каждого объекта вместо паспорта стиля.
9. **Экспорт всей сцены** — лампы, камера, ловец теней, служебные объекты в GLB; нужна коллекция ассета.
10. **Процедурный материал для сайта** — ColorRamp-градиент экрана и thin film теряются в glTF [проверено: 11, 12].
11. **`gltf-transform optimize` без оглядки** — сливает части, которые должны двигаться [проверено: 15].
12. **Cycles 1920×1080 × 4 096 сэмплов «для красоты»** в MCP-вызове — превышение 180 с [проверено: умолчания 5.2.2].
13. **Нет контрольной точки перед разрушительным шагом** — отката нет.
14. **Генератор «на пробу»** — расход платного ключа без разрешения.

## Открытые вопросы и противоречия

- **Параллельные варианты на наших ассетах не проверены** — числа только из исследований (C2); проверить в волне 3 (J):
  2–4 варианта скульптуры, отбор утверждениями и попарным судьёй.
- **Порог рубрики** (сколько «нет» допустимо) не откалиброван на людях; нужен регрессионный набор эталонов (предложение C2).
- **Идемпотентный скрипт против пошаговой работы с человеком в окне**: для совместной работы (пользователь двигает
  объекты руками) пересборка «с нуля» сотрёт его правки — нужен режим «правка поверх» с фиксацией ручных изменений в `P`.
- **Мои объекты C1/12 имеют pivots в нуле мира** (трансформации запечены в меш) — для анимации частей на сайте нужен
  отдельный объект с pivot на оси (крышка на петле); в протоколе это правило, в C1/12 не выполнено.
- **Сила модели меняет узкое место**: для opus протокол нужен прежде всего ради масштаба, бюджета и экспорта; для
  слабых моделей — ради исполнимости. Как выбирать глубину протокола по модели — открыто.
