### 1.2. Почему mcp-for-blender не годится как фоновый сервер

`BlenderMCPServer.start()` при `bpy.app.background` печатает «cannot start server in background mode (blender -b)…
use a virtual display: xvfb-run -a blender» и выходит; автозапуск в фоне тоже (`01 §8.1`). Причина — команды исполняет
колбэк `bpy.app.timers`, а в `blender -b --python` после скрипта нет цикла событий. Обход C1 (`01 §8.2`) — копия аддона,
`gpu.init()` и главный поток, который сам крутит `_drain_command_queue()`; рабочий, но самодельный. Независимое
подтверждение той же схемы (виртуальный дисплей + отдельный поток ИИ + поток UI) — доклад Microsoft/Foundry
[V:`Sg6XOnJ5n1c` ≈15:56].

### 1.3. Официальный сервер без окна (рекомендуемый мост)

`blender -b file.blend --factory-startup --online-mode --command blender_mcp` (проверено C2/02: `register_cli_command`
работает в 5.2.2, EEVEE 256² за 2,89 с, ответ 2 МБ целиком). В фоне цикл `poll_blocking()` (select) исполняет запросы
**синхронно на главном потоке** — отложенных ответов (`check_is_finished`) нет: длинную операцию завершай в одном вызове.
Без `--online-mode` мост отказывает («Online access must be enabled… Use --online-mode»). Контракт: вернуть данные —
присвоить `dict` переменной `result`; `print` → поле `stdout`; ошибка → полный traceback; переменные Python между вызовами
не живут, данные `bpy` — живут (`02 §2.3`).

### 1.4. `blender -b --python` как исполнитель заданий

Базовый детерминированный путь (им работают Willison, 3DCodeBench, blender-to-web — `02 §7.5`): скрипт «собрать с нуля
по параметрам» → проверки → рендер с ракурсов. Нет предела 180 с, свои логи, полная изоляция процесса. Долгоживущий
вариант — процесс с очередью заданий: его и реализует супервизор (§2), общаясь по Unix-сокету.

### 1.5. Порт и число экземпляров

Порт по умолчанию 9876 у обоих серверов (`01 §10.2`, `02 §2.3`). Своему мосту давай другой порт (C2 брал 9901) и
соответствующий `--port` серверу; при двух аддонах в одном Blender поменять порт у одного. Супервизор общается не по TCP,
а по Unix-сокету `WORK/sup/blender.sock` (права 0600) — конфликта портов нет и работает в песочнице без сети (§2, `07 §4`).
Путь `WORK/sup/blender.sock` — не длиннее 107 байт (предел Unix-сокета Linux): WORK в глубоком каталоге → `start` ждёт 90 с и пишет «нет сокета» (`NotRunning`) [проверено: 99-raw/experiments/X/01-rerun, лог `O01_supervisor_try1_longpath.log`].

## 2. Супервизор фонового Blender (`../../scripts/3d/blender_supervisor.py`, ≤300 строк)

Один процесс Blender на рабочую папку WORK. Надзиратель (`nanny`) держит его живым; внутри Blender крутится исполнитель
(`worker`), слушающий Unix-сокет. Команды: `start`, `exec`, `status`, `stop`, `replay`.

```bash
# Blender 5.2.2 — [проверено]
python3 ../../scripts/3d/blender_supervisor.py start WORK --mem 4G --cpu 400%   # поднять (или --sandbox, --online)
python3 ../../scripts/3d/blender_supervisor.py exec  WORK build.py --timeout 120 -- 0.5   # шаг агента; код 0/1/2
python3 ../../scripts/3d/blender_supervisor.py status WORK        # pid, hb_age, busy, последние точки
python3 ../../scripts/3d/blender_supervisor.py stop   WORK        # STOP-файл, при зависании — TERM группе
```

Коды выхода `exec`: **0** — успех (создана контрольная точка), **1** — исключение в коде агента (сцена откатена к
последней точке), **2** — процесс убит/упал (восстановлен из последней точки при перезапуске).

### 2.1. Живучесть и heartbeat

`nanny` запускает Blender в своей группе процессов (`start_new_session`), пишет `state.json` (pid), а `worker` каждую
секунду обновляет `WORK/sup/hb` и на время шага — `WORK/sup/busy.json` с дедлайном. Надзиратель раз в 0,25 с проверяет:
превышен ли дедлайн шага (+GRACE 5 с) → `SIGKILL`; молчит ли heartbeat в простое > 30 с → `SIGKILL`; не поднялся ли
процесс за 90 с → перезапуск. Более 5 перезапусков за 120 с — `give_up` (защита от петли краша). После смерти —
перезапуск и восстановление сцены из последней точки.

### 2.2. Поведение при сбоях (проверено на копии, O/01)

| Сбой в коде агента | Симптом | Как ловит | Восстановление | Код |
|---|---|---|---|---|
| `sys.exit(3)` | у mcp-for-blender закрыл бы Blender; в исполнителе — `SystemExit` | `except BaseException` | откат к последней точке, процесс жив | 1 |
| `raise KeyboardInterrupt` | у mcp-for-blender снял бы таймер | `except BaseException` | откат, процесс жив | 1 |
| `MemoryError` (`bytearray(1<<42)`) | мгновенно | исключение | откат, процесс жив | 1 |
| исключение (`BLENDER_EEVEE_NEXT`, KeyError) | traceback | исключение | откат, процесс жив | 1 |
| бесконечный цикл | нет ответа | таймаут шага → `SIGKILL` (rc −9) | перезапуск + открыть точку (0,008 с) | 2 |
| `os.kill(getpid(), 11)` (segfault) | краш | код выхода −11 (в `bwrap` — **139**) + `.crash.txt` | перезапуск + открыть точку | 2 |
| исчерпание памяти под `--mem` | рост RSS | OOM-killer cgroup (rc −9) | перезапуск + открыть точку | 2 |
| ответ > ~5–6 МБ (у MCP) | «Incomplete JSON» | — | печатать сводку, данные — в файл (`01 §2.3`) | — |
| обрыв сокета | нет ответа | клиент ждёт перезапуска и берёт причину из журнала | — | 2 |

Ключевое: **исключения (`sys.exit`, `KeyboardInterrupt`, `MemoryError`) исполнитель ловит внутри процесса** и откатывает
сцену — Blender не падает; **зависание и segfault ловятся только снаружи** — поэтому надзор обязателен даже поверх
официального сервера, который сам их не переживает.

## 3. Контрольные точки, восстановление, журнал краша

### 3.1. Транзакция шага

Успех шага → `bpy.ops.wm.save_as_mainfile(filepath="WORK/checkpoints/ckpt_%06d.blend", copy=True)` (2,8–4,0 мс на малой
сцене, 91 КБ), ротация — оставить последние `--keep` (5). Ошибка → `bpy.ops.wm.open_mainfile(filepath=<последняя точка>,
load_ui=False)`. Это заменяет отсутствующий undo: официальный сервер undo не создаёт и Ctrl+Z человека после шага не
откатывает (как mcp-for-blender, `01 §3.4`). Правило C1 (`01 §11 п.8`) «сохранять до разрушительного шага» здесь —
автоматическая часть исполнителя.

```python
# Blender 5.2.2 — [проверено] исполнитель: шаг как транзакция (суть)
import bpy, contextlib, io
buf, err = io.StringIO(), None
try:
    with contextlib.redirect_stdout(buf):
        exec(compile(code, name, "exec"), {"__name__": "__main__", "bpy": bpy})
except BaseException as e:                      # SystemExit/KeyboardInterrupt/MemoryError тоже — процесс жив
    err = {"type": type(e).__name__, "message": str(e)}
if err is None:
    bpy.ops.wm.save_as_mainfile(filepath=ckpt_path, copy=True)   # copy=True: не меняет «текущий файл»
else:
    bpy.ops.wm.open_mainfile(filepath=last_ckpt, load_ui=False)  # откат сцены к последней удачной точке
```

### 3.2. Восстановление после перезапуска

При старте (и после каждого краша) исполнитель открывает последнюю `ckpt_NNNNNN.blend` (0,006–0,008 с) — журнал в
событии `ready` пишет `restored`. Дальше агент повторяет идемпотентный `build(P)` (C1 `04 §10.2`, `05` M6.3) — сцена
восстанавливается по параметрам, а не по «памяти диалога». `.blend1` (`save_version=1`) появляется лишь при повторной
записи в один и тот же путь — уникальные имена точек их не плодят (проверено O/01).

### 3.3. Журнал краша Blender на Linux

Blender при падении пишет `<имя_открытого_файла>.crash.txt` (без имени — `blender.crash.txt`) в **`$TMPDIR`**
(`bpy.app.tempdir` = `$TMPDIR/blender_XXXX/`; у пользователя `$TMPDIR = ~/.cache/tmp`). Внутри — версия, хеш сборки и
backtrace с адресами. Супервизор ставит `TMPDIR=WORK/tmp`, ловит файл (событие `exit.crash_log`) и кладёт путь в журнал.
Ответ на вопрос I (§4 отчёта): журнал краша ищи в `$TMPDIR`, а не в рабочей папке проекта.

## 4. Журнал команд и результатов (JSONL)

`WORK/sup/journal.jsonl` — по строке на событие: `ready` (pid, версия, restored), `spawn`, `exit`/`timeout_kill`/
`hang_kill` (rc, signal, uptime, lost_seq, crash_log), `run` (seq, name, ok, dt, error, checkpoint, reverted_to,
`stdout_tail`, `code_sha256`, `code`, args), `stopped`. Итог шага исполнитель печатает **одной строкой JSON последней**
в stdout (в выводе есть и «Info: Saved copy as…» операторов — как чужой stdout при `redirect_stdout`, `01 §2.5`); клиент
разбирает последнюю строку. Журнал — источник данных для J (ворота качества: `scene_check` пишет одну строку JSON шага,
`qa_pipeline` даёт коды 0/1/2/3 — J §4) и регрессионный набор (замена модели/промтов): `replay WORK journal.jsonl`
повторяет все удачные шаги в чистом процессе (проверено O/01: 14 шагов за 2,1 с, включая `build.py -- 0.5` с аргументом).
Формат совпадает с «Журналом задачи» C1 (`04 §10.3`: `runs/NN/`, `checkpoint_NN.blend`) и с трассировкой сессии
production-платформы [V:`Sg6XOnJ5n1c` ≈07:57].

### 5.2. Лимиты памяти и CPU через systemd-run

```bash
# Blender 5.2.2 — [проверено] жёсткий лимит памяти процесса Blender
systemd-run --user --scope -q -p MemoryMax=1500M -p MemorySwapMax=0 -p CPUQuota=400% -- \
  nice -n 10 blender -b --factory-startup -Y --python build.py
```

Проверено: `MemoryMax` **без** `MemorySwapMax=0` при свопе 63 ГБ не срабатывает (300 МБ выделяются под лимитом 100 МБ);
`MemoryMax=100M -p MemorySwapMax=0` → OOM-kill (rc 137) сразу; `MemoryHigh` лишь тормозит процесс (не убивает, шаг висит).
Правило: жёсткий предел — `MemoryMax` **и** `MemorySwapMax=0`; cgroup v2 у пользователя включён (контроллеры cpu, memory,
pids). `nice -n 10` и `CPUQuota` уступают долю другим агентам. Супервизор добавляет эти обёртки по флагам `--mem`, `--cpu`.

## 7. Модель под роль и цена цикла (из данных C1/C2, без новых прогонов)

| Роль в цикле | Модель | Что известно |
|---|---|---|
| черновой код, рутинная сборка `build(P)` | быстрая (haiku/sonnet-класс) | быстрее и дешевле; исполнимость поднимают повторы по traceback |
| форма, композиция, стыки частей | сильная (opus-класс) | лучше форма, но масштаб ×12–25 и неэкспортируемые материалы — частая ошибка (C1 `05 §1, §11`; D1) |
| правка по ошибке | любая + traceback | 2 повтора по traceback: исполнимость 0,70 → 0,97 на Blender 5.0 (3DCodeBench, C2 `03 §2`) |
| визуальная доводка | сильная + рубрика | ≤2–3 итерации, дальше улучшений нет (C2); best-of-N лучше длинных итераций |

Время «первой попытки» (C1 `05 §1`): opus писал сцену ~56 мин, sonnet ~35 мин — при равной исполнимости выбирай по
бюджету времени/токенов, форму доверяй сильной модели, рутину — быстрой. Точных токен-замеров под нашу роль нет
(`[не проверено]`, пробел для отдельного прогона — не в экономном объёме).

## Частые ошибки

- **Ждать, что mcp-for-blender заработает в `blender -b`** — не заработает (`01 §8.1`); для фона без окна — официальный
  сервер или мост C1.
- **Поднять официальный сервер без `--online-mode`** — мост не стартует (проверено C2/02).
- **Два сервера/аддона на 9876** — второй не стартует («port already in use»); разные порты (`01 §10.2`).
- **Считать, что сервер восстановит сцену после краша** — нет: ни официальный, ни mcp-for-blender не делают контрольных
  точек и не перезапускаются; это работа супервизора (§2).
- **`MemoryMax` без `MemorySwapMax=0`** — при большом свопе лимит бесполезен (§5.2).
- **Разбирать не последнюю строку stdout** — в выводе шага есть «Info: Saved copy…» и чужой stdout потоков; итог — последней
  строкой JSON (`01 §2.5`).
- **Искать журнал краша в папке проекта** — Blender пишет его в `$TMPDIR` (§3.3).
- **`os.kill(...,11)` в песочнице ждать как rc −11** — `bwrap` отдаёт 139 (128+сигнал) (§2.2).
- **Держать состояние «в голове диалога»** вместо `build(P)` — после перезапуска теряется; восстановление идёт по
  контрольной точке + идемпотентной пересборке (C1 `05` M6.3).
