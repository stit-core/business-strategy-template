## Выжимка для агента

1. **Исполнимость решается повторами, форма — нет.** Два повтора с traceback поднимают исполнимость кода Blender 5.0 с
   0.702 до 0.974; родная агентная оболочка (Claude Code, Codex, Gemini CLI) тоже даёт 0.973, но **качество формы не
   меняется**. → §2.2 `[исследование, 2026]`
2. **~90 % отказов кода — несовпадения API версии.** Отдавай модели traceback целиком (урезая середину: 70 % начала +
   30 % конца, ≤3 000 символов), а не одно сообщение. → §2.2 `[исследование]`
3. **Главный дефект формы — парящие и оторванные части**, у всех 12 frontier-моделей; у Claude Opus 4.7 — «простые
   парящие примитивы» при лучшей исполнимости 0.910. Стыки вычисляй кодом по габаритам соседей. → §2.2, §9 `[исследование]`
4. **Подкладывай документацию версии, а не надейся на память**: в 5× больше «сложных» операций и −26 % ошибок (LL3M,
   Blender 4.4); у Claude Sonnet 4 CD 0.0405 → 0.0368 с RAG. Официальный MCP Blender Lab уже несёт справочник 5.2. → §2.3, §8 `[исследование]`
5. **Проверяй справку запуском**: даже «проверенная на 5.0» справка 3DCodeBench содержит 2 ложных «запрета» из 27
   (`GeometryNodeCurveStar` и `GeometryNodeCurveQuadraticBezier` существуют). → §13 `[проверено]`
6. **1–3 проверенных примера под похожий объект** — компиляция 40.8 → 70.0 % за один проход (BlenderRAG); **5+ общих
   примеров вредят сильным моделям** (Claude Sonnet 4.5 −17.5 п. п.). → §2.4, §2.10 `[исследование, консенсус 3 работ]`
7. **Собирай объект по частям от опорной детали**, с именами-ориентирами (`front_right_leg`): 0.6 против 0.346 у одного
   скрипта GPT-4 (L3GO); части в GLB — отдельные узлы для интерактива на сайте. → §2.10, §12 `[исследование]`
8. **Координаты — кодом, отношения — моделью.** Прямые координаты LLM в раскладке не лучше случайных (MRR 0.364 против
   0.369); отношения + решатель — 0.706; числа VLM + оптимизация — 94.9 % сцен в границах. → §6 `[исследование, консенсус]`
9. **Не пиши сырые графы нод кодом**: geometry nodes из Python у GPT-4o, o3, DeepSeek-V3 — 0 % компиляции; компактная
   обёртка — 89–94 %. Используй проверенные функции-помощники. → §2.4, §5 `[исследование, единичный источник]`
10. **Шейдерный граф — ≤20 нод, план словами до кода**: валидность падает при >22 нодах; у GPT-5 код графа напрямую не
    исполняется ни в одном кандидате в 30 % промтов, через текстовый план — 100 %. → §5 `[исследование]`
11. **Процедурный материал в веб — только запечённым**; готовый материал из библиотеки часто лучше сгенерированного. → §5, §12 `[исследование]`
12. **Проверки кодом сильнее VLM-критика**: исполняемые тесты требований согласуются с людьми на F1 0.962 против 0.549 у
    VLM-судьи; отчёт среды (габариты, «внутри», зазор) +8.5 п. п. → §3, §8 `[исследование, консенсус 4 работ]`
13. **VLM «на глаз» не видит геометрию**: согласованность геометрии и текстуры GPT-4V — 46.9 % (≈ случай) против 83.0 % у
    измерения нормалей. → §7 `[исследование]`
14. **Судья — попарно, не баллами**: баллы «геометрия 1–3» у GPT-5/Gemini 2.5 Pro — Pearson 0.17–0.37 с людьми; попарные
    решения по рендерам — 74–77 % согласия (пара людей — ~79 %). → §7.1 `[исследование, консенсус 5 работ]`
15. **Соответствие брифу — вопросами да/нет по ракурсам**: 88.7–91.5 % согласия против 72.8 % у целостной оценки. → §7.2 `[исследование]`
16. **Не больше 2 изображений за вызов судьи, два порядка сравнения**: 7 картинок → 100 % ответов «по позиции» у 7B-судьи;
    засчитывай только согласованный вердикт. → §7.2 `[исследование]`
17. **Геометрию показывай «глиной» или нормалями**, не раскрашенной картинкой: раскраска прячет дефекты. → §7.2 `[исследование]`
18. **«Думай дольше» не помогает судье** (GPT-5 low/medium/high — одинаково) и почти не помогает сильной модели-генератору
    (Opus 4.7 на плато уже при minimal). → §7.3, §2.2 `[исследование]`
19. **Судьи не говорят «оба плохи»** (0–3 % против 15.6 % у людей) — ставь явный порог «не годится». → §7.3 `[исследование]`
20. **Не проверяй ассет чтением собственного кода**: по коду модель верно понимает «что изображено» в ~50 %; нужен рендер. → §4.4 `[исследование]`
21. **Визуальная доводка — 1–3 итерации с откатом**: самокритика даёт +0.003…+0.009, после ~8 правок изменения
    пренебрежимы, петля критика +2.4…5.8 %; числовая обратная связь полезна до ~5–10 попыток. → §8, §3.2 `[исследование, консенсус]`
22. **Параллельные кандидаты лучше длинной цепочки**: 3 пути по 1 итерации — IoGT 0.535 за 3.7 мин; 3 пути по 5 — 0.431
    за 18 мин; дерево 4×8 лучше 32 правок подряд; 10 кандидатов с отбором — брак 16.8 → 0.3 %. → §8 `[исследование, консенсус]`
23. **Текущий лучший вариант всегда участвует в отборе** (откат): без этого крупные правки ухудшают результат. → §2.5 `[исследование]`
24. **Передавай текущий код при каждой правке**: иначе модель пишет с нуля и объект «уплывает»; правка ≈38 с против ≈10 мин
    новой генерации. → §2.3 `[исследование]`
25. **Разделяй правки сцены по доменам** (геометрия, материал, свет, камера, фон) с жёсткими числами: 72.1 % подзадач против
    30.4 %; камера и свет — самые трудные. → §2.7 `[исследование, слабая метрика]`
26. **Уточни бриф до кода**: чистое ТЗ снижает невалидные решения Claude Sonnet 4.5 с 56.6 до 11.8 %; уточняющий вопрос —
    брак 14.6 → 0.9 %. → §3 `[исследование]`
27. **Референс-картинку давай вместе с текстом, не вместо**: фото вместо текста ухудшает код у 4 из 5 моделей. → §2.2 `[исследование]`
28. **Размеры — в метрах в паспорте и в утверждениях `obj.dimensions`**: главный кластер отказов — «правдоподобные пропорции
    при неверных размерах»; частая ошибка `bpy` — двойное масштабирование. → §9 `[исследование]`
29. **Органику отдавай генераторам или стилизуй**: худшие категории кода — вилка, ложка, ваза; хвосты и крылья делегируют
    генератору 3D. → §9 `[исследование]`
30. **Для кода `bpy` — только frontier-модели**: Qwen3-VL 8B/30B — 0 % рабочих скриптов Blender; малые локальные — для
    вспомогательных ролей. → §8.1 `[исследование]`
31. **Самописная библиотека агента без тестов копит тихие ошибки**: из 8 функций SceneCraft в 5.2.2 корректна 1 (поворот
    вокруг Y вместо Z, `matrix_world * 2` сдвигает объект, NaN, бесконечный цикл). → §2.9 `[проверено]`
32. **Габариты — по оценённому мешу**, не по `obj.data`: с Array ×3 функция SceneCraft видит 1.0 вместо 5.0. → §2.9 `[проверено]`
33. **Infinigen в Blender 5.2 не ставится** (требует `bpy==4.2.0`, Python 3.11) — источник идей и офлайн-рендеров, не
    ассетов для сайта. → §6.5 `[документация, 2026-09]`
34. **Ни один бенчмарк не мерит «красиво» и «готово для веба»** — только сходство с эталоном и правдоподобие; стиль задаёт
    паспорт серии, эстетику — попарный судья против эталона и человек. → §9, §12 `[консенсус]`

Тренды 2025–2026: (1) переход от «одного скрипта» к **агентам с исполнением и проверкой** (LL3M, VIGA, 3DCodeBench);
(2) **frontier-модели сами пишут рабочий `bpy`** (исполнимость 0.9+ с первого раза), узкие дообученные модели теряют
смысл вне своего распределения; (3) оценка смещается от CLIP к **исполняемым проверкам и попарным судьям** (CADTests,
3DCodeArena); (4) производители софта сами выпускают MCP-мосты (Blender Lab; коннектор Blender в Claude с 28.04.2026)
[S1][S2].

Обзоры, на которые можно опереться: сцены — процедурная, нейросетевая 3D, через изображения и видео; LLM либо планирует
раскладку, либо **управляет процедурными системами как агент** (3D-GPT, SceneCraft пишут Python для Infinigen и Blender)
[S3]; 3D-LLM в целом — генерация лишь малый раздел, процедурные системы объединяет декомпозиция задачи и
специализация ролей LLM [S4]; агентные генераторы сцен делятся на модульные (планирование → поиск → решатель →
проверка; «качество определяется самым слабым модулем») и саморефлексивные (критики и симуляция чинят ошибки)
[S5]; с точки зрения движка «готовый» ассет = манифолдная топология, UV без перекрытий, PBR без запечённого
света, LOD и коллизии — и это почти никто не измеряет [S6]; в CAD почти все подходы генерируют промежуточное
представление (код или параметрический JSON) [S7].

### 2.2. 3DCodeBench: самые свежие числа на Blender 5.0 [S8]

- **Постановка.** 212 категорий из фабрик Infinigen (птицы, крабы, кораллы, мебель, раковины); эталонный скрипт —
  медиана **387 строк** (среднее 531, 20.5 КБ). Промт жёсткий: только Python, Blender 5.0, разрешены `bpy`, `bmesh`,
  `mathutils`, stdlib-математика, `numpy`, `scipy`; **один объект в начале координат, без пола, фона и пьедестала**;
  без текстур, без рендера и сохранения; бюджет 240 с; при неясности — разумные значения молча [S18].
- **Однопроходная исполнимость** (лучший уровень размышлений): Claude Opus 4.7 **0.910**, GPT-5.5 0.906, GPT-5.4 0.866,
  Claude Sonnet 4.6 0.804, GPT-5.4 mini 0.731, Gemini 3.1 Pro 0.725, Gemma 4 31B 0.582, Claude Haiku 4.5 0.502,
  Gemini 3 Flash 0.481. Gemini 2.5 Pro и GPT-5.4 Nano — ниже 10 %, исключены. `[исследование, 2026]`
- **Форма по оценке людей** (арена, ~3 100 голосов, серый материал, только геометрия): GPT-5.5 1163 Elo, Gemini 3.1 Pro
  1147, Gemini 3.5 Flash 1119, GPT-5.4 1074, Claude Sonnet 4.6 1015, **Claude Opus 4.7 1006**. Лучшая исполнимость не
  означает лучшую форму: у Opus 4.7 типичный дефект — «простые парящие примитивы», у Gemini 3.1 Pro — «оторванные
  фрагменты». `[исследование]`
- **~90 % отказов — несовпадения API Blender 5.0**, которые чинятся локально по traceback. Два повтора без истории
  (задача + прошлый скрипт + stderr ≤3 000 символов: 70 % начала + 30 % конца) поднимают исполнимость **0.702 → 0.974**
  (+27.2 п. п.); у Opus 4.7, GPT-5.4 и GPT-5.5 — до 1.000. Цена повторов на всём наборе — 55.54 USD. `[исследование]`
- **Родная агентная оболочка** (Claude Code, Codex CLI, Gemini CLI; 600–900 с на задачу; папка с `out.py` и
  `run_blender.sh`): исполнимость 0.747 → 0.973, но **условное качество формы не меняется** (SigLIP −0.010, Chamfer
  +0.001, Uni3D −0.003). Оболочка чинит API, но не геометрию. `[исследование]`
- **Визуальная самокритика** (до 2 итераций; ответ `NEEDS_FIX: NO|YES` + оценка + полный код; откат при поломке):
  на тексте слабый плюс (+0.003…+0.009 SigLIP), на задачах по картинке — минус. Сильная модель — осторожный критик
  (Gemma 4 31B принимает 41 % результатов), слабые «чинят» агрессивно (откатов 26–28 %). `[исследование]`
- **Картинка-референс вместо текста** (фото от генератора изображений, 0.134 USD): хуже прямого текста у 4 из 5 моделей;
  исполнимость Gemini 3 Flash падает на 27 п. п. — фотореализм толкает к непосильной геометрии. Текст + картинка —
  малый плюс (+0.005…+0.014) только у сильных моделей. `[исследование]`
- **Бюджет размышлений**: лёгкие модели +19 п. п. исполнимости от minimal к high; Pro-класс — меньше 5 п. п.; Opus 4.7
  выходит на плато уже на minimal. Подбор уровня под модель экономит ×3. Число входных ракурсов 1–4 почти не влияет
  (SigLIP ±0.012). Температура 0.7 — оптимум, ≥1.5 хуже, 0 раздувает размышления у Flash-класса. `[исследование]`
- **Автоматика против людей**: сходство ракурсов SigLIP-2 с эталоном — Pearson r = 0.964 с Elo людей по 12 моделям,
  DINOv3 — Spearman ρ = 0.972; исполнимость — худший предиктор. `[исследование]`

### 2.3. LL3M: многоагентная генерация с документацией [S9]

- **Роли.** Планировщик (GPT-4o) бьёт запрос на части (стул → ножки, спинка, сиденье); поиск (GPT-4o) по базе
  документации Blender 4.4 — **1 729 страниц** в RAGFlow; кодер (Claude 3.7 Sonnet) пишет и исполняет код по частям,
  видя код предыдущих частей; критик (Gemini 2.0 Flash) смотрит **5 рендеров EEVEE** с камерой по габаритам и выдаёт
  «проблема → решение»; верификатор сравнивает новые рендеры со старыми и списком замечаний; пользователь правит текстом.
- **Время.** Создание ≈4 мин, автодоводка ≈6 мин, правка пользователя ≈38 с.
- **Документация против памяти.** На 17 объектах: «сложных» операций (bmesh, ноды, прямое редактирование вершин)
  **5.86 с документацией против 1.20 без**; ошибок исполнения **2.43 против 3.29 (−26 %)**. Без документации кодер
  «чинит» ошибку удалением строки и скатывается к примитивам. Пример из статьи: вход `Specular` переименован в
  `Specular IOR Level` в 4.x. `[исследование, выборка мала]`
- **Передавать текущий код обязательно**: без него кодер переписывает с нуля и получается другой объект.
- **Пространственные правки — слабое место**: 59 % правок пользователя удались с одной инструкции, остальным понадобилось
  3–4 уточнения («приставь ручку», «положи мороженое в руку»); критик пропускает зазоры и пересечения; ручки лейки
  остались оторванными после автодоводки. `[исследование]`

### 2.4. Примеры и компактные представления: BlenderRAG и Proc3D

- **BlenderRAG** [S10]: 500 проверенных триплетов «описание — код — рендер» (50 категорий × 10 вариаций,
  черновики Claude Opus 4.1, правка экспертами; код 3 000–24 000 символов). Поиск 3 ближайших примеров по эмбеддингу
  описания. Один проход без повторов: компиляция **40.8 % → 70.0 %** в среднем; Claude Sonnet 4.5 43.3 → 76.7,
  GPT-5 Chat 56.6 → 66.7, Gemini 3 Flash 53.3 → 80.0, Mistral Large 10.1 → 56.7. Без примеров — парящие части и
  несогласованные масштабы. `[исследование, 30 промтов]`
- **Proc3D** [S11]: доля компилирующихся программ при генерации GPT-4o (100 промтов): **сырые geometry nodes — 0 %**
  (6 048 токенов), DSL Infinigen — 5 %, **Python Blender — 30 %**, LLaMA-Mesh — 45 %, компактный граф PCG — **89 %**
  (702 токена, 9 с). У o3: 0 / 15 / 65 / 94 %; у DeepSeek-V3: 0 / 9 / 63 / 92 %. Правка параметра в PCG — 0.01 с
  (≈400× быстрее перегенерации). Ограничение: обучено на кубоидах PartNet — формы «кубические». `[исследование, единичный источник]`
- Вывод для нас: **чем короче и ближе к проверенному образцу представление, тем надёжнее код**. Самые дешёвые рычаги —
  библиотека проверенных примеров под похожие объекты и обёртки-помощники вместо сырого API нод.

### 2.5. Поиск с отбором: BlenderAlchemy и BlenderGym

- **BlenderAlchemy** [S15]: состояние = базовый .blend + несколько коротких программ, каждая отвечает за
  одну часть (материал одного меша, свет сцены). Цикл: генератор даёт b вариантов → все рендерятся → попарный турнир
  VLM за O(log b) запросов → **текущий лучший тоже участвует** (откат) → чередование tweak (только числа) и leap
  (новые ноды и связи). При бюджете 32 вызова: 1×32 — photometric 0.066, 4×8 — **0.049**, 8×4 — 0.050, 32×1 — 0.087.
  Без отката итерации с крупными правками ухудшают результат; только leap — расходится, только tweak — плато.
  CLIP: однопроходный BlenderGPT 25.2, без зрения 25.7, зрение у оценщика 27.8, полная система 28.2.
  Люди (592 сравнения): предпочли BlenderAlchemy текстурам Paint3D в 73 %, TEXTure — в 56 %; с выбором оценщика
  согласны в 71 %. `[исследование]`
- **BlenderGym** [S16]: 245 пар «старт–цель» (геометрия 50, свет 40, материал 40, blend shapes 75,
  размещение 40). 10 «средних» пользователей Blender за ≤8 мин лучше лучшего VLM на порядок: blend shapes PL 0.934
  против 9.140, геометрия 1.269 против 6.747, материал 0.629 против 3.653. Открытые VLM (кроме MiniCPM) не выдают
  исполнимого кода в >75 % задач геометрии и материалов — «проводка нод кодом», скрипты >80 строк. Верификатор:
  совпадение с людьми в попарном выборе лучший **0.66** (Claude 3.5 Sonnet) против **0.79** у пар людей; Qwen всегда
  выбирает второй вариант. При бюджете <30 запросов выгоднее больше генерации, при >100 — больше проверки (доля 0.73). `[исследование]`

### 2.6. VIGA: навыки, память, активная камера [S12]

- Инструменты разделены на **наблюдение** (`set_camera`, `investigate`, `get_scene_info`, `set_visibility`,
  `initialize_view` — без изменений сцены) и **изменение** (`init_scene`, `get_better_assets`, `execute_code`,
  `undo_action`, `end_process`); первый вызов обязателен — `make_plan` с размерами в метрах, началом координат и
  сторонами света и стадиями «ассеты → грубая раскладка (пол, фон, камера, главный свет) → подгонка → детали».
- `execute_code` требует три поля: рассуждение, **минимальный дифф** («-:»/«+:»), полный обновлённый скрипт.
- **Скользящее окно памяти** (последние L итераций; последний скрипт содержит всё состояние): без окна агент теряет
  созданные объекты, с полной историей — «гниение контекста». Память помогает сходиться: мяч пересекает стол → агент
  сравнивает прошлые высоты 0.8 и 0.7 и ставит 0.75.
- Прирост к однопроходному решению на BlenderGym: GPT-4o +26.9 %, Claude Sonnet 4 +33.7 %, Gemini 2.5 Pro +47.4 %,
  Qwen3-VL-8B +22.6 %. **GPT-4o не умеет активно двигать камеру** и проваливает сложные реконструкции. `[исследование]`

### 2.7. EZBlender: домены и скорость [S13]

- Планировщик переводит расплывчатый запрос в **семантические директивы по доменам** {геометрия, материал, свет,
  камера, фон} без кода («киберпанк» → свет «неон, высокий контраст», материал «мокрый металл»); субагент домена
  превращает директиву в жёсткие ограничения («синий свет» → `light.color = (0.05, 0.25, 1.0)`) и сам доводит
  результат; общий отладчик чинит неверные имена нод, отсутствующие атрибуты, значения вне диапазона.
- Мультизадачный тест (5 одновременных подзадач): **72.1 %** выполнено против 30.4 % у BlenderGPT и 18.1 % у
  BlenderAlchemy; без автономии субагентов — 33.4 %. Задержка правки 37.4 с (BlenderAlchemy 286.1 с); токены 5 869
  против 17 805. Хуже всего — **камера и свет**. Оценка только CLIP-классификатором. `[исследование, слабая метрика]`

### 2.8. Planner–Actor–Critic поверх MCP [S14]

Надстройка над MCP for Blender (ahujasid) + LangGraph, GPT-4.1, интерфейс на React Three Fiber с синхронизацией сцены
через WebSocket. Выводы качественные: декомпозиция на короткие фрагменты кода снижает галлюцинации; **после ~3
итераций качество сходится или падает**; исполнитель не всегда учитывает критику. В промте кодера — «не удаляй
объекты, сдвигай на x += 1000»: для экспорта в веб это **антипаттерн** (мусор уходит в GLB). `[мнение авторов]`

### 2.9. «Самообучаемая» библиотека навыков: проверка в 5.2.2

SceneCraft [S17] копит библиотеку функций размещения, которые LLM пишет и правит сама, без эталонов.
Эксперимент C2/01 [S19]: 668 строк из приложения статьи, запуск в Blender 5.2.2. Из 8 проверенных функций корректна
одна (`add_camera`). `rotate_objects_z_axis(90°)` поворачивает вокруг **Y** (брусок встаёт вертикально), при масштабе
объекта (2, 0.5, 0.5) и 45° ещё и искажает форму (габариты 4.11×1.0×4.11 вместо ≈3.54×3.54×1); `scale_group(×2)`
перемещает куб из (1, 2, 3) в (2, 4, 6); у `check_vertex_overlap` два определения с противоположным смыслом;
`parallelism_score` для объектов без поворота = NaN; `put_ontop` ссылается на неопределённую функцию, а с дописанной
уводит лампу в z = −1.19·10⁹ бесконечным циклом; `find_highest_vertex_point` игнорирует модификаторы (1.0 против 5.0
с Array ×3). Все ошибки, кроме `NameError`, тихие. `[проверено]`

### 2.10. Ранние агенты и смежные бенчмарки

- **3D-GPT** [S20] (3DV 2025): три агента без обучения — диспетчер выбирает функции процедурного генератора
  Infinigen, «концептуализатор» расписывает внешний вид по чек-листу атрибутов, моделировщик выводит **параметры функций**
  по их документации (описание параметров, читаемый код, нужные атрибуты, пример). Абляции: без концептуализатора CLIP
  30.30 → 21.51 и сбои разбора 0.8 % → 3.6 %; без диспетчера 29.16 → 22.79. Слабо: кривые и шейдинг (ветви, смешение
  цветов листьев); нет генераторов для волос и меха. Модель пишет не `bpy`, а вызовы готовых генераторов. `[исследование]`
- **L3GO** [S21] (воркшоп ICLR 2024): «необычные» объекты (стул с 5 ножками, кружка с 3 ручками) собираются **по
  деталям от опорной** (сначала сиденье), с критиками имён частей и пространства; **координаты считает код** по габаритам
  соседних деталей; среда возвращает текстовый отчёт (габариты, «деталь внутри другой», лишний зазор). Распознаваемость
  объектов ShapeNet-13 по мнению GPT-4V: L3GO **0.6** против 0.346 у GPT-4 одним скриптом (люди: 0.584 против 0.445);
  оригинальные меши — 0.877. Без критика по данным среды 0.515 (−8.5 п. п.); без вычисления координат кодом шкафы и
  машины падают до 0 (с калькулятором 0.5 и 0.4). Mixtral-8x7B вместо GPT-4 — 0.138. Согласие GPT-4V с людьми по
  распознаванию κ 0.512 при 0.569 у пары людей. `[исследование]`
- **DreamHouse** [S22] (2026, препринт): модели пишут **Blender 4.5.4 LTS** Python каркасных построек по 5 рендерам;
  детерминированный валидатор проверяет граф сцены (10 тестов: передача нагрузки, пролёты, зазоры) и возвращает текст
  («зазор BeamPost больше 3.0 м»). 26 543 конструкции, 133–1 548 элементов. Лучшая одновременная «структурно верно и
  похоже» — **7.1 %** (Claude, пошаговый режим «Atomic»); 9.4 % с визуальной обратной связью на каждом шаге. Структурная
  валидность: GPT-5 79.2 % (Atomic) и 33.3 % (Managed, по фазам); Claude 71.6 / 71.3 %; Gemini 45.4 → **78.5 %**. **Выбор
  «строительных лесов» агента влияет не меньше выбора модели**: переход Atomic → Managed даёт Gemini +33 п. п. и GPT-5
  −46 п. п. После ~8 визуальных правок изменения пренебрежимы (+0.010…+0.033 к сходству). Главный кластер отказов —
  **правдоподобные пропорции при неверных абсолютных размерах**; конёк крыши повёрнут на 90°. Qwen3-VL 8B/30B — 0 %
  рабочих скриптов. `[исследование]`
- **VoxelCodeBench** [S23] (2026, препринт): код воксельных сцен на закрытом API (47 функций + 2–3 примера на
  категорию), один проход. Форма верна: GPT-5 87.9 %, Claude Sonnet 4.5 80.4 %, Claude Opus 4 69.4 %; **геометрические
  задачи — самые трудные** (GPT-5 66.7 %, Claude Sonnet 4.5 52.8 %: сердце, параболоид, пересечения цилиндров);
  «художественные» — 97.5 % и 89.5 %. Эстетика («Look») не выше 5.71/10. **~40 % ошибок исполнения — выдуманные функции и
  перечисления API**, ~25 % — таймауты и тяжёлый код. **5+ примеров вместо 2–3 ухудшили сильные модели** (Claude Sonnet 4.5
  −17.5 п. п., GPT-5 Chat −33.4) и помогли слабой (Gemini Pro +24.8). `[исследование]`
- **Articulate-Anything** [S24] (ICLR 2025): актор пишет высокоуровневый Python на собственном API (компилируется
  в URDF — «длинный XML → больше галлюцинаций»); критик по рендеру или видео, эталону и коду обязан указать место ошибки
  и дать числовую оценку с порогом остановки. Успех предсказания суставов **75 %** против 8.7–12.2 % у прежних методов;
  петля критика даёт лишь +5.8 % (детали) и +2.4 % (суставы); **главная ошибка критика — ложные «успехи»** на малозаметных
  дефектах. Визуальный вход (картинка, видео) даёт больше, чем итерации. `[исследование]`

## 3. CAD-код и параметрические детали

Инженерный CAD вне рамок базы, но эта линия исследований лучше всех измерила, **где ломается код деталей** и **какая

### 3.2. Выводы, переносимые на Blender

1. **Исполнить → traceback → исправить — обязательный нижний слой**, но форму он не чинит (как и в 3DCodeBench, §2.2).
2. **Главные ошибки — пространственные и размерные**: компоновка частей (48 % у CADCodeVerify), двойное масштабирование в
   `bpy` (3D-PreMise), выдуманные размеры и путаница осей (ProCAD), «правдоподобные пропорции при неверных абсолютных
   размерах» (DreamHouse, §2.10). Лечение: размеры в метрах в паспорте и проверка `obj.dimensions` кодом.
3. **Проверки в виде кода сильнее VLM** и как оценка (F1 0.962 против 0.549), и как обратная связь [S33]; для
   ассета — набор утверждений `bpy`: габариты, одно тело после Boolean, нет щелей и проникновений, симметрия, соосность,
   бюджет полигонов.
4. **Best-of-N с автоматическим отбором**: 2–4 варианта скрипта параллельно и отбор по утверждениям — брак 16.8 % → 0.3 %
   у CAD-Recode [S28].
5. **Визуальная правка выдыхается за 1–2 шага**; числовая обратная связь продолжает помогать до ~5–10 попыток [S27][S37].
6. **Кривые и «продвинутые» операции — зона отказов** (дуги, sweep, loft, shell) [S29][S34]; для веб-мокапов —
   примитивы + Boolean + модификаторы Bevel, Solidify, Subdivision в «человеческих» единицах.
7. **Уточнять ТЗ до кода** выгоднее, чем чинить после [S36]; явное «масштабируй эскиз» в ТЗ провоцирует выдуманный API.
8. **Узкие дообученные модели не нужны**: вне своего распределения проваливаются [S34]; BlenderLLM-7B привязан
   к неуказанной старой версии Blender. Для Blender 5.2 — frontier-модель + справка 5.2 + инструменты проверки.

## 4. Меш как текст и программы формы

Две противоположные ставки: (а) модель выдаёт **сам меш** строками OBJ; (б) модель выдаёт **программу по частям** поверх
небольшой библиотеки функций. Для лёгких веб-ассетов в Blender выигрывает (б).

### 4.1. Меш как текст: LLaMA-Mesh и MeshLLM

| | LLaMA-Mesh [S38] | MeshLLM [S39] |
|---|---|---|
| Площадка | 2024, препринт | ICCV 2025 |
| Представление | OBJ-текст `v x y z` / `f i j k`, координаты квантованы в **64 уровня на ось** | то же + разрезание меша на части (KNN и семантические), сборка |
| Модель | полное дообучение LLaMA-3.1-8B, ≈2 400 GPU-ч | дообучение 8B, 128×A800 ≈6 дней |
| Потолок сложности | **≤500 граней** (лимит контекста 8k) | **≤800 треугольников** |
| UV, нормали, материалы | нет | нет |
| Результат | метрики качества нет, только картинки; языковые навыки проседают (GSM8K 77.18 → 62.09) | стулья: COV 47.33 против 19.53 у LLaMA-Mesh; FID 42.39 против 49.83; ≈ уровень MeshXL |

- Шаг сетки 64³ — ≈1.6 % габарита: гладкие формы идут ступенями, нормали плоские.
- Вне обучающего распределения ломается: в сравнении ShapeCraft LLaMA-Mesh худший по VQA (0.28) при 15.64 мин на
  объект [S40].
- Для нашего агента (Claude без дообучения) прямой вывод вершин — **худший путь** `[исследование, консенсус 3 работ]`.
  Переносится только идея **по частям**: объект — набор осмысленных частей, а не «сплошной суп вершин».

### 4.2. Код Blender поверх мини-библиотеки: MeshCoder, ShapeCraft, 3D-CoS

- **MeshCoder** [S41] (облако точек → скрипт Blender по семантическим частям). Библиотека над `bpy`:
  примитивы (куб, цилиндр, UV-сфера, конус, тор), **протяжка сечения вдоль кривой** (прямоугольник, круг, дуга,
  многоугольник, Безье по прямой, ломаной, окружности, Безье), **bridge loop**, булевы операции, массивы, параметр
  `resolution`. Реконструкция: Chamfer ×10⁻² **0.063** и IoU **86.75 %** против 1.87 / 67.62 у PLAD и 6.01 / 45.03 у
  Shape2Prog. Слабые категории: вилка (IoU 58.86), ложка (74.00), ваза (72.26). Органика «не развита», материалов нет.
  Написано под `bpy==4.0.0`. `[исследование, синтетика Infinigen]`
- **ShapeCraft** [S40] (длинное описание → текстурированный ассет по частям). Граф частей глубины 1: у каждой
  части описание формы и положения, **ограничивающий бокс** (cx, cy, cz, h, w, l) и код на обёртках (12 примитивов +
  8 модификаторов: bevel, array, mirror, solidify, boolean…). Критик — VLM по 3 ракурсам со шкалой 0–10 и ранним выходом
  при ≥9. На 26 длинных промтах: IoGT **0.471**, VQA **0.44**, 11.68 мин и 21 вызов на объект против BlenderLLM 0.455 /
  0.43, 3D-PreMise 0.385 / 0.33, CADCodeVerify 0.334 / 0.34, LLaMA-Mesh 0.346 / 0.28. **Прямая генерация
  «думающими» моделями без графа частей компилируется в 60–80 % промтов** (o3 60 %, Gemini 2.5 Pro 60 %,
  o4-mini-high 80 %, DeepSeek-R1 80 %), ShapeCraft — в 100 %. Иерархический разбор поднимает VQA 0.48 → 0.56, IoGT
  0.297 → 0.396. **3 параллельных пути по 1 итерации — IoGT 0.535 за 3.7 мин; 3 пути по 5 итераций — 0.431 за 18 мин.**
  Органику (хвосты, крылья) делегирует генератору Hunyuan3D и вписывает в бокс части. Blender 4.2.9 LTS. `[исследование]`
- **3D-CoS** [S42] (картинка → код Blender; сравнение 5 режимов промтинга frontier-VLM). Gemini 3 Pro: один вызов
  CD 0.0356 → план-чертёж 0.0280 → RAG по документации 0.0251 → few-shot 0.0249 → агент 0.0248; **Claude Sonnet 4**:
  один вызов 0.0405 → RAG **0.0368**, few-shot 0.0374, а «сначала план» — хуже (0.0419). Меш-реконструктор InstantMesh
  всё равно лучше (CD 0.0191). Агентный режим — ~170 000 токенов на объект против 12 107 у одного вызова. Типовые
  ошибки сборки: ножки стола повёрнуты на 90°, 2 А-образные опоры вместо 4, перекладина на середине вместо 1/4 высоты.
  План-«чертёж» задаёт части **в долях базового размера 1.0** — удобный формат пропорций. RAG — по документации
  Blender 4.4 (1 683 страницы, 21 102 функции `bpy`/`bmesh`/`mathutils`, top-k 8). `[исследование, препринт]`

### 4.3. Библиотеки формы, спроектированные LLM: ShapeLib [S43]

- LLM (o1-mini, GPT-4o) по описаниям функций и 20 размеченным формам проектирует библиотеку параметрических
  функций, выдающих кубоиды-прокси частей; **геометрическая проверка** отсеивает ошибки.
- Итог на 5 категориях PartNet: F1 семантики 36 против 18 у «только LLM»; IoU реконструкции 50.0 против 34.9;
  правдоподобие правок, сделанных LLM, выше, чем у библиотеки ShapeCoder, в 75 %; o1-mini сломал 11 из 100 программ
  ShapeCoder и 0 из 100 программ ShapeLib.
- **LLM хорошо выбирают структуру и функцию, плохо — числа**: ошибка параметров, предложенных LLM, 0.1824 → 0.0234 после
  перебора. До проверки 5–10 % предложенных функций содержат баги; аудит нашёл 6 из 28 функций, отклонившихся от замысла.
  Без исходного набора форм даже Claude 3.7 даёт F1 34 против 49. `[исследование]`
- Вывод для нас: параметрические генераторы (кружка, смартфон, полка, стол) с понятными именами параметров — хорошая
  основа для правок агентом; конкретные размеры лучше подбирать по числам сцены (габариты) или перебором по рендеру.
  Совпадает с экспериментом C2/01: функции, написанные LLM без тестов, содержат тихие ошибки [S19].

### 4.4. Понимает ли модель, что нарисует её код: SGP-Bench [S44]

- Вопросы о картинке по одному коду (SVG и CAD-DSL, без рендера): все модели ниже 70 % на SVG и ниже 75 % на CAD.
  Лучший, Claude 3.5 Sonnet: SVG 0.674 (семантика «что изображено» **0.505**, счёт **0.584**, цвет 0.891), CAD 0.742.
  На «бесформенных» контурах (SGP-MNIST) GPT-4o — 13 % при случайных 10 %.
- Иллюзии Эббингауза и Мюллер-Лайера обманывают модель на картинке, но не при рассуждении по координатам.
- Вывод: **проверять ассет «чтением собственного кода» нельзя** — нужен рендер; а размеры и пропорции надёжнее
  проверять числами сцены (`dimensions`, габариты), чем по картинке. `[исследование]`

## 5. Материалы как графы нод

Процедурный материал = граф шейдерных нод (шумы, Voronoi, кирпичи, Color Ramp, Math → Principled BSDF). Модель пишет
его как Python-программу `bpy` или DSL. Для сайта важна оговорка: **процедурный граф не переносится в glTF** — экспорт
понимает Principled BSDF и текстуры-картинки, поэтому процедурный материал перед экспортом **запекают** в карты
baseColor / metallicRoughness / normal (детали — `../08-export-gltf/`, агент E).

### 5.2. Выводы для агента

1. **Держать граф маленьким**: ≤20 нод и ≤2 000 токенов кода на материал [S45]; типичный «учебный» материал —
   14 нод [S47].
2. **Сначала план словами, потом код**: «шаги построения, параметры, замысел» → код; снимает 30 % неисполнимых программ
   у GPT-5 [S47].
3. **По ноде с проверкой**: после каждой ноды — проверка типов связей и превью выхода (временное подключение к Emission
   и рендер); откат при ошибке [S46].
4. **Сначала библиотека**: готовый материал, найденный по сходству, часто лучше сгенерированного [S45];
   1–3 проверенных «рецепта» в контексте — главный рычаг [S47].
5. **Всегда исполнять и рендерить**: без исполнения доля валидных графов у небольшой модели 23–29 % [S45].
6. **Для веба — запекание**: процедурный граф → карты 1–2K → KTX2/WebP (агент E); проще сразу собирать материал из
   Principled BSDF с малым числом параметров там, где процедурная фактура не нужна.
7. **Geometry Nodes из текста не генерирует ни одна прочитанная работа**; Proc3D строит geometry nodes только через
   компактный промежуточный язык, а сырые графы GN у GPT-4o/o3/DeepSeek-V3 компилируются в 0 % [S11]. Для нашего
   агента это пробел: geometry nodes из кода — только через проверенные обёртки (агенты B и D1). `[исследование, пробел]`

### 6.3. Независимая оценка: SceneEval [S49]

500 сцен, одинаковые метрики для всех методов (WACV 2026). **Ни один метод не выполняет больше 30 % требований к
атрибутам и больше 11.52 % отношений «объект–объект»**. LayoutGPT «лучший» по столкновениям (11.46 % объектов) только
потому, что выносит предметы за комнату (72.25 %). Самоотчёты статей несопоставимы: долю столкнувшихся объектов у
Holodeck три работы называют 6.1 %, 12.24 % и 15.91 %. VLM-судьи SceneEval согласны с людьми на 83.5–94.6 %, хуже всего —
на атрибутах. Вывод: **после любого генератора раскладки нужна своя геометрическая проверка** (пересечения мешей, опора,
границы, проходимость). `[исследование]`

### 6.4. Представление сцены и визуальная доводка

- **Иерархический код с говорящими именами** (The Scene Language [S58], CVPR 2025): функции-сущности
  (`chair_leg`), повторы через цикл (`union-loop`), позы через `transform` → **число объектов верно в 100 %** числовых
  промтов против 11 % у графа сцены и у прямой генерации MVDream; правки вида «сузь радиус лестницы на 80 %» — малой правкой
  кода.
- **Рендер с разметкой, а не голый скриншот**: вид сверху с сеткой координат, подписи имён объектов, стрелки «перед»
  (3D-Generalist [S59], HOG-Layout [S56]); без картинок LayoutVLM теряет 10.6 пункта PSA.
- **3D-Generalist** [S59]: действия VLM над сценой-кодом; без коллизий 99.0, в границах 98.0, PSA 67.9 (LayoutVLM
  58.8); 0 → 3 действия — CLIP 0.159 → 0.242, 3 → 10 — лишь до 0.252; **библиотека удачных фрагментов кода** даёт больше
  (0.252 против 0.237), чем 7 лишних итераций.
- **Физика против парения**: член устойчивости и вычисление высоты по опоре убирают парящие предметы (Scenethesis,
  HOG-Layout) — это же лечит «парящие примитивы» в объектах (§2.2).
- **Метаданные ассетов обязательны**: где «перед», габариты в метрах, тип опоры (пол, стена, поверхность, потолок); без
  них ориентация и пропорции ломаются (I-Design) [S52].

### 6.5. Процедурные генераторы на Blender: Infinigen

- **Infinigen** [S60] (CVPR 2023) и **Infinigen Indoors** [S53] (CVPR 2024): процедурные фабрики
  природы, мебели, интерьеров на Blender; лицензия BSD-3-Clause; живой проект (релиз 2.0.0a2 от 27.08.2026).
- **Для нашей машины — не ставится**: все версии требуют `bpy==4.2.0` и Python 3.11, а Blender 5.2.2 работает на
  Python 3.13 (по README репозитория; проверка G3) `[документация, 2026-09]`. Средняя полная сцена природы — 16M
  полигонов, ≈3.5 ч на пару кадров 1080p; экспорт не в glTF и с 4 каналами PBR.
- Как использовать: **источник идей и кода фабрик** (3DCodeBench вырезал из них 212 самостоятельных скриптов под
  Blender 5.0 [S8]), офлайн-рендеры фонов; не как поставщик веб-ассетов. Агенты 3D-GPT, BlenderGym, BlenderAlchemy
  опираются на обёртки Infinigen (`NodeWrangler`, транспайлер нод) — их код привязан к Blender 3.x/4.2.

## 7. Оценка 3D моделями: VLM-судья и согласие с людьми

Вопрос для нашего цикла: можно ли поручить «посмотри на рендер и скажи, хорошо ли» визуально-языковой модели и насколько
её решения совпадают с людьми. Ответ зависит от **формы вопроса**, а не от модели — тот же вывод, что для судей UI в
соседней базе (`../../ui/12-ai-generated-ui/03-research-2024-2026.md` §6.1: «судья без рубрики — шум, судья с
рубрикой, несколькими прогонами и моделями — инструмент»).

### 7.1. Сводная таблица согласия с людьми

примерно в каждом четвёртом решении. `[исследование, консенсус 5 работ]`

### 7.2. Что работает

1. **Попарное сравнение вместо баллов.** Абсолютная оценка «геометрия 1–3» у универсальных VLM почти шум
   (Pearson 0.17–0.37 даже у GPT-5 high) [S61]; попарные вопросы дают 0.66–0.77 [S16][S8][S63].
2. **Разбор брифа на вопросы.** «Есть ли X», «какого цвета Y», «стоит ли Z на W» по каждому ракурсу; вопрос засчитан,
   если ответы соседних ракурсов согласны: 88.7–91.5 % против 72.8 % у целостной оценки [S64]. Целостные судьи
   хуже всего именно на соответствии промту (Kendall τ 0.17–0.50) [S63].
3. **Геометрию — измерять, не спрашивать.** Согласованность нормалей меша и нормалей, предсказанных по рендеру: 83.0 %
   против 46.9 % у GPT-4V [S64]. Для нашего агента проще и точнее: связность частей, зазоры и пересечения,
   габариты, неманифолд, число треугольников — кодом по данным сцены (см. `../11-evaluation-qa/`, волна 3).
4. **Показывать геометрию «глиной» или нормалями.** RGB — главный вход, но для критериев геометрии нужны нормали
   [S62]; раскрашенные рендеры гауссовых сплатов прячут дефекты (судья ≈50/50 на явных дырах), карты нормалей
   меша 2×2 — нет [S65]; 3DGen-Arena показывает людям три видео: нормали, геометрию без текстуры, текстуру [S63].
5. **Мало картинок за вызов.** Эталон + панель из 7 изображений довели 7B-судью до **100 % ответов «по позиции»**;
   лечение — сравнение двух изображений [S65]. 4–9 ракурсов в одной сетке нужны для глобальных критериев,
   1 крупный — для деталей [S62].
6. **Контроль позиции.** Спрашивать в двух порядках (A,B) и (B,A) и засчитывать только согласованный ответ; доля
   «переворотов» показывает реальный разрыв качества: ~26 % между разными генераторами, 94 % между двумя выборками
   одной модели [S65]. Qwen в BlenderGym всегда выбирал второй вариант [S16].
7. **Один критерий за вызов** точнее, чем все сразу; ансамбль по возмущениям входа (раскладка, число ракурсов,
   отражение сторон, подписи «left/right») снижает дисперсию [S62].
8. **Эталон рядом.** Без эталона судья награждает «чистое, но неверное» [S65]; в нашем цикле эталон — паспорт
   стиля, референс-картинка или прошлый утверждённый ассет серии.
9. **Сильный критик.** Слабая модель в роли самокритика «чинит» агрессивно и ломает (откаты 26–28 %), сильная —
   осторожна [S8]. Критик не должен быть слабее генератора.

### 7.3. Что не работает

- **«Думай дольше».** GPT-5 low → medium → high и просьба обосновать оценку не улучшают согласие с людьми [S61];
  узкое место — визуальное кодирование, а не рассуждение.
- **Судьи молчат о «ничьей».** Кроме Gemini 3.1 Pro, судьи почти не отвечают «оба плохи/ничья» (0–3 % против 15.6 %
  у людей) [S8] → в протоколе нужен явный порог «оба не годятся», иначе цикл «выбирает лучшее из плохого».
- **Судья по коду.** Без запуска и рендера — κ 0.25–0.35 [S8]; по коду даже сильная модель верно понимает, что
  изображено, лишь в ~50 % случаев (SGP-Bench, §4) [S44].
- **Судья, обученный на ответах другого судьи**, наследует его смещения: MV-LLaVA на псевдометках GPT-4V — 0.50
  совпадения (монетка) [S63].
- **Счёт и мелкие детали.** GPT-4V не считает объекты (число шаров), отвлекается на мелкий шум и пропускает крупную
  неправдоподобность (лишние лица, ноги) [S62].
- **Галлюцинированные различия.** В BlenderGym генератор видит отличия, которых нет; цепочка «сначала опиши
  различия, потом код» помогает, но модель её нарушает [S16].

### 7.4. Автоматические метрики как замена людям

- SigLIP-2 сходство ракурсов с эталоном — Pearson **0.964** с Elo людей по 12 моделям; DINOv3 — Spearman **0.972**
  [S8]. Это согласие на уровне **моделей** (ранжирование систем), не отдельного ассета.
- CLIP-сходство с текстом слабо: Pearson с людьми 0.074 (геометрия) и 0.228 (соответствие) на отдельных мешах
  [S61]; Kendall τ рейтинга 0.635 [S63].
- Метрики сходства с эталоном (photometric loss, Chamfer, CLIP) не ловят физическую правдоподобность: мяч, «прилипший»
  к корзине, получает хороший балл [S16].
- Для нашего агента эталон почти всегда есть (референс, паспорт стиля, прошлый ассет серии) → сходство эмбеддингов
  ракурсов с эталоном — дешёвый первый фильтр перед VLM-судьёй.

### 8.2. Сборка: рекомендуемый цикл (для протокола C1, `04-agent-operating-protocol.md`)

1. **Бриф → паспорт**: части объекта с размерами в метрах, опорная деталь, материалы (Principled, 3–5 параметров),
   палитра, бюджет треугольников, стиль серии; уточнить неоднозначное (ProCAD) [S36].
2. **Поиск**: 1–3 похожих проверенных рецепта из библиотеки; справка API 5.2 по нужным вызовам [S10][S9].
3. **Код по частям** от опорной, координаты — вычислением по габаритам соседей; обёртки вместо сырого API [S21][S11].
4. **Исполнение в фоне**; при ошибке — traceback и повтор (≤2); при повторе отпечатка — сменить подход [S8].
5. **Утверждения `bpy`** (габариты, связность, зазоры, одно тело, полигоны) → текстовый отчёт → правка [S33][S21].
6. **Рендер 4 ракурсов** (RGB + «глина»); вопросы да/нет по брифу; попарное сравнение с прошлой версией/эталоном в двух
   порядках; ≤2–3 визуальные итерации, откат при ухудшении [S64][S65][S15].
7. **2–4 кандидата параллельно** на шаге с высокой неопределённостью (форма, материал), отбор проверками [S28][S40].
8. **Экспорт** после применения модификаторов и запекания процедурного (агент E); проверка в браузере (`web_view.py`).

## 11. Чем мерить нашего агента

Цель — не рейтинг моделей, а **ворота качества** для каждого ассета и регрессионный набор для самого агента. Бенчмарки
исследований дают готовые метрики и протоколы; ниже — что взять и как адаптировать.

### 11.1. Метрики уровня ассета (каждый прогон)

| Метрика | Что ловит | Как считать у нас | Откуда | Порог-ориентир |
|---|---|---|---|---|
| Исполнимость | ошибки API, синтаксис | скрипт отработал в фоне без исключения, в сцене ≥1 MESH | 3DCodeBench [S8] | 100 % после ≤2 повторов |
| Корзины отказов | тип ошибки | ERR_EXEC / ERR_NO_MESH / ERR_RENDER / ERR_TIMEOUT + «отпечаток» traceback (тип + урезанный стек) | 3DCodeBench | повтор одного отпечатка ≥2 раз → смена подхода |
| Связность и контакты | парящие/оторванные части | число компонент связности, минимальные зазоры между частями, которые должны касаться | 3DCodeBench (главный дефект), LL3M (ручки лейки) [S9] | зазор ≤0.5 % габарита там, где части касаются (предложение C2, проверить в J) |
| Габариты и пропорции | масштаб, «кубические» пропорции | `dimensions` и отношения частей против паспорта (метры) | SceneCraft (словарь высот) [S17], 3D-CoS (доли) [S42] | отклонение ≤5–10 % от ТЗ (предложение C2) |
| Топология и вес | тяжесть для веба | треугольники, неманифолд, n-гоны, материалы, текстуры | Mesh Analyzer 3DCodeBench; `render_views.py stats.json` | бюджеты — агенты A и E |
| Сходство с эталоном | «похоже ли» | SigLIP-2/DINOv3 по 4 ракурсам против референса или прошлого ассета серии | 3DCodeBench: r = 0.964 с Elo людей | относительно: не хуже прошлой версии |
| Соответствие брифу | пропущенные части, цвета, количество, отношения | вопросы да/нет по брифу к VLM по 4–6 ракурсам, согласие соседних ракурсов | Eval3D: 88.7–91.5 % согласия [S64] | все обязательные вопросы — «да» |
| Попарное качество | эстетика, детали, материал | VLM попарно (новая версия против прошлой/эталона), 2 изображения, два порядка | GPTEval3D, Judging to Improve [S62][S65] | новая версия побеждает в обоих порядках |
| Правдоподобие геометрии | «суп из примитивов», лишние части | рендер «глиной»/нормалями, VLM попарно; плюс код | 3DGen-Bench (показ нормалей и геометрии) [S63] | нет замечаний приоритета 1–2 |

Приоритеты замечаний критика — как в промте самокритики 3DCodeBench [S18]: **1)** пропущенные части → **2)** парящие или
оторванные части → **3)** неверные пропорции → **4)** неверное положение/поворот/пересечения → **5)** нехватка
геометрической детали → **6)** неверный силуэт. Останавливаться, когда нет проблем 1–2, а 3–5 мелкие.

## 12. Что переносится на 3D для веба

Исследования меряют сходство с эталоном и правдоподобие; сайту нужны ещё **вес, скорость, стиль серии и повторяемость**.
Ниже — что из работ прямо полезно для лендингов и что придётся добирать самим.

### 12.1. Лёгкие ассеты

- **Части с именами → узлы glTF.** Код по частям (LL3M, ShapeCraft, MeshCoder) даёт в GLB отдельные узлы с понятными
  именами — их можно анимировать и перекрашивать на странице (hover, раскрытие, конфигуратор). Одним мешем это не сделать.
  [S9][S40][S41] `[исследование + практика]`
- **Параметр детализации — рычаг бюджета.** У MeshCoder `resolution` в каждой функции-примитиве [S41]; у нас —
  сегменты, уровень subdivision, число вершин кривых. Бюджет треугольников задаётся в паспорте и проверяется кодом (§11).
- **Модификаторы надо применять перед экспортом**, а процедурные материалы — запекать (§5; детали — агент E,
  `../08-export-gltf/`). Проверка «габариты по `obj.data`» лжёт при модификаторах (эксперимент C2/01, T7: 1.0 против 5.0 с
  Array ×3) [S19].
- **Меш как текст** даёт крошечные файлы, но ступенчатую поверхность (сетка 64³) и никаких UV — для витрины продукта не
  годится (§4.1).
- **Нейросетевые генераторы мешей** (Rodin, Hunyuan3D, Meshy, Tripo, TRELLIS) — тема агента G (волна 2): тяжёлая
  топология и запечённый свет требуют доводки. Исследования этого файла используют их только как «поставщика органики»
  для части, вписанной в бокс (ShapeCraft → Hunyuan3D) [S40].

### 12.2. Стилизация и серия

- **Паспорт стиля вместо картинки-референса.** Фото-референс вместо текста ухудшает генерацию кода у 4 из 5 моделей
  [S8]; текст + картинка помогает только сильным моделям. Для серии (иконки, витрина) — текстовый паспорт
  (камера, свет, материалы, палитра, поля кадра; `../../ui/12-ai-generated-ui/01-image-models-for-ui.md` §6.2)
  плюс утверждённый эталон серии как референс для попарного судьи.
- **Шаблоны вместо генерации с нуля.** Параметрические генераторы (ShapeLib, Proc3D) и проверенные примеры (BlenderRAG)
  дают повторяемость: одна функция `mug(height, radius, handle_style)` → серия кружек одного стиля. LLM хорошо выбирает
  функцию и структуру, хуже — числа [S43]; числа фиксирует паспорт.
- **Материалы серии — из библиотеки.** Готовый материал по сходству часто лучше сгенерированного [S45]; для
  веба — простой Principled BSDF с 3–5 параметрами на материал серии.
- **Low-poly и стилизация — сильная сторона кода**: примитивы + модификаторы (bevel, array, mirror, solidify) — ровно то,
  что модели пишут надёжно (Planner–Actor–Critic на low-poly торте/столе/машине; ShapeCraft; 3DCodeBench просит
  subsurf/bevel/array/mirror/screw). Органика — слабая (§9).

### 12.3. Повторяемость

- Детерминизм: температура 0.7 — оптимум качества в 3DCodeBench, но одинаковый промт даёт разные объекты [S9]; для
  серии фиксировать **код** утверждённого ассета и менять параметры, а не перегенерировать.
- Правка существующего кода, а не переписывание: ≈38 с на правку против ≈10 мин на новую генерацию; без передачи
  текущего кода объект «уплывает» [S9].
- Хранить у каждого ассета: скрипт-источник, паспорт, рендеры 4 ракурсов, статистику, GLB. Это даёт регрессию и
  попарного судью «новая версия против утверждённой».

## Частые ошибки

1. **Считать исполнимость качеством.** «Скрипт отработал» ≠ «объект хороший»: у Opus 4.7 лучшая исполнимость и средняя
   форма; оболочка Claude Code довела исполнимость до ~1.0 без прироста формы [S8].
2. **Просить у модели координаты напрямую** (мебель, реквизит, части объекта) — не лучше случайной раскладки [S50].
3. **Гонять визуальную самокритику «до победного»** — после 2–3 итераций прирост пренебрежим, слабая модель ломает рабочее
   [S8][S22].
4. **Судить форму по коду** («я написал четыре ножки — значит, их четыре») — по коду модель верно понимает изображение лишь
   в ~50 % [S44].
5. **Спрашивать VLM «оцени геометрию от 1 до 10»** — почти шум (Pearson 0.17–0.37) [S61].
6. **Показывать судье 7–9 картинок разом и один порядок** — ответ по позиции [S65][S16].
7. **Раскрашенный рендер для проверки геометрии** — текстура прячет дефекты; нужен рендер «глиной»/нормалями [S65][S62].
8. **Класть в промт много общих примеров** — сильные модели становятся хуже [S23].
9. **Писать сырые графы geometry nodes кодом** — 0 % компиляции у GPT-4o/o3/DeepSeek-V3 [S11].
10. **Доверять самописной библиотеке функций** (своей или «выученной» агентом) без модульных тестов — тихие ошибки осей,
    масштаба, NaN, бесконечных циклов [S19].
11. **Доверять «проверенной» справке API без запуска** на своей версии — 2 ложных «запрета» из 27 [S18].
12. **Удалять объекты «сдвигом на x += 1000»** (промт Planner–Actor–Critic) — мусор уходит в GLB [S14].
13. **Мерить габариты по `obj.data`** при модификаторах — ложные размеры [S19].
14. **Двойное масштабирование в `bpy`**: `primitive_cube_add(size=2.0)` плюс масштаб 2 → объект вдвое больше [S26].
15. **`Matrix.Rotation(angle, 4, 'Y')` вместо `'Z'`, `matrix_world @ R` вместо `R @ matrix_world`, `matrix_world * scalar` для
    масштаба** — типовые ошибки кода, написанного моделью (из библиотеки SceneCraft) [S19].
16. **Референс-фото вместо текстового ТЗ** — теряются конкретные ограничения, модель лезет в непосильную геометрию
    [S8].
17. **Малая локальная модель для `bpy`** — 0 % рабочих скриптов у Qwen3-VL 8B/30B [S22].
18. **Ставить Infinigen в Blender 5.2** — требует `bpy==4.2.0` и Python 3.11 [S60].
19. **Путать две «BlenderRAG»**: в LL3M это база документации, в работе 2026 года — база примеров кода [S9][S10].
20. **Сравнивать числа генераторов сцен из разных статей** — самоотчёты несопоставимы (доля столкновений Holodeck:
    6.1 / 12.24 / 15.91 %) [S49].
21. **Ошибка модели по памяти: код под Blender 3.x/4.x** из статей и репозиториев (Infinigen-обёртки, `bpy==4.0.0` у
    MeshCoder, Blender 4.2.9 у ShapeCraft, 4.4 у LL3M и 3D-CoS, 4.5 у MaterialApprentice и DreamHouse) — перед
    использованием прогнать в 5.2.2 (дрейф API — агент B, `../03-bpy-api/`).

## Открытые вопросы и противоречия

1. **Визуальная самокритика: помогает или нет?** BlenderAlchemy и LL3M показывают заметный плюс; 3DCodeBench — почти ноль
   на тексте и минус на задачах по картинке; Articulate-Anything — +2.4…5.8 %. Позиция базы `[спорно]`: критик полезен
   против **пропущенных и парящих частей** и при наличии эталона; бесполезен для тонких правок и при слабой модели.
   Проверить в J на наших эталонах.
2. **План перед кодом**: для материалов (MaterialApprentice) и у Gemini — плюс; у Claude Sonnet 4 в геометрии — минус
   (3D-CoS), у Claude в DreamHouse — без разницы. `[спорно]`; для Claude — паспорт частей вместо длинного плана.
3. **Примеры**: «больше примеров хуже» (VoxelCodeBench) против «примеры спасают» (BlenderRAG, MaterialApprentice).
   Противоречие снимается релевантностью: 1–3 **похожих** примера помогают, 5+ **общих** мешают.
4. **Судьи**: по рендерам 74–77 % (3DCodeBench) против 0.66 (BlenderGym) — разные задачи (форма объекта против тонких правок
   сцены) и модели разных поколений; для тонких правок доверие ниже.
5. **Нет данных по Blender 5.2** в статьях: 3DCodeBench — 5.0, остальные — 3.x–4.5. Совместимость кода работ с 5.2 не
   проверена (кроме C2/01 и C2/03).
6. **Geometry nodes из текста**: ни одна прочитанная работа не генерирует их напрямую, кроме Proc3D через компактный язык
   (и там 0 % для сырых графов). Нужны собственные эксперименты D1 и B.
7. **Эстетика и «готовность для веба»** не измеряются ни одним бенчмарком (обзор «production-ready» прямо об этом);
   рубрика §7.5 — предложение C2, не проверена на людях.
8. **Площадки не подтверждены**: ShapeLib (ACM TOG по поиску, страница ACM отдала 403), CAD-Coder VLM (ASME IDETC-CIE по
   поиску); 3D-Generalist — 3DV 2026 по странице проекта. HOG-Layout, Scenethesis, 3D-CoS, CAD-Coder (текст) — код не найден.
9. **Числа только на графиках** у части работ (L3GO — предпочтения на UFO; Articulate-Anything — по модальностям;
   3D-Generalist — кривые по раундам; NaLA — нерегулярные комнаты) — в файле не приводились.
