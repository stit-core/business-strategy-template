## 2. Чат-протокол правок по меткам `#N`

### 2.1. Раунд целиком

```text
1 Claude  shot.py design review/iter-NN --tiles --prev review/iter-(NN-1)/marks.json      кадры с метками + marks.md
          показывает заказчику 1–3 кадра с метками (§3) и говорит, где карта номеров
2 Заказ.  «#22: высота ≥ 44 · #16: текст «Посмотреть услуги» → «Услуги и цены» · #37: добавить ссылку «Как добраться» перед #38 · Keep»
3 Claude  эхо до правки: «N1 #22 = `#services … article > a` → правило `.service-card > a`, заденет только #22; …; остальное не трогаю»
4 Claude  правит файлы → git commit «iter-NN»
5 Claude  shot.py … --prev → diffshots.py review/iter-(NN-1) review/iter-NN --expect 16,22,37,38 → «неожиданных изменений: 0»
          показывает «было → стало» по пунктам + таблицу diff.md; есть «НЕОЖИДАННО» — сначала чинит/откатывает, потом показывает
6 Заказ.  «Keep» / следующий пакет / «откат iter-NN»
```

Так прошла итерация 2 смоука: 5 пунктов, 0 неожиданных изменений, номера старых элементов сохранены, новая ссылка получила #39
`[проверено]`.

### 2.2. Метки и карта `marks.json`

- **Что нумеруется:** области (`header`, `nav`, `section`, `footer`, `aside`, `form` — белый бейдж), заголовки, кнопки (включая `summary`),
  ссылки, поля, картинки (`img`, `svg[role=img]`, `picture`, `video`, `canvas`), карточки (`[data-mark]`, `article`, класс-блок `card`/`tile`,
  контейнер с фоном, рамкой или тенью и ≥ 2 детьми). Абзацы и пункты списков не нумеруются — к ним обращаются через контейнер и цитату:
  «#13, абзац «Привозите утром…»: …».
- **Блоки номеров по файлам:** 1-й артборд-файл — #1–#99, 2-й — #101–#199 (или `manifest.marks[file].base`); больше 99 — предупреждение.
- **Один номер — один элемент на всех ширинах и темах файла:** номер считается на «каноническом» кадре и закрепляется для остальных;
  элемент, скрытый на 1440 (меню телефона), номер имеет, бейдж — только там, где виден. Холст и кадры сверяются автоматически
  (`canvas_consistent: true` во всех прогонах) `[проверено]`.
- **Номера живут между итерациями:** `--prev` переносит номер по совпадению «селектор + тег + текст» → «тег + текст» (элемент переехал) →
  «селектор + тег» (сменили текст); новые элементы получают max + 1, удалённые номера не переиспользуются `[проверено: #38 опознан по
  тексту, новая ссылка — #39]`.
- **Метки не меняют раскладку и не закрывают смысл:** оверлей в shadow DOM; бейдж обходит все строки видимого текста и CSS-псевдоэлементы
  (цифры шагов) и другие бейджи; наложения считаются и пишутся в отчёт. Первый прогон без этих правил закрыл подпись «Имя», подписи полей и
  цифры шагов — ловится только глазами, поэтому первый снимок любого нового макета Claude обязан посмотреть сам `[проверено]`.
- **`marks.json`:** на номер — файл, вид, тег, селектор, короткий текст, родитель; по каждому кадру — видимость, прямоугольник, место бейджа,
  отпечатки `sh` (вычисленные стили) и `own` (текст и стили непомеченных потомков). **`marks.md`** — та же карта таблицей для чата.

### 2.3. Грамматика правки

```text
правка    := адрес ":" изменение { " · " изменение }
адрес     := #N | #N–#M | #N, #M | «все <кнопки|карточки|заголовки h2> [в #N]» | «токен --имя» | «везде»
изменение := свойство [старое] "→" новое            #22: min-height 26 → 44 · #7: padding 24 → 32 · #3–#5: цвет → акцент
           | текст «…» → «…»                         #14: текст «Обслужим велосипед за один день» → «ТО за один день»
           | как у #M                                #25: как у #23
           | убрать | добавить <что> перед|после #N  #37: добавить ссылку «Как добраться» перед #38
           | покажи [с --токен=значение]             покажи #29 с space-section=120   (предпросмотр --set, файлы не меняются)
пакет     := до 7 правок + «Keep» (всё не названное — не трогать)
ответ     := «Keep» | «откат iter-NN» | новый пакет
```

Уровень правки Claude называет в эхе сам и выбирает самый узкий: **элемент** (отдельное правило или атрибут) → **компонент** (класс:
«все кнопки» заденет #7, #15, #34, #122) → **токен** (`tokens.css`: заденет всё, что его использует). Числа — в единицах макета (px,
hex, имя токена); «сделай премиальнее» без числа Claude переводит в 2–3 конкретных варианта и показывает их `--set`-предпросмотром.

### 2.4. Широкие правки и «применить ко всему»

- Токен: «везде: углы 8, акцент — #0B6E4F» → Claude снимает предпросмотр `--set`, показывает «было → стало» и список затронутых меток
  (`diffshots --expect all`), после «Keep» пишет значения в `tokens.css` и `DESIGN.md`. В смоуке `--set` перекрасил акцент, колесо, кнопки
  и логотип и поменял углы, не тронув файлы; задело 14 меток главной и 12–15 меток записи `[проверено]`.
- Структура («поменяй местами #18 и #29», «добавь раздел FAQ после #29») — обычной правкой чатом; разделы без спроса не добавлять (§4.2 п. 9).
- Правило базы (`06/03` §3, ui 11/04): системную ошибку чинить в токенах или компоненте, а не в каждом экране.

### 2.5. Пакет, Keep, эхо и проверка «изменилось только то, что просили»

1. Пакет ≤ 7 пунктов по тяжести: раскладка и иерархия → честность (факты, заглушки) → мобильная → цвет и контраст → типографика → форма →
   движение (`06/03` §2); мобильную переделку — отдельным раундом.
2. «Keep» и «ничего сверх списка»: замеченное сверх — строкой «предлагаю ещё: …» после показа, не правкой.
3. Эхо до правки (номер → селектор → файл и правило) и после («Применено: N1 #22 …») — журнал в чате; по желанию сохраняется в
   `review/iter-NN/NOTES.md` (формат пункта — `06/03` §2: тяжесть, кадр, где, симптом с числом, ожидаемое с числом, «не трогать»).
4. Проверка — два уровня `diffshots.py`: DOM-отпечатки метки (стили и собственное содержимое — без шума) и вырез картинки (допуск ±1 px,
   дробный сдвиг, размытие). Смоук: правильный пакет — 0 неожиданных; отрицательный контроль с тремя непрошеными правками (текст абзаца в
   #13, отступы карточек, цвет подписей в #35) — пойманы все три; чисто пиксельная версия давала ложные тревоги от дробного сдвига
   (ссылка выросла на 17,65 px) и пропускала мелкие правки внутри больших блоков `[проверено]`.
5. Мера прогресса и стоп — `06/03` §5: W = 3·critical + major; две правки без прогресса — сменить стратегию; бюджет — до 3 раундов правок
   на экран, дальше решение заказчика.

### 4.2. Правила ремесла (пересказ)

1. **Шаг 0 по умолчанию, без просьбы:** если есть кодовая база — повторить существующее приложение точно: найти токены, тему,
   компоненты, иконки, шрифты и ближайшие экраны; брать точные значения, не округляя к сетке 4/8; новое расширяет существующий
   словарь; одной строкой сказать, с чем сверился. Только если ни приложения, ни ДС нет — своё направление.
2. **Один вопрос о природе результата:** статичные макеты или кликабельный прототип. Нельзя спросить — решить по брифу и назвать выбор.
3. **Эстетику согласовать с человеком, а не выбрать за него:** спросить или показать 2–4 действительно разных low-fi направления
   артбордами; молча выбранная своя эстетика — прямой путь к «slop» (внутреннее). Если спросить нельзя — одно направление по
   имеющимся сигналам плюс 1–2 low-fi альтернативы рядом.
4. **Варианты:** каждый — по оси, которую можно назвать («тёплый редакционный» против «плотный, данные прежде всего»), с честной
   мотивацией и главным компромиссом у каждого (не «подтасованное голосование»); имена вариантов не меняются между ходами; направления —
   отдельными артбордами, итог — в главном; выбранное собирается в главный артборд, остальное уходит на вторую страницу. Варианты «на
   хранение» — 3+ по нескольким измерениям, от канона к смелым, атомарные, чтобы смешивать.
5. **Ранняя разведка — вайрфреймы:** 3–5 разных подходов, простые формы, текст-заглушки, минимум цвета, ч/б с каплей цвета.
6. **Мини-система до вёрстки:** 1–3 шрифта с запасными стеками близкой метрики (экспорт PNG/PDF не встраивает Google Fonts); тон
   нейтралей; 0–2 акцента в OKLCH с одинаковыми светлотой и хромой; цвета бренда в приоритете.
7. **Вёрстка, переживающая прямую правку:** группы — flex/grid с `gap`, а не поля и пробелы; `text-wrap: pretty`.
8. **Масштабы:** цели касания ≥ 44 px; печать — тело ≥ 12 pt. Мобильные макеты — без нарисованного статус-бара и клавиатуры.
9. **Содержание:** без наполнителя и «data slop»; разделы не добавлять без спроса; недостающие факты — видимые заглушки
   (`[ВАША ЦЕНА]`), не выдумка; лендинг: оффер одним предложением, одно главное действие, доказательства из материалов заказчика.
10. **Точечная правка остаётся точечной:** менять только названное, остальное — предложить, а не применить.
11. **«Твики» — рычаги, а не текст:** немного и осознанно — переключатели (тёмная тема, плотность, вариант, количество) и сквозные
    значения (акцент, шкала отступов или шрифта); не для копирайта и не для цвета, использованного в одном месте.
12. **Пересоздание UI — из исходников**, не по памяти модели; скриншоты — только общий ориентир; чужой фирменный дизайн не копировать.
13. **Модель не видит свой холст:** «you will not normally see the canvas before the user does» (внутреннее, canvas-скилл) — поэтому
    размеры рамок считаются сложением вертикального ритма с запасом ~5 %, а посмотреть на результат разрешено, только если браузер
    уже есть под рукой. Скилл `prototype` — «одна перечитка файла перед публикацией, без тест-стендов»; `artifact-design` — «написать,
    посмотреть один раз, опубликовать».
14. **Цикл решений `workshop`:** решение — блок со стабильным id, 2–5 вариантами и рекомендацией с причиной; каждое применённое решение
    эхом пишется в чат («Applied: … -> …») как журнал; черновик плана переписывается «как решено сейчас».
15. **Живые документы артефактов** (`artifact.d.ts`, контракт 0.2.58): сервер ставит `data-id` на каждый элемент, правка адресуется по
    нему, сеанс Claude получает «что изменилось». Это та же идея, что наши номера `#N` (§2), только внутри страницы.

## 5. Официальный путь, когда включат `/design`

### 5.1. Что даст каждый режим (`02/01` §2–§5; Claude Code 2.1.281)

| Режим | Что делает | Кто исполнитель | Глаза модели | Что это даст заказчику «в чате» |
|---|---|---|---|---|
| canvas (скилл `design`) | `/design <бриф>` → артборды `.dc.html` + `canvas.json` → артефакт с редактором Claude Design | модель Claude Code | нет | ссылка на холст; правка мышью в браузере и Save; из чата — «поправь артборд X» → пересев и повторная публикация |
| types (Artifact-тип «Design») | `/design <бриф>` → `Artifact quickstart intent: design` → файлы `project/*` | модель Claude Code | нет | холст claude.ai, ДС как артефакт «Design System»; чтение правок обратно `Artifact read` |
| hub (`ClaudeDesign`) | живой системный промт Claude Design, проекты claude.ai/design: создать, читать, писать, `render_preview`, `get_conversation` | модель Claude Code по инструкциям Claude Design | `render_preview` (картинка ≤ 130 000 знаков base64) | ближе всего к «Claude Design в чате»: промт Claude Design + превью в чате; редактор — в claude.ai |
| consent (**у заказчика сейчас**) | только `/design consent` / `revoke` | — | — | ничего для макетов |

Во всех трёх рабочих режимах исполнитель — модель сессии Claude Code; «агента Claude Design по брифу» не вызывает ни один путь
`[исходник]` (`02/01` §9.1). Значит, полноценность «Claude Design в чате» определяется не режимом, а тем, есть ли у модели глаза, холст
и цикл правок — это и даёт `kit/` уже сейчас. Режимы добавляют редактор мышью, шаринг и (hub) живой промт Claude Design.

### 5.2. Как заказчику проверить режим (не запуская ничего лишнего)

1. В Claude Code (терминал или десктоп) набрать `/` и найти `/design` в меню — прочитать описание (дословно, `02/01` §2.2):
   - consent — «Grant or revoke Claude agent access to your Design projects» (ожидаем сейчас);
   - canvas — «Draft a design on a canvas Artifact — editable where saving is enabled (Claude Design preview)»;
   - types — «Make a new Design artifact from a brief»;
   - hub — «Work with Claude Design (claude.ai/design) — create, import, export, sync, login».
2. Сопутствующие признаки: в hub у сессии появляется инструмент `ClaudeDesign`; в types у `Artifact` — параметры `type_url`, `intent`
   и работает `/slides`; в canvas в списке скиллов модели появляется `design`.
3. Проверять после каждого обновления Claude Code и раз в неделю: флаги GrowthBook меняются без релиза (18.09 `/design` у заказчика ещё
   работал, 25.09 — только consent; `02/01` §2.4).

### 5.3. Что делать до включения и после

- **До:** работать по `kit/` и протоколу §2 (схема А, `02/01` §10, но без ручной работы в claude.ai/design). Держать ДС проекта в коде
  (`tokens.css` + `DESIGN.md`; для будущего `/design-sync` — React-пакетом со сборкой, `02/01` §6.4).
- **Когда появится canvas или types:** прогнать тест T-D10 (§9): тот же бриф через `/design` и через `kit/`, сравнить качество, число
  правок до приёмки, расход лимита. Холст `/design` можно «кормить» артбордами из `kit/`: наш артборд — обычный HTML на токенах, его
  перенос в `.dc.html` — механический (разметка + inline-стили, `<x-dc>`), но делает это только модель по инструкциям режима.
- **Когда появится hub:** первым делом сохранить в кэш базы результат `get_claude_design_prompt` (живой промт Claude Design — главный
  неизвестный фактор качества, `02/01` «Открытые вопросы») и сверить с правилами §4.2 и спецификацией §7.
- **Не делать никогда:** не включать флаги руками, не править `~/.claude.json`, не подменять ответы сервера, не ставить сторонние
  «моки» бэкенда (claude-code-router, `03/01` §9.1), не автоматизировать claude.ai/design браузером (Consumer Terms п. 3.7, `02/01` §9.4).

### 6.4. Ограничения прототипа

- Не редактор: правит только Claude, числом по номеру (так задумано). Живых слайдеров нет — только `--set`-предпросмотр.

## Частые ошибки

1. **Ждать `/design`** или вызывать `DesignSync` ради макета: у заказчика режим consent, `DesignSync` видит только проекты-ДС (`02/01` §2.4, §6.1).
2. **Номер из старого снимка:** правка «#22» по кадру прошлой итерации, а Claude смотрит новую карту → всегда `marks.json` снимка, который
   видел заказчик, и `--prev` для переноса номеров.
3. **Правка класса вместо элемента без предупреждения:** «#7: зелёный» правкой `.btn` перекрашивает все кнопки → в эхе назвать уровень
   (элемент / компонент / токен) и список затронутых меток; `diffshots` покажет лишнее.
4. **Приёмка по одному кадру 1440:** правка ломает 390 или тёмную тему → снимать все рамки манифеста.
5. **Полагаться только на глаза или только на числа:** счётчик наложений был 0, а бейджи закрывали подписи и цифры шагов (run0) — это
   увидели глаза; а тёмный текст на синей кнопке шапки (2,55:1) глаза пропустили — поймал `ui_audit.py`. Нужны оба слоя.
6. **Верить чисто пиксельному сравнению:** дробный сдвиг раскладки даёт ложные «изменения» (у нас 7,6 % пикселей у неизменной кнопки), а
   мелкая правка внутри большого блока проходит незамеченной → DOM-отпечатки + пиксели (`diffshots` v2).
7. **Открывать `canvas.html` по file://** (в том числе автопоказ во встроенном браузере) → холст не читает манифест → `standalone.html`
   или `shot.py serve`.
8. **`vh` в артбордах** → рамка холста растягивается по содержимому и раздувает первый экран.
9. **Публиковать артефакт без спроса** или с реальными данными клиента: публикация — выгрузка на серверы Anthropic (дока артефактов).
10. **«Сделай премиальнее»** без чисел → Claude переводит в 2–3 конкретных варианта и показывает `--set`-предпросмотром (§2.3).
11. **Смешивать мобильную переделку с десктопными пунктами** в одном пакете (`06/03` §2).
12. **Копировать закрытые тексты Anthropic** (canvas-скилл, тип «Design») в свой скилл — только пересказ принципов.

## 9. Что проверить в тестах

1. **T-D1 Точность меток и карты.** На 4 страницах разных типов (лендинг, дашборд, длинная форма, таблица) → у каждого видимого
   значимого элемента есть номер; наложений на метки и текст 0; холст = кадры; заказчик называет 10 элементов номерами — Claude
   резолвит 10 из 10 → успех: всё выполнено, глазами наложений нет.
2. **T-D2 Локальность правки.** 10 атомарных правок по номерам (5 стилевых, 3 текстовых, 2 структурных) → `diffshots` 0 неожиданных в
   ≥ 9 из 10; отрицательный контроль (3 непрошеные правки) пойман 3 из 3 → успех: оба условия.
3. **T-D3 «Применить ко всему».** Правка токена → список затронутых меток совпадает со всеми местами использования токена (grep по
   `var(--токен)`); литералов вне `tokens.css` 0 → успех: совпадение полное.
4. **T-D4 Паритет экспорта.** PDF, PNG 2×, standalone против кадров → ≤ 3 % пикселей после размытия, текст PDF извлекается, standalone по
   file:// с метками, zip собирается на чистой машине → успех: все четыре.
5. **T-D5 Время и лимит цикла.** Раунд «сообщение с 5 правками → показ после `diffshots`»: минуты и доля 5-часового окна (`/usage` до и
   после) на Opus 5.5 `high` против `medium` → успех: числа записаны; ориентир ≤ 10 мин и ≤ 3 % окна на раунд `[не проверено]`.
6. **T-D6 Качество против Claude Design.** Один бриф далеко от дом-стиля Claude: kit-сессия против Claude Design (руками заказчика или
   `/design`, когда включат) → слепое попарное сравнение по рубрике ui 13/02, 34 маркера, число раундов до приёмки → успех: решение, какой
   путь основной.
8. **T-D8 Каналы просмотра.** В десктоп-приложении: видит ли заказчик в ленте PNG, прочитанные Claude; показывает ли панель Files PNG
   картинкой; открывает ли встроенный браузер `standalone.html?marks=1&theme=dark` и `serve` через `launch.json` → успех: выбран основной канал.
9. **T-D9 Артефакт** (с разрешения заказчика): публикация `standalone.html` → открывается на телефоне; метки и тема работают под CSP
   артефакта; на Team/Ent — комментарий «Send to Claude» доходит до сессии → успех: ссылка рабочая, ограничения записаны.
10. **T-D10 Когда включат `/design`.** Тот же бриф через `/design` (canvas или types; hub — с сохранением живого промта в кэш) и через kit →
    качество, раунды, лимит, можно ли подать наши артборды → успех: решение о переходе.
11. **T-D11 Устойчивость номеров.** 5 итераций со вставками, удалениями, перестановками разделов → ≥ 95 % номеров сохраняются, ложных
    переносов 0 → успех: оба условия.
12. **T-D12 Протокол для человека.** Заказчик проходит 3 раунда правок только из чата → время на формулировку, ошибки адресации, что
    неудобно → успех: протокол принят или список правок к нему.

## Открытые вопросы и противоречия

1. Видит ли заказчик в ленте десктоп-приложения картинки, которые Claude открыл через Read, и показывает ли панель Files PNG картинкой →
   T-D8. Что встроенный браузер сам открывает записанный HTML — видно по хуку этой сессии, но для файлов, созданных скриптом, — нет данных.
2. Работают ли метки и холст внутри опубликованного артефакта (CSP, песочница, `srcdoc`-iframe) — публикация не делалась → T-D9.
3. Как Claude Design технически привязывает инлайн-комментарий к элементу, неизвестно; сравнить устойчивость с нашими номерами можно
   только запуском.
4. Живой промт Claude Design (hub) против наших правил: даёт ли он заметно лучший дизайн — главный неизвестный фактор (`02/01` «Открытые вопросы»).
5. Дока Claude Code: `/design` canvas «your edits save automatically», canvas-скилл — явная кнопка Save (`02/01` §4) `[спорно]`; для нашей схемы
   не важно.
6. Дока артефактов: «Relative links do not resolve» против описания инструмента `Artifact` с многофайловой публикацией (`files`) — одна
   страница `standalone.html` снимает вопрос; многофайловый холст в артефакте `[не проверено]`.
7. Комментарии: в ростере возможностей страницы есть `comments`, а дока ограничивает комментарии Team/Enterprise — на тарифе заказчика
   `[не проверено]`.
8. Разные DOM для мобильной и десктопной версии (отдельная разметка) дадут разные номера одного смыслового элемента — для таких проектов
   нужен `data-mark` в исходниках (по решению заказчика).
