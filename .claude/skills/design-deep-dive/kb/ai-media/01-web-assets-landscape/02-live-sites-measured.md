## Выжимка для агента

1. **Первый экран лидеров весит 4,2 МБ (медиана; Q1 2,4, Q3 7,0), сессия с прокруткой — 6,5 МБ (Q3 21,8)**: это в 1,5 раза
   тяжелее медианной главной веба (2,86 МБ, WA 2025). Ориентир для генерации — Q1 лидеров: ≤ 2,5 МБ первый экран десктопа,
   ≤ 1,5 МБ телефона → §4. [проверено]
2. **Hero-картинка — 55 КБ медиана (Q3 131 КБ)**, отдаётся AVIF/WebP ровно под ширину экрана (медиана 1440 px при DPR 1);
   hero занимает медиану 74 % первого экрана, соотношение бокса 1,6:1 → бюджет hero ≤ 150 КБ десктоп / ≤ 80 КБ телефон → §4.2. [проверено]
3. **На телефоне 8 из 10 сайтов показывают другой hero** (портретный кадр 9:16–4:5 или картинку вместо видео), почти всегда
   без `<picture media>` → в плане ассетов hero — два кадра с разной композицией → §8. [проверено]
4. **Вес на телефоне почти равен десктопному** (медиана 0,98); легче только там, где выключено видео (Apple −13 МБ) → телефонный
   бюджет надо закладывать явно, сам он не появится → §8. [проверено]
5. **LCP ≤ 2,5 с — только у 16 из 43** (медиана 3,2 с, лаборатория); лёгкий первый экран (< 3 МБ) проходит у 8 из 13, тяжёлый
   (≥ 5 МБ) — у 4 из 19 → §5. [проверено]
6. **Canvas не бывает LCP; hero, видимая часть которого равна вьюпорту, — тоже никогда** (LCP = H1; перепроверка J/01 по
   `sites.csv`: `lcp_is_hero = 1` лишь у 2 из 12 полноэкранных, и оба меньше вьюпорта — видео 96 % экрана и CSS-фон 99,8 % с
   анимацией масштаба; правило выполняется 12 из 12) → быстрыми должны быть и H1 со шрифтом, и hero меньше вьюпорта

7. **Форматы**: WebP — формат по умолчанию (42 % картинок без секвенций), AVIF отдают 19 из 43 сайтов, у русских — 0 из 5;

9. **Переотдача пикселей > 3× — у 19 % картинок** (Midjourney: PNG 1024² в 194 px) → `srcset` + точный `sizes` → §6.2. [проверено]
10. **Видео у лидеров в 2,5–3 раза чаще среднего веба** (видимое — 20 из 43, в hero — 10 из 43), байты двувершинные: одна петля
    < 0,6 МБ или 6–163 МБ за сессию (карусели и HLS-стримы Mux/Vimeo) → §7.1. [проверено]

14. **og:image объявлен у 41 из 43**, типовой размер 1200×630 (или 2400×1260), PNG/JPEG, медиана 132 КБ; битые и тяжёлые OG

15. **Полный набор фавиконов редок** (SVG 8, apple-touch 26, manifest 11 из 43) → генератор выдаёт набор по рецепту → §6.4,

## 1. Метод и ограничения

- **Инструмент** — `asset_inventory.py` (описание — `../../scripts/ai-media/README.md`, раздел «Инвентарь визуальных ассетов сайта»). Для каждого `<img>`/`<picture>`,
  CSS-фона (`background-image`, `mask-image`, `::before/::after`), `<video>`, inline SVG, Lottie, canvas, iframe: URL, формат
  **по сигнатуре первых байт**, переданные байты, естественный и отрисованный размер, положение относительно первого экрана,
  `srcset`/`<picture media>`, `loading`, `fetchpriority`, `alt`; LCP с элементом **до прокрутки**; `og:image` (скачивается:
  байты, формат, размеры); фавиконы; «движение в покое» (доля пикселей, изменившихся за 1 с на первом экране).
- **Байты** — «на проводе» по CDP (`Network.dataReceived` / `loadingFinished` / `loadingFailed`): браузер обрывает Range-
  запросы видео, когда буфер полон, и событие Playwright `requestfinished` не приходит — пилотный прогон v1 из-за этого
  показал 0 байт видео у Notion при играющем ролике; с CDP — 64–406 КБ в разных прогонах (сколько браузер успел
  забуферить из файла 2,1 МБ): видео-байты сессии зависят от буферизации и шумят. Потоковое видео (HLS/DASH/CMAF, `blob:`) учитывается по
  сегментам. [проверено: `sites_v1/` против `sites/`]
- **Сценарий**: десктоп 1440×900 DPR 1, UA Chrome 153 без «Headless», `--disable-blink-features=AutomationControlled`;
  `load` (таймаут 90 с) → 6 с простоя → 2 снимка через 1 с (движение) → прокрутка колесом (8–40 шагов по 250 мс, 3 снимка) →
  возврат наверх → инвентарь DOM. Мобильный — дескриптор Playwright «Pixel 7» (412×839, DPR 2,625, UA Android), без
  троттлинга. Reduced motion — контекст `prefers-reduced-motion: reduce`, режим `--quick` (без прокрутки) в паре с обычным
  `--quick`.
- **Кодеки в этом Chromium** (без GPU-флагов): H.264, AV1, VP9 играют; **HEVC — нет** (`canPlayType` пусто; с флагами VAAPI —
  «probably», но кадр чёрный, J/02 — `../10-web-integration/02-video-delivery.md` §1.1) → сайты с HEVC-only видео выглядели
  бы без видео (в выборке таких нет). `Accept` картинок: `image/avif,image/webp,image/apng,image/svg+xml,image/*` — CDN с
  автоформатом (`f=auto`) отдают AVIF/WebP. [проверено]
- **Сеть**: VPN, выход в Литве (EU): у всех сайтов EU-баннеры cookies, EU-цены (Glossier €), модалки выбора страны (Allbirds,
  SÖM, Nike без `/gb/`). Баннеры не закрывались — в LCP иногда попадает их текст (Tilda — 34 с).
- **Вес «до прокрутки»** = всё, что пришло за `load` + 6 с; **«после прокрутки»** = за всю сессию (≈ 30–60 с) — это верхняя
  граница: потоковые видео качают сегменты, пока играют (Sunday 163 МБ, Secret Level 63 МБ, Klarna 53 МБ видео за сессию), ленивые
  картинки подгружаются по мере прокрутки (Raycast 41,5 МБ PNG). Сравнивать с Web Almanac (вес при загрузке) — по «до прокрутки».
- **Ограничения**: один прогон на сайт (повтор Raycast дал 2,4 МБ картинок в v1 и 41,5 МБ в v2 — разная глубина ленивой
  подгрузки); headless без GPU-ускорения видео; LCP — лабораторный, без троттлинга, через VPN (≠ полевые CrUX); INP не
  мерился; эвристика слотов (hero, стена логотипов, аватары) проверялась глазами по контактным листам `sheet.jpg`
  (4 кадра: первый экран, ⅓, ⅔, конец).

### 5.3. Шесть наблюдений, важных для генерации hero

1. **Canvas не бывает LCP** (5 из 5 hero-canvas): LCP = H1/P (Vercel, Raycast, Cerebrium, Midjourney) или картинка-фолбэк
   (Stripe: `wave-fallback-desktop-1x.webp` 6,4 с, потом скрывается под WebGL). Совпадает с опытом 3d A/04. [проверено]
2. **Hero на весь экран — LCP непредсказуем**: из 12 hero ≥ 95 % экрана в 7 LCP = текст (Luma, White Desert 18 с, Seasats,
   Spylt, Cerebrium, Secret Level, Maison Meta — эвристика «весь экран = фон» сработала), в 5 — сам hero (Rylo 2,0 с,
   Lightship 3,3 с, Drinksom 9,1 с, United Carriers 10,4 с, Weavy 19 с). Опыт 3d A/04 на синтетике показал только первый
   исход → **план должен выдерживать оба**: H1 в HTML с быстрым шрифтом **и** лёгкий приоритетный hero. [проверено]
3. **Постер-картинка → видео** — самый быстрый видео-hero: Apple iPhone 18 Pro LCP = `hero_startframe.jpg` 1,1 с, видео
   подменяет кадр позже; Apple главная — 1,3 с. Видео-LCP без такого кадра — 1,9–3,3 с. [проверено]
4. **`loading="lazy"` на LCP-картинке — 3 из 43** (Linear 12,8 с, OpenAI 7,5 с, boc.studio — LCP стал data-URI SVG-заглушкой
   размытия). WA 2024: 9,5 % LCP-картинок ленивые [S1]. [проверено]
5. **`fetchpriority="high"` на LCP — 5 из 43**: Ozon 0,8 с, VkusVill 1,2 с, Rylo 2,0 с, Sunday 2,1 с, Runway 5,4 с — медиана

6. **Анимация появления и прелоадер двигают LCP к концу анимации**: Figma 22 с, Framer 19,9 с, Weavy 19 с, White Desert 18 с
   (текст «ANTARCTICA» проявляется поверх видео) — LCP считается по моменту отрисовки, а не загрузки. [проверено; web.dev]

Расхождение с 3d `02` §2.1: там полноэкранный постер всегда отбрасывался (синтетика), здесь в 5 из 12 живых
полноэкранных hero LCP = сам hero. Позиция: правило «H1 спасёт LCP» верно только для canvas; для картинки или видео на весь
экран — готовить оба случая. [проверено; спорно для других браузеров — Safari и Firefox считают LCP иначе]
**Разрешено J/01 (поправка X 24.09.2026):** по `sites.csv` у Rylo, Drinksom и United Carriers `lcp_is_hero = 0` (LCP — другая
картинка), два случая `= 1` — не весь вьюпорт (видео Lightship 96 % экрана, CSS-фон Weavy 99,8 % с анимацией масштаба); правило

- **WebP — формат по умолчанию** (Next.js `/_next/image` отдаёт WebP, AVIF включается отдельно — `formats` в `next.config`

  собственного конвейера) и Lightship. Русские сайты (5) — WebP, **AVIF ни у одного**.
- **PNG — половина всех байт картинок, но из-за четырёх сайтов**: Raycast 39,7 МБ (10 PNG-обоев по 3,6–6,4 МБ), Runway

  картинок по сайтам — 1 %; PNG > 50 % байт — у 7 из 42 сайтов с картинками. Все четыре «рекордсмена» — ИИ- и
  дизайн-продукты, выкладывающие рендеры и генерации как есть.
- Вывод для конвейера (J): **PNG — только для прозрачности и плоской графики малого размера**; выход моделей (обычно PNG)
  обязательно перекодировать в AVIF/WebP перед публикацией; JPEG XL — не раньше 06.10.2026 (Chrome 155) и только первым
  необязательным `<source>` (`../08-image-post-processing/04-encoding-metadata.md` §2). [проверено; документация]

### 6.2. Адаптивность и арт-дирекшн

- 1841 видимая картинка: `srcset` с w-дескрипторами — 707, с x-дескрипторами — 361, `sizes="auto"` — 1. `<picture>` с
  `media` (арт-дирекшн по разметке) — на 6 из 43 сайтов.

разметка `hero_type`, `ai_visual`, `manual_notes`. Мобильные и reduce-прогоны — `mobile_compare.md`, `rm_compare.md` рядом.

## Частые ошибки

- **Мерить видео по событию `requestfinished`**: браузер обрывает Range-запросы видео, байты теряются (Notion: 0 вместо 406 КБ) →
  считать по CDP `Network.dataReceived`/`loadingFinished`/`loadingFailed`.
- **Брать LCP после прокрутки** — LCP перестаёт записываться после ввода пользователя (web.dev), а программная прокрутка
  вводом не считается и может «перевести» LCP на картинку, подгруженную прокруткой → фиксировать LCP до прокрутки (в утилите —
  снимок `pre_scroll`; в v2 у всех 43 сайтов LCP до и после прокрутки совпал, прокрутка шла колесом).
- **Считать доли форматов «по штукам»** — секвенции кадров (Seasats — 852 AVIF) искажают картину → смотреть и штуки, и байты, и
  долю сайтов.
- **Сравнивать «вес за сессию» с Web Almanac** — WA меряет загрузку, а не 30–60 с жизни страницы со стримами → сравнивать «до
  прокрутки».
- **Путать «полноэкранный» и «на весь вьюпорт»**: hero, видимая часть которого равна вьюпорту, LCP не станет (12 из 12, J/01),
  а hero 96–99,8 % экрана или с интро-масштабом — станет [поправка X 24.09.2026: было «в 5 из 12 живых случаев стал»].
- **Делать выводы о телефоне по десктопу** — 8 из 10 сайтов показывают другой hero, а вес почти тот же.
- **Считать `<picture media>` мерой арт-дирекшна** — лидеры переключают кадры JS и CSS (6 из 43 по разметке против 8 из 10 по
  факту на телефоне).
- **Мерить с VPN или серверного IP и считать выборку полной** — 7 из 52 URL закрыты антиботом и гео.
- **Один прогон = истина** — Raycast дал 2,4 и 41,5 МБ картинок в двух прогонах (разная глубина ленивой подгрузки); кампании
  e-commerce меняются часто → фиксировать дату и повторять.

### Ошибки нейросетей-агентов

- Брать бюджеты «по памяти» (например, «страница 1–2 МБ») — у лидеров 2026 первый экран 4,2 МБ, у медианного веба 2,86 МБ;
  нормы — из замера и Web Almanac с датой.
- Считать, что Lighthouse или `requestfinished` дают вес видео — не дают (обрыв Range-запросов); нужен CDP.
- Предлагать JPEG XL «как современный формат» до 06.10.2026 (в Chrome 153 и Firefox по умолчанию выключен, caniuse 2026-09)
  или «не поддерживается» после 06.10.2026 (Chrome 155) [поправка X 24.09.2026].
- Ставить `priority` у `next/image` — в Next.js 16 устарел, вместо него `preload` или `fetchPriority="high"` (S5).
- Считать, что `prefers-reduced-motion` «сайты уже учитывают», — у лидеров 4 из 16.
- Путать «сайт с ИИ-визуалом» и «сайт ИИ-компании»: у лидеров ИИ-рынка hero — продукт и текст, а ИИ-картинки — у ИИ-вендоров
  как товар и у второго эшелона как клише.

## Чек-лист замера сайта (для агента-генератора и приёмки K)

- [ ] Сняты десктоп 1440×900 и телефон (Pixel 7), записаны дата и регион сети?
- [ ] Байты посчитаны по CDP, форматы — по сигнатуре, LCP — до прокрутки и с элементом?
- [ ] Первый экран ≤ 2,5 МБ на десктопе и ≤ 1,5 МБ на телефоне?
- [ ] Hero ≤ 150/80 КБ, LCP-картинка без `lazy` и с `fetchpriority="high"`?
- [ ] У hero на телефоне свой кадр; `srcset` и точный `sizes` есть; переотдача ≤ 2× при DPR 1?
- [ ] Картинки в AVIF/WebP, а PNG — только для прозрачности и мелкой графики?
- [ ] У каждого автоплей-видео есть `muted playsinline loop`, `poster`, кнопка паузы с доступным именем и ветка
      `prefers-reduced-motion` без загрузки видео?
- [ ] Шов петли `seam_ratio` ≤ 1,5?
- [ ] og:image 1200×630 PNG/JPEG ≤ 300 КБ открывается по адресу, есть `og:image:alt`, `:width`, `:height`?
- [ ] Фавиконы полным набором: ico 32, SVG с тёмной темой, apple-touch 180, manifest 192/512 + maskable?
- [ ] Контактный лист просмотрен глазами: нет клише и «ИИ-глянца», слоты определены верно (§6.5, `03-…` §5)?

## Открытые вопросы и противоречия

1. **Лаборатория ≠ поле**: LCP мерился без троттлинга, через VPN, один раз; полевые данные (CrUX) для этих сайтов не
   сопоставлялись. Сверить LCP-типы с CrUX API (бесплатно, нужен ключ) — в следующей волне (J).
2. **Полноэкранный hero и LCP**: почему у Rylo, Drinksom, Weavy, Lightship, United Carriers hero стал LCP, а у Seasats, Spylt,
   Luma, White Desert — нет (размер больше вьюпорта? CSS-фон против `<img>`? прозрачность на старте?) — нужен синтетический
   опыт с вариантами разметки (J).
3. **Вес на телефоне ≈ десктоп** у 10 обычных сайтов против «легче в 1,5–6 раз» у 3D-сайтов (3d) — разные жанры; выборка
   10 сайтов мала.
4. **Reduced motion**: эвристика «движение в покое» видит только первый экран и 1 с; CSS-анимации ниже и анимации по прокрутке
   не мерились.
5. **Русская выборка** — 5 сайтов через VPN из Литвы; Avito, Самокат, Tilda не измерены → повторить без VPN.
6. **ИИ-визуал без раскрытия** (Klarna, Cursor — пейзажи) по замеру не определить; метки C2PA в файлах не проверялись (H, L).
7. **Видео-байты — верхняя граница**: WA 2025 видел «дубли» Range-запросов; суммирование по URL может завышать.
