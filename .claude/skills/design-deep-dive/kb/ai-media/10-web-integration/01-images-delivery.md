### 1.3 JPEG XL: не сейчас, но скоро

- Chrome 153 (CfT и брендированный), Chromium 152: `image/jxl` **не декодируется**, в `Accept` картинок — `image/avif,image/webp,
  image/apng,image/svg+xml,image/*,*/*;q=0.8` (JXL нет) → CDN с согласованием по `Accept` JXL в Chrome не отдаст; WebKit
  Playwright 26.6 декодирует и заявляет `image/jxl` `[проверено]`.
- Chrome 155 включает декодер JXL по умолчанию, стабильный — **06.10.2026** (chromestatus 5114042131808256, chromiumdash; сверено
  H 23.09.2026) → с этой даты `<source type="image/jxl">` **первым и необязательным** — там, где JXL выигрывает (волосы,
  фактуры, «без потерь на глаз» — H/04a), единственным форматом никогда (Firefox — за флагом) `[документация]`.
- После 06.10.2026 перепроверить: `python3 99-raw/experiments/J/02-codecs/run_probe.py google-chrome` (строка `img.jxl` и `Accept`).

### 1.4 Цвет картинок

- AVIF 4:2:0 из Pillow и avifenc: ΔE00 до 1,87 на насыщенных плашках (красный 200/50/50, бирюза 13/148/136), WebP q80 — 0,63

## 2. `srcset` и `sizes`

### 2.1 Лестница и выбор файла

```html
<!-- hero на всю ширину · Chromium 153 · [проверено: pages/01-image-hero.html, J/06] -->
<img src="dawn-16x9-1280.webp" sizes="100vw" width="2560" height="1440" alt="" fetchpriority="high" decoding="async"
     srcset="dawn-16x9-640.webp 640w, dawn-16x9-960.webp 960w, dawn-16x9-1280.webp 1280w, dawn-16x9-1920.webp 1920w">
```

| Экран | CSS-ширина × DPR | Выбран | Переотдача |
|---|---|---|---|
| десктоп 1440×900, DPR 1 | 1440 | `…-1920.avif` (90 КБ) | 1,33 |
| Pixel 7 412×839, DPR 2,625 | 1082 | `dawn-4x5-1080.avif` (46 КБ) | 1,0 |
| карточка 360 CSS-px, DPR 1 (`sizes="auto, …"`) | 360 | `…-480.avif` (5–9 КБ) | 1,33 |

- Лестница базы: 640, 960, 1280, 1920, 2560 (+ 3840 только для полноэкранного hero на ретине 1920 CSS-px); Next.js по умолчанию
  — 640, 750, 828, 1080, 1200, 1920, 2048, 3840 (A `01/01` §4.2) `[документация Next.js]`.
- `sizes` — по раскладке, а не «100vw везде»: у 20 % десктопных страниц ошибочный `sizes` меняет выбор файла, p75 лишних 179 КБ
  (Web Almanac 2024, A) `[исследование]`.

### 2.2 `sizes` с условиями и `<picture media>` — не смешивать

- `media` на `<source>` — только для арт-дирекшна (другой кадр), размеры внутри кадра решает `sizes`; `sizes` с медиаусловиями
  вместе с `media` — ошибка F `06/03` («Ошибки нейросетей-агентов») `[документация MDN]`.

### 2.3 Ленивые картинки: `sizes="auto"`

```html
<!-- карточка ниже первого экрана · Chromium 153 · [проверено: pages/01, J/06: выбран 480w при колонке 360 px] -->
<picture>
  <source type="image/avif" sizes="auto, (min-width: 1180px) 360px, 100vw"
          srcset="sky-480.avif 480w, sky-720.avif 720w, sky-960.avif 960w">
  <img loading="lazy" decoding="async" width="960" height="720" alt="Персиковое небо над гладкой водой на рассвете"
       sizes="auto, (min-width: 1180px) 360px, 100vw" src="sky-720.webp"
       srcset="sky-480.webp 480w, sky-720.webp 720w, sky-960.webp 960w">
</picture>
```

- `sizes="auto"` работает только с `loading="lazy"` (браузер знает ширину после раскладки); список после `auto` — запас для
  браузеров без поддержки `[проверено: Chromium 153; документация]`.
- Карточки — AVIF по порогу ≥ 70: 480w 5–9 КБ, 720w 8–16 КБ, 960w 12–25 КБ (WebP в 1,3–1,7 раза тяжелее) `[проверено]`.

## 3. Телефонный кадр и фокус

### 3.1 Разметка арт-дирекшна

```html
<!-- hero: телефон — отдельный мастер 4:5, десктоп — 16:9 · [проверено: pages/01-image-hero.html, J/06: CLS 0, LCP = hero] -->
<picture>
  <source media="(max-width: 699px)" type="image/avif" sizes="100vw" width="1080" height="1350"
          srcset="dawn-4x5-480.avif 480w, dawn-4x5-720.avif 720w, dawn-4x5-1080.avif 1080w">
  <source media="(max-width: 699px)" type="image/webp" sizes="100vw" width="1080" height="1350"
          srcset="dawn-4x5-480.webp 480w, dawn-4x5-720.webp 720w, dawn-4x5-1080.webp 1080w">
  <source type="image/avif" sizes="100vw" width="2560" height="1440"
          srcset="dawn-16x9-640.avif 640w, dawn-16x9-960.avif 960w, dawn-16x9-1280.avif 1280w, dawn-16x9-1920.avif 1920w, dawn-16x9-2560.avif 2560w">
  <img src="dawn-16x9-1280.webp" sizes="100vw" width="2560" height="1440" alt="" fetchpriority="high" decoding="async"
       srcset="dawn-16x9-640.webp 640w, dawn-16x9-960.webp 960w, dawn-16x9-1280.webp 1280w, dawn-16x9-1920.webp 1920w"
       data-focal='{"16:9":[0.56,0.5,0.66,0.5],"4:5":[0.70,0.62,0.86,0.62]}'>
</picture>
```

- Порядок `<source>`: сначала `media` телефона (AVIF, затем WebP), потом десктоп; браузер берёт первый подходящий по `media`
  **и** `type` `[документация MDN]`.
- `width`/`height` на каждом `<source>` — соотношение для резервирования места под свой кадр (web.dev «The picture element»);
  без них на телефоне бокс сначала получает 16:9 от `<img>` → сдвиг `[документация]`; на страницах `pages/` CLS = 0 `[проверено]`.
- Телефонный кадр — **новый мастер** (генерация под 4:5 со своей зоной текста или аутпейнт с проверкой H), а не кроп: в J/05 он
  переснят из той же панорамы (yaw 21°, pitch −2°, hfov 38°: небо — верхние 43 % под текст, дерево на 0,70 ширины) `[проверено]`.

### 3.2 `object-position` по фокусу

```js
// js/focal.js — формула F (06-art-direction-consistency/03 §3.2): точка фокуса (fx, fy) встаёт в (tx, ty) бокса cover
// data-focal='{"16:9":[fx,fy,tx,ty],"4:5":[…]}' — ключ выбирается по соотношению ЗАГРУЖЕННОГО файла (арт-дирекшн)
export function objectPosition(fx, fy, iw, ih, bw, bh, tx = fx, ty = fy) {
  const s = Math.max(bw / iw, bh / ih), ox = iw * s - bw, oy = ih * s - bh;
  const clamp = (v) => Math.min(Math.max(v, 0), 1);
  const px = ox < 1e-9 ? 0.5 : clamp((fx * iw * s - tx * bw) / ox);
  const py = oy < 1e-9 ? 0.5 : clamp((fy * ih * s - ty * bh) / oy);
  return `${(px * 100).toFixed(2)}% ${(py * 100).toFixed(2)}%`;
}
```

- Пересчёт — на `load` каждой картинки (смена `<source>` на брейкпоинте даёт новый `load`) и по `ResizeObserver`; у видео
  поверх — тот же `object-position`, что у постера (страница `02`) `[проверено]`.
- Случай из J/06: на Pixel 7 лид «Четыре дня без уведомлений…» ложился на ветви дерева → F83 худший пиксель 2,79 (нужно 4,5);
  фокус дерева 0,70 → точка бокса 0,86 + лид 27ch → проходит (F83 11,5 со скримом) `[проверено]`.

## 4. LCP: какой элемент станет LCP и как сделать его быстрым

### 4.1 «Весь вьюпорт» — не LCP

Код Chromium (`largest_contentful_paint_calculator.cc`, ветка main, 23.09.2026): площадь элемента = видимая часть
(пересечение с вьюпортом); **если она ≥ площади вьюпорта без полос прокрутки — кандидат отбрасывается**
(`is_viewport_covered`); то же в спецификации W3C (шаг 7) и журнале Chromium M88 «Full viewport images… no longer
considered» [S1][S2][S3].

| Вариант (десктоп 1440×900; H1 56 px, 105 148 px²) | LCP | Размер кандидата |
|---|---|---|
| `<img>` 100vh; 120vh; CSS-фон 100vh; `<video poster>` 100vh; 100vh под прозрачной fixed-шапкой | **H1** | — |
| `<img>` `calc(100vh − 1px)` | IMG | 1 294 560 |
| шапка 72 px в потоке + `calc(100vh − 72px)` | IMG | 1 192 320 |
| 78vh; 80vw × 80vh; «карточка» 100vh с полями 12 px | IMG | 1 010 880 / 829 440 / 1 240 416 |
| CSS-фон 78vh | SECTION | 1 010 880 |
| `<video poster>` 78vh; без постера | VIDEO (постер / первый кадр) | 921 600 (= 1280×720: апскейл считается по натуральной площади) |

`[проверено: J/01, Chromium 153 CfT; Pixel 7 — то же]`

- **Разрешение спора A ↔ 3d**: A (`01-web-assets-landscape/02` §5.3) насчитал «5 из 12 полноэкранных hero стали LCP», но в
  `sites.csv` у Rylo, Drinksom и United Carriers `lcp_is_hero = 0` (LCP — другая картинка), а два случая `= 1` — не весь
  вьюпорт: видео Lightship 1409×884 (96 %) и CSS-фон Weavy 99,8 % с анимацией масштаба (первый кадр меньше вьюпорта, как в
  варианте `scale(.9)` §4.3). Правило выполняется 12/12 `[проверено]` → поправка к A — аудитору X.
- **Что делать**: решить заранее, кто LCP. (а) Hero на весь экран → LCP = H1: быстрый шрифт (системный стек или preload +
  `font-display: swap`), H1 в HTML, без анимации появления; картинку всё равно грузить приоритетно — её ждёт глаз, а не
  метрика. (б) Hero меньше вьюпорта (шапка в потоке, `calc(100svh − 64px)`) → LCP = картинка: ≤ 150/80 КБ, `fetchpriority`,
  не lazy. Шаблоны `pages/` — вариант (б).

### 4.2 Энтропия: гладкий ИИ-фон может «выпасть» из LCP

- Порог Chromium — **0,05 бита данных на отображаемый пиксель** (`ContentSizeForEntropy()·8 / size`; размер — видимая площадь
  после поправки на апскейл; байты — `Content-Length`) с Chrome 112; в спецификации W3C — 0,004 байта (0,032 бита) на пиксель,
  в коде стоит TODO согласовать [S1][S2][S3].
- J/01 (бокс 1440×702 = 1 010 880 px, порог 6 318 Б): гладкий тёмный градиент AVIF q40 (2 978 Б, 0,024) и q60 (4 843 Б,
  0,038) → LCP = H1; q70 (6 384 Б, 0,0505) и q80 → LCP = IMG; тот же q40 на Pixel 7 (412×654) — 0,088 → IMG `[проверено]`.
- Кросс-доменная картинка без CORS в Chrome 153 проверяется так же (q40 с другого origin → H1); в ветке main уже есть флаг
  `kLcpEntropyGatedOnCors` (проверка только для CORS-same-origin) — поведение изменится в будущих версиях `[проверено: J/01;
  документация: код]`.
- Следствие: сверхсжатый ИИ-фон (4–5 КБ на 1920) на десктопе не будет LCP — это нормально, если H1 быстрый; «накачивать»
  байты ради метрики не нужно. XMP `DigitalSourceType` (+1–3 КБ, L) энтропию только повышает.

### 4.3 Анимации появления

| Вариант (78vh, десктоп) | Записи LCP |
|---|---|
| картинка `animation: fade` из `opacity: 0` | только H1 (картинка не кандидат вовсе) |
| картинка и текст из `opacity: 0` | мелкий абзац ниже hero (4 704 px²) |
| hero 100vh + текст появляется через 1,2 с | **ни одной записи** за 3,5 с |
| картинка из `opacity: 0.01` | IMG |
| 100vh-картинка с интро `transform: scale(.9) → none` | IMG (первый кадр меньше вьюпорта) |

`[проверено]` → hero и H1 не прятать за `opacity: 0`: метрика либо лжёт в плюс, либо пропадает (поле CrUX запишет
что-то случайное); появление — `transform`/`clip-path` или из 0,01, и лучше не на LCP-элементе.

### 4.4 Время: lazy, CSS-фон, JS, приоритет

74vh-hero 69 КБ AVIF, CPU×4, 1,6 Мбит/с (J/01b):

| Вариант | Троттлинг DevTools (на запрос), медиана 5 прогонов | Общая полоса на сервере, 3 прогона |
|---|---|---|
| `<img>` eager | 2 388 мс | 3 156 |
| `<img fetchpriority="high">` | 2 392 | 2 488 |
| `<img loading="lazy">` | 3 396 (+1,0 с) | 2 420 |
| CSS-фон | 3 392 (+1,0 с) | 2 520 |
| CSS-фон + `<link rel=preload as=image fetchpriority=high>` | 2 388 | 1 820 |
| вставка `<img>` из JS | 3 396 | 2 360 |
| вставка после синхронного бандла 177 КБ | 4 244 (+1,85 с) | 3 588 |
| постер видео 23 КБ | 1 128 | 1 160 |
| 16 картинок 217 КБ в первом экране до hero: eager / high / **lazy** | 2 404 / 2 404 / **21 756** | 1 884 / 2 212 / **21 744** |

- Троттлинг DevTools (`Network.emulateNetworkConditions`) режет каждый запрос отдельно — конкуренции не создаёт; для опытов с
  приоритетом полосу надо делить на сервере (`jlib.Bucket`) — там шум ±1 с `[проверено]`.
- Устойчиво: **lazy на LCP-картинке при конкуренции — катастрофа** (×11), CSS-фон без preload и вставка скриптом — +1 с,
  время определяют байты. `fetchpriority="high"` — дешёвая страховка (web.dev: Google Flights 2,6 → 1,9 с на HTTP/2 [S6]);
  на HTTP/1.1-стенде разницы нет `[проверено]`; ставить на **одну-две** картинки (web.dev [S5]).
- Preload `<link rel=preload as=image>` — только для CSS-фона и картинок, найденных поздно (скрипт, стиль); для `<picture>` в
  HTML не нужен: сканер предзагрузки видит `<img>` сам [S5].

## 5. LQIP: что показать до прихода картинки

| Способ | Вес | Как | LCP |
|---|---|---|---|
| средний цвет кадра | 0 Б | `background-color` бокса (из мастера: рассвет `#b6b1a9`, ночь `#83755f`) | не влияет |
| 32-px WebP в data-URI | 132–158 Б (200–235 символов) | `background: url(data:…) center/cover` бокса; браузер растягивает плавно | не кандидат: натуральная площадь 32×18 |
| ThumbHash | ≈ 25 Б + JS-декодер | «more detail in the same space», соотношение сторон, альфа (README) | как data-URI |
| размытая `<img>`-заглушка с подменой `src` | 200+ Б | подмена после `load` | LCP = финальная картинка (t 336 мс в J/01) |

`[проверено: J/01, J/05; документация ThumbHash]`

- В шаблонах `pages/` — цвет + 32-px WebP на `.hero__media`: 0 запросов, 0 JS; LCP-картинка ложится поверх.
- Заглушка не заменяет приоритет: без `fetchpriority` и при lazy LCP всё равно поздний (§4.4).

## 6. Прозрачность и вырез

- Кадр с альфой (вырез 160×272, J/05): AVIF q60 `--qalpha` 30 / 50 / 70 / 90 / 100 → 2,0 / 2,1 / 2,2 / 2,3 / 2,6 КБ при одинаковой
  ошибке альфы к эталону (IoU 0,985, MAE 3,8 ‰); WebP q80 `-alpha_q` 30…100 → 1,7…2,2 КБ; PNG — 22,6 КБ `[проверено]`.
  Ошибку края задаёт кеинг/вырез (H `08/01`), а не кодек → `--qalpha 50–70`, WebP `-alpha_q 80–90 -exact`.
- Поле вокруг объекта ≥ 2 % стороны (H `08/01` §7); тень выреза — слоем multiply (`03-…` §4.5, J/07).

## 8. Доступность и провенанс картинки

- **`alt`**: декоративный ИИ-фон hero — `alt=""` (смысл — в H1); информационная — описание сцены: «Персиковое небо над гладкой
  водой на рассвете»; ИИ-кадр не называть «фото», факты о месте и товаре — только правдивые (L `12/02` §7.2) `[документация]`.
- `page_accept.py` требует атрибут `alt` у каждой `<img>` (пустой разрешён) и `width`/`height` `[проверено]`.
- Провенанс (позиция L, `../12-legal-provenance/02-labeling-ai-act-provenance.md` §5): мастер с манифестом вендора — хранить
  побайтно; производные `srcset` — без встроенного C2PA (манифест 56–113 КБ тяжелее картинки, H/04b), с XMP
  `DigitalSourceType` после финального кодирования (`provenance_check.py stamp`, +1–3 КБ); видимая иконка ЕС «AI» — только
  дипфейкам на сайтах с аудиторией ЕС (компонент — L §7.1); ссылка «Об ИИ-контенте» в подвале.

## Частые ошибки

- Hero на `100vh`/`100dvh` без шапки в потоке и ожидание, что LCP = картинка (будет H1); «накачка» LCP заглушкой.
- `loading="lazy"` на LCP-картинке; CSS-фон hero без preload; hero, вставляемый фреймворком после гидратации.
- Появление hero и H1 из `opacity: 0` (LCP пропадает или показывает мелочь).
- `srcset` из AVIF без `<picture type>` (браузер без AVIF получает битую картинку); `sizes="100vw"` у картинки в колонке 360 px.
- Один мастер 16:9 на телефон через `object-fit: cover` с `object-position: center` (фокус уезжает, зона текста пропадает).
- WebP 2560 «для полноты» (266 КБ) и PNG от модели в слоте 400 px.
- Нет `width`/`height` у `<source>` телефонного кадра → сдвиг раскладки.
- **Ошибки нейросетей-агентов**: «полноэкранный hero — всегда LCP» и обратное «никогда»; «fetchpriority ускоряет всегда» (при
  HTTP/1.1 и короткой очереди — нет); «JPEG XL уже работает в Chrome» до 06.10.2026 и «не работает» после; `priority` у
  `next/image` (Next 16 — `preload`/`fetchPriority`, A); перенос `quality` Pillow на avifenc; blur-заглушка как «LCP-оптимизация».
