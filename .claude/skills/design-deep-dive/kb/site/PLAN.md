# План ресёрча: логика сайтов — лендинги и многостраничные сайты

Фундамент: 24 сентября 2026 (архитектор, Opus 5.5). Волны запускает оркестратор следующей сессии. Исполнители —
Opus-агенты без помощников (инструмент Agent не запускается), не больше 4 одновременно, 16 агентов в четырёх волнах
вместе с видео-треком, аудитом и синтезом. Соседи (только чтение): `../ux/` (UX сервисов, закрыта),
`../ui/` (визуальный слой сервисов, закрыта), `../ai-media/` (картинки, видео, SVG нейросетями),
`../3d/` (3D для сайтов, закрыта), `../kimi-research/` (исполнитель Kimi K3). Сёстры, которые строятся
параллельно по одному контракту: `../creative/` (подача), `../text/` (тексты). Контракт тройки —
`99-raw/notes/triad-contract-2026-09-24.md` (дальше «контракт §N»); пять отчётов аудита «через линзу лендинга» —
`99-raw/notes/audit-2026-09-24/` (дальше «аудит UX §4», «аудит MEDIA §4.7» и т. п.).

## Зачем

Заказчик строит систему генеративного дизайна: агент (Claude как арт-директор, Kimi K3 как исполнитель вёрстки) по
брифу собирает сервисы, лендинги и многостраничные сайты. Для сервисов логику и визуал дают `ux` и
`ui`, но обе базы лендинги и маркетинговые сайты исключили (`../ux-research/PLAN.md:29`,
`../ui-research/PLAN.md:29`). Логика сайта сейчас ничья: ai-media отправляет за секциями в UX
(`../ai-media/01-web-assets-landscape/01-asset-slots-by-page-type.md` §1 п. 1), а UX лендинги не разбирает
(`../ux-research/13-app-types/02-client-facing-app-playbook.md:10`); пакет kimi собирает лендинг из чужих норм и
внешних скиллов (аудит KIMI §2.8), а проверки соседей на сайте дают ложные блокеры (аудит UX §4, UI §4.3).

База отвечает: **какой сайт и какие страницы нужны под задачу; из каких секций и в каком порядке собрать страницу; как
устроен каждый блок; как страница ведёт к действию и не обманывает; как её найдут люди, поисковики и нейросети; как её
измерить; что обязательно по закону; как проверить результат**. Подачу (арт-дирекшн, движение, эффекты, референсы) ведёт
`creative`, тексты — `text`; эта база задаёт им каркас: типы страниц, идентификаторы блоков и слотов,
план страницы, бюджет и ворота страницы.

Читатель — ИИ-агент (Claude: разбор брифа, карта сайта, план страницы, пакет задачи, приёмка) и заказчик, который его
настраивает. Итог заказчик соберёт в скиллы Claude и Kimi, поэтому знание пишется в исполнимой форме:
- правило «если <тип страницы, осведомлённость, трафик, устройство> — <что делать>, <число или порог>» с меткой и `→ §`;
- каталоги YAML с идентификаторами: типы сайтов и страниц, блоки, слоты, события аналитики, ИИ-боты, требования права;
- схемы контрактов (JSON Schema + пример): `site-brief`, `site-map`, `page-plan`, `blocks.yaml` (контракт §3);
- процедуры по шагам с артефактом и проверкой на выходе каждого шага;
- чек-листы с серьёзностью и способом проверки, утилиты автопроверки, рубрика судьи;
- плейбуки по типам сайтов и полные примеры «бриф → карта → планы → пакет исполнителя».

## Главные риски темы

1. **Доказательная база конверсии слабая и смещённая.** Фольклор («кнопка другого цвета подняла конверсию»), кейсы
   одной компании, бенчмарки продавцов конструкторов, замеры по главным страницам брендов (ai-media — 43 главные,
   3d — 33 наградных сайта). Правило: кейс — `[кейс]`, в норму не переносится; число без методики (выборка,
   период, метрика, сравнение) правилом не становится; бенчмарк вендора — `[данные]` с пометкой «выборка клиентов
   вендора»; свой замер — на посадочных страницах с записью условий (сеть, cookie-баннер, устройство, дата).
2. **Хайп GEO.** Тема забита агентскими «гайдами» без методики. Правило: заявления GEO-агентств и продавцов
   GEO-инструментов — `[вендор-GEO]`, основанием правила не служат; первоисточники — документация платформ (Google,
   OpenAI, Anthropic, Perplexity, Яндекс) и работы с методикой (Aggarwal и др., «GEO», KDD 2024; Pew Research 2025);
   у каждого факта о ботах — дата проверки.
3. **Нормы приложений ломают жанр.** Проверки соседей написаны для рабочих экранов: «одна primary-кнопка», запреты
   попапов и движения, пороги весов и LCP (аудит UX §4, UI §4.3, MEDIA §4.3 и §4.9, BLENDER §4, KIMI §4). Правило: к сайту
   правило соседа применяется только со строкой в таблице «Поправки к правилам соседей» или с пометкой «переносится как
   есть»; проверки — через маркетинговый профиль (агент K).
4. **Выдуманные доказательства.** Генераторы пишут «10 000+ клиентов», «Нам доверяют» с чужими логотипами, лживые
   таймеры (157 лживых из 393 — `../ux/06-feedback-states-motion/04-dark-patterns-and-ethics.md`; эталон
   «Кварц» у kimi — аудит KIMI §2.7). Правило: инвентарь доказательств в брифе — единственный источник чисел, отзывов,
   логотипов, наград и людей; каждый слот `data` плана страницы ссылается на id факта; нет факта — нет блока.
5. **Право меняется и зависит от юрисдикции.** 152-ФЗ: согласие отдельным документом с 01.09.2025; позиция РКН по
   cookie; маркировка рекламы (38-ФЗ ст. 18.1); EAA с 28.06.2025. Правило: `[стандарт]` — только по тексту закона с
   датой редакции; разъяснения и практика надзора — `[регулятор]`; у требования — юрисдикция, дата проверки,
   источник; файлы права — «не юридическое заключение»; юрисдикция по умолчанию — решение заказчика.
6. **Шаблон вместо структуры под задачу.** «Hero → 3 фичи → отзывы → тарифы → CTA» — медиана обучающих данных
   (`../ux/11-ai-generated-ui/01-failure-modes-catalog.md` F12.1; `../ui/12-ai-generated-ui/02-codegen-tools-and-default-look.md` §3.1;
   гейт 8 Hallmark). Уникальность при этом не ломает конвенции взаимодействия (контракт §6.11). Правило: макроструктура
   и порядок секций выводятся из типа страницы, осведомлённости и источника трафика; «общий хвост» без причины — дефект;
   конвенции (логотип слева ведёт на главную, навигация сверху, предсказуемые формы) обязательны.
7. **Эффектность против скорости и индексируемости.** Цель заказчика — насыщенные страницы; ИИ-краулеры JS не
   исполняют (`../3d/01-web-3d-landscape/02-when-3d-budgets-loading.md` §6.1), тяжёлый hero портит LCP и
   INP. Правило: профили бюджета по типу страницы и уровню амбиций вместо одного числа; смысловой текст, цены и CTA — в
   исходном HTML до любых эффектов; ворота меряют исход (LCP, INP, CLS, доступность, индексируемость), а не запрещают
   приёмы.

## Рамки

**В фокусе:**
- типы сайтов и страниц: лендинги (лидогенерация услуг, SaaS и продукт, waitlist, мероприятие и вебинар, приложение,
  промо товара и кампании, курс); многостраничные сайты (корпоративный, услуги и локальный бизнес, портфолио и студия,
  мероприятие, личный бренд, школа и курсы, маркетинговый сайт SaaS-продукта); страницы-спутники (тарифы, функция,
  сценарий использования, сравнение и «альтернативы», кейс и список кейсов, о компании, контакты, «спасибо», 404,
  юридические);
- бриф сайта и процедура «бриф → карта сайта → планы страниц → пакет исполнителя → приёмка»;
- структура и сюжет страницы: роли и порядок секций, макроструктуры, длина, одна цель, message match, первый экран как
  стратегия, мобильный порядок секций;
- библиотека блоков (анатомия, варианты, слоты, мобильное поведение, конверсия, SEO, доступность, события) и единый
  словарь идентификаторов системы;
- конверсия: CTA, лид-формы, квизы, калькуляторы, обратный звонок, мессенджеры, запись; доверие и доказательства;
  тарифы; снятие риска; срочность без обмана; страница «спасибо»; воронки из нескольких страниц;
- многостраничная ИА: карты по типам сайтов, шаблоны, навигация сайта, перелинковка, мультиязычность, модель контента;
- SEO (Google и Яндекс, техническое и структурное); **GEO — техническая часть** (решение заказчика 24.09.2026);
  скорость и бюджет всей страницы; единые ворота страницы; аналитика, события, методика A/B;
- право сайтов РФ и ЕС по юрисдикции; подлинность доказательств; доступность маркетинговых страниц; тёмные паттерны
  сайтов;
- генерация и оценка: дефолты генераторов сайтов по структуре и конверсии, маркеры «ИИ-лендинга», чек-лист сайта,
  автопроверки, экспертный протокол, рубрика судьи, маркетинговый профиль проверок UX;
- замер живых посадочных страниц и многостраничников, включая русский рынок.

**Вне фокуса:** подача — визуальный язык, дисплейная типографика, ритм и фоны секций, движение, эффекты, референсы
(`creative`); тексты — смысл, оффер, копирайтинг блоков, голос, SEO- и GEO-тексты, формулировки юридических
ограничений (`text`); UX сервисов и продукт после входа (`ux`, закрыта); интернет-магазин целиком —
каталог, корзина, оформление, оплата (будущая отдельная база; в рамках — промо-страница товара и кампании); генерация
картинок, видео и 3D (`ai-media`, `3d`); механика исполнителя (`kimi-research`); айдентика;
настройка рекламных кампаний (здесь — посадочная страница и соответствие объявлению).

## Вопросы, на которые база обязана ответить

По ним аудитор X сверяет итог: у каждого вопроса — агент, файл и способ проверки.

1. **Какой сайт и какие страницы нужны под задачу?** Типология сайтов и страниц с целью, действием, трафиком, длиной и
   обязательными страницами; правило выбора по брифу. → B `02-site-types/01`, J `10-playbooks-contracts/02–03`;
   проверка — каждый тип из «Рамок» имеет строку в `vocabulary.yaml` и плейбук.
2. **Что спросить у заказчика и как записать бриф?** Поля, вопросы, минимальный набор по типу сайта; совместимость с
   `brief.yaml` kimi и поля сестёр. → A `01-foundations/03` + `site-brief.schema.json`; J — v1; проверка — проекция
   проходит `build_package.py check` без ошибок формы.
3. **Из каких секций и в каком порядке собрать страницу каждого типа?** Роли секций, сюжетные каркасы, макроструктуры,
   правило выбора по осведомлённости и источнику трафика. → C `03-page-structure/01`; проверка — для каждого типа
   страницы есть порядок секций по умолчанию и условия отклонения.
4. **Какой длины страница, одна ли у неё цель, как она продолжает объявление?** → C `03-page-structure/02`; проверка —
   правила с условием и числом, у каждого метка не ниже `[практика]` или пометка `[спорно]`.
5. **Что обязано быть в первом экране и как страница перестраивается на телефоне?** → C `03-page-structure/03`;

## Как всё сочетается: конвейер и контракты

Схема архитектора; база её проверяет, агент J закрепляет процедурой (`10-playbooks-contracts/01`).

```
заказчик: задача, факты и доказательства, бренд, референсы, юрисдикция, стек
   │
site-brief (схема — site; поля «смысл» — text; «подача», референсы, уровень амбиций L0/L1/L2 — creative)
   │   разбор: пробелы → вопросы заказчику; инвентарь доказательств — только реальные факты с источником
тип сайта → site-map (страницы, шаблоны, навигация, перелинковка, языки)
```

## Формат содержательного файла и машиночитаемые артефакты

Файл: строка метаданных (волна · агент · дата · сколько источников прочитано целиком · опыты) → «Выжимка для агента»
(15–40 правил «делай / не делай»: условие, число, метка, `→ §`) → разделы с деталями, таблицами, кодом, примерами и
антипримерами → «Частые ошибки» (включая ошибки генераторов и агентов) → «Чек-лист» (да/нет) → «Открытые вопросы и
противоречия» → «Источники» (`[S1]` …: автор или организация, название, дата, URL, строка о надёжности). Объём
250–500 строк. Ссылки на соседей — полным относительным путём с разделом (`../ux/04-components-patterns/05-forms-and-validation.md §2.5`),
внутри базы — от своего файла (`../<папка>/<файл>.md §N`, например из `03-page-structure/` на `04-blocks/01-blocks-catalog.md` §3). Поправка к соседу — отдельной строкой «Поправка к … для сайта:
… потому что …». В каждой папке `README.md` (владелец папки): файлы с одной строкой и выжимка на 10 строк.

Машиночитаемое лежит рядом с Markdown: JSON Schema + пример; поля `version` и `checked: YYYY-MM-DD`; идентификаторы —
kebab-case латиницей, названия и описания по-русски (контракт §3); ссылка на чужой идентификатор — с пространством
имён (`block:hero-split`, `slot:headline`, `effect:…`, `task:IMG-HERO-PHOTO`). YAML, выводимый из Markdown (чек-лист),
генерируется скриптом и руками не правится.

## Метки доказательности

Общий набор тройки (контракт §4) и три метки базы:

| Метка | Значение |
|---|---|
| `[исследование]` | работа с методикой: эксперимент, айтрекинг, панель, опрос с известным N; год и выборка рядом с числом |
| `[консенсус]` | несколько независимых авторитетных источников сходятся |
| `[стандарт]` | закон (статья, дата редакции) или спецификация (WCAG, schema.org, RFC 9309 для robots.txt) |
| `[документация]` | официальная документация платформы: Google Search Central, Яндекс Вебмастер, OpenAI, Anthropic, web.dev, GOV.UK |
| `[данные]` | замер или бенчмарк с методикой (Web Almanac, CrUX, SparkToro; бенчмарк вендора — с пометкой «выборка клиентов») |
| `[кейс]` | результат одной компании; в норму не переносится |
| `[практика]` | устоявшийся приём без измерения; синтез агента по механизму |
| `[мнение]` | позиция одного автора |
| `[спорно]` | источники расходятся; позиция базы — с условием |
| `[проверено]` | наш бесплатный опыт или замер (`99-raw/experiments/…`) |
| `[не проверено]` | проверяется только генерацией, живым трафиком или юристом — строка «Что проверить в живой фазе» |
| `[V:<id> mm:ss]` | дайджест ролика; рядом одна из меток выше |
| `[мнение вендора]` — своя | заявление продавца конструктора, CRO- или SEO-сервиса без методики (вынесено из практики соседей: ai-media, kimi) |
| `[вендор-GEO]` — своя | заявление GEO-агентства или продавца GEO-инструмента: правилом не становится, в выжимку не попадает; повышается до `[данные]` только при открытой методике (выборка, период, метрика, сравнение) |
| `[регулятор]` — своя | разъяснение, письмо или практика надзора (РКН, ФАС, EDPB, CNIL, FTC): не норма закона, но задаёт риск и дату |
