## 1. Core Web Vitals: что меряем и где

### 1.1. Метрики и пороги

| Метрика | Хорошо | Плохо | Что меряет | Где меряется |
|---|---|---|---|---|
| LCP | ≤ 2 500 мс | > 4 000 мс | отрисовка главного элемента (картинка, постер, блок текста) | поле и лаборатория |
| INP | ≤ 200 мс | > 500 мс | худшее взаимодействие (клик, тап, клавиша) до следующего кадра | поле; в лаборатории — по сценарию |
| CLS | ≤ 0,1 | > 0,25 | наибольшая «сессия» неожиданных сдвигов (промежутки < 1 с, окно ≤ 5 с) | поле и лаборатория (только загрузка) |
| TBT | < 200 мс на средней мобильной технике | — | сумма «сверх 50 мс» долгих задач после FCP | только лаборатория |
| FCP, TTFB | 1,8 с / 0,8 с | 3,0 с / 1,8 с | диагностика LCP | обе |

- Страница «проходит», когда все три CWV в норме на p75 визитов, отдельно для телефона и десктопа; пороги одинаковые для
  устройств и заданы по достижимости на телефоне (≥ 10 % origin «хорошо», 10–30 % — «плохо») [S1][S6] `[документация]`.
- Stable-метрики меняются не чаще раза в год (журнал Chromium metrics_changelog) — у каждого порога дата проверки [S1].
- INP учитывает клик, тап и клавишу; прокрутку, наведение и зум — нет; на каждые 50 взаимодействий отбрасывается одно
  худшее; если человек только прокручивал — INP у визита нет [S4].
- CLS: сдвиг в течение 500 мс после ввода не считается; анимация `transform` не сдвигает макет [S3].
- Поддержка вне Chromium: LCP и INP заявлены Baseline с Safari 26.2 (2025-12-12) — по дайджесту W, первоисточник не открыт
  `[не проверено]`; CrUX — только Chrome (без iOS, WebView и других Chromium, включая Яндекс Браузер) → для РФ поле CrUX
  смещено; свой RUM на web-vitals закрывает разрыв [S10 через M] `[документация]`.

### 1.2. Поле против лаборатории

| Фактор | Поле | Лаборатория | Для лендинга под рекламу |
|---|---|---|---|
| устройство и сеть | распределение, p75 | одно устройство, одна сеть | средний телефон — CPU×4 + медленный 4G |
| кэш и bfcache | повторные визиты быстрее | холодный кэш | первый визит почти всегда холодный → поле ≈ лаборатории |

| CLS | весь жизненный цикл, ленивое без размеров | загрузка, первый экран | резерв места под всё ниже сгиба |
| охват | только тех, кто дождался загрузки | все | лаборатория видит тех, кто ушёл |

## 2. Исходы и что их ломает

### 2.1. LCP

- Подэтапы: TTFB ≈ 40 %, задержка загрузки ресурса < 10 %, загрузка ≈ 40 %, задержка отрисовки < 10 % — ориентир, не
  правило; время вне загрузки HTML и LCP-ресурса — резерв [S2] `[документация]`.
- LCP-ресурс находим сканером предзагрузки: `<img src|srcset>` в HTML; CSS-фон и веб-шрифт — через `<link rel=preload>`;
  не через JS и `data-src` [S2].
- `fetchpriority="high"` — на 1–2 картинки; скрытым слайдам карусели — `low`; `loading="lazy"` на LCP — запрещено (WA 2025:
  так делают 16–17 % страниц, M/ai-media: Linear 12,8 с) [S2][S7].
- Задержку отрисовки дают: блокирующие CSS и синхронные скрипты в `<head>`, элемент ждёт JS, **библиотека A/B прячет
  элемент до выбора варианта**, долгие задачи [S2].
- Hero на весь вьюпорт → LCP = H1 (Chromium исключает «фон»); hero меньше вьюпорта → LCP = картинка; canvas не кандидат;
  анимация появления и прелоадер двигают LCP к концу анимации (ai-media 01/02 §5) — план страницы решает оба случая
  (поле E `lcp_candidate`) [S12] `[проверено: ai-media A]`.
- Шрифты: `font-display` не `auto`/`block` у текстовых — текст не ждёт шрифт; 87 % телефонных страниц с веб-шрифтами,
  preload шрифтов — у 15–16 % [S2][S7].
- TTFB: редиректы из рекламы и сокращённых ссылок; уникальные параметры аналитики ломают кэш CDN [S2].

### 2.2. INP и TBT

- Задержка = ожидание ввода + обработчики + отрисовка следующего кадра; при старте ввод ждёт разбор и выполнение скриптов
  [S4][S11].
- Сценарий лаборатории: меню, CTA, аккордеон, фокус в поле **и одно нажатие во время загрузки** (DCL + 500 мс) — иначе INP
  занижен: web.dev прямо советует «interacting with the page during load» [S4] `[документация]`; M — сценарий только после
  загрузки, все значения хорошие [проверено].
- TBT «сверх 50 мс» — прокси: показывает риск, которого у людей может не быть, и не видит 300 мс задержки тапа без
  `viewport` [S5][S13]. На телефоне M TBT > 200 мс у 55 % страниц — профиль TBT — S, не B.
- Кнопка «Принять» баннера cookie — частая причина плохого INP: разом стартуют теги; CMP уступает поток после клика [S9].

### 2.3. CLS

- Причины на лендинге: картинки и iframe без размеров (62 % телефонных страниц WA 2025), поздние шрифты, баннер сверху,
  вставленный после отрисовки, сторонние встраивания, подстановка текста после отрисовки (C: подстановка — до первой
  отрисовки), некомпозитные анимации (40 % страниц) [S3][S7][S9].
- M: CLS сессии телефона > 0,25 у 13 % страниц, у лидогенерации РФ — у 36 % → строка SG-PERF-03 B [проверено].
- Лаборатория видит загрузку; ленивое без размеров ниже сгиба ловит прокрутка (`page_anatomy.py` меряет CLS сессии).

### 2.4. bfcache и повторные визиты

- `unload`/`beforeunload` и `Cache-Control: no-store` выключают bfcache; unload — у 10–11 % страниц (топ-1k — 20–28 %) [S7] —
  строка D (для посадочных повторные визиты редки).

## 3. Профили бюджета «тип страницы × уровень амбиций»

### 3.1. Как выбирается профиль

- Формат — `<page_type>@L<n>` (`page-plan.page.budget_profile`, схема E). Уровни L0–L2 определяет creative
  (`../creative/01-creative-direction/ambition-levels.yaml`); P сводит страницу целиком.
- Умолчания (решение 20): L0 — service-page, seo-landing-page, pricing-page, comparison-page, alternatives-page, faq-page,
  contacts-page, form-page, thank-you-page, legal-page, article-page, blog-index-page, careers-page, case-list-page,

  landing-campaign, portfolio-page. Уровень страницы не выше уровня сайта.
- `landing-lead-services`: L1, но блоки конверсии — L0, вес первого экрана телефона — L0; при горячем мобильном трафике
  ≥ 50 % и `price_band` low/mid — L0 по умолчанию.
- Разрешение профиля — `page_gates.py --resolve <id>` (самопроверка 64/64, v1.2) [проверено].

## 5. Сторонние скрипты: аналитика, чаты, виджеты, пиксели, баннер

### 5.1. Порядок загрузки

1. Свой HTML, CSS первого экрана, LCP-ресурс, шрифт первого экрана.
2. Крошечный inline-код согласия (состояние выбора) и скрипт CMP `async` прямо в HTML с `preconnect` [S9].
3. После согласия — счётчики и пиксели: `async`, параллельно, после гидратации (Vercel: «none of them block the LCP»),
   часть — серверной передачей (Measurement Protocol, офлайн-конверсии) [S14][S9] `[документация]` `[мнение вендора]`.
4. Виджеты — по видимости или нажатию (§5.2).
- Порядок в `<head>`: свои теги раньше сторонних; `preconnect` — к 1–2 важным origin (экономия 100–500 мс), остальным —
  `dns-prefetch` [S15].
- Self-host скрипта даёт контроль кэша и меньше соединений (кейс Casper: −1,7 с на self-host скрипта A/B [кейс]); минус —
  обновления. Шрифты — со своего домена: это и скорость, и строка права SG-LEGAL-07 (зарубежные сервисы) [S15].
- M (телефон, доля страниц · медиана КБ за сессию): Яндекс Метрика 52 % · 122; GTM 48 % · 352 (макс. 2 134); Meta Pixel
  21 % · 194; Яндекс Карты 26 % · 141; reCAPTCHA 10 % · 177; Jivo 17 % (макс. 376); Tilda 5 % · 416
  (`99-raw/experiments/P/00-m-extract/vendors.tsv`) — ориентир: метод P не сохранён, реимплементация X2 даёт иные доли
  (`99-raw/experiments/P/00-m-extract/vendors-final.tsv`: телефон — Метрика 40 % · 124 КБ, GTM 46 % · 332 КБ, Jivo 7 % · 373 КБ).
- Цепочки: медиана глубины включения сторонних — 3 (сторонний тянет стороннего) [S16] — GTM с десятком тегов = десяток
  скриптов; каждый тег — строка в брифе с причиной.

### 5.2. Виджеты: фасад, видимость, нажатие (правило для E, `blocks.yaml`)

| Виджет | Загрузка | Фасад | Основание |
|---|---|---|---|
| видео YouTube / VK / Rutube | по нажатию | постер + кнопка (lite-youtube-embed) | web.dev: −500 КБ на старте |
| карта (Яндекс, 2ГИС, Google) | по нажатию или видимости секции | статичная картинка карты + ссылка «Открыть в картах» | web.dev embeds; M: Яндекс Карты до 903 КБ |
| чат | по нажатию, наведению или долгому простою | кнопка-двойник | web.dev; M: Jivo до 376 КБ |
| запись (YCLIENTS и подобные) | по нажатию «Записаться» | кнопка | по механизму |
| отзывы-виджеты (Яндекс Карты, 2ГИС) | по видимости секции | статичные отзывы с источником | F/I — подлинность |
| соцвиджеты | не ставить; ссылка | — | web.dev: «remove or replace with links» |
| капча | не ставить (honeypot + лимит частоты) — F, I | — | M: reCAPTCHA 177 КБ, зарубежный сервис |

- Место под виджет резервируется (`width`/`height`, `min-height`) — иначе CLS [S17].
- Слот плана: поле `load: on-visible | on-interaction` (E уже ввёл его для 3D-слота) — предлагается для всех виджетов.

### 5.3. Баннер cookie

- Скорость: `async`, прямо в HTML (не через менеджер тегов — web.dev; Google для своего баннера в GTM советует шаблон
  согласия — **расхождение источников**, для сайта базы — HTML); снизу или немодально (без CLS); без анимации «выезда»
  через `top`; стили и шрифты CMP — не отдельной цепочкой [S9].
- Мерить три состояния; RUM на cookie теряет отказавшихся — web-vitals cookie не использует [S9].
- Право, вид и тексты баннера — I (`08-legal-trust-a11y/`); A/B вариантов баннера — методика `04` §5.

### 5.4. Кэш, редиректы и метки рекламы

- `Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800` для статичных посадочных (Vercel) `[мнение вендора]`;
  ключ кэша CDN — без `utm_*`, `yclid`, `gclid`, `fbclid`, `_openstat` [S2][S14].
- Ссылка объявления ведёт прямо на канонический URL (редиректов ≤ 1) [S2].

### 5.5. A/B и скорость

- Клиентский A/B с anti-flicker прячет страницу до выбора варианта → задержка отрисовки LCP [S2]; вариант назначать на
  сервере или крае и отдавать закэшированную версию варианта (Vercel: «A/B test logic at the edge, not in the page») [S14]
  `[мнение вендора]`. LCP и INP — guardrail каждого теста (`04` §5.4).

## 7. Бюджет регрессии живой страницы

- Цель (goal) — пороги профиля; бюджет (budget) — худшее значение за 4 недели RUM или синтетики на заданных URL; пересмотр
  каждые 2–4 недели, только вниз; нарушение → разбор, какое изменение (картинка, тег, код) его дало [V:cnr3CJwpaps 32:32].
- Метрики бюджета (минимум): p75 LCP, INP, CLS; вес картинок первого экрана (страховка LCP: новый hero на 1 МБ от
  контент-менеджера); long tasks сторонних (вес тегов стабилен, их долгие задачи скачут) [V:cnr3CJwpaps 24:23, 27:26].
- Начинать со страниц, где решается действие: посадочные под рекламу, страницы услуг с формой, тарифы.
- RUM: web-vitals (attribution-сборка) → событие `web-vitals` (`events.yaml`) с `page_type`, `variant_id`, `release`;
  перцентили, не средние; отправка при `visibilitychange` [S10] `[документация]`.

## Частые ошибки

- Блокировать страницу за вес при хороших LCP, INP и CLS; или пропускать страницу с LCP 5 с, потому что «вес в норме».
- Мерить телефон без замедления сети и сравнивать с порогом 2,5 с (M: медиана 1,9 с без троттлинга ≠ приёмка).
- Считать INP по сценарию после загрузки — «INP хороший»; не нажимать во время загрузки.
- Считать TBT блокером: WA 2025 — медиана 1,9 с в лаборатории при хорошем полевом INP у 77 % сайтов.
- `loading="lazy"` на hero; hero из `data-src` через JS; появление hero из `opacity: 0`; прелоадер поверх H1.
- Счётчики, пиксели и GTM с десятком тегов синхронно в `<head>` до согласия (M: трекинг до выбора — 91 % страниц).
- Карта, чат, YouTube, запись — iframe при загрузке страницы; капча на лид-форме.
- Баннер cookie сверху, вставленный после отрисовки (CLS); скрипт баннера через менеджер тегов.
- Клиентский A/B с anti-flicker; параметры рекламы в ключе кэша; цепочка редиректов из объявления.
- Одно число бюджета на все страницы и жанры; «бюджет = цель» (вечный красный); медиана рынка как норма.
- **Ошибки генераторов и ИИ-агентов:** «страница 1–2 МБ» по памяти; Lighthouse-балл вместо CWV; «вес видео» без CDP
  (Range-запросы); `THREE` и GSAP в `<head>` синхронно; шрифты с Google Fonts по умолчанию (скорость и право РФ); виджеты
  карт и отзывов «из коробки» конструктора.

## Чек-лист

- [ ] У страницы есть `budget_profile` `<page_type>@L<n>`, уровень не выше сайта, исключения записаны?
- [ ] LCP-элемент решён в плане для телефона и десктопа (H1 или постер из HTML), без lazy, с `fetchpriority` при картинке?
- [ ] Лаборатория телефона с троттлингом: LCP ≤ цели, CLS ≤ 0,1, INP-сценарий (с нажатием во время загрузки) ≤ 200 мс?
- [ ] Вес первого экрана, сессии, JS, шрифтов, сторонних — в профиле или записано обоснование?
- [ ] До согласия — только CMP; счётчики и пиксели — после; виджеты — фасадом по видимости или нажатию?
- [ ] Баннер cookie снизу или немодально, скрипт `async` в HTML, без сдвига; «Принять» без долгой задачи?
- [ ] Ключ кэша без UTM и click id; редиректов из объявления ≤ 1?
- [ ] HTML и каждый CSS/JS < 2 МБ без сжатия; нет base64-картинок > 10 КБ?
- [ ] `page_gates.py` — нет B; каждая S исправлена или в `x-gate-exception`?
- [ ] В живой фазе: RUM web-vitals с `variant_id` и `release`, бюджет регрессии = худшее за 4 недели?

## Открытые вопросы и противоречия

- Поле по URL для выборки не получено (PSI API без ключа — квота 0) → проверка профилей полем — живая фаза (ключ CrUX API
  или RUM заказчика).
- CrUX без Яндекс Браузера и iOS: для РФ нужен свой RUM; как Метрика отдаёт CWV — не проверено.
- Порог «сторонних доменов до ввода ≤ 1» опирается на позицию I «согласие до счётчиков» `[спорно]`; при режиме без
  opt-in для РФ профиль L0 — 2 домена.
- Baseline LCP/INP в Safari 26.2 — по дайджесту W, первоисточник не открыт.
- WA 2025 Page Weight: расхождение текста и рисунка (2–3 МБ: 63 / 53 % против 53 / 45 %); подпись рисунка Lighthouse LCP
  p90 (3,0 / 3,6 с) против текста (15,1 с) — брались рисунки и связный текст.
- Google (шаблон согласия через GTM) против web.dev (скрипт CMP прямо в HTML) — для сайтов базы выбран HTML.
- JS-бюджеты L0–L2 — синтез без полевой проверки на генерированных страницах; калибрует K по страницам K3.
