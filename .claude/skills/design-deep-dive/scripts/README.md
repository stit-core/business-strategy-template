# Утилиты скилла design-deep-dive

Указатель по папкам: утилиты баз знаний, `project` — утилиты по файлам проекта, `lib` — общие модули, `tests` — смоук и
фикстуры, `maint` — обслуживание; цепочка ворот собранной страницы — § Ворота после сборки.
Пути — от `scripts/`. Запуск — Python окружения: `~/.cache/design-deep-dive/venv/bin/python scripts/<домен>/<утилита>.py --help`;
пути к базе, выходы, кэши, блокировки, бинарники — `lib/kbpaths.py` (`python3 lib/kbpaths.py` показывает, что где).
Окружение ставит `install.sh` (§ Окружение); проверка — `tests/smoke.py` (§ tests).

Колонки: назначение — первая фраза описания утилиты; вход — как её запускать (подробно — `--help` и README домена);
выход — куда пишет по умолчанию (`$DDD_HOME` = `~/.cache/design-deep-dive`); зависимости — Python, npm, бинарники.

## Окружение — `install.sh`

| утилита | вид | назначение | вход | выход | зависимости |
|---|---|---|---|---|---|
| `install.sh` | maint | окружение утилит скилла вне репозитория — одно на машину для всех клонов; повторный запуск ставит только недостающее. | без ключей — venv (группа pip `core`), npm-пакеты группы `page` (замеры страницы и доступности), каталоги выходов; `--npm-groups page,media,3d` или `all` — группы npm (`media` — SVG, иконки и Lottie, `3d` — проверка glTF и эталонные 3D-сборки; поставленные раньше группы остаются); `--python python3.13` — Python 3.12–3.13 (без ключа — python3.13, python3.12 или python3 не ниже 3.12); `--groups core,net,morph,svg,ocr,media` или `all` (scipy — в `media` и `svg`); `--bin`, `--models`, `--browsers`, `--ffmpeg`; `--all` — всё это сразу; `--from DIR` и `--models-from DIR` — бинарники и модели из локальных папок, ключ повтором; `--playwright-match` — Playwright под Chromium из `PLAYWRIGHT_BROWSERS_PATH`; `--catalogs` — снимки каталогов генерации и список доверия C2PA (сеть, 0 ₽); `--dry-run` — план без изменений; `--check` — сверка установленного (версии, sha256); оба печатают и план npm; неработающий `esbuild` — предупреждение: он нужен только эталонным 3D-сборкам базы | `$DDD_HOME`: venv, node, bin, models, out, cache, locks | bash; Python 3.12–3.13; Node 24 и npm |

Системное, которое скрипт не ставит, и переменные его путей (Blender 5.2.2 — `DDD_BLENDER`, Node — `DDD_NODE`, Brave —
`DDD_BRAVE`, bwrap, systemd-run, flock, lzip, libcairo2) — `install.sh --help`; что нашлось — `install.sh --check`.

Браузер на машине — один за раз, под замком `kbpaths.lock('browser')` (`$DDD_HOME/locks/browser.lock`); утилита с
браузером берёт его сама на время работы браузера. Прямо — `ai-media/asset_inventory.py`, `ai-media/layout_check.py`,
`claude-design/mockup_checks.py`, `claude-design/kit/shot.py`, `claude-design/kit/export.py`,
`creative/marketing_audit.py`, `creative/scroll_record.py`, `site/geo_probe.py`, `site/run_axe_targets.py`,
`ui/measure_ui.py`, `ui/ui_audit.py` и утилиты 3d `anim_diff.py`, `fx_probe.py`, `gltf_diff.py`,
`gltf_load_bench.py`, `gltf_web_inspect.py`, `three_probe.py`; замеры времени — через `page_gates.heavy_lock`, вместе с
тяжёлым замком тишины: `ai-media/page_accept.py`, `creative/motion_check.py`, `site/page_anatomy.py`,
`3d/site_probe.py`, `3d/web_view.py`. `--no-lock` у замеров — прогон без замков, у `page_accept.py` — без
замка тишины (замок браузера остаётся). Клиент референсов `creative/refs_client.py` общего замка не берёт — у него свой
слот `browser-refs`. `kbpaths.lock()` реентерабелен по дереву процессов: утилита, запущенная из процесса, который
держит тот же замок, его не ждёт (держатель называет файл замка в `DDD_LOCKS_HELD`; `3d/slot_run.py` так называет
команде удержанные замки браузера и рендера). Свой скрипт с браузером берёт `kbpaths.lock('browser')`; внешний `flock`
на файл замка не нужен: под ним прогон ждёт замок, который держит его же обёртка.

## Ворота после сборки — кто кого зовёт

Фаза `build` в репозитории кода: собранную страницу проверяют утилиты этого скилла, запущенные соседним чекаутом
`../strategy/.claude/skills/design-deep-dive/scripts/…` на коммите лока снимка, с рабочей папкой код-репо; окружение —
`$DDD_HOME` машины. Порядок: замеры (`page_anatomy`, `page_accept --budget-profile`, `motion_check`; у страницы с 3D —
`site_probe` дважды, второй раз с `--no-3d`, и `gate_check` по каждому прогону) → вердикт `page_gates.py --brief
<бриф> --plan <план> --ready <манифест> --anatomy … --accept … --motion … --gate3d …`, бриф, план и манифест
готовности — файлы снимка. Код-репо читает поля JSON, а не коды выхода: коды выхода замеров вердикт не решают
(`page_accept.py` и `gate_check.py` при выполненном замере возвращают 0, находки — в JSON; выход по находкам — ключом
`--strict`, у `page_accept` — по своим порогам: LCP, `alt`, петля без паузы, а не B), поэтому цепочку не обрывают на
коде звена (`set -e`, `&&`). Вердикт — поля `verdict`, `B`, `S` вывода `page_gates.py --json`: B > 0 — страница не
передаётся; S — исправить или записать исключением `x-gate-exception` плана (строка под исключением — `excepted`, в S
не идёт); `tool` и `skill_version` — какая утилита ответила и версия контракта, `params` — ключи вердикта после брифа
и плана. Пункт `after_build` манифеста `ready.yaml` (`{id, severity, check}`,
`docs/projects/_template/design/README.md § Пакет для кода`) со способом `gates` судит сам вердикт с `--ready`:
`after_build[] {id, gates, status, severity}` — `pass`, `fail` с худшей тяжестью строк или `unchecked` с тяжестью
пункта, непроверенный идёт в `B` и `S` (правило — `kb/common/acceptance-criteria.yaml`, поле `check`); со способом
`tool` — путь пункта в JSON, который названная утилита печатает в stdout: `ui/ui_audit.py URL --acceptance --json` —
`tool`, `skill_version`, `findings[] {id, verdict OK · WARN · FAIL, severity, run}`;
`claude-design/mockup_checks.py resize URL` — `tool`, `skill_version`, `command`, `verdict` (`pass`, `fail`; `error` —
проверка не шла, причина — поле `error`), `problems`. У `copydeck.py` и
`claims_check.py` с `--json ФАЙЛ` — в файле `tool`, `skill_version`, `command`, `summary {error, warning, info}`:

## project — утилиты по артефактам проекта

Утилиты папки `project/` знают раскладку `docs/projects/<slug>/` и читают артефакты проекта: слой страницы, слой
дизайна, файлы уровня продукта, экраны. Движки без знания раскладки — перевод копий холста, кадры, контраст, покрытие по
двум спискам — живут в папках баз; знание о раскладке собрано здесь, чтобы смена формы слоя правилась в одной папке.
Корень данных — ключ `--repo DIR`, переменная `DDD_REPO` или репозиторий скилла (модуль `lib/docpaths.py`, рядом с
`kbpaths`): так репозиторий кода указывает соседний чекаут стратегии. Соседние скиллы шаблона зовут их по пути
`../design-deep-dive/scripts/project/…` — одна копия утилит и одно окружение на все скиллы. Ниже `…` — папка проекта
`docs/projects/<slug>`.

- **Вызов** — `<утилита> <команда> <slug> [<surface>] [--repo DIR] [--stage …] [--out DIR] [--json]`: `build` пишет
  свои производные файлы проекта (с `--out DIR` — вне проекта), `check` ничего не пишет, `show` печатает разбор;
  `--selftest` — самопроверка на встроенной фикстуре, без сети. Без `<surface>` — все поверхности, которые ведёт
  утилита.
- **Вывод `check`** — находки: без `--json` — таблица и строка итога по тяжести (`error` · `warning` · `hint`); с
  `--json` — только строки JSON `{rule, severity, surface, kind, ref, path, message, fix}` (формат —
  `project/findings.py`). `rule` — id правила аудита (`/design-audit`, у экранов — `/screen-audit`), `ref` — запись и
  место в ней, `fix` — что сделать и каким скиллом.
- **Коды выхода:** 0 — ошибок нет (предупреждения и подсказки не мешают); 1 — есть `error` (у `normalize check` — есть
  правки); 2 — ошибка вызова или окружения: нет проекта, поверхности, файла словаря.
- **Что дальше:** `error` — правка там, куда ведёт `fix`, затем повтор `check`; `warning` и `hint` — доклад владельцу.
  Какие находки держат работу, а какие решает заказчик, — `../references/phases.md § Принципы всех этапов`.
