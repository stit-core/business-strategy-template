# interface-audit

Аудит консистентности восьми файлов interface **одной поверхности** проекта в
`docs/projects/<project-slug>/interface/<surface>/`: участник (who), этап (stage), ситуация (situation), сценарий
(scenario), зона (zone), блок (block), субстрат (ux-substrate), данные (data-items). Канон формы —
`docs/projects/_template/interface/README.md`. Аудит **читает и сообщает**, ничего не правит: правки идут через
`/interface-deep-dive`.

UX-слой **партиционируется по поверхности**: на каждую поверхность реестра `docs/projects/<project-slug>/surface.md` —
своя папка `interface/<surface>/`, кроме `web` рода `landing` и `site` — у них на месте interface слой страницы. Все
ссылочные проверки идут **в пределах одной поверхности**; аудит проходит каждую папку поверхности отдельно. Кроме папки
он читает только то, что называют правила: тип и род поверхности в `surface.md`, объекты глоссария `object.md` и
возможности поверхности `capability/<surface>.md` того же проекта, поле `situations` экранов той же поверхности.

## Выбор проекта и поверхности

Аргументы позиционны — `<project-slug>` первый, `<surface>` второй (опционален):

| вызов | проект · поверхность |
|---|---|
| `/interface-audit <project-slug> <surface> …` | взять `<project-slug>` и `<surface>` |
| `/interface-audit <project-slug> …` | проект задан; **все** папки поверхностей проекта |
| `/interface-audit …` | пикер по именам проектов (исключая `_template` и `infrastructure`); затем все поверхности |

1. Первый аргумент совпал с подпапкой `docs/projects/` (кроме `_template` и `infrastructure`) — это `<project-slug>`; иначе — пикер по
   именам. Проектов нет — «нечего аудитить», выйти.
2. Прочитать `surface.md`. Следующий аргумент совпал со `slug` строки — это `<surface>` (одна поверхность), остаток —
   scope; аргумента нет — все поверхности, отчёт группируется по поверхности.
3. Все чтения скоупятся в папку поверхности (одну или каждую), названные правилами файлы того же проекта и
   `audit-state/<project-slug>/`.

## Точки входа

| вызов | поведение |
|---|---|
| `/interface-audit <project-slug>` | полный прогон каждой папки поверхности |
| `/interface-audit <project-slug> <surface>` | полный прогон одной поверхности |
| `/interface-audit <project-slug> <surface> <kind>` | один файл поверхности и перекрёстные ссылки внутри неё |
| `/interface-audit <project-slug> <surface> <kind>:<slug>` | одна запись и её соседи на один шаг |

`kind` ∈ {`who`, `stage`, `situation`, `scenario`, `zone`, `block`, `ux-substrate`, `data-items`}. `<kind>` и
`<kind>:<slug>` требуют заданной `<surface>` — kind живёт в конкретной поверхности.

## Что делать при запуске

1. Определить `<project-slug>` и, если задана, `<surface>`.
2. Прочитать `docs/projects/_template/interface/README.md` и формы kind из scope — канон, по которому идёт сверка.
3. Прочитать `references/rules.md` — реестр правил с тяжестью и нормой.
4. Сверить подпапки `interface/` с реестром `surface.md`: папка вне реестра — R-SURF-001, папка у сайта или лендинга —
   R-SURF-003, поверхность без папки — R-SURF-002.
5. Для каждой папки поверхности из scope прочитать её восемь файлов (или подмножество по аргументам), а для правил,
   которые смотрят наверх и вниз, — `object.md`, файл возможностей поверхности и поле `situations` её экранов.
6. Прогнать правила в пределах поверхности; обойти граф блоков от стартовых (R-STRUCT-010); собрать находки.
7. Сгруппировать по поверхности, внутри — по записи, в пределах записи — по тяжести; вывести отчёт в чат.
8. Перезаписать `audit-state/<project-slug>/last-report.md` с reasoning-trace.

## Уровни тяжести

| severity | смысл | пример |
|---|---|---|
| `error` | Структурное нарушение, ломает модель | невалидная ссылка; цикл `parent-zone`; дубль slug; рассинхрон зеркал; блок без субстратов или без участников; stable-блок недостижим; папка вне реестра или у сайта и лендинга; ссылка в другую поверхность; объект глоссария в пустоту; шаг сценария вне ситуаций; исход без «что дальше»; пустой раздел stable-сценария |
| `warning` | Семантическое подозрение | пустой обязательный слот у draft; `goal` как предусловие; облик в `using-what`; ситуация экрана без отказов; два участника без «Чей ход»; дерево зон глубже рабочего потолка; имя-свалка; черновой блок без входа |
| `hint` | Покрытие и стиль, не ломает | stable со ссылкой на draft; участник или этап без ситуаций; зона без блоков; stable-ситуация без возможности; корневая зона без объекта и хаба; цель сценария словами системы; поверхность без папки interface |

Реестр с нормой каждого правила — `references/rules.md`.

## Формат отчёта

Отчёт читает человек, который правила аудита не писал, поэтому в чат он идёт словами (`.claude/rules/guiding.md` §4, §5):

- **Итог — первым.** Одна-две фразы: что в порядке, что держит работу, что можно отложить; затем два-три хода дальше,
  один рекомендован.
- **Находка — три части:** что нарушено → чем грозит → как исправить (кто и каким шагом). Уровень — словом («ошибка»,
  «предупреждение», «подсказка»); код правила и уровень латиницей — в скобках в конце. Запись названа словами, её адрес
  — в скобках: по нему находят файл и вызывают команду. «Чем грозит» берётся из нормы правила (`references/rules.md`),
  а не сочиняется.
- **Дефект проверки — не вопрос человеку.** Находку, в которой аудит видит дефект самой проверки, а не слоя (правило
  сработало мимо своей нормы), он записывает с причиной в reasoning-trace `audit-state/<project-slug>/last-report.md` и
  называет одной строкой отчёта; вопросом выносится только то, где у человека есть выбор.
- **Группировка** — по поверхности, внутри — по записи; в пределах записи — ошибки, предупреждения, подсказки.

Пример — иллюстрация формы на вымышленных данных:

```
Проверка interface проекта «Клиника „Утро“» (/interface-audit <project-slug>): кабинет клиники, бот и папка у
лендинга.

Итог. Зоны и блоки кабинета связаны, ссылки между ситуациями и блоками сходятся. Работу держат три ошибки: у лендинга
лежит папка interface, один сценарий кабинета ведёт в пустоту, один блок недостижим. Предупреждение об отказах и
подсказку об участнике без ситуаций можно отложить.

Дальше можно:
1) исправить три ошибки — рекомендую: по сценарию с пустым шагом экран не собрать;
   /interface-deep-dive <project-slug> web-clinic, от вас — три решения;
2) начать с предупреждения — назвать отказы шага «Отправить направление»: одно решение, его ждёт набор состояний экрана;
3) идти к экранам, не правя, — ошибки останутся и повторятся в следующем прогоне.

── Лендинг «Промо» (promo) ──

Ошибка. У лендинга лежит папка interface, а у сайта и лендинга на её месте стоит слой страницы.
  Чем грозит: код сайта читает слой страницы — записанное в этой папке до него не дойдёт.
  Как исправить: аналитик переносит смысл страницы в слой страницы — /design-deep-dive <project-slug> promo; если это
  на деле кабинет — называет род «кабинет» (app) через /project-deep-dive <project-slug> (R-SURF-003, error).

── Кабинет клиники (web-clinic) ──

Ошибка. В сценарии «Отправка направления» (scenario:send-referral) шаг 2 ведёт к ситуации «Проверить направление»
  (check-referral), которой нет в ситуациях кабинета.
  Чем грозит: шаг сценария ведёт в пустоту — экрану под него не на что опереться.
  Как исправить: аналитик заводит ситуацию — /interface-deep-dive <project-slug> web-clinic situation:check-referral
  (R-SC-003, error).

Ошибка. Блок «Архив направлений» (block:archive-list) закрыт (stable), но от стартового блока до него не дойти.
  Чем грозит: пользователь в блок не попадёт — к нему не ведут ни зона, ни переход, ни пункт навигации.
  Как исправить: аналитик даёт блоку вход — /interface-deep-dive <project-slug> web-clinic block:archive-list
  (R-STRUCT-010, error).

Предупреждение. Ситуация «Отправить направление» (situation:submit-referral) стоит на экране и закрыта (stable), а
  отказы шага не названы.
  Чем грозит: отказы ситуаций входят в обязательный набор состояний экрана — экран останется без них.
  Как исправить: аналитик называет отказы или пишет «отказов нет» —
  /interface-deep-dive <project-slug> web-clinic situation:submit-referral (R-SEM-006, warning).

── Бот (tg-bot) ──

Подсказка. У участника «Врач» (who:doctor) нет ни одной ситуации.
  Чем грозит: участник заведён, а в диалогах бота ему нечего делать.
  Как исправить: аналитик заводит ситуацию, которую начинает врач, или удаляет участника —
  /interface-deep-dive <project-slug> tg-bot (R-COV-001, hint).

Что проверено: файлы interface кабинета и бота, глоссарий объектов (object.md), 2 файла возможностей.
Счёт: 3 ошибки, 1 предупреждение, 1 подсказка.
```

## `audit-state/<project-slug>/last-report.md`

Отчёт лежит рядом со скиллом, а не в папке interface и не в корне папки продукта, и скоупится по проекту:

```
.claude/skills/interface-audit/audit-state/<project-slug>/last-report.md
```

Дальше по тексту — короткое `audit-state/<project-slug>/`. После каждого прогона файл перезаписывается reasoning-trace:
какие правила запускал, какие записи проверил, что нашёл и почему, как прошёл обход блоков. Это не журнал — следующий
прогон перезаписывает его. Файл в git, чтобы команда могла читать.

```markdown
---
project: <project-slug>
ran-on: <all-surfaces | surface | surface kind | surface kind:slug>
surfaces: [<surface-1>, <surface-2>]
files-read: 8 × surfaces + object.md + capability/<surface>.md + situations экранов
records-checked: N
totals: { error: X, warning: Y, hint: Z }
---

# Reasoning trace

## Хребет (R-SURF-*)
- R-SURF-001 «папка вне реестра»: ...
- R-SURF-003 «папка у сайта или лендинга»: ...

## Поверхность <surface-1>

### Структура (R-STRUCT-*)
- R-STRUCT-001 «валидность ссылок»: проверил M ссылок, нашёл K битых.
- R-STRUCT-010 «достижимость»: стартовые блоки …; не достигнуты …

### Зеркала (R-MIRROR-*) · Семантика (R-SEM-*) · Покрытие (R-COV-*)
- ...

### Сценарии (R-SC-*) · Информационная архитектура (R-IA-*) · Покрытие вверх (R-CAP-*)
- ...

## Поверхность <surface-2>
- ...
```

## Что не делать

- **Только отчёт.** Артефакты правит `/interface-deep-dive`; аудит его не запускает — это делает аналитик по выводу.
- **Не понижать `stable → draft`.** Максимум — подсказка «возможно, понизить?». Пустые обязательные слоты stable-записей
  у папки, чьи файлы разошлись с формой слоя, — список работ приведения к канону.
- **Не выдумывать находки.** Правило не сработало — находки нет; правило, требующее суждения, приводит цитату.
- **Без suppressions.** Структурные правила детерминированы — зеркало синхронно или нет, ссылка есть или нет. Подозрения
  R-SEM и правила «чтением» аналитик может объяснить в диалоге, и ответ снимает их в этом прогоне, но отчёт их не
  подавляет: следующий прогон вправе сработать снова (в отличие от `/cross-audit`, `/swot-audit` и
  `/hypothesis-map-audit`, которые ведут suppressions).
- **Один проект; каждая поверхность — в своих границах.** Ссылка из папки поверхности в другую — ошибка R-XSURF-001;
  «один датум, один slug» считается внутри поверхности. Смысл связей с продуктом и кросс-поверхностная сверка —
  `/cross-audit`; покрытие возможностей ситуациями и хабов сценариями — `/project-audit`.
