# mobile-deep-dive

Проектирование карты **одной мобильной поверхности** проекта в
`docs/projects/<project-slug>/mobile/<surface>/`. Канон формы —
`docs/projects/_template/mobile/README.md` и двенадцать форм в подпапке
`_template/`. Скилл ведёт сеанс через структурированные вопросы, фиксирует
контекст в своей ветке единого дерева state оркестратора
(`../entrypoint/state/projects/<project-slug>/mobile/<surface>/`), не
выдумывает продукт и платформенную механику.

Слой **двухролевой**: композиция (экраны, сценарии, оболочка, виджеты — что
видит пользователь) и карта кода (фичи, сущности, точки входа, системные
действия, фоновые задачи — из чего форк `<org>/mobile` выводит пути в
`shared/`, `androidApp/`, `iosApp/`). Источники — `interface/<surface>/`
(ситуации, блоки, роли, данные) и `services/<svc>/domains/<ctx>/` (агрегаты,
use-case'ы, события) **того же проекта**. Для поверхности с `type: mobile`
слой встаёт **на место** `screens/<surface>/`; слоя `fsd/` у неё нет.
Граница со stack код-репо: **здесь — продукт и его карта; платформа и её
значения (магазины, SDK, хосты, планировщики, версии) — `docs/stack/`
форка**. Код по stable-записям разворачивает агент в `<org>/mobile` (форк
`mobile-template`, его `/scaffold`) — по задаче из корня проекта (или фазе
программы хаба `<org>/infra`) либо при прямом заходе.

Использовать как **единственную точку входа** в mobile-слой: заведение,
углубление, разбор сырья, переход `draft → stable`, удаление с каскадом.

## Выбор проекта и поверхности

Скилл работает в контексте **одного** проекта и **одной** его мобильной
поверхности. Аргументы позиционны — `<project-slug>` первый, `<surface>`
второй:

| вызов | проект · поверхность |
|---|---|
| `/mobile-deep-dive <project-slug> <surface> …` | взять `<project-slug>` и `<surface>` |
| `/mobile-deep-dive <project-slug> …` (без surface) | проект задан; поверхность — `AskUserQuestion`-пикер **по именам** мобильных поверхностей из `surface.md` |
| `/mobile-deep-dive …` (без slug) | пикеры **по именам**: сначала проект, затем поверхность |

Алгоритм определения при запуске:

1. **Проект.** Если первый аргумент совпадает с именем подпапки
   `docs/projects/` (кроме `_template` и `infrastructure`) — это `<project-slug>`. Иначе —
   пикер по именам проектов (имя из `vision`, slug — деталь). Если проектов
   нет — «сначала заведи проект через `/project-deep-dive`», выйти.
2. **Поверхность.** Прочитать реестр
   `docs/projects/<project-slug>/surface.md`; кандидаты — только строки с
   `type: mobile`. Если следующий аргумент совпадает со `slug` такой строки
   — это `<surface>`. Если он совпал с поверхностью **другого типа** —
   сказать, какой слой для неё работает (`screens/` + `fsd/` для фронтовой поверхности,
   `telegram-bot-flow/` для `bot`), выйти. Иначе — пикер по именам
   мобильных поверхностей; одна — взять без вопроса. Мобильных поверхностей
   нет — «сначала заведи поверхность с `type: mobile` в `surface.md` через
   `/project-deep-dive <project-slug>`», выйти. Поверхность вне реестра не
   принимается.
3. **Scaffold.** Если папки `docs/projects/<project-slug>/mobile/<surface>/`
   ещё нет — первый заход (см. ниже).
4. Все дальнейшие чтения/записи скоупятся в выбранную поверхность и ветку
   state `../entrypoint/state/projects/<project-slug>/mobile/<surface>/`.

## Scaffold первого захода

Каталог руками не создаётся в обход скила. При первом заходе:

1. Раунд `AskUserQuestion` (до 3 вопросов) — рамка приложения, от которой
   зависят обязательные заготовки:
   - есть ли у приложения **вход** (аккаунт, сессия) — от этого зависят
     сценарий `login` и `Auth-gate` оболочки;
   - пойдёт ли приложение **в магазины** — от этого зависит точка входа
     `demo` (ревью магазина) и правовые документы оболочки; личная установка
     обходится без них;
   - **платформы** поверхности: `all` \| `android` \| `ios` — дефолт колонки
     `platforms` для всех записей.
2. Скопировать двенадцать форм из
   `docs/projects/_template/mobile/_template/` в папку поверхности. Строки-
   образцы (`<slug>`, `<Key>`, примеры под таблицами) убрать; **обязательные
   заготовки оставить** как `draft` с незаполненными `<…>`: сценарий
   `app-start` (и `login` — при входе), точку входа `demo` (при магазинах),
   секции `shell.md`, локаль `ru` в `shared-lib.md`. Преднаполненные
   reference-строки канона, не относящиеся к продукту (ресурсы `auth` /
   `devices`, ключи ошибок, флаг `demo_login`, разрешение `notifications`),
   оставлять только если рамка из шага 1 их требует; иначе убрать.
3. Ответы рамки записать в state-заметку поверхности
   (`…/mobile/<surface>/_frame.md`, секция `## Доменные решения`).

## Точки входа

После того как `<project-slug>` и `<surface>` определены, остаток args
задаёт режим:

| вызов | поведение |
|---|---|
| `/mobile-deep-dive <project-slug> <surface>` | сводка состояния поверхности + топ-3 кандидата на углубление |
| `/mobile-deep-dive <project-slug> <surface> <kind>` | завести новую запись kind'а (режим A) |
| `/mobile-deep-dive <project-slug> <surface> <kind>:<slug>` | углубить существующую запись (режим C); для экрана — `screens:<Key>` |
| `/mobile-deep-dive <project-slug> <surface> <slug>` | найти slug/key; одиночный → C; конфликт kind → переспросить |
| `/mobile-deep-dive <project-slug> <surface> <свободный текст / приложение>` | сырьё (эскиз экранов, описание сценария, скриншоты аналога, транскрипт) → разбор (режим B) |
| `/mobile-deep-dive <project-slug> <surface> --lens` | пройти линзу возможностей платформы (см. ниже) |

`kind` ∈ {`entities`, `screens`, `flows`, `features`, `shell`,
`entry-points`, `permissions`, `system-actions`, `widgets`,
`background-tasks`, `shared-api`, `shared-lib`}. Синтаксис `kind:slug` —
ускоритель; заход без аргументов с пикером по именам есть всегда
(`.claude/rules/naming.md`).

## Что делать сразу при запуске

1. Определить `<project-slug>` и `<surface>`, при первом заходе — scaffold.
2. Прочитать `docs/projects/_template/mobile/README.md` и формы kind'ов, с
   которыми пойдёт работа, — освежить критерии, словари состояний, enum'ы,
   инварианты, anti-patterns.
3. Прочитать источники поверхности: `vision.md`, строку поверхности в
   `surface.md`, `capability/<surface>.md`, весь `interface/<surface>/`
   (+ `references/interface-context.md` — карта синтеза), реестр
   `services/service.md` и домены сервисов `services/*/domains/` (если
   сервисный слой есть). Для контекста границ — `integration.md` и
   `constraint.md` проекта. Пустота источников — не ошибка, а сигнал режима
   (см. `references/workflow-patterns.md`).
4. Если остаток args пуст — сводка (см. ниже) + `AskUserQuestion`-выбор.
5. Если указывает на запись — определить kind и режим (A/B/C), применить
   порядок копания из `references/field-checklists.md`.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`;
условия работы, названные человеком, читаются до первого вопроса.

## Сводка состояния (без args)

1. Прочитать все 12 файлов поверхности.
2. Подсчитать `draft` / `stable` по каждому kind.
3. Прочитать свою ветку state (если есть), собрать открытые вопросы;
   `**blocker**` приоритетны.
4. Топ-3 кандидата: blocker-записи → записи с пустыми обязательными слотами
   → нарушения инвариантов канона (экран-сирота, фича без носителя, вход
   `widget` без виджета, фоновая задача без `fallback`, зеркало
   `widgets.actions`) → draft-записи, на которые ссылаются stable-соседи →
   дыры синтеза (ситуации interface без экрана/фичи) → kind'ы без единой
   записи в порядке inside-out.
5. Отдельной строкой — **линза платформы**: какие её разделы ещё не
   пройдены (по `_frame.md`), если поверхность молодая.
6. Сводка в чат (с человеческим «в работе»/«закрыто» рядом со статусами) +
   `AskUserQuestion`-выбор.

## Порядок проектирования — inside-out

`entities` → `screens` → `flows` → `features` → `shell` → `entry-points` →
`permissions` → `system-actions` → `widgets` → `background-tasks` →
`shared-api` → `shared-lib`. Не догма обхода, а приоритет при пустом слое:
сначала данные и экраны, потом действия и каркас, потом всё, что живёт вне
экранов, в конце — контракт и сквозное.

## Три режима

Детали и примеры вопросов — `references/workflow-patterns.md`; порядок
копания полей по kind — `references/field-checklists.md`.

- **A. Новая запись.** Args = `<kind>` или `<kind>:<новый-slug>`. Сначала —
  кандидат-источник из interface/доменов (ситуация → фича и экран, агрегат
  → сущность, шаг системного участника → фоновая задача, бизнес-средство
  «голос/виджет/уведомление» → системное действие/виджет/точка входа),
  затем батч `AskUserQuestion` по `Критерии <kind>`; опции — anti-patterns
  из `Что <kind> НЕ`.
- **B. Сырьё.** Args = свободный текст / приложение. Извлечь кандидатов,
  показать план по kind'ам, по подтверждению завести stub-строки,
  погрузиться через режим C. Извлечённое — кандидаты, не факты.
- **C. Углубление.** Args = `<kind>:<slug>` или выбор из сводки. Точечные
  вопросы по дырам и подозрениям; чек-лист `draft → stable` после каждой
  правки.

## Линза платформы

`references/platform-lens.md` — обход возможностей телефона **вопросами**:
что должно происходить, когда приложение закрыто; как пользователь попадает
внутрь извне; что ему удобно делать, не открывая приложение; что должно быть
видно «на лету»; что работает без сети; какие возможности устройства нужны.
Линза не придумывает ответы — она гарантирует, что аналитик **осознанно**
решил про каждый раздел (включая «не нужно»), и раскладывает ответы по
kind'ам. Запускается по `--lens`, из сводки или когда аналитик говорит «не
понимаю, что тут вообще возможно». Пройденные разделы отмечаются в
`_frame.md`.

Если ответ линзы выходит за слой (нужен сервис доставки пушей, облачное
распознавание речи, всплыло ограничение платформы или магазина, новая
ценность для пользователя) — это **продуктовый слой**: записать требование
в state и предложить `/project-deep-dive <project-slug>` (`integration` /
`constraint` / `capability`), своими руками туда не писать.

## Стиль вопросов

- Вопросы — через `AskUserQuestion`, до 4 в раунде (лимит инструмента).
- **Опции** — для anti-patterns (`Что <kind> НЕ`), тест-критерия (✅/❌),
  структурных перечислений канона (`entry`, словари `states`, `kind` точки
  входа и виджета, `mode`, `channels`, `trigger`, `timing`, `refresh`,
  `result`, `conditions`, `cache`, `platforms`, `shared`, `root`) и выбора
  существующего slug-соседа или источника (ситуация, агрегат, событие).
- **Свободная форма** (через Other) — для значений: `name`, `description`,
  `rationale`, `fallback`, `phrases`, `parameters`, `response`, `freshness`,
  `when`, тексты ошибок, сценарии данных.
- Продуктовые формулировки — фразы голосовых команд, тексты rationale,
  обещания свежести, названия экранов — приходят от аналитика: это его
  экспертиза (`CLAUDE.md` §3, «Мобильная»). Поэтому опциями идут
  anti-patterns и enum'ы, а сами формулировки скилл не подсказывает.
- Кандидатов предлагать **только из источника** (`situation.name`, имя
  агрегата, блок interface). Запись без источника — сначала спросить, вести
  ли аналитика в `/interface-deep-dive` / `/domain-deep-dive`.

## Идентификаторы: выводит скилл, не аналитик

Аналитик говорит именами (`.claude/rules/naming.md`):

- `slug` — из человекочитаемого `name` (транслит в kebab-case); при коллизии
  в файле — числовой суффикс;
- `key` экрана (PascalCase, англ., уникален в поверхности) — скилл
  предлагает из `name` смысловым английским корнем;
- push-категория (`pattern` у `kind: push`, UPPER_SNAKE, англ.) — из `name`
  точки входа.

Каждый идентификатор показывается **одной строкой для контроля** («завожу
экран как `TodoDetail`, ок?»), не как поле ввода. `key`, `slug` и
push-категория неизменяемы после заведения — их читает код-репо;
переименование — отдельный каскад через рефактор-режим оркестратора.

## Память: своя ветка единого дерева state

Скилл не держит своего `state/`. Заметки — в ветке
`../entrypoint/state/projects/<project-slug>/mobile/<surface>/<kind>/<slug>.md`
(для экрана slug заметки = `key`; для секционных `shell` / `shared-lib` —
имя секции). Рамка приложения и отметки линзы — `…/<surface>/_frame.md`.
Формат — канон `../entrypoint/references/state-model.md`: frontmatter
`kind` · `slug` · `ref`; секции `## Открытые вопросы` (опц. `**blocker**`),
`## Доменные решения` (сюда же — требования к соседним слоям: «нужен
`event:<ctx>.<Event>`», «нужна `integration` доставки пушей»), `## Что
копать дальше`; пусто → удалить файл; forward-only, не журнал.

Единый контекст: read-only видимость всего дерева `../entrypoint/state/`
(проектные ветки — только текущего `<project-slug>`) и клиентского дома
`../entrypoint-for-business/state/`; rw — только своя ветка
`projects/<project-slug>/mobile/<surface>/`. Маркер `**жду аналитика**` —
blocker-кандидат.

## Зеркало

`widgets.actions` — **производное** поле; канонический источник —
`system-actions.channels ∋ widget:<slug>`. После любой правки `channels`
системного действия — пересчитать `actions` затронутых виджетов
автоматически, без подтверждения (механический пересчёт, не смысловое
решение).

## Мосты к соседним слоям

- **interface той же поверхности** — источник ситуаций (`situation-ref`,
  `situation`). Скилл **не заводит ничего** в `interface/<surface>/`: при
  ссылке на несуществующую ситуацию — `AskUserQuestion`: запустить
  `/interface-deep-dive <project-slug> <surface> situation:<slug>` (запись
  остаётся `draft` с `**blocker**`) / заменить на существующую / убрать.
- **домены сервисов** — `entities.source` / `domain-ref`, `shared-api.владелец`,
  `trigger: event:<ctx>.<Event>` (push, фоновая задача, обновление виджета).
  Опции — из существующих агрегатов и событий; нужного нет — связь
  семантическая: имя пишется как есть, требование — в state + предложение
  `/domain-deep-dive <project-slug> <ctx>`. Приложение без бэкенда —
  `source: local`, `shared-api` пуст. Скилл **не пишет** в `services/`.
- **продуктовый слой** — внешние системы-посредники и ограничения платформы
  (см. «Линза платформы»): только предложение `/project-deep-dive`.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки:

1. Обязательные слоты заполнены (опциональные могут быть `—`).
2. Ссылки на источники валидны: ситуации — в `interface/<surface>/`;
   `source` / `domain-ref` / `event:` — в `services/*/domains/` (или
   зафиксированы требованием в state).
3. Внутрислойные ссылки валидны и держат инварианты канона: достижимость
   экрана, носитель у фичи, нет cross-feature, вход `widget` ↔ виджет,
   зеркало `widgets.actions`, `exact` ⇒ уведомление, `continuous` ⇒
   разрешение и видимость, покрытие `shared-api`.
4. Тест-критерий из формы kind'а подтверждён аналитиком в этой сессии.
5. В ветке state нет `**blocker**`-вопросов по записи.
6. Нет платформенной механики и кода в ячейках (интервалы, планировщики,
   имена API и файлов).

Все 6 ✅ → предложить «Готов к stable, повышаем?»; повышение — только по
подтверждению. Понижение `stable → draft` — только аналитик руками.
Stable-записи читает `/scaffold` форка `<org>/mobile`, поэтому незрелый
stable материализуется в код.

## Stub-записи

Ссылка на не существующий slug/key **той же поверхности** (фича → сущность,
системное действие → фича, виджет → точка входа, фоновая задача →
разрешение): завести stub-строку (`slug`/`key` + `name` + `description` +
`status=draft`, остальное `—`), заметку в state «заведён как stub в
контексте `<откуда>` — докопать», вернуться к исходной записи. Stub'ы в
слоях-источниках (ситуация, агрегат, событие) не заводятся — это работа их
deep-dive-скиллов; фиксируй blocker.

## Удаление записи (каскад)

1. Прочитать все 12 файлов поверхности + свою ветку state — найти ссылки на
   удаляемый slug/key (карта каскадов — `references/workflow-patterns.md`).
2. Показать каскад: «ссылаются X, Y — вот что сломается» (удаление экрана
   может осиротить фичу, точку входа и системное действие `opens-app`;
   удаление виджета — точку входа `widget` и каналы `widget:<slug>`).
3. `AskUserQuestion` по каждому месту: заменить / `—` / удалить ссылающуюся
   запись.
4. По подтверждению — все правки одним пакетом, запись удалить, заметку
   state удалить, зеркало `widgets.actions` пересчитать.

## Завершение сессии

1. Перечислить затронутые записи (заведены / углублены / удалены /
   повышены в stable).
2. Перечислить нерешённые открытые вопросы и накопленные требования к
   соседним слоям (interface, домены, продуктовый слой).
3. Предложить: «Прогнать `/mobile-audit <project-slug> <surface>`?» — по
   «да» сказать «Запусти `/mobile-audit …`», сам не вызываю.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`:
итог сессии, ходы дальше и строка «как продолжить» идут по нему.

## Границы

- Платформенная механика и код в карту не пишутся: интервалы и расписания
  в минутах, планировщики, имена API, Kotlin/Swift-файлов, Gradle-модулей,
  SwiftPM-таргетов, библиотек — это `docs/stack/` и `/scaffold` форка
  `<org>/mobile`.
- Карта не обещает невозможного для платформы — точного времени
  исполнения кода в фоне, гарантированной доставки и свежести: требование
  формулируется смыслом, отказ описывает `fallback`.
- Постоянное прослушивание микрофона как «голосовой ввод» заводится только
  фоновой задачей `continuous` с разрешением и явным решением владельца.
- Структурные идентификаторы канона (имена файлов и колонок,
  enum-значения, словари состояний) не переименовываются — это
  handoff-контракт с `<org>/mobile`.
- Облик (цвет, типографика, отступы, раскладка виджета) в карту не
  пишется: значения темы — токены дизайн-системы продукта
  (`docs/projects/<project-slug>/design/system.tokens.json`, слой дизайна),
  применяет их код-репо `<org>/mobile`; облик скилл не выдумывает, а
  оболочка держит только политику темы.
- Ссылка из одной поверхности в сущность другой не заводится; общее
  сводит `/cross-audit`.
- В web скилл выходит только по явной просьбе аналитика.

Итог ключевого: записи и формулировки приходят из источника и от
аналитика, в stable запись поднимается только по его подтверждению; в
interface, services и продуктовый слой скилл не пишет, а другие скиллы,
включая аудит, не запускает — только предлагает.
