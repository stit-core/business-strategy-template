# entrypoint

**Единая точка входа аналитика** во всю систему проектирования. Не новый
слой и не новый артефакт — **оркестратор-фасад** над существующими
скиллами-исполнителями. Аналитик приходит сюда «не думая, в какой слой»:
приносит сырьё или намерение, оркестратор классифицирует, предлагает
маршрут и по подтверждению делегирует исполнителю.

Слои под фасадом (сверху вниз):

| слой | исполнители |
|---|---|
| `docs/business/` (профиль + реестр проблем + стейкхолдеры) | `/business-deep-dive` |
| `docs/ajtbd/` (сегменты + граф работ) | `/segment-deep-dive` · `/job-graph-deep-dive` · `/jtbd-interview` |
| `docs/swot/` (LinkedSWOT) | `/swot-deep-dive` |
| `docs/hypothesis-map/` (Карта гипотез) | `/hypothesis-map-deep-dive` |
| `docs/projects/<slug>/` (продукт: vision, роли, хребет `surface` с родом, объекты и действия, `capability/<surface>`) | `/project-deep-dive <slug>` |
| `docs/projects/<slug>/` — файлы уровня продукта: факты, голос, слова клиента (`…/facts*.yaml`, `…/voice*.yaml`, `…/voc.yaml`) | `/design-deep-dive <slug>` |
| `docs/projects/<slug>/site/<surface>/` (слой страницы: `web` рода `landing` · `site`) | `/design-deep-dive <slug> [<surface>]` |
| `docs/projects/<slug>/interface/<surface>/` | `/interface-deep-dive <slug> [<surface>]` |
| `docs/projects/<slug>/services/` (сервисная топология) | `/service-deep-dive <slug>` |
| `docs/projects/<slug>/services/<svc>/domains/<ctx>/` (по bounded-context) | `/domain-deep-dive <slug> <ctx>` |
| `docs/projects/infrastructure/` (ИТ-периметр бизнеса) | `/infrastructure-deep-dive` |
| `docs/projects/<slug>/screens/<surface>/` | `/screen-deep-dive <slug> [<surface>]` |
| `docs/projects/<slug>/fsd/<surface>/` (фронтовые поверхности, мост к коду фронта) | `/fsd-deep-dive <slug> [<surface>]` |
| `docs/projects/<slug>/telegram-bot-flow/<surface>/` (bot-поверхности) | `/telegram-bot-flow-deep-dive <slug> [<surface>]` |
| `docs/projects/<slug>/mobile/<surface>/` (мобильные поверхности, карта приложения и мост к его коду) | `/mobile-deep-dive <slug> [<surface>]` |
| `docs/projects/<slug>/design/` (облик продукта; `design/<surface>/` — поверхность) | `/design-deep-dive <slug> [<surface>]` |
| `docs/projects/project-map.md` (межпроектные стыки) | `/project-deep-dive <slug>` (авторская сторона — `integration` инициатора) |
| аудиты | `/swot-audit` · `/hypothesis-map-audit` · `/ajtbd-audit` · `/project-audit <slug>` · `/interface-audit <slug>` · `/screen-audit <slug>` · `/fsd-audit <slug>` · `/telegram-bot-flow-audit <slug>` · `/mobile-audit <slug>` · `/design-audit <slug>` · `/service-audit <slug>` · `/infrastructure-audit` · `/cross-audit` |

Поверхность (`surface`) — ось продукта: реестр-хребет `surface.md`
партиционирует возможности (`capability/<surface>`), интерфейс
(`interface/<surface>/`) и композицию — экраны (`screens/<surface>/`), слой
страницы (`site/<surface>/` у `web` рода `landing` и `site`) либо
диалоги бота (`telegram-bot-flow/<surface>/` при `type: bot`), либо карту
мобильного приложения (`mobile/<surface>/` при `type: mobile`) — по своим
slug'ам; фронтовые поверхности кабинета несут ещё FSD-карту
(`fsd/<surface>/`), поверхности маршрута дизайна — облик
(`design/<surface>/`). Маршрут поверхности выбирают её `type` и род
`web-kind` (`references/routing.md`, «Маршрут по роду поверхности»). Скиллы
`interface`/`screen`/`fsd`/`telegram-bot-flow`/`mobile`/`design` берут поверхность
**вторым аргументом** `[<surface>]` — без него `interface` … `mobile`
предлагают пикер поверхностей по `surface.name`, а `design-deep-dive` ведёт
уровень продукта: факты, голос, бренд, дизайн-систему, бриф на вид.

Полная таблица «сигнал → слой → kind → исполнитель → режим» —
`references/routing.md`.

## Фасад: кто кого активирует

Это **единственный** скилл, которому **разрешено активировать другие**.
Исполнители (`*-deep-dive`/`*-audit`) друг друга не зовут — это разные
точки входа, каждый держится своего слоя. Оркестратор же по подтверждению
аналитика **сам запускает** нужного исполнителя для подтверждённого чанка,
затем возвращается, чтобы продолжить маршрутизацию оставшегося.

Прямой вызов исполнителя из чата допустим — оркестратор рекомендуемый, но
не единственный вход. Когда аналитик уже знает слой и сущность, короче зайти
прямо в `/swot-deep-dive` и т.п.

## Пять режимов (намерений)

Оркестратор работает в одном из пяти намерений; режим определяет, **как**
он маршрутизирует (см. `references/routing.md`):

| режим | что значит | куда ведёт |
|---|---|---|
| `наполнить` | новые/частичные сущности из сырья или с нуля | `*-deep-dive` (режим A/B исполнителя) |
| `актуализировать` | сверить накопленное с новым сырьём, обновить | `*-deep-dive` (режим B/C) |
| `рефакторить` | переименования/переносы/слияния slug с каскадом | `*-deep-dive` (каскад-правка) |
| `чистить` | удаления с показом каскада ссылок | `*-deep-dive` (каскад-удаление) |
| `аудитить` | запустить нужный аудит-рой | `*-audit` / `/cross-audit` |

Режим распознаётся из намерения аналитика (или спрашивается через
`AskUserQuestion`, если неоднозначно). Один заход может смешивать режимы
по разным чанкам сырья — оркестратор разводит их в маршруте.

## Точки входа

| вызов | поведение |
|---|---|
| `/entrypoint` | сводка «где мы во всём воркфлоу» (срез по слоям) + `AskUserQuestion` с выбором хода |
| `/entrypoint <свободный текст / транскрипт / ссылка / путь>` | сырьё → конвейер intake (`references/intake.md`) |
| `/entrypoint --mode <name>` | принудительно работать в указанном режиме |
| `/entrypoint --audit [<scope>]` | режим `аудитить`: предложить нужный аудит-рой по `scope` или по всем затронутым слоям |
| `/entrypoint --upstream [<slug>]` | восходящий поток `project → business`: сверить дозревший продукт с верхним слоем (`references/lifecycle-upstream.md`) |

`mode` ∈ {`наполнить`, `актуализировать`, `рефакторить`, `чистить`,
`аудитить`}.

## Что делать сразу при запуске

1. Прочитать `references/routing.md` — таблицу маршрутизации по слоям ×
   режимам.
2. Прочитать `references/state-model.md` — формат единого state.
3. Прочитать единое дерево `state/` (если есть) — свой срез `index.md` +
   `threads/` и read-only ветки исполнителей; плюс клиентский дом
   `../entrypoint-for-business/state/` (см. `references/cross-read.md`) —
   собрать срез по слоям и открытые нити, особенно `**жду аналитика**` от
   клиента.
   Там же — условия работы человека: что он просил о способе работы и что
   отдал исполнителю (`references/state-model.md § Условия работы`); они
   читаются до сводки, отданное не переспрашивается.
4. Если args = сырьё (текст/транскрипт/ссылка/путь) → конвейер intake
   (`references/intake.md`).
5. Если args пустые → **сводка «где мы»** (см. ниже) + `AskUserQuestion`.
6. Если `--mode` / `--audit` / `--upstream` — открыть соответствующий
   маршрут.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`:
сводка, каждый переход и завершение сессии идут по нему.

## Сводка «где мы во всём воркфлоу» (без args)

Оркестратор даёт аналитику **карту по всем слоям сразу** — чего нет у
отдельного исполнителя (тот видит только свой слой). Источник — индекс
state (`references/state-model.md`) + быстрый проход по `docs/`.

1. Прочитать `state/index.md` (если есть) — срез по слоям/проектам.
2. Для слоёв, по которым индекс устарел или пуст, — короткий проход по
   `docs/` (счётчики draft/stable, текущая фаза по дереву каждого слоя,
   как это делает соответствующий исполнитель). У слоя страницы и дизайна
   «закрыто» — статус в самом машинном файле, этапы считаются по статусам
   файлов, как в сводке исполнителя
   (`.claude/skills/design-deep-dive/references/phases.md § Сводка этапов`).
3. Собрать открытые нити (`state/threads/`) и `**жду аналитика**` из
   клиентского state, а из передачи клиентской ветки — решения заказчика,
   которые ещё не перенесены в файлы.
4. Вывести срез словами (`.claude/rules/guiding.md` §2, §4): слой, этап и
   статус названы по-человечески, идентификатор — в скобках, место работы
   отмечено «вы здесь», последняя строка говорит, чем путь кончается.
   Пример — иллюстрация формы, а не данные проекта:

   ```
   Где мы — вся работа, от бизнеса до макета:

   Бизнес                          профиль закрыт · проблем 5: закрыты 4, в работе 1
   Клиенты и их работы (AJTBD)     3 группы клиентов закрыты · граф работ собран у 2 из 3
   Стороны и ставки (SWOT)         факторы по 4 проблемам · 1 проблема без ставок
   Цель и число (Карта гипотез)    показатели по 3 проблемам · 1 цель без показателя
   Продукт «Клиника удержания» (clinic)
     зачем и для кого              закрыто (vision — stable) · стадия: первая версия (mvp)
     поверхности   ← вы здесь      кабинет, бот и лендинг «Промо» (web, bot, promo)
     что продукт умеет             кабинет: 3 возможности закрыты · бот: 1 в работе (draft)
     как им пользуются             кабинет: участники и ситуации есть, разделов навигации нет · бот: не начато
     экраны                        не начаты
     сайт «Промо»                  задание на страницу ✓ · факты: 12 ✓, 2 пробела · планы страниц 1 из 2 · тексты — черновик
     облик                         дизайн-система утверждена · макет «Промо»: принято 0 из 2 страниц · к сборке не готово
     долг                          сайт «Промо»: Карта гипотез пропущена — показатель назван словом заказчика
     условия работы                тексты страницы — на исполнителе · картинки — до 3 000 ₽ за круг без вопроса
     стыки с соседями              баллы лояльности уходят в интернет-магазин (loyalty-sync → web-store)
   Продукт «Интейк-форма» (intake)   зачем и для кого — в работе (vision — draft)
   Открытые нити: 1 (разбор транскрипта созвона)
   От клиента ждёт аналитика: 2 вопроса (о показателях)
   Решения заказчика к переносу: 1 (выбран вариант вида лендинга «Промо»)
   Финал: продукт спроектирован — у каждой поверхности закрыто то, по чему пишут код, и проверки чистые
   ```

   Поверхности идут **перед** возможностями: реестр-хребет `surface.md`
   называет поверхности, а возможности, interface, экраны, слой страницы и
   холст даются по поверхности; уровень продукта в дизайне (факты, голос,
   бренд, ДС) — строкой «облик». Долг заметок пропусков и условия работы,
   названные человеком, — отдельными строками: они не блокируют, но должны
   быть видны. Межпроектные стыки — отдельной строкой (сводятся в
   `project-map`).

   Проекты в сводке и пикерах называются **по-человечески** (имя из
   `vision`); slug — деталь в скобках, аналитик его не вводит (см.
   `.claude/rules/naming.md`). Слой и статус называются словами, флаг и
   идентификатор — в скобках и только там, где они человеку пригодятся
   (`.claude/rules/guiding.md` §4).

5. Через `AskUserQuestion` предложить ходы по месту — до четырёх из
   списка, по срезу; один рекомендован, у каждого — что он даст и чего
   стоит (`.claude/rules/guiding.md` §5):
   - начать сверху: бизнес, клиенты, цель;
   - начать с продукта или сайта — быстрый путь
     (`references/routing.md § Быстрый путь и вход с середины`);
   - продолжить, где остановились: открытая нить или слой в работе;
   - улучшить сделанное: вернуться и перебрать;
   - проверить: аудит затронутого слоя.

   Новое сырьё человек приносит свободным ответом — оно уходит в intake.

## Приём сырья (intake)

Главная сила оркестратора — **принять много и разнородного** и не
потерять. Полный конвейер — `references/intake.md`. Кратко:

1. **ingest** — забрать содержимое: `Read` файлов, `WebFetch` ссылок,
   вставленный текст как есть.
2. **сегментация** — разбить на тематические чанки (3-часовой транскрипт
   обычно покрывает несколько слоёв сразу).
3. **классификация** — каждый чанк → слой + kind по `references/routing.md`;
   неоднозначное помечается под вопрос.
4. **предложение маршрута** — для каждого чанка: исполнитель + сущность +
   режим, батчем `AskUserQuestion`.
5. **делегирование** — по подтверждению активировать исполнителя; нить
   маршрута записать в `state/threads/`.

Оркестратор **не выдумывает доменный текст** — извлекает кандидатов и
маршрутизирует; формулировки добивает исполнитель через свой
`AskUserQuestion` (экспертиза священна, `CLAUDE.md` §3).

## Делегирование исполнителю (контракт)

Подтверждён маршрут → оркестратор:

1. Записывает строку маршрута в открытую нить `state/threads/<slug>.md`
   (чанк → слой/kind/исполнитель → ждёт).
2. **Активирует исполнителя** с нужными аргументами (для проектных
   слоёв — первым аргументом `<project-slug>`; для `interface`/`screens`/
   `fsd`/`telegram-bot-flow`/`mobile` — вторым аргументом `[<surface>]`, без
   него исполнитель сам предложит пикер поверхностей по `surface.name`;
   для слоя страницы и дизайна — `<project-slug>` первым, `[<surface>]`
   вторым, без поверхности — уровень продукта (факты, голос, бренд, ДС,
   бриф на вид); для `services` — без доп. аргументов или `<service-slug>`; для
   `domains` — `<ctx>` (сервис выводится); для `infrastructure` — без
   аргументов; сырьё передаёт чанком). Этап оркестратор не выбирает: первый
   этап с готовым входом находит исполнитель.
3. Исполнитель ведёт свой слой по своим фазам и пишет per-kind заметку в
   **свою ветку** общего дерева (`state/<слой>/...`) — оркестратор её не
   дублирует.
4. По возвращении оркестратор убирает закрытый чанк из нити и предлагает
   следующий (оставшиеся чанки / следующий слой / аудит).

Оркестратор **держит маршрут и срез**, исполнитель — **детальную
проработку**. Граница: всё, что про конкретный kind (критерии,
anti-patterns, draft→stable, каскады внутри слоя) — у исполнителя.

## Единый state

Весь аналитический state — **одно дерево** `entrypoint/state/`; и
оркестратор, и исполнители пишут сюда (своего `state/` исполнители не
держат). Полный формат и раскладка веток — `references/state-model.md`.
Кратко:

```
.claude/skills/entrypoint/state/
├── index.md                 ← оркестратор: срез по слоям/проектам
├── threads/<slug>.md        ← оркестратор: открытая нить (маршрут)
├── _conditions.md           ← общая заметка: условия работы, названные человеком
├── business/ · ajtbd/ · swot/ · hypothesis-map/   ← исполнители верхних слоёв
├── infrastructure/                                 ← infrastructure-deep-dive
└── projects/<slug>/                                ← проектные исполнители
    ├── _conditions.md                              ← общая заметка: условия работы над продуктом
    ├── project/ (vision + плоские kind + capability/<surface>/)
    ├── interface/<surface>/ · screens/<surface>/ · fsd/<surface>/ · telegram-bot-flow/<surface>/ · mobile/<surface>/ ← по поверхности
    ├── site/ · design/                             ← design-deep-dive: слой страницы с фактами и голосом продукта; слой дизайна
    ├── services/                                   ← service-deep-dive (топология)
    └── domains/<context>/                          ← по bounded-context (ключ — контекст, не сервис)
```

- Оркестратор владеет `index.md` (карта «где мы») + `threads/` и **не
  дублирует** per-kind содержимое веток.
- Исполнители владеют своими слоевыми ветками (per-kind заметки).
- Условия работы, названные человеком, — общая заметка: её пишет тот, кому
  условие названо, читает каждый вход
  (`references/state-model.md § Условия работы`).
- `state/` создаётся **по требованию** (когда есть что записать), не
  заранее. Forward-only, без истории.

## Перекрёстная видимость (read-only)

Правила — `references/cross-read.md`. Оркестратор read-only видит **всё**
дерево: ветки всех исполнителей и клиентский дом
(`../entrypoint-for-business/state/`). Аналитику anti-leak не ограничивает
— он видит сырое; правило одно: пишет только в `index.md` + `threads/`, в
чужие ветки и клиентский дом — **не пишет**.
Оговорка одна — общая заметка условий работы: её пишет тот, кому человек
назвал условие, оркестратор в том числе.

Маркеры `**жду аналитика**` из клиентского state — это входящая очередь
аналитика: оркестратор поднимает их в сводке и предлагает разобрать.
Ответ уходит в `main` (правка артефактов/своего state); клиент подхватит
его при следующем rebase своей ветки `client`.

Решения заказчика — выбор варианта внешнего вида, утверждения задания на
страницу, списка картинок и видео, набора цветов и шрифтов, текстов,
макета, разрешение проверять макет — приходят разделом «Решения
заказчика» передачи клиентской ветки
(`../entrypoint-for-business/references/escalation.md`). Это тоже входящая
очередь: оркестратор поднимает их в сводке и передаёт исполнителю сырьём —
облик, картинки, тексты страницы, задание и макет —
`/design-deep-dive <slug> <surface>`, тексты кабинета —
`/screen-deep-dive <slug> <surface>`; в файл решение переносит исполнитель
по версии, которую видел заказчик.

## Восходящий поток (reconcile-up)

Триггер — переход `vision.lifecycle → stable` (или ручной `--upstream
<slug>`): дозревший продукт меняет реальность бизнеса. Оркестратор ведёт
сверку **сам**, но **пишет через делегирование** — четыре шага, каждый
через `AskUserQuestion`, без авто-записи:

1. **продукт как офер** → `business/offering` с `from-project` (через
   `/business-deep-dive`);
2. **профиль** → правка `profile.md`, если продукт сдвинул «как
   зарабатывает / кого обслуживает» (через `/business-deep-dive`);
3. **метрики** → новые baseline в `business/current-metric` с
   `from-project` (через `/business-deep-dive`);
4. **проспективное → обслуживаемое** → повысить `served` у связанных
   `ajtbd/segment` (через `/segment-deep-dive`) и
   `business/business-problem` (через `/business-deep-dive`), проставив
   `from-project`.

Провенанс-поля `*.from-project` делают контур наблюдаемым; обратную
сторону (что породил каждый продукт, замкнут ли контур) сводит
`/cross-audit` (угол `provenance-upstream`). Контур **процессный** — не
ломает «downstream read-only» для форков-соседей. Полная процедура —
`references/lifecycle-upstream.md`.

## Завершение сессии

1. Сказать, что сделано, — результатом: что появилось или изменилось в
   каждом затронутом слое и что это дало; сущности и исполнители — деталью
   (`.claude/rules/guiding.md` §1).
2. Перечислить открытые нити и нерешённые `**blocker**`/`**жду
   аналитика**`.
3. Показать карту пути с меткой «вы здесь» и назвать ходы дальше — два-три,
   один рекомендован (`.claude/rules/guiding.md` §2, §5). Продукт
   спроектирован — у каждой поверхности закрыто то, что читает её код-репо,
   по роду поверхности, и аудиты чистые — рекомендованный ход уже вне этого
   репо: реализация из корня проекта — `/init-project` в хабе `<org>/infra`
   читает strategy и проектирует инфру (`references/routing.md` § «Продукт
   спроектирован»).
4. Через `AskUserQuestion` предложить эти ходы: продолжить нить / войти в
   другой слой, где вход готов / вернуться к сделанному / прогнать нужный
   аудит (`/swot-audit`,
   `/hypothesis-map-audit`, `/ajtbd-audit`, `/project-audit <slug>`,
   `/interface-audit <slug>`, `/screen-audit <slug>`, `/fsd-audit <slug>`,
   `/telegram-bot-flow-audit <slug>`, `/mobile-audit <slug>`,
   `/design-audit <slug>`, `/service-audit <slug>`, `/infrastructure-audit`,
   `/cross-audit`).
5. Сказать, как продолжить: «в новой сессии — `/entrypoint`: карта
   поднимется из файлов». То, что должно пережить сессию и не лежит в
   артефактах, — в нить или заметку state, а не в отдельный промпт
   (`.claude/rules/guiding.md` §2).

## Границы

- Не редактировать артефакты слоёв напрямую в обход исполнителя — правки
  каждого слоя идут через его `*-deep-dive`. Оркестратор маршрутизирует,
  не пишет в `docs/` сам.
- Не выдумывать доменные/методологические формулировки — это экспертиза,
  её добивает исполнитель через `AskUserQuestion` (`CLAUDE.md` §3).
- Не дублировать per-kind детали в `index.md`/`threads/` — только срез и
  маршрут (детали — в ветках исполнителей).
- Не писать в чужие ветки дерева и в клиентский дом
  (`../entrypoint-for-business/state/`) — только read-only.
- Не аккумулировать историю в `state/` — forward-only (закрытое
  удаляется).
- Не пушить и не коммитить. Коммит/push — решение аналитика (`CLAUDE.md` §5).
- В восходящем потоке (`reconcile-up`) не писать в `docs/` напрямую —
  каждое изменение наверху уезжает через `/business-deep-dive` или
  `/segment-deep-dive`, всё через `AskUserQuestion`, без авто-записи.
