# project-deep-dive

Проектирование продуктового слоя **одного проекта** в `docs/projects/<project-slug>/` — от vision до возможностей по
поверхностям. Канон формы — `docs/projects/_template/project/README.md` (форма живёт один раз в `_template/`, данные
каждого проекта — в его папке). Скилл ведёт аналитика по девяти фазам структурированными вопросами (`AskUserQuestion`),
держит контекст в своей ветке единого state оркестратора (`../entrypoint/state/projects/<project-slug>/project/`), домен
не выдумывает, маркетинговую копию и облик не пишет.

Продукт описывается до экранов: экраны строятся от объектов и сценариев, а не от списка функций (ux 13/04 §1). Поэтому
роли и постуры идут до поверхностей, объекты и действия — до возможностей, а сценарии хабов, которые пишет
`/interface-deep-dive`, — до экранов.

**Поверхность (surface) — ось продукта.** Реестр-хребет `surface.md` объявляет поверхности, а их `type` и род `web-kind`
решают, какие слои поверхность получит: файл возможностей `capability/<surface>.md`, interface, экраны и FSD-карта у
кабинета; слой страницы у сайта и лендинга; карта приложения у мобильного; диалоги у бота. Возможности живут в папке
возможностей, по файлу `capability/<surface>.md` на поверхность; остальные kind — плоские таблицы в корне папки продукта.

Скилл — **единственная точка входа** аналитика в продуктовый слой: заведение проекта и записей, углубление, разбор
сырья, навигация по фазам, приведение к канону, переход `draft → stable`, удаление с каскадом, research рынка и
регуляторики роем агентов.

## Мультипроект: выбор контекста

Шаблон держит **несколько проектов** под одним бизнесом, каждый — папка `docs/projects/<project-slug>/`
(`docs/projects/README.md`). Все чтения и записи скилла скоупятся в один выбранный проект.

- `/project-deep-dive <project-slug> …` — первый аргумент задаёт проект; остальные — kind, slug, сырьё, флаги.
- Без `<project-slug>` — пикер `AskUserQuestion` по существующим проектам, **исключая `_template` и `infrastructure`** (образец формы и ИТ-периметр, не
  проекты). Опции — человекочитаемые имена проектов (заголовок из vision; slug — деталью) + «Завести новый проект»; slug
  аналитик не вводит (`.claude/rules/naming.md`).
- Переданного slug нет среди папок — переспросить: «Проекта `<slug>` нет. Завести новый или выбрать из существующих?».

Выбранный `<project-slug>` фиксируется на сессию и подставляется во все пути: `docs/projects/<project-slug>/vision.md`,
`…/surface.md`, `…/user.md`, `…/object.md`, `…/capability/<surface>.md` … и в ветку state
`../entrypoint/state/projects/<project-slug>/project/`.

### Заведение нового проекта

Новый проект — **копия формы** `docs/projects/_template/project/` в новую папку `docs/projects/<new-slug>/`; каталоги
руками не плодят, скаффолдит скилл:

1. Спросить человекочитаемое имя продукта; `slug` вывести из имени (транслит в kebab-case, при коллизии — суффикс) и
   показать одной строкой для контроля.
2. Скопировать из формы: `vision.md` (singleton), реестр `surface.md` и семь плоских таблиц — `user.md`, `object.md`,
   `action.md`, `integration.md`, `boundary.md`, `constraint.md`, `market.md`. Возможности живут не плоским файлом, а
   папкой: файл `capability/<surface>.md` заводится из формы `capability.md` позже, в фазе `capability`, когда реестр
   уже знает поверхность. README-канон в папку проекта не копируется (`CLAUDE.md` §6).
3. Войти в фазу `discovery` на свежем `vision.md`.

Соседние слои — `interface/`, `screens/`, `fsd/`, `site/`, `design/`, `telegram-bot-flow/`, `mobile/` — заводят их
скиллы при первом заходе на поверхность; `services/` — `/service-deep-dive`, домены — `/domain-deep-dive`; этот скилл
их не создаёт. Файлы уровня продукта — факты и голос
(`<slug>/facts.yaml`, `<slug>/voice.yaml`, `<slug>/voice.product.yaml`) — ведёт `/design-deep-dive <slug>`.

## Вышестоящий вход (реестр проблем, SWOT, Карта гипотез)

Продукт — не корень всего, а решение под уже формализованную проблему бизнеса. Над папками проектов лежат общие верхние
слои: `docs/business/` (профиль и реестр проблем `business-problem.md`), `docs/swot/`, `docs/hypothesis-map/`,
`docs/ajtbd/`. Якоря продукта приходят оттуда (связь семантическая, не slug):

- `Problem` vision ← `business/business-problem.md` и `hypothesis-map/goal.md`;
- `Success` vision ← `hypothesis-map/metric.md` — целевые метрики: совместный best-effort таргет, **не** гарантия; не
  копировать как обещание;
- `user` ← `hypothesis-map/subject.md` (субъект влияния) и `ajtbd/segment.md` (сегмент по работам);
- `capability` реализует `swot/bet.md` и `hypothesis-map/goal.md`; авторская трасса вверх — колонка `trace` возможности
  (`job:<slug>` → `ajtbd/job.md`, `hypothesis:<slug>` → `hypothesis-map/hypothesis.md`) — ведётся здесь, на стороне
  продукта.

Слои есть — в фазе `discovery` скилл сначала читает реестр проблем, цели и метрики и предлагает опереть vision на них;
их нет — работа идёт как обычно. Несостыковки ловит `/cross-audit`.

### `addresses-problem` — какие проблемы закрывает продукт

`docs/business/business-problem.md` — реестр проблем, общий для всех проектов. Проект объявляет, какие проблемы
закрывает, полем `addresses-problem` в своём vision (M:N: проблему бьют несколько проектов, проект — несколько проблем).
Авторская сторона связи — здесь, обратную сводит `/cross-audit`. Привязку даёт аналитик: скилл показывает строки реестра
опциями и проблем не придумывает (`references/phases.md`, фаза 1). Без привязки продукт висит в воздухе, а `Success` не
во что целить.

## Точки входа

Первый позиционный аргумент — **всегда `<project-slug>`**; дальше — kind, slug, сырьё, флаги.

| вызов | поведение |
|---|---|
| `/project-deep-dive` | пикер проекта → сводка по фазам |
| `/project-deep-dive <slug>` | `<slug>` — папка проекта: сводка по фазам; иначе — пикер с предложением завести новый |
| `/project-deep-dive <project-slug> <kind>` | завести новую запись kind (режим A) |
| `/project-deep-dive <project-slug> <kind>:<entity-slug>` | углубить существующую запись (режим C) |
| `/project-deep-dive <project-slug> capability:<surface>:<entity-slug>` | возможность в файле поверхности `<surface>` (режим A или C) |
| `/project-deep-dive <project-slug> <entity-slug>` | найти запись; одна — режим C; совпала в нескольких kind — переспросить |
| `/project-deep-dive <project-slug> <свободный текст / транскрипт>` | сырьё → разбор (режим B) |
| `/project-deep-dive <project-slug> --phase <name>` | работать в указанной фазе |
| `/project-deep-dive <project-slug> --research <kind>:<query>` | рой агентов на тему |
| `/project-deep-dive --new` | завести новый проект из формы (спросит имя, slug выведет сам) |

`kind` ∈ {`vision`, `surface`, `user`, `object`, `action`, `capability`, `integration`, `boundary`, `constraint`,
`market`}. `vision` — singleton; `surface` — реестр-хребет; остальные семь — плоские кросс-поверхностные таблицы в корне
папки продукта (постура — вторая таблица `user.md`, атрибуты и представления — таблицы `object.md`); `capability` — **папка**,
файл на поверхность: без явного `<surface>` скилл показывает пикер по реестру `surface.md`.

`phase` ∈ {`discovery`, `user`, `surface`, `objects`, `capability`, `integration`, `constraint`, `market`, `cohesion`}.
Порядок не случаен: роли и постуры — до поверхностей, поверхности — до возможностей (хребет вперёд), объекты и действия
— до возможностей (ядро возможности ссылается на них).

`kind:slug` — ускоритель: заход без аргументов с пикером по именам есть всегда.

## Что делать сразу при запуске

1. **Проект.** Разобрать первый аргумент как `<project-slug>`; не задан или не совпал с папкой — пикер по именам
   (исключая `_template` и `infrastructure`) + «Завести новый»; после пикера остальные аргументы применяются к выбранному проекту.
   Зафиксировать проект на сессию.
2. Прочитать `docs/projects/_template/project/README.md` — канон слоя: состав, порядок этапов, файлы уровня продукта,
   связи.
3. Прочитать `references/phases.md` — карту девяти фаз и то, какие фазы нужны продукту по его поверхностям.
4. **Сверить проект с каноном:** файлы слоя, колонки таблиц и их порядок, разделы vision, таблицы «Постура», «Атрибуты»,
   разделы «Паспорта» и «Урезание». Расхождений много — первым пунктом сводки предложить пакет «Привести к канону»
   (`references/workflow-patterns.md § Привести к канону`).
5. Нет аргументов после `<project-slug>` — **сводка по фазам** (ниже) и выбор через `AskUserQuestion`: продолжить
   текущую фазу, перепрыгнуть, разобрать сырьё, запустить research.
6. Аргументы указывают на запись — определить kind и режим (A, B, C) и идти по `references/workflow-patterns.md`.
7. `--research` — `references/research-rays.md`; `--phase` — карта фазы из `references/phases.md`.
8. `--new` или «Завести новый» — заведение проекта, затем фаза `discovery`.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`; условия работы, названные человеком, читаются
до первого вопроса.

## Сводка состояния

Скилл всегда показывает аналитику **карту, где он в маршруте**, а не просто список черновиков.

1. Прочитать vision, реестр поверхностей, семь плоских таблиц и все файлы возможностей `capability/<surface>.md`.
2. Посчитать `draft` и `stable` по каждому kind; у vision — набор разделов (полный или минимум) и заполненные разделы; у
   пользователей — строки постуры; у возможностей — **по поверхностям**: у каких поверхностей реестра есть файл и
   сколько в нём записей, у каких хабов и критичных нет паспорта.
3. Прочитать свою ветку `../entrypoint/state/projects/<project-slug>/project/` (rw), заметку пропусков
   `…/project/_phase-jump.md` и read-only — остальное дерево state и клиентский дом (раздел «Единый контекст»): открытые
   вопросы, особенно `**blocker**`, и долг.
4. Определить **текущую фазу** — первую с незакрытым выходом:
   - vision нет или его разделы этапа vision не заполнены → `discovery`;
   - `user.md` пуст или у пользователя поверхности маршрута приложения нет строки постуры → `user`;
   - реестр поверхностей пуст или у `web` не назван род → `surface`;
   - у продукта с интерактивной поверхностью — кабинетом, мобильным приложением, ботом — пусты `object.md` и `action.md`
     или возможности держат `object`, `action` = `—` → `objects`;
   - у поверхности маршрута нет непустого `capability/<surface>.md` → `capability` (**не стартует без `surface`**: нет
     поверхностей — некуда партиционировать возможности);
   - пусты `integration`, `constraint`, `market` → соответствующая фаза;
   - всё заведено, но есть черновики, blocker'ы, не добиты `MVP` и сводки vision → `cohesion`.

   Фазы, которые продукту не нужны (у продукта только из сайтов и лендингов — `objects` и `capability`), показываются
   «не нужна» с причиной, пока аналитик не захочет их вести.
5. Вывести сводку (пример — иллюстрация формы):

   ```
   Проект: <project-slug> · набор vision: полный
   Текущая фаза: objects (4/9)
   docs/projects/<project-slug>/:
     vision         [draft]  разделы 10 из 12 (MVP и сводки — в cohesion); addresses-problem: 1
     user           3 stable, 1 draft; постура: 3 из 4
     surface        2 (web-partner · web, app; tg-bot · bot)
     object         2 draft · action 1 draft
     capability/
       web-partner  2 draft (object и action = —); хаб без паспорта: 1
       tg-bot       — (файла ещё нет)
     integration    —
     constraint     —
     market         —
     boundary       1 stable
   Открытых blocker-вопросов: 2 · Долг: возможности заведены до объектов
   Готов клиент-черновик в ветке: client  (если есть)
   ```

6. Через `AskUserQuestion` (до четырёх опций): продолжить текущую фазу — что копать первым; перепрыгнуть в другую (скилл
   назовёт цену пропуска и запишет долг); разобрать сырьё; запустить research.

## Фазы проработки

Скилл ведёт по девяти фазам; полная карта, переходы и то, какие фазы нужны продукту, — `references/phases.md`.

| фаза | цель | выход |
|---|---|---|
| `discovery` | vision своего набора: проблема, пользователи, позиционирование, принципы опыта, голос, успех, устройства и доступность, ограничения, non-goals, допущения | `vision.md` |
| `user` — роли и постуры | адресаты продукта и то, как каждый живёт в продукте | `user.md` + таблица «Постура» |
| `surface` — поверхности и их род | где продукт встречает пользователя; `type`, род `web-kind`, разделение приложений | `surface.md` |
| `objects` — объекты и действия | язык продукта: глоссарий объектов с атрибутами, словарь действий | `object.md`, `action.md` |
| `capability` — возможности | что продукт умеет **на каждой поверхности**: ядро, приоритет, трасса, паспорта, урезание | `capability/<surface>.md` |
| `integration` | внешние системы и стыки с соседями: провайдеры и их функции | `integration.md` |
| `constraint` | регуляторика, SLA, контракты | `constraint.md` |
| `market` | конкуренты и аналоги (с роем агентов) | `market.md` |
| `cohesion` | `MVP` и сводки vision, границы, сквозная проверка, повышение `draft → stable` | `boundary.md`; vision |

Фазы — сторона продуктового слоя в маршруте продукта; таблица маршрутов с колонкой «ведёт» —
`.claude/skills/design-deep-dive/references/phases.md` §1. После `cohesion` рекомендованный ход — дальше по маршруту
поверхности: у кабинета и приложения — `/interface-deep-dive <slug> <surface>` (первыми — сценарии хабов, после них —
первый вход дизайна кабинета, бриф на вид), у сайта и лендинга — `/design-deep-dive <slug> <surface>`, у мобильного и
бота — `/interface-deep-dive`, затем `/mobile-deep-dive` или `/telegram-bot-flow-deep-dive`.

Порядок — рекомендация, не закон: аналитик может перепрыгнуть. В начале сессии скилл напоминает, какая фаза сейчас и
почему, после каждой записи предлагает ходы дальше — два-три, один рекомендован (`.claude/rules/guiding.md` §1, §5), а
при перепрыгивании называет цену пропуска одной фразой, пишет долг и работает; вопрос «почему сейчас?» — только когда
пропуск задевает обязательный артефакт маршрута (`references/phases.md § Перепрыгивание`).

## Три режима

Шаги, примеры вопросов, stub-сущности, удаление с каскадом и приведение к канону — `references/workflow-patterns.md`.

- **A. Новая сущность** — `<project-slug> <kind>` или `<kind>:<новый-slug>`: вопросы по `Критерии <kind>` формы, опции —
  anti-patterns `Что <kind> НЕ` и перечисления, значения — через Other.
- **B. Сырьё** — `<project-slug>` + текст или транскрипт: кандидаты по kind (возможность — с поверхностью), план,
  stub-строки по подтверждению, затем углубление каждой через C.
- **C. Углубление** — `<kind>:<slug>` или выбор из сводки: точечные вопросы по дырам и подозрениям, чек-лист
  `draft → stable` после каждой правки.

Ссылка на ещё не заведённую сущность (возможность назвала объект, которого нет) отрабатывается stub-строкой в её файле и
открытым вопросом в заметке; удаление — каскадом по всем упоминаниям.

## Стиль вопросов

Полные правила — `references/workflow-patterns.md § Стиль вопросов`. Кратко:

- Вопросы — через `AskUserQuestion`, до четырёх в раунде.
- **Опции** — anti-patterns из `Что <kind> НЕ`, примеры тест-критерия, перечисления (`surface.type`, `web-kind`,
  значения постуры, `priority`, поля паспорта, `reversibility`, `integration.direction`, `constraint.kind`), выбор
  существующего соседа («связать с X / Y / нужен новый»).
- **Свободная форма** (Other) — для значений: `name`, `description`, `value`, `jobs`, `pains`, `why`, `payload`,
  `source`, глаголы действий, примеры объектов.
- Формулировки доменных полей даёт владелец (`CLAUDE.md` §3): догаданная формулировка стала бы ложным фактом для всех,
  кто читает продуктовый слой. Пункты разделов vision агент может предложить «допущением» — с пометкой `(допущение)`,
  владелец подтверждает или отклоняет; примеры объектов — только из материалов клиента; числа, сроки и метрики
  допущением не бывают.

## Память: своя ветка единого state

Своей папки state у скилла нет. Заметки пишутся в свою ветку единого дерева state оркестратора, формат —
`../entrypoint/references/state-model.md`:

- запись — `../entrypoint/state/projects/<project-slug>/project/<kind>/<slug>.md` (в том числе `object`, `action`;
  атрибуты и представления — в заметке объекта, постура — в заметке пользователя, паспорт и урезание — в заметке
  возможности);
- vision — singleton `…/project/vision.md`;
- возможность — по поверхности: `…/project/capability/<surface>/<slug>.md`, чтобы записи разных поверхностей не
  сталкивались;
- отчёты роя — `…/project/research/` (`references/research-rays.md`);
- заметка пропусков — `…/project/_phase-jump.md`: «Доменные решения» — что пропущено и почему, «Что копать дальше» —
  долг.

Заметка существует, пока в ней есть хоть одна секция с содержимым: `## Открытые вопросы` (пометка `**blocker**`
блокирует `draft → stable`), `## Доменные решения`, `## Что копать дальше`; frontmatter — `kind`, `slug`, `ref`. Заметка
держит текущее знание о записи, а не историю: закрытое удаляется, пустая заметка удаляется целиком. Ветка скоупится по
проекту — заметки разных продуктов не сталкиваются.

### Единый контекст: read-only видимость дерева

Для единой картины скилл читает read-only всё дерево state оркестратора — срез `…/state/index.md`, открытые нити,
верхние слои `business/`, `ajtbd/`, `swot/`, `hypothesis-map/` — и клиентский дом `../entrypoint-for-business/state/…`.
Проектные ветки читаются только по текущему `<project-slug>`. Своя ветка — rw, остальное — read-only: в чужое не писать.
Маркер `**жду аналитика**` в клиентском доме — кандидат в blocker. Черновик, присланный клиентом в ветку `client`,
появляется в файловой системе после merge или fetch.

## Связи внутри слоя и с соседями

Структурно в продуктовом слое проверяются поверхность и ссылки ядра — их ловит `/project-audit`:

- файл `capability/<surface>.md` соответствует строке реестра `surface.md` (имя файла — slug поверхности), а папки слоёв
  поверхности — её типу и роду;
- `user`, `object`, `action` возможности называют существующие записи `user.md`, `object.md`, `action.md`;
- `integration.surface` ссылается на поверхности реестра; функция `## Функции` — на провайдера того же файла;
- строка постуры — на пользователя и поверхность реестра; атрибут `ref:<object>` и `action.objects` — на объекты
  глоссария.

Там же — внутрипроектные тупики: возможность или поверхность без пользователя, пустые обязательные слоты, черновик с
дырами без открытых вопросов; фаза `cohesion` поднимает их до закрытия. Остальные связи семантические: трасса `trace`
вверх, согласованность пользователей с участниками (who) interface, продукт против `addresses-problem`,
межпроектные стыки против `project-map.md` — их сверяет `/cross-audit`. Сам скилл — не аудитор: в конце сессии он
предлагает прогон.

## Контракт `draft → stable`

Чек-лист после каждой правки — `references/draft-stable.md`:

1. Обязательные слоты заполнены (у vision — разделы своего набора; у возможности — ядро, приоритет и паспорт, где он
   нужен).
2. `Критерии <kind>` подтверждены аналитиком через `AskUserQuestion`.
3. `Что <kind> НЕ` не нарушены.
4. `Тест-критерий` ✅ — аналитик соотнёс свой случай с примером.
5. В заметке записи нет `**blocker**`-вопросов.

Все пять ✅ — «Готов к stable, повышаем?»; по подтверждению — `status: draft → stable`. Скилл **не повышает сам** и не
понижает: `stable → draft` делает только аналитик, скилл лишь подсвечивает.

## Web-research через рой агентов

Основной источник кандидатов для `market` и `constraint`, подспорье для `integration` и `surface`. Запускается только по
решению аналитика через `AskUserQuestion` (по умолчанию — пять агентов): рой параллельных агентов с WebSearch и WebFetch
смотрит тему под разными углами, скилл сводит отчёты в
`../entrypoint/state/projects/<project-slug>/project/research/<query-slug>-<UTC-ts>.md` и раскладывает кандидатов по
kind. В артефакт кандидат попадает только решением аналитика: находки веба бывают неточными или выдуманными, и без
проверки стали бы фактами продукта. Углы, промпт агента и формат сводки — `references/research-rays.md`.

## Завершение сессии

1. Перечислить затронутые записи: заведены, углублены, удалены, повышены в stable.
2. Перечислить нерешённые открытые вопросы и долг заметки пропусков.
3. Назвать текущую фазу и ходы дальше — два-три, один рекомендован: рекомендованный — по маршруту поверхности (раздел
   «Фазы проработки»); у продукта с интерактивной поверхностью без профиля голоса продукта — `/design-deep-dive <slug>`.
4. Предложить через `AskUserQuestion`:
   - «Прогнать `/project-audit <project-slug>`?» — внутрипроектная консистентность, хребет, матрица «пользователь ×
     объект × действие»;
   - «Прогнать `/cross-audit`?» — продукт против interface, сервисов и экранов, `addresses-problem`, трасса вверх,
     межпроектные стыки;
   - «Передать клиенту через `/entrypoint-for-business` блок <X>?» — если фаза подходит под бизнес-домашку.

Другие скиллы этот скилл сам не вызывает — это разные точки входа, запускает их аналитик.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`: итог сессии, ходы дальше и строка «как
продолжить» идут по нему.

## Границы

- Один проект за сессию: пути и ветка state скоупятся в выбранный `<project-slug>`, и записи разных продуктов не
  смешиваются.
- Значения доменных полей и привязку `addresses-problem` даёт аналитик или бизнес (`CLAUDE.md` §3); скилл спрашивает,
  предлагает anti-patterns опциями, а пункты vision — «допущением» с пометкой.
- Возможности живут только в `capability/<surface>.md` поверхностей из реестра: файла для поверхности вне реестра нет,
  хребет ведёт реестр.
- Облика в продуктовом слое нет: цвет, шрифт, «как выглядит» — слой дизайна `design/` (`/design-deep-dive`); vision даёт
  ему проекции — тип приложения, постуры, статусы объектов, мобильный объём, цель доступности.
- Факты и голос продукта (`<slug>/facts.yaml`, `<slug>/voice.yaml`, `<slug>/voice.product.yaml`) скилл читает и
  ссылается на них из vision, но не пишет — их ведёт исполнитель слоя страницы (`CLAUDE.md` §6).
- Статус меняет аналитик: `draft → stable` — по его подтверждению после чек-листа; `stable → draft` скилл только
  подсвечивает.
- Пишет скилл в `docs/projects/<project-slug>/` (md-файлы продуктового слоя) и в свою ветку state; находки research-роя
  попадают в артефакты только через `AskUserQuestion`.
