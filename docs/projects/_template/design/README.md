# Слой дизайна: облик продукта

Слой отвечает на вопрос **как продукт выглядит и движется**: бренд, дизайн-система (ДС), направления и карточки стиля,
арт-дирекция, ассеты, макет в Claude Design и его приёмка, пакет для репозитория кода. Облик мира делается один раз:
бренд, ДС, бриф на вид кабинета и продуктовый паспорт визуала — на продукт (`…/design/`), а у поверхности — её
арт-дирекция, ассеты, холст и готовность к сборке (`…/design/<surface>/`). Здесь и ниже `…` — папка проекта
`docs/projects/<slug>`, пути `kb/…` и `scripts/…` — от папки скилла `.claude/skills/design-deep-dive/`.

Этот файл — канон слоя. Формы файлов, у которых нет схемы в базе знаний, лежат рядом в [`_template/`](_template/):
[`app-brief.yaml`](_template/app-brief.yaml), [`system.yaml`](_template/system.yaml), [`brand.yaml`](_template/brand.yaml),
[`ARTIFACTS.md`](_template/ARTIFACTS.md), [`REVIEW.md`](_template/REVIEW.md), [`ready.yaml`](_template/ready.yaml); у
остальных файлов форма — схема базы (§ Файлы). Ведёт слой исполнитель `/design-deep-dive <slug> [<surface>]` — он же
ведёт слой страницы и факты с голосом продукта, — проверяет `/design-audit <slug>`; этапы с контрактами «вход → выход →
проверка → кто утверждает» — `phases.md` скилла. Сайт и лендинг приходят сюда из слоя страницы
([`../site/README.md`](../site/README.md)), кабинет — из экранов ([`../screens/README.md`](../screens/README.md)).

## Уровни

- **Продукт** (`…/design/`): бренд, ДС, ассеты продуктового мира (логотип, шрифты, набор иконок, иллюстрации),
  `ARTIFACTS.md` — артефакты claude.ai всего продукта; бриф на вид кабинета и продуктовый паспорт визуала — когда у
  продукта есть поверхность маршрута кабинета.
- **Поверхность сайта** (`web` рода `landing` или `site`, `…/design/<surface>/`): арт-дирекция, маркетинговый паспорт
  визуала, планы ассетов и ассеты, спецификации движения, холст с входом и проверками, манифест готовности. Бриф —
  `site-brief` слоя страницы; подача секций — в планах страниц, её заполняет этот слой.
- **Поверхность кабинета** (`web` рода `app`; `admin`, `desktop`, `embed`; `…/design/<surface>/`): холст с входом и
  проверками, манифест готовности, свои ассеты, если есть; дополнение брифа на вид — раздел `surfaces.<surface>`
  продуктового `app-brief.yaml`.
- **Мобильное приложение, бот, API** — без папки `design/<surface>/`: их облик — токены ДС продукта и голос, которые
  читают слои `mobile/` и `telegram-bot-flow/`; макета этих поверхностей в слое нет.

**Смешанный продукт.** У каждой поверхности свой маршрут; бренд, ДС, факты и голос — общие. ДС одна: её строит маршрут,
первым дошедший до этапа `design-system`, второй расширяет, а не перестраивает — иначе он ломал бы принятые макеты
первого.

- **Сайт первым** — ядро ДС по ключевым ассетам сайта. Кабинет не делает карточек по уже заданным ручкам (акцент,
  нейтраль, шрифт, радиус) — берёт их из ДС; по желанию владельца продукта — карточки по незаданным (плотность, тени).
  Его этап ДС — расширение: `size.panel.*`, границы приложения, режимы плотности, компоненты экранов.
- **Кабинет первым** — ядро по выбранной карточке стиля. Сайт ведёт арт-дирекцию с ДС как брендом
  (`brand.expression.mode: extend` по умолчанию); его этап ДС пишет расширение для страниц (дисплейные стили, отступы
  секций, поверхности, маркетинговое движение) и сверяет палитру ассетов с ядром.
- **Начали вместе** — ядро строит маршрут, у которого раньше готов вход этапа ДС; ждать другой не нужно.
- Смена основной ручки после макетов меняет ДС всего продукта: каждый холст пересинхронизируется, принятые макеты
  проходят приёмку заново по затронутым пунктам. Решает владелец продукта.
- Два мира — два паспорта визуала, а не один средний (ai-media 06/01 §1): маркетинговый — у поверхности сайта,
  продуктовый — один на продукт. Арт-дирекции у кабинета нет: один документ — один мир (creative 01/02 §7.5), рабочие
  экраны вне уровней амбиций (creative 01/03 §1.3). Шкала брейкпоинтов одна — объединение границ всех поверхностей с
  именами по смыслу (позиция).

## Облик

Облик — визуальные решения: цвет (палитра, роли цвета, темы), типографика (гарнитуры, шкала, стили текста),
пространство (отступы, плотность, сетка, ширины, брейкпоинты), форма и глубина (радиусы, границы, тени), движение
(длительности, кривые, моменты, подача секций), изображения (стиль, свет, камера, материалы, сюжеты, иллюстрации,
иконки, 3D), выражение бренда, вид и размер компонентов. «Ремесло» — качество исполнения, оценка рубрик, а не область
решений (`kb/common/glossary.md § Облик`).

- **Где пишется:** только в этом слое и в подаче секций плана страницы (`treatment`), которую заполняет этап дизайна.
  В interface, экранах, FSD-карте и mobile облика нет.
- **Не облик — остаётся в своих слоях:** структура и дерево экранов; уровень действия (главное, второстепенное) — смысл
  по матрице действий; имена размеров намерения и диапазонов `responsive` — значения им дают токены ДС; тексты и
  факты; уровень амбиций — решение брифа.
- **Владелец — владелец продукта** (CLAUDE.md §3): агент предлагает облик «допущением» — направлениями и карточками
  стиля, — выбирает и утверждает владелец продукта. Факты бренда — логотип, фирменные цвета и шрифты, брендбук —
  материалы заказчика.

## ДС

ДС продукта — три файла репозитория и артефакт, собранный из них в одну сторону:

1. **Токены DTCG** — `…/design/system.tokens.json`, источник правды значений. База — схема ui 09/04 (примитивы и
   семантика), пресет ui 14/11 и ручки выбранной карточки стиля или палитра арт-дирекции и ключевых ассетов; расширение
   для страниц сайта — `marketing-tokens.json` (дисплейные стили, `space.section-*`, поверхности, `motion.marketing.*`).
   Режимы — темы, плотность, сокращённое движение; правила применения — внутри токена (`$extensions`, ui 14/08). Тема
   значений `$value` — светлая; продукт, у которого значения тёмные (одна тёмная тема или тёмная со светлым режимом),
   объявляет в корне токенов `$extensions["org.design-deep-dive.modes"].base: dark` — от этого `color-scheme` производного
   CSS и имя первой темы артефакта. Темы, которых ждут брифы — `themes` брифа сайта каждой поверхности и брифа на вид
   кабинета, — есть у токенов темой значений или режимом с её именем: иначе код получит не ту `color-scheme`
   (`ds_build check`, R-COV-010 — предупреждение; в манифесте готовности — строка `open` «тема: …», § Пакет для кода).
   Каждый блок светлой и тёмной темы производного CSS объявляет её `color-scheme`: у продукта с одной темой —
   `:root`; у продукта с двумя `:root` несёт обе, и тему выбирает система, парная тема — блок по системе
   (`prefers-color-scheme`) и под атрибутом `data-theme`, тема значений под атрибутом — блок с одной её схемой
   (`:root[data-theme="light"] { color-scheme: light; }`). Режим с другим именем правит действующую тему: своей схемы
   у его блока нет, и второй темой он продукт не делает. Выбор темы атрибутом против темы системы меняет и системные
   элементы страницы — чекбокс, полосы прокрутки, — поэтому своей `color-scheme` код не объявляет (норма
   переключателя — ui 01/04 §9.2). Выбор движения так же сильнее системы в обе стороны: блок сокращённого движения
   (режим `reduced` токенов движения) действует по системе (`prefers-reduced-motion: reduce`) на
   `:root:not([data-motion="full"])` — выбор «полное» оставляет значения `$value`, — а под атрибутом
   `data-motion="reduced"` — при любой системе; без атрибута решает система (норма переключателя — creative 05/01
   §4.4). Пружина — токен `transition` с расширением `org.design-deep-dive.spring` (`dampingRatio`, `stiffness`; масса 1):
   сборка выводит в CSS кривую `linear(…)` с длительностью — временем успокоения, а параметры пружины для кода —
   разделом `x-springs` передней части прозы ДС; переходы интерфейса по шаблонам (смена экрана, диалог, панели,
   вкладки, раскрытие, список, скелет, уведомление) — токенами (ui 08/04 §3, ui 09/04 §2.10).
   Семейство шрифта токенов, которое не системное (первое имя стека не родовое и не системное; прочие имена стека —
   запасные, файлов им не нужно), — файлы `…/design/_assets/fonts/` со строками манифеста продукта (§ Ассеты) на каждое
   начертание: насыщенности `fontWeight` типографических токенов семейства, начертание `normal`. По строкам код
   подключает шрифты, своей декларации `@font-face` производные не несут. В производном CSS стек такого семейства — у
   токена гарнитуры и у роли текста — идёт ссылкой на переменную семейства со стеком в запасе,
   `var(--font-<ключ>, <стек>)`; ключ — имя семейства (первое имя стека, оно же `font.family` строки манифеста)
   строчными, каждый отрезок знаков вне латинских букв и цифр — один дефис, дефисы по краям срезаются: гарнитура Golos
   Text — `--font-golos-text`, «M+ 1p» — `--font-m-1p`, роль —
   `--type-body-family: var(--font-golos-text, "Golos Text", Arial, sans-serif)`. Файл эту переменную не объявляет: без
   загрузчика шрифтов действует стек, а загрузчик кода, который подключает файл под своим именем `@font-face`,
   объявляет её на `:root` — и роли берут его семейство. Стек остаётся литералом, и загрузчик его не подменит, у
   семейства без ключа (в имени нет латинских букв и цифр) и у семейства, чьё имя переменной занято переменной токена
   (`font.inter` при гарнитуре Inter); два семейства с одним ключом (`PT Sans` и `PT-Sans`) ссылаются на одну
   переменную. Каждый из трёх случаев — предупреждение R-STRUCT-006: имя семейства пишут латиницей и одним
   написанием, токен гарнитуры называют ролью (`font.text`), а не семейством. Путь токена — имя переменной в коде:
   переименование токена, который код уже читает, решает владелец продукта. Расширения токенов — ключи `$extensions`
   пространства `org.design-deep-dive.`: `modes`, `reduce`, `fluid`, `css` и `artifact` читает сборка, `llm`, `meta` и
   `limits` — пометки; ключ вне списка сборка не читает и называет предупреждением R-STRUCT-006. Тема значений живёт в
   `$value`: режим токена с её именем — предупреждение. В том же файле — `breakpoint.*` и `size.panel.*`: развал
   каркаса считается по обоим (ui 05/02 §7).
   Границы у сайта — из каталога блоков (`blocks.yaml#conventions.breakpoints`), у приложения — эталон ui 09/04 §1.3, у
   смешанного продукта — объединение (позиция); ДС объявляет границы до экранов. Шкала `space.*` — одна.
2. **Проза** — `…/design/DESIGN.md` в порядке разделов формата Google Labs (ui 12/04 §2.3): Overview, Colors, Typography,
   Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts. Внутри — характер числами, роли цвета с частотой и
   контрастом, правила с именами токенов, иконография, доступность и известные проблемы, источник (cd 05/01 §4,
   cd 06/02 §2); голос — проекцией профиля голоса продукта (text 05/01 §8.3). Передняя часть с токенами — производная
   (в ней `x-narrow` — основной кегль узкой ширины, его берёт и мобильное приложение); из прозы собирается README
   артефакта — бренд-бук.
3. **Карта решений** — `system.yaml` (форма [`_template/system.yaml`](_template/system.yaml)): компонент ДС на каждый
   тип словаря, расширения словаря, стиль для каждой роли текста (`text_styles`: роли ux 07/06 §7.2 и `body` → стили
   `type.*`; стиль заголовка секции сайта задаёт подача ролями `marketing-tokens.json`), конвенции, эталонные экраны
   (`starter`), статус всей ДС.
4. **Артефакт Design System** — исходники в `…/design/_design-system/project/`: `tokens.json` и `README.md` — производные
   (поля артефакта, которых нет в DTCG, — расширение `$extensions["org.design-deep-dive.artifact"]` токенов);
   компоненты — превью с обязательными и объявленными необязательными состояниями (образец состояния — элемент с
   атрибутом `data-state="<состояние>"`), карточки сгруппированы по группам словаря (`@dsCard group` —
   `components.yaml#groups`); длительности и кривые — `bundle.css` артефакта (у формата токенов артефакта нет
   семейства движения — cd 05/01 §3.2); шрифты — из `…/design/_assets/`; картинки исходники называют путём к файлу
   ассета репозитория от своего файла (`../../../../_assets/icons/play.svg` в превью компонента), id загрузок —
   производное: копию исходников с `/_blob/<id>` собирает
   `ds_build artifact <slug> --bind-assets <ответ загрузки> --out DIR`, публикуется копия; обложка и индекс —
   последними. Правила формата типа отдаёт инструмент `Artifact`, в шаблон они не копируются.

Пакет ДС ui 12/04 §2.6 ложится на эти файлы: бренд-бук — README артефакта; описания компонентов — карточки
артефакта и раздел Components прозы по тем же группам, отдельной папки описаний нет; стартовые экраны — `starter`;
проверки — `kit` и `/design-audit`. Блок «Дизайн-система» контракта генерации экранов — типы продукта из словаря,
сопоставление карты решений, токены и правило заземления.

Правка заказчика в редакторе claude.ai — в артефакте ДС или на холсте — поднимается в токены DTCG (`ds_sync`), и ДС
пересобирается (`ds_build build`): сборка идёт в одну сторону и иначе затёрла бы правку. После правки токенов контраст
пар пересчитывается; слабая пара не чинится молча, а показывается заказчику.

### Покрытие компонентов

Каждый тип, названный в стабильных экранах узлом `ui:<Тип>`, — ключ `components` или `extensions` карты решений; его
компонент есть в артефакте; нарисованы обязательные состояния типа (`states.required` словаря) и объявленные
необязательные; на поверхности без указателя (`type: mobile` или `core.pointer.<surface>: touch` брифа на вид) наведение
не требуется (`kb/common/components.yaml`, правила в шапке). У сайта экранов нет: набор — типы слотов действия и форм
планов — Button, Link, Field, TextInput, Checkbox, Select (`components.yaml#outside`), поля форм — `lead-forms.yaml`.
Цепочка одна: `ui:<Тип>` экрана → компонент ДС → код (слайс `shared-ui` FSD-карты называет тип, который реализует);
покрытие — работа ДС, а не `shared-ui`. Этап `ds-components` покрывает все типы; покрытие считает
`scripts/project/ds_coverage.py` — `ds_coverage check <slug> [<surface>] --stage ds-components` (правило R-COV-005
`/design-audit`), таблица «тип → ключ → компонент» — `ds_coverage show`. Нарисованное состояние — образец в превью
компонента с атрибутом `data-state="<состояние>[ <состояние>]"` (`rest` — у любого образца). Работу держит только тип
экрана без ключа карты решений или компонента, когда кабинет на макете: макету нечем его рисовать; не нарисованное
состояние и покрытие сайта — доклад заказчику.

### Расширения словаря

Потребность, которую не закрывает ни один тип словаря, проект оформляет расширением — запись `extensions` карты
решений: поля `components.yaml#project_extension`, среди них `keyboard` (клавиатурный контракт — без него тип не
принимается) и `text_roles` текстовых частей (без них не работает проверка «роль ключа текста = роль части»). Узел
`ui:` экрана может называть id расширения. Расширение действует только в своём проекте; тип, который понадобился второму
проекту, — кандидат в словарь шаблона.

### Конвенции ДС

Одно решение на продукт — для сайта, кабинета и писем; поля `conventions` карты решений:

- знак диапазона — «–» по умолчанию, «—» — вариант (text 08/02 §1.3); смешение ловит межстрочная проверка текстов;
- пробел в разрядах — неразрывный U+00A0 (ux 07/03 §6.6);
- выравнивание пустого состояния — по центру по умолчанию, по левому краю — вариант (ui 06/06 §4); что показать и
  почему пусто, решают экраны (ux 06/01 §4), а состояния отказа (S13, S18, S21) — не пустота;
- набор иконок — имя, начертание (`style`: контурный `line` или с заливкой `fill`), размеры; штрих — только у
  контурного (ui 07/01);
- цвета статусов объектов — статус из глоссария объектов (`object.md`) → роль цвета (ux 13/04 §25);
- маркеры объектов — иконка и роль цвета.

## Направления

Направление — вариант облика страницы: тезис, бумага, стиль заголовков, тон акцента, макроструктура (creative 01/01 §6).
У кабинета эту роль играет карточка стиля — ручки характера без раскладки (ui 11/02 §2.1).

- **Сайт** — несколько направлений в `art-direction.directions` с одной рекомендацией, риском и ценой у каждого; сколько
  их и по каким осям пары различаются — creative 01/01 §6; схема держит от одного до пяти, отступление от нормы —
  предупреждение `ad_check.py` с основанием (строгий бренд, референс заказчика), решает заказчик. Форму страницы
  заказчик выбирает на этапе плана — одну из трёх макроструктур (site 10/01 §1.3): направление держит выбранную форму
  или берёт одну из двух альтернатив плана с риском «меняет форму плана»; выбор такого направления возвращает план на
  правку макроструктуры. Направления строятся по плану главной, у многостраничника — один раз на сайт.
- **Кабинет** — карточки стиля в `app-brief.style_tiles` по семи ручкам: акцент, нейтраль, радиус, плотность, шрифт,
  тени, тема (ui 14/09); у карточки — поля плитки и отчёт контраста, раскладки нет; последняя — заведомо смелее; сколько
  карточек — ui 11/02 §2.4. Выбор комбинирует, а не усредняет; после выбора у каждой ручки явное значение — оно уходит в
  токены. Ручки, уже заданные ДС продукта, карточки не варьируют.
- **Кто выбирает** — заказчик как владелец облика: `choice.chosen_by: customer` (у арт-дирекции ещё `approved_by` —
  роль, и `approved_at`); молчание — `default`, статус остаётся `proposed` со строкой «Going with»; строгий бренд —
  `art-director` с подтверждением заказчика (creative 01/01 §7.1). Судья — по желанию, попарно в обоих порядках;
  решает человек (`kb/common/judge.md § 5`, `§ 7`).
- **Страница холста «Направления»:** у сайта — артборд первого экрана на направление (тексты слотов первого экрана из
  copy deck — слоты `first_screen.must_show` плана, варианты H1 списком; черновые допустимы, строки нет — видимая
  заглушка), стикер «мотивация / компромисс», заметка «направление × оси»
  (cd 06/01 §5); у кабинета — артборд на карточку без раскладки. Артборды рисует модель сессии — это не платная
  генерация; картинки направлений генерацией — только вместе с владельцем денег.
- **Карта возможностей подачи** — на уровнях L1–L2, до прототипа: приёмы каталога, разрешённые уровнем брифа, — что
  каждый даёт продукту, его цена и где его увидеть до кода: на холсте, прототипом вне холста, только по спецификации
  (cd 05/03 §4). Заказчик выбирает из показанного: приём, которого в карте нет, для него не существует. Холст в Play
  исполняет JavaScript, WebGL, three.js и библиотеки движения — приёмы на 3D и коде стоят в карте наравне с CSS.
- **Прототип главного эффекта** (`art-direction.prototype`) — до утверждения направления: на уровне L2 он идёт по
  умолчанию, отказ от него — слово заказчика; на уровнях ниже — по желанию. Прототип доказывает, что приём исполним; в
  макет он не идёт (creative 09/01 §5).
- **Раунд концептов «Креатив»** — на уровнях L1–L2, после выбора направления: широкий круг живых эскизов сигнатурных
  идей продукта на странице холста «Креатив» — сцены 3D и кода, прокрутка, движение, взаимодействие, язык картинок; у
  каждого — карточка: смысл, место на странице, из чего собран, цена. Заказчик отмечает «беру / не беру / ещё в эту
  сторону», отмеченное растёт ветками; концепты и отметки — в заметке этапа, в файлы слоя они не идут. Сколько
  концептов и семейств и чем они проверяются — `phases.md` скилла, этап `art-direction`.
- **Варианты подачи** выбранного направления на L1–L2 (`treatment_variants`) — живые прототипы на странице холста
  «Подача», собранные из отмеченного в «Креативе»: заказчик выбирает глазами (`phases.md` скилла, этапы `moodboard` и
  `art-direction`). Вход холста страниц «Креатив» и «Подача» — вид `treatment`: выбранное направление с обликом до
  ДС (палитра, стратегия цвета, шрифты, сигнатурный приём, первый экран), тема и логотип бренда, варианты (`id`,
  `name`, `shows`, `effects`, `chosen`), прототипы вне холста отдельным полем (`lab_path` и `recording` варианта,
  запись `prototype`) и тексты первого экрана.
- **Прототип вне холста.** Приём, которого холст не исполняет (cd 05/03 §4), показывается лабораторной страницей
  `…/design/<surface>/motion/lab/<id>/` (`prototype.lab_path`): на странице «Подача» — её запись роликом
  (`prototype.recording`) и строка, как открыть её живьём. Вариант с таким приёмом остаётся вариантом, а не снимается
  молча. Лабораторная страница принятого приёма — образец для кода (§ Пакет для кода).

## Арт-дирекция

Арт-дирекция — одна на поверхность сайта, `…/design/<surface>/art-direction.json` по схеме `art-direction.v1`
(документ — creative 01/02): `inputs`, `ambition`, `concept`, `territories`, `directions`, `choice`, `moodboard`,
`visual_language`, `motion_system`, `effects_by_section`, `decisions`, `exclusions`, `budget`, `handoff` (паспорт
визуала, бриф 3D), `lifecycle`. Блок `ambition` — проекция уровня из брифа: правится только бриф, равенство сверяет
`/design-audit`. Этап `art-direction` пишет подачу страниц и секций в планы (`treatment` в статусе `draft`,
`refs.treatment`) — план остаётся `approved`; у многостраничника подача — на каждый план шаблона. Проверки — чек-лист
creative 01/02 § Чек-лист и стык подачи с уровнем в `site_validate.py` (подача не выше уровня, секции конверсии — L0).

- **Снятые приметы.** `exclusions.lifted_markers` (`marker`, `decision_ref`) — умолчания уровня L0 соседних баз (ui,
  ai-media, 3d), снятые решением по пяти проверкам (creative 08/01 §4, creative 01/02 §5); `decisions[].k3_allow` и
  `exclusions.k3_allow` — ключи `--allow` утилиты макета (`kb/common/tells.yaml`, раздел `checks`, поле `allow`) —
  только с решением; `exclusions.bans` — запреты предметно и с проверкой; `forbidden_hues`, `forbidden_markers` — что
  остаётся запретом у этого сайта. Отступление от нормы движения, которое заказчик принял на прототипе или макете,
  записывается так же: `marker` — id правила из находки `spec_check.py spec` (MS-08, MS-09, MS-10, MS-23) или
  `spec_check.py plan` (нормы облика подачи `TR-…`), `decision_ref` — решение `decisions[]` вида `use` или `twist`,
  которым приём принят; на каждое правило — своя запись. Необязательные `page` (id страницы плана) и `section` (id
  секции) сужают запись: без них она действует на всю поверхность.
- Приметы, которые заказал сам заказчик, — `site-brief.ambition.allow.markers`; вход холста получает объединение обоих
  списков. У кабинета приметы снимают бриф на вид и ДС — `app-brief.allow` той же формы (домен `app-visual`).

## Референсы

Запись референса живёт там, где решается облик мира: у сайта — `art-direction.directions[].refs` (до выбора) и
`art-direction.moodboard` (выбранного направления), у кабинета — `app-brief.moodboard`; предел мудборда — схема
`art-direction.v1`. Исполнителю макета уходит несколько из них по ролям — сколько и каких, cd 06/02 §3.

- **Поля:** `url` или `ref` (запись библиотеки заказчика); `role`; `applies_to` — одно место (у сайта — роль секции или
  блок каталога, у кабинета — тип экрана или тип словаря); `take` — объект, свойство и число (creative 02/03 §3.2);
  `dont_take` — всегда: логотип, тексты, фото и цвета чужого бренда, приметы бан-листа; значения текстом — `values`:
  `measured` (замер живого сайта `shot.py` и `measure_ui.py`; движение — `motion_probe.py probe`: длительности, кривые,
  шаг между элементами, закрепления и станции) или `estimated` (оценка по картинке, с пометкой); `method` — чем сняты
  значения: `shot`, `measure_ui`, `probe` или `code` (из кода страницы без кадров); `passport` — паспорт движения, из
  которого взяты числа; `captured` — дата и вьюпорт; `source` — `customer`, `claude` или `creative-library`. Снимок и
  кадры живого сайта для замера разрешены и в git не идут; «не выкачивать» — о картинках площадок-галерей.
- **Площадки листает заказчик сам;** агент записывает ссылку, роль, «брать / не брать» и значения. Поля автора и
  превью нет, картинки с площадок не выкачиваются; FWA — отложено (creative 02/02 §6). Чужой макет или скриншот —
  референс, а не источник.
- Референсы, которые заказчик принёс на брифе или отметил в списке, который собрал агент, остаются в
  `site-brief.references[]` записью его слова; в мудборд
  выбранного направления такой референс попадает, когда направление его берёт, — со своими «брать / не брать» для секции.
  Референсы отклонённых направлений уходят вместе с ними.

## Ассеты

**План ассетов** — файл на страницу-шаблон `…/design/<surface>/assets/plans/<page-id>.yaml` в формате ai-media 01/01 §8
(схема — `kb/ai-media/05-prompting/asset-plan.schema.json`), ссылка из плана страницы — `refs.asset_plan`. Каркас строит
`plan_to_assets.py build <slug> <surface> --write` по медиа- и 3D-слотам утверждённого плана страницы (страницам без
плана ассетов; готовый план утилита не перезаписывает; слот `edit-real` при подлинности `real-only` каркас пишет
строкой `real` с заглушкой `local_edit` — кадр доводится без генерации; класс `media_class` — по типу сайта брифа, у
типа сайта без строки таблицы — по типу страницы), проверяет —
`plan_to_assets.py check <slug> <surface> [--page ID …]`; предмет,
варианты, вес и фокус дописывает агент; тексты ассетов (alt, подписи, текст в кадре) — строки copy deck
(`copydeck.py export-assets`), в плане — ссылки `alt_ref`, `caption_ref` на текстовые слоты плана страницы. План пишется
до ДС и у страниц без генерации: кодовые и реальные слоты тоже.

- **Решение по слоту** — «код / генерация / Blender»: `ladder` (лестница дешевизны — ai-media 01/01 §1), `source`
  (`generate` · `edit-real` · `real` · `code` · `template` · `render` — свой рендер Blender или кода; источник
  варианта, если он другой, — `variants[].source`; доводка настоящего кадра без генерации — `local_edit`), `task_codes`
  (`routing.yaml`) или рецепт `recipe:`; ключевой ассет — поле `key`; у 3D — дорога `three_d.road` по
  `3d/15-showcase/VERDICT.md` (`code` · `blender-frame` · `blender-sequence` · `hybrid`). Когда не
  генерировать — ai-media 13/03 §6; люди-доказательства, товар «как есть» и чужие знаки — только реальные (ai-media
  12/04 §2, site 08/02 §2.1); нужен ли 3D — 3d 01/02 §7, а 3D — только Blender и код; режим и бюджет 3D по уровню —
  `ambition-levels.yaml#levels.maps_to` и `#levels.budgets.effects`; у 3D-слота — постер (`page-plan`, `slot-3d`).
- **Утверждение плана — до генерации.** Картинки, видео и 3D генерируются только после «да» заказчика плану ассетов:
  это траты, деньги и ключи — у владельца денег. Статус плана — поле `status` (`draft` → `proposed` → `approved`) с
  `approval`: кто и когда утвердил.
- **Порядок ассетов и ДС** — у сайта ключевые ассеты (визуал первого экрана, атмосфера, ключевой кадр Blender)
  делаются до ДС, и ДС берёт у принятых палитру, свет и материал; остальные ассеты — после ДС, по токенам и
  паспорту; у кабинета ДС первой, иконки и иллюстрации — по ней. Норма целиком — этапы скилла
  [`phases.md § Порядок ассетов и ДС`](../../../../.claude/skills/design-deep-dive/references/phases.md#порядок-ассетов-и-дс).

**Хранение.** Готовые ассеты в пределах бюджетов (ai-media 10/04 §1.1) — AVIF, WebP, постеры, петли видео, GLB, SVG,
шрифты с лицензиями — лежат в git форка стратегии: код появляется позже и берёт их снимком стратегии, а облачная
сессия теряет незакоммиченное. Продукта — `…/design/_assets/`, поверхности — `…/design/<surface>/assets/`; у
каждого файла — строка манифеста папки (`…/design/_assets/manifest.yaml`, `…/design/<surface>/assets/manifest.yaml`):
слот, файл, роль, лицензия, происхождение, пометка ИИ, sha256, статус (`draft` → `accepted`); у файла шрифта
(`…/design/_assets/fonts/`, WOFF2) вместо роли — `font: {family, weight, style}`: семейство — первое имя стека
токенов ДС, насыщенность — число или диапазон вариативного шрифта («100 900» закрывает все насыщенности внутри),
начертание; начертание токенов закрывает принятая строка с файлом и лицензией `license` (§ Пакет для кода,
«Публикация»). Форма манифеста —
`kb/ai-media/05-prompting/asset-manifest.schema.json`; `plan_to_assets.py check` сверяет форму манифеста поверхности,
`font` у строк файлов шрифта, а у принятых строк обоих манифестов — файл и `sha256` (отпечаток снимка, § Пакет для
кода). Вне git —
мастер-файлы и исходники генераций, файлы Blender, записи видео, кадры проверок, выходы утилит; где лежит мастер,
говорит строка манифеста («исходник: у <роль>, <где>»). В git идёт только принятое: замена ассета оставляет старый файл
в истории. Лабораторная страница принятого приёма (`…/design/<surface>/motion/lab/<id>/`) — код, ассеты в тех же
бюджетах и запись, по которой заказчик её утверждал, — лежит в git: это образец для кода.

**Строка манифеста — файл.** У слота столько строк, сколько у него файлов: форматы (`format` — AVIF и WebP одного
кадра), варианты кадра (`variant` — id варианта плана ассетов: `desktop`, `mobile`; один файл на несколько вариантов —
`desktop+mobile`), версии знака. Путь `file` — от папки манифеста.

- **Ключ ассета — страница и слот.** Id слотов у страниц совпадают (`header-logo`, `hero-visual`, `og-image` есть и у
  главной, и у шаблонов), поэтому строка манифеста поверхности называет страницу полем `page` — id страницы плана
  ассетов. Строка без `page` — общая: её берёт каждая страница с таким слотом, у которой нет своих строк (знак шапки и
  подвала). Файлы страниц с одинаковыми слотами различаются именем: подпапка страницы
  `<page-id>/<слот>-<вариант>.<формат>` или префикс страницы.
- **Что уходит на холст.** Вход макета берёт только строки `status: accepted`: слот без принятого файла — заглушка
  «placeholder». У каждого варианта — файлы одного формата: вектор, затем растр и видео, которые открывает любой браузер
  (порядок — `format_order` в `scripts/project/data/canvas.yaml` скилла); AVIF и WebM остаются файлами публикации. Те же
  файлы входят в отпечаток одобрения страницы: замена файла, который стоит на макете, снимает одобрение.
- **Демо-картинка макета** — картинка, которая стоит на макете, пока настоящего файла нет или его ещё нельзя показать
  (портреты до письменных согласий, стилизованная версия кадра). В манифест и в git она не идёт: её путь вне git
  называет слот плана ассетов расширением `x-demo` — `file: <путь>` или `files: {<вариант>: <путь>}`, `what` — что это
  за картинка. Вход холста ставит её отдельной строкой с пометкой «демо»; в публикацию идёт файл слота. Демо-кадры
  образцов называют записи блоков плана ассетов `x-collection` (`pages[].slots[]`: образец и слот плана) и `x-works`
  (`covers[]`) тем же `x-demo`; вход ставит их строками страницы шаблона.
- **Общие ассеты продукта** — принятые файлы `…/design/_assets/` (знак, иконки, иллюстрации): вход холста показывает их
  строками у каждой страницы; слот плана без строк манифеста поверхности берёт на макете принятую строку
  `…/design/_assets/manifest.yaml` с тем же `slot`; шрифты — часть ДС, в ассеты страницы не идут.
- **Загрузки холста** живут в claude.ai, их id — в `ARTIFACTS.md` («Загрузки»): строка на загрузку с путём файла и его
  `sha256` в момент загрузки — по отпечатку видно, что файл заменили после загрузки и артборд показывает кадр до замены.

## Паспорт визуала

Паспорт визуала — правила изображений мира: палитра, свет, камера, сюжеты, запреты, приёмка (схема
`ai-media/06-art-direction-consistency/visual-dna.schema.json`). Паспорт один на мир (ai-media 06/01 §1), утверждает
человек (ai-media 06/01 §6).

- **Сайт** — маркетинговый паспорт `…/design/<surface>/visual-dna.json`, когда страница генерирует картинки:
  выводится из арт-дирекции (`handoff.visual_dna`, creative 01/02 §4.1) на этапе `art-direction`, до первой генерации и
  до ДС; без генерации (фото заказчика, код) паспорта нет — «не применимо: причина» в заметке этапа. После ДС в нём
  заполняется `derived_from_ui.tokens` и сверяются палитра иллюстраций и цвет среды (ai-media 06/01 §3). Утверждённый
  паспорт молча не правится: изменение — новой версией с подтверждением (creative 01/02 §7.6).
- **Кабинет** — продуктовый паспорт `…/design/visual-dna.json`, когда у экранов есть иллюстрации или картинки
  генерацией: из токенов (`vlm_to_dna.py from-tokens`) на этапе `passport-icons`, после ДС; два кабинета одного продукта
  делят его. Нет ни того, ни другого — «не применимо: причина». Стиль фото, сюжеты и контрольные кадры по эталонам
  разбирает сессия Opus пакетом: `vlm_to_dna.py build` → агент `design-judge` → `vlm_to_dna.py parse`; проверка паспорта
  — `vlm_to_dna.py validate`.
- Иллюстрации — раздел паспорта (ai-media 06/01 §2.2): экран называет метафору пустого состояния (`illustration=` у
  `ui:EmptyState`) из списка паспорта.

## Движение

Движение, живое 3D, видео и эффекты — слой поверх принятого статичного макета: уровень задан брифом заранее, поздно
накладываются только сами эффекты. На макете — постер 3D-слота, ключевой кадр Blender, постер или ключевой кадр петли,
станции сцены прокрутки; кандидат LCP первого экрана — постер, а не холст 3D (3d 09/05 §7.2).

- **Уровень — из брифа** (`site-brief.ambition`: `level`, `motion_cap`, `by_section_role`):
  `ambition-levels.yaml#levels.maps_to` даёт уровень движения исполнителя и режим 3D, бюджеты — `#levels.budgets.effects`.
- **Подача и спецификация.** Подача секций (`treatment`) пишется на этапе `art-direction` в статусе `draft`: уровень,
  визуальная роль, уровень движения, эффекты, фон, композиция, `display_role`, сокращённое движение, телефон; числа,
  принятые на живом эскизе, — `art-direction.motion_system.tuning`. Спецификация движения пиков и акцентов —
  `…/design/<surface>/motion/<page-id>.motion-spec.yaml` на этапе `motion`: моменты привязаны к раскладке принятого
  макета (creative 09/02 §3), каждый собирается примитивом набора движения (`primitive`), эффектом каталога или своим
  кодом с причиной (`custom`), числа — с эскиза, с замера референса (`source`) или токены. Затем подача → `proposed` со
  ссылкой `motion_spec_ref` → `approved` после показа заказчику.
- **Набор движения** — код движения страницы (`kb/creative/11-motion-code/` скилла): на холсте — файл поддержки и CSS
  в `<helmet>`, во входе холста — папка `lib/`; в коде сайта — тот же код, CSS — в слой, скрипт — островом. Код по
  спецификации пишется разметкой примитивов, а не заново.
- **Проход движения на холсте** — отдельное задание «движение для принятой статичной страницы; раскладку, тексты и цвета
  не менять» (cd 06/07 §6); после него статичные пункты, которые он задел, проверяются заново, а копия прототипа с
  набором (`dc_to_html.py convert --motion`) проходит `motion_check.py --spec` и, при референсе, сверку
  `motion_probe.py compare` — сводку заказчик видит вместе с Play.
- **Видео-референс** — листом, кадрами с таймкодами и таймлайном моментов; отрезки «что взять» — объект, свойство,
  число и «чего не брать» (creative 09/02 §4.3). Сам ролик исполнителю не передаётся: файлы — в
  `…/design/<surface>/motion/`, во входе холста — ссылки на них.
- **Живая сцена.** Холст в Play исполняет WebGL, three.js и библиотеки движения: живая сцена собирается на холсте
  своим движком (`kb/3d/16-js-scenes/`; библиотека — модулем с CDN, когда нужна модель GLB, модель — текстом, под
  `<canvas>` — постер; cd 05/03 §3), а сцена, которой холст не
  исполняет, — лабораторной страницей. Заказчик утверждает живую сцену по Play, живой странице или её записи, а не по
  постеру макета (`3d/15-showcase/VERDICT.md` §5.1).
- Отклик компонентов (наведение, фокус) и переходы интерфейса по шаблонам (смена экрана, диалог, панель, список) —
  токены движения ДС, пружины — тоже токенами (ui 08, ui 09/04 §2.10). У кабинета этапа движения нет: рабочие экраны
  без движения подачи, отклик и переходы — токенами. Прототип главного эффекта до выбора направления (§ Направления) — прототип, а не
  эффект макета.

## Холст

Макет рисует Claude Design: холст — артефакт типа Design на поверхность, ДС — артефакт типа Design System на продукт.
Исходники обоих — в репозитории, claude.ai — живой редактор и канал показа; артефакты публикуются по ходу работы,
публичная у них ссылка или приватная — постоянное решение заказчика на проект, строкой «Ссылки» в `ARTIFACTS.md`;
реальные данные клиентов в публичной ссылке — только с согласия их владельца. Публикация («прочитать →
слить → опубликовать»), задания по этапам и стоп — протокол холста скилла
`.claude/skills/design-deep-dive/references/claude-design.md`; правила формата типов отдаёт инструмент `Artifact`.

- **Вход** — `…/design/<surface>/input/`: производный, собирается под вид входа (`directions` — страница «Направления»
  внутри `moodboard` и `style-tiles`; `treatment` — страницы «Креатив» и «Подача» внутри `art-direction`, только
  сайт; `mockup`, `motion`) из закрытых источников и руками не правится;
  прошлые входы — в git. В нём только проекции и манифест — `…/design/<surface>/input/INPUT.md` (этап; источники с
  путём, статусом и отпечатком; что заполнил агент — строкой «Going with»; пробелы; итог проверки), бриф холста, факты с
  разделом «Нельзя утверждать», референсы исполнителю, критерии приёмки; у сайта — на страницу структура из плана,
  тексты, ассеты, блок движения; у кабинета — контракт генерации экранов, тексты интерфейса, демо-набор, ассеты.
  Источники, которые исполнитель читает как есть (токены, проза и карта решений ДС, арт-дирекция, спецификации движения,
  планы ассетов, экраны), не копируются: копия отстала бы от источника. Тексты — по этапу: направления и подача берут
  строки первого экрана `assumed` · `checked` · `approved`, макет — только `approved`; факты — подтверждённые, пробел —
  видимая заглушка. Вход
  собирается на партию — страницы или экраны, которые холст рисует сейчас (поле `units` манифеста; остальные — строка
  «вне партии»): `scripts/project/canvas_input.py build <slug> <surface> --stage <вид входа> [--page … | --screen …]`,
  проверяет `canvas_input check <slug> [<surface>]` (свежесть, ручные правки, критерии по роду, проверка входа до
  публикации: этап держат гейт текстов и фактов и целостность входа, остальное — доклад);
  когда окружения нет, этап собирает вход по той же раскладке, отмечает в манифесте входа, что он собран без утилиты,
  и проходит ту же проверку чтением.
- **Адаптивы и копии.** Артборды холста — все ширины приёмки (`kb/common/acceptance-widths.yaml#artboards`): оригинал
  макета со всеми адаптивами — холст, заказчик смотрит его по ссылке, копий для просмотра нет. Артборд — страница
  фиксированной ширины, поэтому горизонтальный вылет на 320, ресайз, зум и обе темы на всех ширинах проверяются на
  собранной странице — пункты «после сборки»; тёмная тема на макете — твиком холста. Статичные HTML-копии артбордов
  (`…/design/<surface>/canvas/html/`, производные — `scripts/claude-design/dc_to_html.py build <slug> <surface>`)
  нужны только скриптам автопроверок: их собирают при постоянной просьбе о проверках, без неё копий нет, и это не
  находка; манифест `kit` считает съёмка (`scripts/claude-design/kit/shot.py`), в папке проекта его нет.
- **Проверки** — только по постоянной просьбе заказчика (строка «Проверки макета» в `ARTIFACTS.md`) или разовой просьбе
  в сессии: без просьбы агент результат не смотрит. Порядок — от дешёвого к дорогому: скрипты → сверка с фактами → глаза
  → судья → свежий аудит → заказчик (`phases.md` скилла). Файлы репозитория — схемы, вход, токены, контраст —
  проверяются без просьбы; свежесть статичных копий — только при постоянной просьбе.
- **Приёмка.** Критерии `…/design/<surface>/input/ACCEPTANCE.md` собираются вместе со входом по роду и уровню
  поверхности: у сайта — ещё SEO, право, формы и события, у кабинета — состояния экранов по набору, доступность и узкий
  экран; у пункта сказано, где он проверяется — на макете или на собранной странице. Итог, вердикт (`accepted` ·
  `accepted_with_notes` · `blocked`) и одобрение заказчика на страницу или экран — `REVIEW.md` поверхности (форма
  [`_template/REVIEW.md`](_template/REVIEW.md)) с отпечатком одобрения — артбордов и источников единицы (текущий —
  `ready show <slug> <surface>`): одобрение снимает правка артборда или источника своей единицы, а не пересборка входа и
  не правка соседней. Пункты «после сборки» уходят в манифест готовности. Принимает заказчик.
- **Правки заказчика на холсте** поднимаются в источник по роду правки — иначе следующая сборка входа их затрёт: облик
  системный (акцент, радиус, шрифт, плотность, тема; одно значение на многих элементах) — в токены DTCG с пересборкой
  ДС; облик разовый — ближайший токен в исходниках холста; текст — в copy deck или тексты интерфейса экранов: правка
  заказчика — его утверждение, откат на холсте — только при находке фактов или права; число, имя, цена, срок — новым
  фактом с источником; структура — в план страницы или экраны с согласия
  заказчика; картинка заказчика — в план ассетов и манифест; положение и размеры на артборде — в исходниках холста.
- **Коммиты.** Синхронизация с холстом работает без коммитов; в точках сохранения — конец итерации, приёмка, конец
  этапа и сессии — агент предлагает коммит с готовым сообщением (облачная сессия теряет незакоммиченное); коммитит
  человек или агент по его явной просьбе (CLAUDE.md §5).
- **Артефакты и условия** — `ARTIFACTS.md` продукта (форма [`_template/ARTIFACTS.md`](_template/ARTIFACTS.md)): адреса,
  релизы и чтения артефактов, чей аккаунт ими владеет, загрузки, условия холста по поверхностям, просьба о проверке,
  решение о ссылках.

## Пакет для кода

Репозиторий кода берёт файлы стратегии по контракту путей (`docs/README.md § Что docs отдаёт соседям`) снимком —
правило ниже. Готовность каждой поверхности сводит манифест `…/design/<surface>/ready.yaml` (форма
[`_template/ready.yaml`](_template/ready.yaml)): что закрыто, что принято на макете, что можно публиковать и что
проверить после сборки. Его
собирает `scripts/project/ready.py build <slug> <surface>` на этапе `package` после аудита — `design_audit check` на
переходе, скилл `/design-audit` перед коммитом: дефекты файлов из аудита исправляют до пакета, а дефект, который без
данных заказчика не исправить, — доклад, и собрать пакет с ним решает заказчик
([`phases.md § Принципы всех этапов`](../../../../.claude/skills/design-deep-dive/references/phases.md#принципы-всех-этапов)).
Свежесть сверяет `ready check` (манифест равен сборке по текущим файлам); руками он не правится. Когда окружения нет,
этап собирает его по форме и сверяет статусы и отпечатки с файлами. Манифест несёт версию скилла, которым собран,
`skill_version` (файл `VERSION`): его форма — контракт этой версии; `ready check` версию не сравнивает — смена версии
без смены содержания манифест не устаревает.

- **Снимок.** Копия файлов стратегии в репозитории кода — только снимок: файлы одного коммита стратегии, только для
  чтения, и лок — коммит, версия скилла (`.claude/skills/design-deep-dive/VERSION`) и отпечаток каждого файла.
  Обновляет снимок только синхронизация, правят файлы только в стратегии: снимок — не второй источник, а копия
  коммита, и сборка и образ кода не зависят от соседнего чекаута; ворота после сборки гоняют утилиты соседнего чекаута
  на коммите лока, бриф, план и манифест им — файлы снимка (ниже). Снимок берут с коммита, на котором манифест свеж —
  `ready check` поверхности без находок; манифест отстал — снимок с этого коммита не берут, манифест пересобирает
  стратегия (у сайта — по блоку `STRATEGY-ISSUE`, `docs/README.md § Что docs отдаёт соседям`). Снимок поверхности:
  - **состав** — файлы `sources[]` манифеста (путь от папки проекта, у папки — все её файлы); файлы строк
    `status: accepted` манифестов ассетов продукта и поверхности (путь — от папки манифеста); у сайта — каталоги базы
    скилла, которые код читает на сборке как данные: блоки, формы, события, `head` и боты
    (`kb/site/04-blocks/blocks.yaml`, `kb/site/05-conversion-funnels/lead-forms.yaml`,
    `kb/site/07-seo-geo-performance-analytics/` — `events.yaml`, `head-kit.yaml`, `crawlers.yaml`): их версия — коммит
    и версия скилла, а `status` каталога — зрелость нормы в базе, не закрытость, код берёт их как есть; сам манифест.
    Прочие каталоги, на которые ссылаются файлы стратегии, — пороги ворот (`budgets.yaml`, `page-gates.yaml`) и нормы
    проектирования (каталог эффектов, уровни амбиций, словарь сайта, правовые требования) — в снимок не идут: их
    читают ворота и агенты из соседнего чекаута;
  - **отпечаток** — sha256, в локе — 64 строчные шестнадцатеричные цифры без префикса: у файла — его байтов, как
    `sources[].sha256`; у папки — один на папку, от строк «путь файла от папки, табуляция, sha256 файла» через перевод
    строки, UTF-8, в порядке путей по сегментам, а сегментов — посимвольно по кодовым точкам Unicode, без учёта
    локали (`dir_sha` в `scripts/project/ready.py` скилла), как у папки в `sources[]`; у ассета — `sha256` его
    принятой строки манифеста без префикса `sha256:`: он равен файлу (`plan_to_assets.py check`, иначе `error`); у
    каталога базы и манифеста — sha256 файла. Отпечатки лока равны `sources[].sha256` и `sha256` принятых строк:
    расхождение значит, что снимок отстал или правлен, — его обновляет синхронизация, а не правка.
- **Что читает код.** Сайт (`<org>/site`) — слой страницы, факты и голос, ДС (токены с CSS-переменными, прозу, карту
  решений), бренд и ассеты продукта, арт-дирекцию, спецификации движения и лабораторные страницы принятых приёмов
  (`…/design/<surface>/motion/lab/<id>/`), ассеты поверхности с манифестом, исходники холста с принятыми артбордами,
  `REVIEW.md` и манифест. Кабинет (`<org>/frontend`) — FSD-карту, экраны с картой
  маршрутов и текстами интерфейса, ДС, бриф на вид (плотность, темы), продуктовый паспорт, ассеты, исходники холста с
  артбордами принятых экранов, `REVIEW.md` и манифест. Мобильное приложение и бот берут токены ДС и голос; хаб
  `<org>/infra` по роду поверхности выбирает, какой код поднимать.
- **Единица готова** (`ready: true`), когда закрыта её композиция (план `approved`, экран `stable`), тексты
  `approved`, факты публикуемы или пробел назван, макет принят с совпавшим отпечатком одобрения, а у сайта закрыта и
  поверхность — бриф и у рода `site` карта `approved` (иначе блокер «поверхность: …» и ни одна единица не готова).
  Публикуем факт с разрешением, сроком и проверкой (`claims_check.py`), а его машинное значение `machine`, которое
  берёт страница, — из формулировки `canonical`: страница называет факт, на него ведёт цель `messenger:<fact-id>`
  (плана или призыва шапки карты) или его `machine` стоит литералом цели плана. `machine` не по форме или не из
  формулировки (error COPY-F-MACHINE `lint-facts`) — блокер «факты: …» этой единицы: код взял бы значение, которого
  нет в утверждённом факте; исправление `machine` снимает блокер без новой приёмки макета — в отпечаток одобрения оно
  не входит. Проверка, которой нечем сверять, готовой единицу не называет: файл фактов не читается (YAML не
  разбирается, не форма фактов) — блокер «факты: файл фактов не читается» у единицы, которая берёт факты: называет
  факт или пробел либо ведёт цель телефона, почты, мессенджера или адресом ссылки. ДС не утверждена, покрытие ДС
  типов своего экрана не полное, FSD-карта кабинета не `stable`, открытый источник контекста (ниже) — строки `open`
  «решение заказчика: …»: готовность они не держат, решает заказчик; FSD-карту код читает сам. Статус манифеста
  `partial` законен: код собирает готовые единицы. Единица без макета готова только решением заказчика, записанным
  в заметке пропусков поверхности, и пометкой `mockup: skipped` в манифесте.
- **Публикация.** Код публикует единицу с `publishable: true` — она готова, а в `open` только строки «решение
  заказчика: …» (заглушек, демо-фактов, демо-кадров, шрифтов без файла и темы брифа без темы токенов нет), — и с
  `copydeck.py validate --final` по её copy deck без `error` (гейт 3): `open` видит демо-кадры `x-demo`, шрифты и
  тему, `--final` — пустую мету и неутверждённую страницу. Две строки `open` — у каждой единицы поверхности:
  - «шрифт: <семейство> <насыщенности> …» — у начертания токенов ДС, которому нужен файл (§ ДС), нет принятой строки
    манифеста продукта с этим `font` (семейство, насыщенность числом или диапазоном, `style: normal`), файлом и
    лицензией `license`; семейству без типографического токена хватает одного такого файла. Без файла начертания
    страница не та, что одобрена на макете: браузер подставит запасной шрифт или синтезирует насыщенность;
  - «тема: …» — бриф поверхности ждёт темы, которой нет у токенов ДС (§ ДС, правило R-COV-010): код ставит тему
    брифа атрибутом `data-theme`, и без неё у токенов страница получит не ту `color-scheme`. Строку снимает тема
    значений `modes.base` или режим токенов и пересборка производных — правка, которая снимает одобрения единиц, или
    правка темы брифа: решает владелец продукта.

  Обе строки готовность не держат — код собирает единицу для показа, — а публикацию держат. Вход сверки, который
  есть, но не читается, публикацию держит той же строкой с причиной «… сверить нечем»: токены ДС (файл не
  разбирается, не объект или не по форме — ошибки R-STRUCT-006) — «шрифт: …» и «тема: …», бриф поверхности —
  «тема: …», план ассетов страницы — «демо-кадр: …». Готовность такая строка не держит: ДС и план ассетов —
  контекст, принятый макет стоит на производном CSS; токенов или брифа нет — сверять нечего, строки нет.
- **Что обязано быть закрыто.** Каждый источник `sources[]` входит в одну из трёх групп:
  - **единица** — композиция (план страницы, экран кабинета), тексты (copy deck страницы, строки `texts.md` экрана),
    факты, которые она называет, и макет (артборды принятой единицы с их статичными копиями, `REVIEW.md`): закрыта
    по правилу «Единица готова» — код собирает только единицы с `ready: true`;
  - **поверхность** — у сайта бриф и у рода `site` карта: закрыты, на них стоит композиция; их закрытость входит в
    `ready` единицы;
  - **контекст** — всё прочее: ДС (токены, CSS-переменные, проза, `system.yaml`), бренд, голос, арт-дирекция,
    спецификации движения и лабораторные страницы приёмов, получатели заявок (`integration.md`), манифесты ассетов, у
    кабинета ещё карта экранов, блоки и каркасы, FSD-карта, бриф на вид и паспорт визуала, а также строка поверхности
    в `surface.md` (поля `surface`, `type`, `web_kind` манифеста). Контекст может быть открыт: код берёт его как есть,
    решает заказчик — открытый источник со статусом становится строкой `open` «решение заказчика: <путь> <статус>» у
    единиц, которые на нём стоят (спецификация движения — у своей страницы, блок и каркас кабинета — у своих экранов,
    прочее — у всех); правка контекста, на котором стоит макет единицы, снимает её одобрение (отпечаток одобрения). Из
    манифестов ассетов код берёт только строки `accepted`.
- **Ворота после сборки.** Скорость, вес и поведение собранной страницы, а с ними пункты среды, которых на артбордах
  не проверить, — вылет на 320, ресайз, зум и обе темы на ширинах приёмки — проверяет репозиторий кода утилитами этого
  скилла из соседнего чекаута стратегии (`../strategy/.claude/skills/design-deep-dive/scripts/…`) в окружении машины
  `~/.cache/design-deep-dive/`: одна копия утилит и порогов, версия — коммит стратегии
  (`page-gates.yaml#phases`). До сборки стратегия проверяет своё: схемы, план, ассеты, макет (по просьбе заказчика — на
  статичных копиях артбордов). У страницы сайта пороги —
  профиль бюджета плана (`budget_profile`, `x-gate-exception`); у кабинета лабораторных порогов для экранов в базе нет —
  поле p75, RUM и сценарии реакции AC-PRF-04…06 на собранном приложении (ux 12/03 §9, позиция). Цепочка утилит —
  `docs/README.md § Что docs отдаёт соседям` (абзац «Ворота после сборки»), поля их отчётов —
  `scripts/README.md § Ворота после сборки`; вердикт — `page_gates.py --brief … --plan … --ready … --json`: ключи
  вердикта — из брифа и плана, код читает поля JSON (`verdict`, `B`, `S`, `after_build`, версия контракта
  `skill_version`), а не код выхода. Пункт `after_build` манифеста — `{id, severity, check}` из критериев приёмки
  (`kb/common/acceptance-criteria.yaml` скилла). Способ `check` — строки вердикта `page_gates.py` с id ворот
  (`{gates: […]}`: исход пункта вердикт с `--ready` пишет сам), утилита скилла с путём в её JSON и условием
  (`{tool, field, pass}`), тест самого репозитория кода (`code`) или человек с записью итога (`manual`); форма способа,
  исход пункта и его тяжесть — правило этих критериев (поле `check`). Блокирует только B — вердикта и непройденного
  пункта `after_build` со способом `code`, `tool`, `manual` (гейт 5).
- **`frontend-design` в код-репо.** Манифест несёт бриф для этого скилла: род поверхности, уровень амбиций и потолок
  движения — у страницы сайта; у экранов кабинета — поправки `ui/CONTRADICTIONS.md §[C25]` (фон сплошной, градиент
  только в названных местах, без оркестрованной загрузки, гарнитура с проверенной кириллицей). Облик — только токены и
  проза ДС проекта: свою палитру и шрифты скилл не выбирает; сам скилл не отключается.

## Статусы

«Закрыто» — статус в самом файле по его схеме или форме; ставится по слову того, кто закрывает. Что код обязан
получить закрытым, а что берёт как есть, — правило «Что обязано быть закрыто» (§ Пакет для кода).

| kind | поле | в работе | закрыто | кто закрывает |
|---|---|---|---|---|
| `brand` | `status` | `none`, `draft` | `verified` + `approval` | заказчик — факты бренда |
| `design-system` | `status` карты решений | `draft`, `proposed` | `approved` + `approval` | заказчик — «Keep» ДС до экранов |
| `app-brief` | `project.status` | `draft`, `proposed` | `approved` + `project.approval` | владелец продукта |
| `art-direction` | `status` | `draft`, `proposed` | `approved` + `approved_by`, `approved_at` | заказчик |
| `visual-dna` | `status` | `draft` | `approved` + `approved_by` | человек |
| `asset-plan` | `status` | `draft` | `approved` + `approval` | заказчик; траты — вместе с владельцем денег |
| ассет | `status` строки манифеста | `draft` | `accepted` | заказчик; мелкие кодовые — в составе ДС |
| `treatment`, `motion-spec` | `status` | `draft`, `proposed` | `approved` | заказчик |
| макет | вердикт и одобрение в `REVIEW.md` на страницу или экран | `blocked`, нет одобрения | `accepted`, `accepted_with_notes` с совпавшим отпечатком | заказчик |

У входа холста и манифеста готовности своего статуса нет: они производные от статусов источников.

**Forward-only** (`.claude/rules/forward-only.md`). В файле — текущая версия и запись того, как выбрано: направления и
карточки с `choice` (выбранное, `merged_from`, отклонённые с причиной — схема держит направления и у `approved`),
версия, `review_by`, `on_brand_change`, `provenance`, `checked_at`. Уходят записи `lifecycle.history` старше текущей
версии (остаётся одна), статусы `superseded` и `retired`, поле `supersedes` — заменённый документ перезаписывается,
старый живёт в git; папок по итерациям проверок нет — `…/design/<surface>/review/` держит последний результат;
референсы отклонённых направлений уходят из мудборда.

## Производные

Производное собирает утилита скилла из источника — команда `build`, свежесть сверяет её `check` (вызов и вывод —
`scripts/README.md § project — утилиты по артефактам проекта`); руками его не правят, в git оно лежит рядом с
источником (его читают код и холст), а `/design-audit` сверяет свежесть: пересборка даёт те же файлы. Когда окружения
нет, этап собирает производное по той же форме или раскладке, а первая сессия с окружением пересобирает его утилитой.

| производное | из чего | утилита |
|---|---|---|
| `…/design/system.tokens.css` | токены DTCG | `ds_build` |
| передняя часть прозы ДС с токенами (с параметрами пружин `x-springs`) | токены DTCG | `ds_build` |
| `tokens.json` и `README.md` артефакта Design System | токены DTCG; проза ДС | `ds_build` |
| вход холста `…/design/<surface>/input/` с критериями приёмки | закрытые источники этапа | `canvas_input` |
| статичные копии в `…/design/<surface>/canvas/html/` — при постоянной просьбе о проверках | артборды холста | `dc_to_html.py` |
| манифест готовности `…/design/<surface>/ready.yaml` | закрытые файлы поверхности и `REVIEW.md` | `ready` |

`REVIEW.md` — не производное: его пишут этапы холста и утилиты `kit`, а одобрение в нём сверяется отпечатком единицы —
её артбордов и источников (`ready show`). Производный CSS ДС — источник этого отпечатка у каждой единицы: пересборка,
которая меняет файл — после правки токенов или версией скилла с другой формой файла, — снимает одобрения всех единиц до
новой приёмки, и решает её владелец продукта. Отставший файл (`ds_build check`, R-FRESH-001) остаётся рабочим: код
берёт его как есть, готовность, публикацию и снимок отставание не держит.

## Клиентский режим

В сессии `/entrypoint-for-business` клиент сам рассказывает о бренде и приносит свои референсы (что нравится,
«брать / не брать» — словами): черновик фактов бренда ложится в `brand.yaml`, референсы — в `references[]` брифа с
`source: customer`. Выбор направления или карточки, утверждение плана и ключевых ассетов, «Keep» ДС, приёмка макета и
просьба о проверке — решения заказчика: клиентский оркестратор записывает их у себя, исполнитель переносит в файлы
(`choice`, статус плана ассетов, одобрение в `REVIEW.md`, строка просьбы в `ARTIFACTS.md`) с отпечатком версии, по
которой решал заказчик; версия с тех пор изменилась — переспрашивает.

## Связи с другими слоями

- **Слой страницы** (`site/<surface>/`): точки старта дизайна и что он пишет в план —
  `../site/README.md § Связь со слоем дизайна`. Бриф даёт уровень амбиций, темы (режимы ДС), выражение бренда и
  референсы заказчика; план — макроструктуры для «Направлений», медиа- и 3D-слоты для плана ассетов, контейнеры подачи;
  copy deck — тексты холста и строки ассетов; факты и голос — вход холста и README ДС.
- **Слой проекта.** Vision («Name», «Devices and accessibility»), таблица постур `user.md`, `surface.md` (тип и род),
  статусы объектов `object.md`, паспорта `ai` возможностей, `constraint.md` — проекции ядра брифа на вид; изменились
  источники — проекции пересобираются, а не правятся в брифе.
- **Экраны кабинета** (`screens/<surface>/`). Каждый `ui:<Тип>` стабильных экранов → компонент ДС; роли строк
  `screens/<surface>/texts.md` → стили текста; длина строки (`maxlen`) выводится из ширины компонентов ДС; ключи
  `responsive` каркаса — имена диапазонов, границы — токены `breakpoint.*` (таблица — README экранов); метафора
  `illustration=` пустого состояния — из паспорта; конвенции карты экранов исполняет ДС; наборы `states` экранов →
  состояния с визуальным кодом в брифе на вид; `screens/<surface>/assets/` — сырьё экранов, а не мудборд.
- **FSD-карта** (`fsd/<surface>/`): слайс `shared-ui` называет тип словаря, который реализует; тема фронта — из токенов.
- **Мобильное приложение и бот:** значения темы `<org>/mobile` — токены ДС продукта (оболочка приложения, «Theme &
  locale»); голос продукта — у приложения и бота; своих этапов дизайна у них нет.
- **Сквозной аудит** (`/cross-audit`): у поверхности с закрытой композицией есть принятый макет с совпавшим
  отпечатком; облик поверхности не спорит с её назначением.

## Язык контракта

Структурные идентификаторы, которые читают репозитории кода, — английские и не переименовываются: пути токенов DTCG —
они же имена CSS-переменных, имена компонентов ДС, типы словаря и id расширений, ключи `--allow`, id слотов плана
ассетов, id страниц и экранов манифеста готовности, род поверхности `web-kind`. Ключи машинных файлов — ключи схем базы
и форм [`_template/`](_template/). Значения-тексты — описания, причины, правила бренда, подписи — по-русски.

## Anti-patterns

- ❌ Облик вне слоя дизайна и подачи секций плана — в interface, экранах, FSD-карте, mobile.
- ❌ Облик без выбора владельца продукта: направление, карточка стиля, замена шрифта «по умолчанию агента»; факты бренда
  без материалов заказчика.
- ❌ Второй бриф или паспорт одного мира: `app-brief` на поверхность, арт-дирекция у кабинета, средний паспорт на два
  мира.
- ❌ Правка производного руками: вход холста, статичные копии, манифест готовности, CSS-переменные, передняя часть
  прозы, `tokens.json` и README артефакта; копии источников во входе холста.
- ❌ Копия макета для просмотра: оригинал — холст в claude.ai, второй источник разошёлся бы с ним; статичные копии —
  только для автопроверок по просьбе заказчика.
