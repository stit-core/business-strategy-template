# Артефакты экранов

Слой композиции экранов проекта, **партиционированный по поверхности (surface)**: из аналитических артефактов
`docs/projects/<project-slug>/interface/<surface>/` синтезируется детерминированная карта экранов той же поверхности —
экраны с маршрутами и состояниями, блоки с контрактами, каркасы с навигацией, свод карты экранов и реестр текстов
интерфейса. По ним слой дизайна собирает макет, а FSD-карта — карту кода фронта. Этот файл — **канон
слоя**; форма одной папки поверхности (4 файла-формы по kind и формы `map.md`, `texts.md`) лежит рядом в `_template/`.
Данные каждого проекта живут в `docs/projects/<project-slug>/screens/<surface>/`.

Экраны есть у поверхностей маршрута приложения: `web` рода `app`; `admin`, `desktop`, `embed`. У `type: web` —
только у рода `app`: у рода `landing` и `site` на месте экранов, интерфейса и FSD-карты стоит слой страницы
`site/<surface>/` (`../site/README.md`). Поверхность с `type: bot` вместо экранов получает слой диалогов
`telegram-bot-flow/<surface>/` (`../telegram-bot-flow/README.md`), с `type: mobile` — карту приложения
`mobile/<surface>/` (`../mobile/README.md`).

Артефакты — **аналитика композиции**: семантическое дерево из компонентов (типов закрытого словаря, `ui:`), узлов
раскладки, блоков, данных и ключей текстов. **Маппинг на FSD здесь не делается** — карта слайсов живёт в слое
`fsd/<surface>/` (`../fsd/README.md`), который читает экраны и блоки этого слоя как источник. **Облика здесь нет**:
цвет, типографика, пространство, движение, вид и размер компонентов решает слой дизайна `design/` токенами
дизайн-системы; макет собирает слой дизайна по контракту генерации, который отдаёт этот слой (раздел «Что слой отдаёт
макету»).

## Воркфлоу

```
interface/<surface>/  ──►  screens/<surface>/  ──►  texts.md  ──►  макет (слой дизайна design/)
 ситуации, сценарии,        карта и маршруты,        черновик →       контракт генерации:
 зоны, блоки, данные        экраны и состояния,      проверка →       экраны, состояния, данные,
                            блоки и контракты,       утверждение      тексты, дизайн-система
                            каркасы, доступность
                                    │
                                    └──►  fsd/<surface>/  (карта кода фронта)
```

(все слои — в папке поверхности проекта `docs/projects/<project-slug>/{interface,screens,fsd}/<surface>/`)

1. В `docs/projects/<project-slug>/interface/<surface>/` заведены и углублены сущности и сценарии хабов (через
   `interface-deep-dive`).
2. На их базе создаются артефакты в `docs/projects/<project-slug>/screens/<surface>/` (через `screen-deep-dive`) —
   каждый ссылается на свой источник в interface той же поверхности через `slug`.
3. Тексты интерфейса ложатся в реестр `texts.md`: черновик, проверка, утверждение владельцем продукта.
4. Слой дизайна собирает по экранам макет; карту слайсов для фронт-кода строит слой `fsd/<surface>/`.

**Порядок внутри этапа «экраны»** (ux 13/04 §13–§24): раздел «Переход» `map.md` → основной каркас и навигация
(корневые зоны, вариант навигации) → экраны: тип, объект, главная задача, ключевое действие, маршрут, доступ,
переходы → блоки и их контракты → состояния по обязательному набору → служебные экраны (решения — раздел `MVP`
vision) → доступность (конвенции, лендмарки) → узкий экран (потоки, раздел «Узкий экран» `map.md`). Шаги обязательны,
кроме разделения приложений при одной роли и узкого экрана, если vision записал «только десктоп».

## Состав слоя

| kind / файл | сущность | один-в-одно про |
|---|---|---|
| [`flow`](_template/flow.md) | поток: серия экранов одной задачи по вьюпортам | вьюпорт-вариативность |
| [`screen`](_template/screen.md) | экран: маршрут с типом, объектом, главной задачей и заполненными слотами каркаса | что в каких слотах, состояния, маршрут и доступ |
| [`block`](_template/block.md) | раскрытие блока interface в дерево узлов; контракты формы, коллекции, плиток | как реализуется аналитический блок |
| [`shell`](_template/shell.md) | каркас: слоты, навигация, лендмарки, состояния приложения | капсула экрана + облицовочный адаптив |
| [`map.md`](_template/map.md) | singleton поверхности: свод карты экранов, маршрутов и навигации + решения «один раз на приложение» | карта и маршруты поверхности |
| [`texts.md`](_template/texts.md) | реестр текстов интерфейса поверхности | строки по ключам: роль, длина, статус |

**Поток (flow) — не пользовательский сценарий.** Сценарий задачи — шаги, ветвления, ошибки, исходы — kind `scenario`
в interface той же поверхности; какой экран на шаге, что сохраняется при переходе и как вернуться — поля экрана и
раздел «Переход» `map.md`. Поток заводится, только когда число экранов одной задачи на десктопе и на телефоне разное.

## Структура папок

Канон формы (этот README + формы по kind, как в `_template/interface/`) живёт один раз в
`docs/projects/_template/screens/`; подпапка `_template/` описывает **одну папку поверхности**:

```
docs/projects/_template/screens/
├── README.md                       (этот файл — канон слоя)
└── _template/                      (форма одной папки поверхности)
    ├── map.md                      (форма свода карты экранов — singleton поверхности)
    ├── texts.md                    (форма реестра текстов интерфейса)
    ├── flow.md                     (форма flow)
    ├── screen.md                   (форма screen)
    ├── block.md                    (форма block)
    └── shell.md                    (форма shell)
```

Данные экранов живут в папке поверхности проекта `docs/projects/<project-slug>/screens/<surface>/` (одна папка на
поверхность маршрута приложения из реестра `surface.md`):

```
docs/projects/<project-slug>/screens/
└── <surface>/
    ├── map.md                      (свод карты экранов и решения поверхности)
    ├── texts.md                    (реестр текстов интерфейса)
    ├── flows/
    │   └── <slug>/index.md
    ├── screens/
    │   └── <slug>/index.md
    ├── blocks/
    │   └── <slug>/index.md
    ├── shells/
    │   └── <slug>/index.md
    └── assets/
        └── <kind>/<slug>/          (сырьё экранов: снимки интерфейса заказчика, наброски, чужие экраны)
```

Каждая сущность — папка `<slug>/` с файлом `<slug>/index.md`. Папка оставляет место для будущих add-on (заметки,
скриншоты, отдельные macro-вью), не плодя файлов сейчас. Если у сущности кроме него ничего нет — это нормально.
Поверхности изолированы: ссылки внутри `screens/<surface>/` и зеркала с `interface/<surface>/` — в пределах одной
поверхности.

`assets/` — сырьё экранов: снимки действующего интерфейса заказчика, наброски, чужие экраны как референс композиции.
Это не мудборд и не облик: мудборд, направления, иллюстрации и иконки живут в слое дизайна `design/`.

## Форма артефакта

```markdown
---
slug: <kebab-case>
name: <человекочитаемое имя>
description: <одна фраза о сущности>
status: draft | stable
<доменные поля по kind>
---

# <slug>

<одна-две поясняющие фразы>

​```yaml
<дерево | slot-fills | states | прочая структура>
​```
```

Маркеры `<>` — заполняемые места. `status` — зрелость записи относительно критериев своего kind (как в каноне
`docs/projects/_template/interface/`). Связи — слаг-рефами в бэктиках (форма ячеек — как в interface).
Frontmatter — YAML, дерево — fenced ```yaml```-блок в теле. `map.md` и `texts.md` — своя форма: свод таблиц и реестр
(`_template/map.md`, `_template/texts.md`).

## Нотация дерева

Дерево живёт в ```yaml```-блоке тела артефакта и **парсится как YAML** — компактная форма: узел без детей — строка,
узел с детьми — словарь из одного ключа-головы со списком детей, узел со структурными атрибутами — словарь атрибутов.
Узлы — **семантические**: описывают намерение композиции, не CSS-детали. Облик (пиксели, цвета, шрифты, вид и размер
компонента) в дерево не пишется.

```
узел       := лист | ветвь
лист       := голова                      строка YAML; в draft допустим литерал текста в кавычках
ветвь      := { голова: дети | структура } словарь из одного ключа
дети       := [ узел, … ]
структура  := { атрибут: значение, …, children?: [ узел, … ] }    items, columns, areas, fill, children
голова     := префикс ":" имя { " " атрибут "=" значение }
префикс    := ui | layout | block | data | text | icon
имя        := ui: <Тип>[.<Часть>] · data: <item>[.<атрибут>] · text: ключ реестра · layout: row|stack|grid|layer · block, icon: slug
значение   := токен без пробелов: slug, data:…, text:…, $слот, число
```

- **Корни.** У блока `tree` — словарь внутренних областей (`block-header` · `block-body` · `block-footer` ·
  `block-aside`) → дети; у каркаса `tree` — дети; у экрана `slot-fills` — слот → `block:<slug>` \| дети \| `—`;
  `states` — ключ состояния → слот → дети \| `'не применимо: причина'`.
- **Атрибут — в одном месте узла.** Простое значение пишется в голове (`items=nav`, `value=data:study.name`),
  составное (список колонок, области сетки) — ключом структуры. Голову разбирает одна регулярка: префикс, имя, пары
  `атрибут=значение` без пробелов внутри.
- **Проверка.** Дерево, которое не парсится как YAML, — ошибка; ключ структуры или атрибут вне списка — предупреждение.
  Узел с детьми всегда кончается двоеточием, слот каркаса — атрибутом `fills=$<slot>` в голове узла.

```yaml
tree:
  block-header:
    - layout:row justify=between align=center gap=md:
        - ui:SearchInput
        - ui:Button level=primary action=create:
            - icon:plus
            - text:studies.list.create.action
  block-body:
    - ui:Table items=data:study:
        columns:
          - {field: data:study.name, label: text:studies.list.name.column-header}
          - {field: data:study.status, label: text:studies.list.status.column-header}
  block-footer:
    - ui:Pagination
```

### Узлы

| префикс | что это | пример |
|---|---|---|
| `ui:` | компонент — тип закрытого словаря `kb/common/components.yaml` (раздел `types`) или тип расширения проекта; часть составного — `ui:<Тип>.<Часть>` из `parts` типа | `ui:Button`, `ui:SearchInput`, `ui:Field.Label` |
| `layout:` | нейтральный узел раскладки — не компонент (см. «Узлы раскладки») | `layout:stack`, `layout:row`, `layout:grid` |
| `block:` | блок этой поверхности `screens/<surface>/blocks/<slug>` | `block:filters-panel` |
| `data:` | датум `interface/<surface>/data-items.md`; через точку — атрибут объекта, на который датум ссылается (`data-items.object`) | `data:study`, `data:study.name` |
| `text:` | ключ строки реестра `texts.md` той же поверхности | `text:studies.list.create.action` |
| `icon:` | иконка набора дизайн-системы проекта; имя сверяет слой дизайна | `icon:plus`, `icon:chevron-down` |
| `block-*` | внутренняя область блока — корень `tree` блока | `block-header`, `block-body`, `block-footer`, `block-aside` |

**Компонент — тип закрытого словаря.** Одна потребность — один тип: два способа выбрать дату в одном продукте со
временем расходятся. Имя берут из словаря по потребности (`purpose`) и группе (`group`) типа, а не придумывают по
месту; имена из `aka` в экранах не пишутся — проверка подсказывает тип (`Navbar` → `TopBar`, `Search` →
`SearchInput`). Потребность, которую не закрывает ни один тип, проект оформляет расширением словаря в слое дизайна —
рядом с сопоставлением «тип → компонент дизайн-системы», с клавиатурным контрактом и ролями текстов частей. Дизайн-
система обязана создать компонент для каждого типа, названного в экранах. `ui:` вне словаря и расширения, часть вне
`parts` — ошибка.

**Композиции — не компоненты.** Каркас приложения, шапка страницы, список объектов, master-detail, панель фильтров,
панель массовых действий собираются каркасами и блоками из типов словаря (`kb/common/components.yaml`, раздел
`outside`); тип экрана — поле `type` экрана (раздел «Экран: тип, карта и маршрут»).

### Атрибуты

Список атрибутов закрыт; атрибут вне списка — предупреждение.

| узел | атрибут | значение |
|---|---|---|
| `ui:` | `level` | уровень действия: `primary` · `secondary` · `tertiary` (ux 04/10 §1.1–§1.2); «в меню» и «контекстное» — структурой, узлом внутри `ui:Menu` |
| `ui:` | `action` | действие словаря `projects/<slug>/action.md` — у `ui:Button`, `ui:Menu.Item` и других узлов действия |
| `ui:` | `illustration` | у `ui:EmptyState` — метафора из списка паспорта визуала продукта (слой дизайна) |
| `ui:` | `items`, `columns`, `value` | привязка данных: `data:<item>[.<атрибут>]`, у навигации — `items=nav` (пункты `map.md`, раздел «Навигация») |
| `ui:`, `layout:` | `fills` | в дереве каркаса — слот, который заполнит экран: `fills=$<slot>` |
| `layout:` | `gap` | размер намерения — имя токена группы `space` дизайн-системы: `gap=md` берёт значение токена `md` |
| `layout:` | `justify`, `align`, `wrap` | `start` · `center` · `end` · `between`; `start` · `center` · `stretch`; `true` · `false` |
| `layout:` | `columns`, `areas`, `fill`, `span` | сетка: число колонок или области; `fill` — узлы областей; `span` — у дочернего узла сетки |

Вид и размер компонента (`variant`, `size`) — не атрибуты: их решает дизайн-система. Уровень действия — смысл по
матрице действий, а не облик, поэтому он остаётся в экранах.

### Узлы раскладки

Стеки, сетки и отступы — не компоненты, а **композиция дерева** (внутренние области и порядок узлов). Намерение
раскладки дерево несёт нейтральными `layout:`-узлами; исполняют его макет и код по токенам дизайн-системы.

| узел | намерение | ключевые атрибуты |
|---|---|---|
| `layout:stack` | вертикальная композиция | `gap`, `justify`, `align` |
| `layout:row` | горизонтальная композиция | `gap`, `justify`, `align`, `wrap` |
| `layout:grid` | сетка | `columns`, `gap`, либо `areas` и `fill` |
| `layout:layer` | слой поверх потока (якорь оверлея) | `fills` |

**Размер намерения** — имя токена `space.*` дизайн-системы (`xs`, `sm`, `md`, `lg` …): значение даёт одноимённый
токен в текущем режиме плотности. Пиксели в дереве не пишутся.

### Внутренние области блока

Дерево `block`-артефакта **начинается с внутренних областей**, а не layout-узлов: у блока есть роли — шапка, тело,
подвал, боковая дорожка (`block-header` · `block-body` · `block-footer` · `block-aside`; идентификаторы —
handoff-контракт, не переименовываются). Их облик (бордеры, липкая шапка, закреплённый подвал) решает слой дизайна,
не дерево. Области опциональны; блок может содержать только `block-body`.

### Сетка с областями

Для нетривиальных сеток (дашборды, многопанельные рабочие места):

```yaml
- layout:grid:
    areas:
      - [search, search, action]
      - [filters, list, detail]
    fill:
      search: ui:SearchInput
      action:
        - ui:Button level=primary action=create:
            - text:studies.workspace.create.action
      filters: block:filters-panel
      list: block:studies-list
      detail: block:study-preview
```

### Данные и тексты в дереве

- **Данные.** `data:<slug>` — датум из `interface/<surface>/data-items.md`; `data:<slug>.<атрибут>` — атрибут
  объекта, на который ссылается датум (`data-items.object`). Тип, длины и перечень значений берутся у атрибута
  глоссария объектов; реальный источник данных — слой кода, артефакт фиксирует контракт.
- **Тексты.** Текст — ребёнок узла `text:<key>`, а не атрибут и не литерал: подпись кнопки, заголовок колонки
  (`label: text:<key>`), текст пустого состояния. В `draft` допустим литерал в кавычках (`- 'Новое'`); в `stable`
  литерал — ошибка, у ключа есть строка в `texts.md` (раздел «Тексты интерфейса»).
- **Иконка** — ребёнок узла (`- icon:plus`), не атрибут.

## Экран: тип, карта и маршрут

Карта экранов и реестр маршрутов поверхности — **поля экранов**: тип, объект глоссария, главная задача (возможность
этой поверхности), ключевое действие словаря, зона interface (мост «зона → раздел навигации → маршрут»), маршрут с
параметрами, доступ, состояние в адресе, индексация и переходы «куда · чем вызван · что сохраняется · как вернуться»
(форма — `_template/screen.md`). Свод по ним — `map.md` поверхности; его руками не авторят (`_template/map.md`). В
адресе живут вкладка, страница, фильтры, сортировка, вид и открытая панель; несохранённого ввода и секретов там нет.
Тип экрана — закрытый список ux 13/04 §14: он решает анатомию, строку обязательных состояний и трансформацию на узком
экране; экран без объекта и роли («главная», «обзор») без решения в `map.md` — типовая ошибка.

| `type` | тип экрана | каркас | строки матрицы ux 06/01 §3.1 |
|---|---|---|---|
| `dashboard` | дашборд, обзор | основной | «Дашборд и плитка показателя»; плитки — у блоков |
| `list` | список объектов | основной | «Список и таблица»; «Поиск» — при поиске |
| `object` | карточка объекта | основной; инспектор — слот `detail` | «Карточка объекта» |
| `edit` | создание и редактирование | основной; модальное окно — слот `overlay` | «Форма»; «Файл и вложение» — при вложениях |
| `wizard` | мастер | полноэкранный; на телефоне — поток | «Мастер и многошаговый процесс»; «Форма» — по шагам |
| `settings` | настройки | основной | «Настройки»; «Форма» |
| `master-detail` | список и детали рядом | основной; детали — слот `detail` | «Список и таблица» — панель списка; «Карточка объекта» — панель деталей |
| `canvas` | редактор и полотно | полноэкранный | строки нет: позиция `kb/common/CONTRADICTIONS.md`, «Состояния редактора и полотна» |
| `auth` | вход и регистрация | каркас входа | «Форма» |
| `service` | служебный экран: маршрут вне реестра, ошибка сервиса, плановые работы | основной | «Экран или маршрут целиком» |

У каждого экрана — ещё строка «Экран или маршрут целиком». Пустой экран нового аккаунта — не тип, а
`empty-first-run` стартового экрана; «нет прав» и «нет связи» — состояния `no-permission` и `offline`, а не
служебные экраны. При четырёх и больше экранах типы не все одинаковы: одинаковая структура всех экранов — признак
шаблона вместо проектирования (ux 13/04 §14).

**Реестр маршрутов закрыт.** Маршруты вне реестра `map.md` не создаются; ссылка на незарегистрированный маршрут —
ошибка. Служебные маршруты — маршрут вне реестра, ошибка сервиса, плановые работы — экраны `type: service`; есть ли
они, решает раздел `MVP` vision (системные сценарии ux 13/04 §22).

**Навигация — узел дерева основного каркаса** (`ui:Sidebar`, `ui:TopBar`, `ui:BottomNav` с `items=nav`), одна на
продукт. Пункты уровня 1 — корневые зоны interface по `order`, уровня 2 — их дочерние зоны; уровень 3 — вкладки
объекта внутри экрана. Вариант навигации — по числу разделов, типу приложения и частоте переключений (ux 02/02 §1.6);
видимость пунктов по ролям выводится из полей экранов `who` и `access`: разные роли — разные меню (ux 13/04 §16).
Боковая панель экрана (фильтры, меню настроек) — не навигация, а слот `side` или блок экрана.

## Состояния экрана

Один словарь состояний экрана на веб, мобильное приложение и бота — ux 06/01 §2. Ключи `states` экрана — slug
словаря; идеальное (заполненное) состояние — `slot-fills`, без ключа и без id. Мобильный слой и бот держат свои ключи
контракта с кодом и сопоставляют их этому словарю в своих канонах (`../mobile/README.md`,
`../telegram-bot-flow/README.md`).

| id | ключ `states` | группа | когда |
|---|---|---|---|
| S01 | `empty-first-run` | данные | объектов этого типа у пользователя ещё нет |
| S02 | `empty-filtered` | данные | поиск или фильтр не дал результатов |
| S03 | `empty-cleared` | данные | пользователь сам всё разобрал: задачи выполнены, входящие пусты |
| S04 | `partial-few` | данные | данных мало: одна-три записи при раскладке на много |
| S05 | `overflow-many` | данные | записей кратно больше расчётного |
| S06 | `stale` | данные | данные из кэша, обновление не прошло |
| S07 | `loading-initial` | процесс | первый показ экрана или блока |
| S08 | `loading-refresh` | процесс | повторный запрос: старые данные остаются видимыми |
| S09 | `loading-more` | процесс | догрузка следующей порции |
| S10 | `in-progress-background` | процесс | длительная операция идёт в фоне |
| S11 | `saving` | процесс | изменение отправлено, ответа нет |
| S12 | `success` | процесс | значимое действие завершено |
| S13 | `error-load` | отказ | данные не получены |
| S14 | `error-action` | отказ | действие пользователя не выполнено, ввод сохранён |
| S15 | `partial-failure` | отказ | часть блоков или массовой операции не прошла |
| S16 | `offline` | отказ | нет связи |
| S17 | `timeout` | отказ | ответ не пришёл за отведённое время |
| S18 | `no-permission` | доступ и правила | у роли нет прав на объект или раздел |
| S19 | `locked` | доступ и правила | объект редактирует другой пользователь или держит процесс |
| S20 | `archived-deleted` | доступ и правила | объект в архиве, в корзине или удалён |
| S21 | `limit-reached` | доступ и правила | достигнут предел тарифа, квоты или размера |
| S22 | `read-only` | доступ и правила | режим только для чтения |
| S23 | `not-found` | доступ и правила | объекта по адресу нет или его существование скрыто (ux 05/04 §4.1) |
| S24 | `generating` | процесс | идёт потоковый ответ ИИ (ux 13/03 §6) |

Что показать и что предложить в каждом состоянии и как это проверить — строки ux 06/01 §2.1–§2.4. Значение ключа
`states` — дельта слотов относительно `slot-fills` (дерево) или строка `'не применимо: причина'`.

### Обязательный набор

Набор экрана — объединение условий; каждое обязательное состояние — дельта или «не применимо: причина», прочие
добавляются свободно:

- `loading-initial`, `error-load` — экран грузит данные;
- `empty-first-run`, `partial-few` — на экране есть коллекция; `empty-filtered` — есть поиск или фильтр;
- строка типа экрана и строка «Экран или маршрут целиком» (таблица типов выше);
- строки компонентов блоков экрана — у типов с ключом `screen_states` в `kb/common/components.yaml` (таблица, список,
  плитка показателя, график, поле поиска, загрузка файлов);
- `no-permission` — доступ к маршруту ограничен ролями (`access: roles`);
- `not-found` — у маршрута есть параметр объекта (`params`);
- `offline` — поверхность работает без сети (решение в `map.md`, раздел «Решения»);
- `stale` — экран показывает живые данные;
- отказы ситуаций экрана (`situation.refusals` interface);
- `in-progress-background` — действие экрана у возможности с `duration: background` (паспорт возможности).

Набор составляет исполнитель экранов по этому списку; `/screen-audit` сверяет его с полями экрана, блоков и ситуаций:
непокрытое обязательное состояние — предупреждение, у `stable` — ошибка. «Продумай состояния» словами набор не
заменяет: в контракт генерации уходит список ключей.

### Приоритет

Когда состояний несколько, экран показывает одно по порядку:
`no-permission` > `offline` > `not-found` > `error-load` > `loading-initial` > `empty-filtered` > `empty-first-run`.
`stale` и `limit-reached` накладываются поверх содержимого, а не заменяют его.

**Пусто — только после загрузки**: пустое состояние показывается, когда загрузка закончилась без ошибки и данных нет;
«нет данных» во время загрузки — дефект (ux 06/01 §4.6).

### Частные правила

- **Блок со своим источником** (`source: own` во frontmatter блока) держит свои состояния в разделе `states` блока:
  `loading-initial`, `error-load`, у коллекции — ещё `empty-first-run`, `empty-filtered`, `partial-few`.
  `partial-failure` и общий `error-load`, когда без источника экран бессмыслен, — у экрана. Индикаторы и состояния в
  `tree` блока не пишутся — только в его разделе `states`.
- **`not-found` и `archived-deleted` — разные состояния.** `not-found` — объекта по адресу нет или его существование
  скрыто; `archived-deleted` — объект есть в архиве или корзине: статус, дата, кто, восстановить. Маршрут вне реестра —
  служебный экран, а не состояние.
- **`generating`** — у блока с ответом ИИ; действие остановки обязательно (ux 13/03 §6).
- **Пустое и главная кнопка шапки.** Главная кнопка видна в шапке экрана — пустое состояние указывает на неё текстом
  или кнопкой `level=tertiary`; шапки нет или кнопка в ней скрыта — главная кнопка стоит в пустом состоянии; несколько
  пустых состояний на экране (дашборд) — только текст и третичные кнопки (ux 06/01 §4.8, §3.3).
- **`offline`** — дельта называет, что доступно из кэша, что отложено и какие статусы у отложенных правок.
- **Иллюстрация пустого состояния** — атрибут `illustration` у `ui:EmptyState`: метафора из списка паспорта визуала
  продукта. Иллюстрации — только в местах ui 07/02 §1.1 (пустое состояние, онбординг, ошибка, успех и веха, анонс); на
  рабочих экранах админки их нет.
- **Состояния приложения** — сервис недоступен и плановые работы, истечение сессии, нет связи, демо-режим —
  объявляются один раз в разделе «Состояния приложения» основного каркаса; экран их не повторяет.
- **Тексты состояний** — строки реестра с ролями: пустые состояния — `empty` и `action`; `error-load` — `error`,
  `inline-message` или `banner`; `loading-initial`, `generating` — `status`; `no-permission`, `not-found` — `title`,
  `body`, `action`.

## Контракты блоков

Контракт действия на экране (ux 04/10 §1.1: имя, объект, кто может, уровень, результат, состояния, обратимость)
**собирается, а не пишется**:

| поле контракта | откуда |
|---|---|
| имя, глагол, прошедшее время, обратимость | строка словаря действий `action.md` |
| объект | `object` возможности или `data:` узла |
| кто может | матрица «пользователь × объект × действие» продуктового слоя (вычисляемая) |
| уровень | атрибут `level`; «в меню» и «контекстное» — узел внутри `ui:Menu` |
| результат | `transitions-to-screen` экрана и строка события в `map.md` (раздел «События») |
| состояния элемента | дизайн-система по `kb/common/components.yaml` (ключ `states` типа) |
| защита | шаг сценария interface; частое обратимое действие — отмена без подтверждения |
| длительность | `duration` паспорта возможности: `long` — индикатор прогресса и действие остановки в дереве, `background` — `in-progress-background` в наборе экрана |

- Одна главная кнопка (`level=primary`) на экран вне оверлеев; вторая — только в блоке со своим источником. Действие с
  обратимостью `soft-delete` или `irreversible` главной кнопкой не бывает (ux 04/10 §1.2).
- Действие частой ситуации (`frequency` — `hours-daily`, `daily`) не прячется только в меню (ux 04/10 §1.2).
- Модальное окно — для короткой задачи; правка строки таблицы — не в модальном окне; ошибка — не тостом; одно событие
  — одна форма сообщения (ux 04/07 §1, ux 04/08 §2.2).

Контракты семейств компонентов, без которых макет не собирается, блок несёт во frontmatter — поля и правила в форме
`_template/block.md`:

- **`form`** — у блока с субстратом `ввод` или `выбор`: запись на поле формы (ux 04/05 §1.1); тип, длины и перечень —
  у атрибута объекта, правило-инвариант — у домена.
- **`collection`** — у блока с `ui:Table`, `ui:List`, `ui:TreeView` или повторяемой `ui:Card`: задача, объём, фильтры,
  сортировка, массовые действия, способ на узком экране; от объёма по порогам ux 04/01 §2 зависят пагинация, поиск,
  управление колонками, `url-state` экрана, массовые действия и экспорт.
- **`tiles`** — у блока с `ui:KpiTile`: запись на плитку показателя (ux 04/03 §4.3); плитка без базы сравнения не
  выводится.

## Тексты интерфейса

Тексты интерфейса поверхности живут в реестре `texts.md` (форма — `_template/texts.md`); дерево экрана держит ключ
`text:<key>`, а не литерал. Ключ строится по месту и роли строки, а не по её значению:
`{раздел}.{экран}.{элемент}.{роль}` (ux 07/05 §3.1). Роль строки — из закрытого списка ролей текста ux 07/06 §7.2; роль текстовой части компонента задаёт
`kb/common/components.yaml` (раздел `text_roles`): текст под `ui:Button` — `action`, под `ui:Field.Error` — `error`.
Роль ключа, не совпавшая с ролью части, — ошибка.

Черновик строки пишет агент «допущением», проверяют словарь запретов и межстрочные проверки, утверждает владелец
продукта; статусы `assumed` → `checked` → `approved` и что проверяется на каждом — в форме реестра. Для экранов важно,
когда какой статус нужен: stable-экран требует, чтобы каждый его ключ был в реестре со статусом не ниже `checked`;
утверждение владельцем нужно до чистового макета и до передачи в код, а не для `stable` экрана: структура экранов не
ждёт утверждения каждой строки, а на макет и в код идут утверждённые тексты. Ключи реестра — они же ключи строк
локализации FSD-карты.

## Доступность и узкий экран

Слой экранов объявляет структуру доступности и узкого экрана до макета; исполняют и проверяют их дизайн-система и
приёмка макета.

**Доступность** (ux 13/04 §23):

- **Лендмарки** — поле слота каркаса `landmark` (`main` · `navigation` · `complementary` · `region` · `—`) и неявные
  лендмарки типов: `ui:TopBar` — `banner`, `ui:Sidebar` и `ui:BottomNav` — `navigation`. Ровно один `main`.
- **Заголовок** — ровно один текстовый узел роли `title` в основном содержимом экрана вне оверлеев (H1); у оверлея —
  `Modal.Header` или `Drawer.Header`.
- **Порядок табуляции** — порядок дерева; клавиатурный контракт — ключ `keyboard` типа в
  `kb/common/components.yaml`, в экране не пишется; тип расширения проекта обязан его назвать.
- **Конвенции «одно на приложение»** — строки раздела «Конвенции» `map.md`: фокус при открытии и закрытии оверлея,
  удалении строки, смене маршрута и ошибке формы; объявления (найдено, сохраняется, готово, тост); помощь в одном месте
  (узел помощи — один, в каркасе); повторный ввод и вставка в поля входа; лимит времени сессии. Видимый фокус и размер
  целей нажатия — дизайн-система.
- **Отступления экрана** — необязательный раздел `## Доступность` экрана: путь без перетаскивания у узла с
  перетаскиванием (например, `ui:FileUpload`), особая фокусировка.
- **Статус объекта** — текстом из статусов объекта глоссария, а не только цветом.

**Узкий экран** (ux 09/01 §8; ux 13/04 §24):

- Решения поверхности — способ реализации мобильного (нативное приложение — отдельная поверхность `mobile`) и
  трансформация каждого типа экрана на узкой ширине — разделы «Решения» и «Узкий экран» `map.md`.
- Функции от ширины не меняются, меняется их видимость: слот с `hidden` на узкой ширине — его функции доступны иначе.
- Навигация основного каркаса на узком экране — по числу разделов (ux 09/02 §1.6): нижняя панель вкладок или выдвижная
  панель; запись — колонка `narrow` раздела «Навигация» `map.md`.
- `type: master-detail` на телефоне — поток из двух экранов.
- Коллекция — способ `collection.narrow` блока.
- Оверлей на узкой ширине — поведение слота `overlay`: `fullscreen` или `bottom-sheet` (ux 04/07 §1.4).
- Планшетная ширина (класс medium M3) попадает в диапазон `sm`: у слотов каркаса — поведение на `sm` или «не
  применимо».

### Ключи `responsive` и брейкпоинты

Ключи `shell.responsive` — имена диапазонов ширины, границы диапазонов — токены `breakpoint.*` дизайн-системы
проекта. Пиксели в экранах не пишутся: сменится граница в дизайн-системе — диапазон сдвинется сам.

| ключ | диапазон | с эталонной шкалой ui 09/04 §1.3 |
|---|---|---|
| `xs` | ниже первой границы | ниже `breakpoint.tablet` |
| `sm` | от первой до второй границы | от `breakpoint.tablet` до `breakpoint.desktop` |
| `md` | от второй до третьей границы | от `breakpoint.desktop` до `breakpoint.wide` |
| `lg` | от третьей границы | от `breakpoint.wide` |
| `xl` | от четвёртой границы, если дизайн-система её объявила | в эталонной шкале нет — ключ не используется |

Классы окна M3 (compact, medium, expanded, large, extra-large; ux 09/01 §4.1) — словарь правил перестроения: что
меняется на переходе, решают пять вопросов ux 09/01 §4.2, а где проходит граница — токены дизайн-системы.

### Ширины приёмки

`viewport` экрана и потока задаёт ширины, на которых экран принимают на макете и собранной странице:
`kb/common/acceptance-widths.yaml` (ключ `by_viewport`). `mobile` — ширины ниже первого брейкпоинта дизайн-системы и
проверка вылета на самой узкой ширине; `desktop` — ширины от первого брейкпоинта; `any` — все ширины. Ширина приёмки
— не брейкпоинт: перестроение проверяют отдельно, на границах `breakpoint.*`.

## Что слой отдаёт макету

Макет экранов собирает слой дизайна по контракту генерации — десять разделов ux 11/04 §7.3. Контракт собирается во
вход холста из stable-артефактов; руками его по источникам не переписывают, и второго источника у него нет. Сборщики —
утилиты скилла дизайна `.claude/skills/design-deep-dive/scripts/project/`: контракт — `contract.py`, демо-набор —
`demo_data.py`, свод `map.md` — `screen_map.py`; во вход холста их кладёт
`canvas_input.py build <slug> <surface> --stage mockup`, а незаполненный пункт блока PRE показывает
`contract.py check` находкой R-MAT-011.

| раздел контракта | источник в слое проекта |
|---|---|
| Контекст продукта | vision (`Problem` — наблюдения ограничениями, `Users`); постура `user.md`; поля экрана `type`, `main-task`, `key-action` |
| Объектная модель | `object.md` с атрибутами, `action.md`, матрица «пользователь × объект × действие» |
| Карта экранов | свод `map.md`: закрытый список маршрутов, переходы, раздел «Переход» |
| Дизайн-система | слой дизайна: дизайн-система и «тип → компонент»; раздел «Конвенции» `map.md` |
| Обязательные состояния | список ключей на экран: ключи `states` ∪ обязательный набор; «не применимо» — с причиной |
| Данные | производный демо-набор: из глоссария объектов (типы, длины, перечни, примеры), объёмов коллекций и крайних случаев ux 06/01 §6.2; каждая запись — `example: true` |
| Тексты | строки `texts.md` в статусе `approved` — на чистовой макет; `aliases` объектов и `banned` действий; словарь запретов ux 07/06 |
| Запреты | ux 11/04 §1.7; этика ux 06/04 |
| Примеры | эталонный экран дизайн-системы; взаимодействия — из сценариев и переходов |
| Критерии приёмки | раздел «Приёмка» сценариев, «как проверить» ux 06/01 §2 по ключам состояний, закрытость маршрутов |

- **Демо-данные — производные**, авторского файла фикстур нет: он стал бы вторым источником. Макет на демо-данных
  допустим, публикация — нет.
- **Массовый провал возвращает работу сюда.** Провал состояний — обязательный набор экрана; маршрутов и тупиков —
  карта и переходы; переживания перехода — раздел «Переход»; текстов и чисел — реестр текстов и демо-набор;
  компонентов вне системы — `ui:` и сопоставление в дизайн-системе; форм — блоки с `form`; доступности — цель vision и
  лендмарки каркаса.

## Статус записи

- Потоки, экраны, блоки, каркасы и `map.md` — `draft` \| `stable`: зрелость записи относительно критериев своего kind.
  `map.md` в `stable` — авторские разделы полны, свод совпадает с экранами.
- Строки `texts.md` — свой статус: `assumed` → `checked` → `approved` (раздел «Тексты интерфейса»).
- Повышение в `stable` — через `screen-deep-dive` по подтверждению аналитика; понижение — только аналитик руками.

## Язык контракта

Структурные идентификаторы, которые читает код-репо `<org>/frontend` и FSD-карта, — **английские** и не
переименовываются: kind и поля frontmatter (`type`, `object`, `main-task`, `key-action`, `zone`, `route`, `params`,
`access`, `url-state`, `indexed`, `transitions-to-screen`, `slots`, `landmark`, `responsive`, `source`, `form`,
`collection`, `tiles`), ключи `states`, ключи текстов, префиксы узлов, имена типов словаря и внутренних областей блока.
Всё остальное — русский контент: названия, описания, тексты реестра.

## Anti-patterns

- ❌ Облик в артефакте: цвета, типографика, пиксели, `style=`, вид и размер компонента (`variant`, `size`). Облик
  решает слой дизайна токенами дизайн-системы.
- ❌ Оси контекста приложения (тема, бренд, плотность, направление письма) как атрибуты узлов или поля артефактов — их
  решают бриф на вид и дизайн-система, применяет корень приложения в коде.
- ❌ FSD-маппинг в screens (widget/feature/entity-имена в дереве, ссылки на слайсы `pages` и `widgets`). Карта
  слайсов живёт в своём слое `fsd/<surface>/`; артефакты screens остаются чистой композицией.
- ❌ Inline-логика: `if`/`then`, тернарники, вычислимые выражения. Артефакт — декларативный.
- ❌ Битый slug-реф (на несуществующий screen/block/shell/data-item), `text:` без строки в реестре, `ui:` вне словаря,
  имя из `aka`, атрибут вне списка.
- ❌ Литерал текста в дереве `stable`-артефакта.
- ❌ Ключ `states` вне словаря состояний экрана.
- ❌ Индикаторы и состояния в `tree` блока: состояния блока со своим источником — раздел `states` блока, остальные —
  у экрана.
- ❌ Маршрут вне реестра `map.md`; ручная правка свода `map.md` вместо правки экранов.
- ❌ Ссылка из папки одной поверхности в сущность другой поверхности — поверхности изолированы.
- ❌ Расхождение зеркал interface ↔ screens: если у `interface-block` в
  `docs/projects/<project-slug>/interface/<surface>/block.md` объявлены `ux-substrates`, тот же набор должен быть в
  frontmatter соответствующего `block`-артефакта той же поверхности.
- ❌ Breakpoints в `shell.tree` или в `screen.slot-fills`: облицовочный адаптив (sidebar→drawer) — только в
  `shell.responsive`. Структурный адаптив (1 desktop ↔ N mobile) — через `flow`, не через `screen`.
- ❌ `screen` без `shell`, `type`, `route` или `access`; `shell` без `slots`; `block` без `interface-block`; `flow` без
  `desktop` или без `mobile`.
- ❌ `block` 1:1 экрану: блок — содержимое слота, не route.
- ❌ `screens/<surface>/` у поверхности `web` рода `landing` или `site`: на его месте слой страницы.

## Связь с `interface/<surface>/` и продуктом

Источник синтеза — UX-слой **той же поверхности** того же проекта, `docs/projects/<project-slug>/interface/<surface>/`,
и продуктовый слой проекта:

| screens | → ссылается на → | источник |
|---|---|---|
| `screen.blocks` | M:N | interface `block.md` |
| `screen.situations` | M:N | interface `situation.md` (их `refusals` — в обязательный набор) |
| `screen.who` | M:N | interface `who.md` |
| `screen.zone` | M:1 | interface `zone.md` |
| `block.interface-block` | M:1 | interface `block.md` |
| `block.ux-substrates` | M:N | interface `ux-substrate.md` (зеркало interface) |
| `data:<slug>` в дереве | M:1 | interface `data-items.md` → объект глоссария |
| `screen.main-task` | M:1 | `capability/<surface>.md` той же поверхности |
| `screen.object`, колонка `object` реестра текстов | M:1 | глоссарий `object.md` |
| `screen.key-action`, атрибут `action=`, колонка `action` реестра текстов | M:1 | словарь `action.md` |

Когда сущность interface или продукта удаляется — каскадно удаляются ссылки в screens (правило forward-only).

## Связь с кодом

Прямой автоматической связи нет. Карту слайсов для фронт-кода строит отдельный слой `fsd/<surface>/` (мост к
`<org>/frontend`), читая экраны и блоки этого слоя как источник: путь страницы — маршрут экрана, охрана — доступ
экрана, тип `shared-ui` — тип словаря, ключи локализации — ключи реестра текстов. `url-state` экрана код читает из
screens как контекст. Макет по экранам собирает слой дизайна `design/` по контракту генерации.
