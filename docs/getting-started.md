# Getting started — от шаблона к репо стратегии

**[META]** Этот файл — для потребителя шаблона. Описывает путь от форка до
наполненного аналитикой репо стратегии проекта.

Принцип: **аналитика первична.** Рекомендуемый вход — оркестратор `/entrypoint`
(аналитик) или `/entrypoint-for-business` (клиент): принимает сырьё любого объёма,
классифицирует по слоям и маршрутизирует к рою deep-dive-исполнителей (прямой
вызов исполнителя тоже допустим). Семантический поток сверху вниз: бизнес
заказчика (+ реестр проблем) → сегменты и граф работ → SWOT → Карта гипотез
(терминал — `task`). Исход — задача, закрывающая проблему, либо **опционально**
продукт → интерфейс / сервисы и домены / экраны. Артефакты `docs/` — design-time
source of truth; когда дело дошло до продукта, их читают соседние форки
(`<org>/{backend,frontend,site,mobile,infra}` и `<org>/<bot>`).

## 0. Форк

1. Корень проекта — первым: папка `~/git/<org>/` с картой проекта `CLAUDE.md` и
   общими настройками сессии, по
   [`docs/reference/project-root.md`](https://github.com/stit-core/project-infra-template-compose/blob/main/docs/reference/project-root.md)
   шаблона хаба. В неё клонируются все репо проекта, и из неё ведётся вся работа.
2. Gitea (`https://git.stit.tech`) → `stit-core/business-strategy-template` →
   **Use this template** → `<org>/strategy`.
3. Клон в корень: `git clone git@git.stit.tech:<org>/strategy.git ~/git/<org>/strategy`.
4. `claude` — в корне проекта: `cd ~/git/<org> && claude`. Перед работой здесь
   сессия корня читает `CLAUDE.md` этого репо — с ним подхватываются правила и
   скиллы strategy; дальше вход `/entrypoint` (клиент — `/entrypoint-for-business`).
   Сессия прямо в `~/git/<org>/strategy` — тоже нормальный режим.
5. Форкается **первым** в экосистеме: проектирование стартует здесь. Когда
   стратегия рождает продукт, остальные форки читают `<org>/strategy` как
   upstream-аналитику (`docs/README.md § Что docs отдаёт соседям`), а программы
   сквозных задач и выкатка — в хабе `<org>/infra` (`docs/README.md § Где это в
   экосистеме`).

## Путь

```
0. Корень ~/git/<org>/ → Use this template → <org>/strategy → клон в корень → claude в корне
   Вход аналитика: /entrypoint — приносишь сырьё, оркестратор маршрутизирует.
                   Прямой вызов исполнителей ниже тоже допустим.
   Вход клиента:   /entrypoint-for-business — одной командой про всё (бизнес,
                   клиенты, продукт); оркестратор сам ведёт все темы.
1. Бизнес заказчика → /business-deep-dive (профиль + реестр проблем business-problem)
2. Сегменты и работы → /segment-deep-dive (сегменты по работам + Score, рой)
   ├─ /job-graph-deep-dive <segment> (граф работ, решения, трения)
   ├─ /jtbd-interview (опц.: рекрут → скрипт → интервью → конспект)
   └─ /ajtbd-audit — инварианты графа работ (рой)
3. SWOT и Карта гипотез
   ├─ /swot-deep-dive (факторы → ставки)            → /swot-audit
   └─ /hypothesis-map-deep-dive (цель → метрика → субъект → гипотеза) → /hypothesis-map-audit
4. Продукты (опц.)  → /project-deep-dive <slug> (vision + surface-реестр + kind + capability/<surface>)
   ├─ /project-audit <slug>
   ├─ /interface-deep-dive <slug> [<surface>]  → /interface-audit <slug>
   ├─ /service-deep-dive <slug> (сервисная топология) → /service-audit <slug>
   ├─ /domain-deep-dive <slug> <ctx> (DDD внутри сервиса)
   ├─ /screen-deep-dive <slug> [<surface>]     → /screen-audit <slug>
   ├─ /fsd-deep-dive <slug> [<surface>] (фронтовые поверхности) → /fsd-audit <slug>
   ├─ /design-deep-dive <slug> [<surface>] (факты и голос продукта, слой страницы
   │  сайта и лендинга, облик и макет) → /design-audit <slug>
   ├─ /telegram-bot-flow-deep-dive <slug> [<surface>] (bot-поверхности — вместо
   │  screen) → /telegram-bot-flow-audit <slug>
   └─ /mobile-deep-dive <slug> [<surface>] (мобильные поверхности — вместо
      screen) → /mobile-audit <slug>
5. ИТ-периметр бизнеса → /infrastructure-deep-dive (сервера · рантаймы ·
   общие ресурсы · джобы · размещение) → /infrastructure-audit
6. /cross-audit — сквозная семантика между слоями (рой)
7. готовый репо стратегии (с продуктами, если до них дошло)
   → продукт спроектирован: реализация из корня — /init-project в <org>/infra,
     сквозные задачи — программами хаба <org>/infra
```

Это не жёсткая лестница: информация приходит не линейно, оркестратор ведёт по
слоям в нужном порядке. Семантический поток зависимостей и рой исполнителей — в
корневом `README.md § Воркфлоу`. В клиент-режиме все темы — включая SWOT и
Карту гипотез — ведёт сам `/entrypoint-for-business`, единый клиентский вход.

## 1. Бизнес заказчика — `docs/business/`

Самая верхняя точка. Без профиля бизнеса проблемы и продукты висят в воздухе.

- **`/business-deep-dive`** (аналитик) — приём материалов клиента (сайт, PDF,
  презентации, соцсети, интервью) + рой web-research рынка и конкурентов;
  ведёт через фазы intake → profile → market → structure → metrics → problems →
  cohesion, заполняет `docs/business/{profile,offering,channel,competitor,current-metric,material,business-problem}.md`
  (включая реестр проблем бизнеса — граница гарантии scope и best-effort таргета).
- Заказчик/основатель ведёт сессию сам — через единый вход
  **`/entrypoint-for-business`** (режим «домашнее задание», бизнес-язык без
  slug/kind): оркестратор сам разложит рассказ по темам и упакует результат в
  единую ветку `client` для передачи аналитику.

## 2. Сегменты и граф работ — `docs/ajtbd/`

Разведка по методологии Advanced JTBD: кто наш сегмент **по работам**, а не по
демографии, его граф работ и где он трётся с текущими решениями. 5 kind:
`segment` · `job` · `job-graph` · `solution` · `segment-problem`. Слой питает
проблемы бизнеса (трения доказывают проблему) и продукты (механики ценности →
возможности).

- **`/segment-deep-dive`** (аналитик) — поиск, кластеризация и скоринг
  сегментов (Score = важность × частотность × размер × (10 − удовлетворённость))
  через многоволновой рой web-research.
- **`/job-graph-deep-dive <segment>`** (аналитик) — граф работ выбранного
  сегмента: целевая работа вверх/вниз/по последовательности, нанятые решения,
  трения, CPR и кандидаты-механики ценности.
- В клиент-режиме клиенты и их работы заказчик описывает сам через единый
  вход **`/entrypoint-for-business`** (бизнес-язык, без slug).
- **`/jtbd-interview`** — опц. тяжёлый процесс живых JTBD-интервью (рекрут →
  скрипт → проведение → конспект), собирает сырьё в ветку
  `entrypoint/state/ajtbd/_interview/`; выход разбирается через intake в
  скилы выше. Запускается по явному запросу.
- **`/ajtbd-audit`** — рой агентов проверяет инварианты графа работ по каждому
  сегменту. Только отчёт.

## 3. SWOT и Карта гипотез — `docs/swot/` · `docs/hypothesis-map/`

Реестр проблем бизнеса (`business-problem` в `docs/business/`) разворачивается в
два строгих многопроблемных слоя: каждая запись несёт массив `business-problem` (M:N к
строкам реестра).

- **`/swot-deep-dive`** (аналитик, `docs/swot/`) — из сильных/слабых сторон и
  трендов/угроз бизнеса (`factor`) рождаются стратегические ставки (`bet`),
  доводимые (`promoted-to`) до цели или гипотезы Карты гипотез.
- **`/swot-audit`** — рой агентов проверяет инварианты LinkedSWOT по каждой
  проблеме (баланс факторов, ставка-висяк, фактор без ставки, …).
- **`/hypothesis-map-deep-dive`** (аналитик, `docs/hypothesis-map/`) — причинная
  цепь цель → измеримая метрика → субъект → гипотеза → задача проверки. Ядро —
  метрика как **best-effort таргет** (не гарантия) с baseline, источником истины,
  атрибуцией и критерием приёмки.
- **`/hypothesis-map-audit`** — рой агентов проверяет инварианты Карты гипотез по
  каждой проблеме (задача-сирота, «тогда» без метрики, метрика без влияния,
  целевая без guardrail, …). Только отчёт, не правит.

В клиент-режиме SWOT и Карту гипотез, как и все остальные темы, ведёт сам
`/entrypoint-for-business` — единый клиентский вход.

## 4. Продукты — `docs/projects/<slug>/` (опционально)

Опциональный downstream — когда исход стратегии требует продукта (иначе проблему
закрывает задача `task` Карты гипотез). Несколько продуктов под одним бизнесом, у
каждого своя папка. Все скиллы слоёв принимают `<project-slug>` первым аргументом
(без него — пикер по именам проектов, исключая `_template`); interface, screen,
fsd, design, telegram-bot-flow и mobile берут вторым аргументом поверхность (без
неё — пикер по именам из `surface.md`; `/design-deep-dive` без поверхности ведёт
уровень продукта).

- **`/project-deep-dive <slug>`** (аналитик) — vision (+ `addresses-problem`
  M:N к проблемам) + реестр-хребет `surface.md` (тип и род поверхности) +
  кросс-поверхностные kind (user / object / action / integration / boundary /
  constraint / market) + возможности по поверхности
  `capability/<surface>.md`. Поверхность — ось: её slug'и
  партиционируют capability / interface / screens. Новый проект заводит сам
  скилл (копирует форму из `_template/project/`). В клиент-режиме продукт
  заказчик описывает сам через единый вход **`/entrypoint-for-business`**.
- **`/project-audit <slug>`** — узкий аудит внутри продуктового слоя.
- **`/interface-deep-dive <slug> [<surface>]`** → **`/interface-audit <slug>`**
  — UX-слой по поверхности (who / stage / situation / scenario / zone / block /
  ux-substrate / data-items в `interface/<surface>/`; у сайта и лендинга его нет).
- **`/service-deep-dive <slug>`** → **`/service-audit <slug>`** — сервисная
  топология бэкенда: реестр сервисов (`service.md`), паспорта (Exposes /
  Dependencies / Resources / Messaging), платформенные ресурсы
  (`platform.md`), свод и решения разбиения (`architecture.md`); монолит =
  один сервис.
- **`/domain-deep-dive <slug> <ctx>`** — DDD-артефакты бэкенда продукта по
  bounded-context, внутри сервиса-владельца (surface-агностичны; внешние и
  межпроектные интеграции — через конкретный клиент
  `services/_shared/integrations/<slug>/` и потребление функций в use-case,
  домен transport-agnostic). Завершается на stable-артефакте; Go-код по ним
  разворачивает соседний `<org>/backend`, не этот репо.
- **`/infrastructure-deep-dive`** → **`/infrastructure-audit`** —
  ИТ-периметр бизнеса (`docs/projects/infrastructure/`, один на все
  проекты): учёт серверов, рантаймы (kubernetes/compose по окружениям),
  общие платформенные ресурсы, обслуживающие джобы (бэкапы, ротация,
  сертификаты), размещение юнитов (`placement.md`). По нему
  `<org>/infra` понимает, что билдить и где располагать.
- **`/screen-deep-dive <slug> [<surface>]`** → **`/screen-audit <slug>`** —
  композиция экранов по поверхности (flow / screen / block / shell, карта
  экранов `map.md` и тексты интерфейса `texts.md` в `screens/<surface>/`) в
  нотации семантического дерева; макет по ней собирает слой дизайна
  (`design/`).
- **`/fsd-deep-dive <slug> [<surface>]`** → **`/fsd-audit <slug>`** — FSD-карта
  фронтовой поверхности кабинета (`fsd/<surface>/`): слайсы из ситуаций, экранов
  и доменов — мост к коду `<org>/frontend`.
- **`/design-deep-dive <slug> [<surface>]`** (аналитик) — факты и
  голос продукта в корне проекта (вызов без поверхности — и у продукта без
  сайта), слой страницы сайта и лендинга (`site/<surface>/` у `web` рода
  `landing` и `site` — вместо interface, screens и FSD: бриф, смысл, карта,
  планы, тексты по слотам) и облик продукта (`design/`: бренд, дизайн-система,
  направления, ассеты, макет в Claude Design, приёмка, манифест готовности для
  код-репо). Тексты и облик агент предлагает «допущением», утверждает владелец
  продукта; картинки, видео и 3D генерируются только после утверждения плана
  ассетов. Закрытое читают `<org>/site` и `<org>/frontend`.
- **`/design-audit <slug>`** — проверка слоя страницы, слоя дизайна и файлов
  уровня продукта: схемы, ссылки, покрытие текстами, фактами, ассетами и
  компонентами дизайн-системы, свежесть производных и приёмки; макет на всех
  ширинах — только по просьбе заказчика. Только отчёт.
- **`/telegram-bot-flow-deep-dive <slug> [<surface>]`** →
  **`/telegram-bot-flow-audit <slug>`** — диалоги телеграм-бота по
  bot-поверхности (вместо screens): фичи `features/<feature>/` (dialog /
  window / use-case бота) + сквозные command / notification в
  `telegram-bot-flow/<surface>/`. Stable-артефакты читает форк
  `<org>/<bot>`.
- **`/mobile-deep-dive <slug> [<surface>]`** → **`/mobile-audit <slug>`** —
  карта мобильного приложения по мобильной поверхности (вместо screens):
  сущности, экраны, сценарии, фичи, оболочка, точки входа (deep link, push,
  ярлык, share, тап по виджету), разрешения, системные действия (голос,
  автоматизации, кнопки виджета и уведомления), виджеты и фоновые задачи в
  `mobile/<surface>/`. Скилл проводит по линзе возможностей платформы —
  знать заранее, что умеет телефон, не нужно. Stable-артефакты читает форк
  `<org>/mobile`.

Точки стыка **между продуктами** бизнеса фиксируются в
`docs/projects/project-map.md` (авторская сторона — `integration` с
`target: sibling-project`); сверяет `/cross-audit`.

Каждый deep-dive ведёт сессию через `AskUserQuestion`, пишет память в свою
ветку единого дерева оркестратора (`.claude/skills/entrypoint/state/`;
клиент-режим — `.claude/skills/entrypoint-for-business/state/`), не
выдумывает домен (облик предлагает только слой дизайна — «допущением»), не
повышает `draft → stable` без явного подтверждения.

**Окружение скилла дизайна.** Утилиты скилла дизайна ставит
`.claude/skills/design-deep-dive/scripts/install.sh` вне репозитория, в
`~/.cache/design-deep-dive/` — одно окружение на машину. Нужен Python 3.12–3.13:
скрипт берёт python3.13 или python3.12 сам, другой путь — ключом `--python`.
npm-пакеты ставятся группами — по умолчанию замеры страницы и доступности,
`--npm-groups media,3d` добавляет SVG и Lottie, проверку glTF и 3D-сборки;
утилитам ai-media с метриками картинок нужна группа pip `media`. Что стоит и
чего нет — `install.sh --check`, что утилиты отвечают —
`scripts/tests/smoke.py` скилла. Ключи генерации картинок и видео — у владельца
денег; 3D делается Blender и кодом, генераторов 3D нет. База знаний, утилиты и калибровочный
набор скилла — часть шаблона: в форке их не правят (ошибку нормы или утилиты —
записью в бэклог шаблона), а скилл обновляют заменой его папки
`.claude/skills/design-deep-dive/` из шаблона и переустановкой окружения; версия скилла — файл
`VERSION` в его папке.

**Бэклог шаблона.** Что мешало в работе с репозиторием — скилл повёл не туда,
проверка ошиблась, шаг непонятен, — агент записывает в `.claude/backlog/`, файл
на проблему (`CLAUDE.md` §10). По этим записям шаблон развивают: тот, кто его
ведёт, заходит в проект и читает бэклог.

## 5. Сквозной аудит — `/cross-audit`

В конце или после крупных изменений. Рой агентов проверяет семантику между
слоями: business ↔ ajtbd ↔ swot ↔ hypothesis-map ↔ (по каждому проекту: project ↔
interface ↔ services/domain ↔ screen, по каждой поверхности) ↔ межпроектные стыки
(`project-map`). Не slug-валидация — смысловая проверка («пользователь
без UX-покрытия», «сегмент без пользователя», «проблема бизнеса без единого
трения-доказательства», «проблема, которую не закрывает ни один проект»,
«поверхность без возможностей», «интеграция к соседнему проекту без ребра в
карте», «метрика как гарантия»). Только отчёт; деструктивные правки — через
соответствующий deep-dive.

## Готово

Репо наполнено стратегией бизнеса: свой бизнес, свои проблемы, ставки и гипотезы —
и продукты, если до них дошло. Дальше — обычный аналитический флоу по воркфлоу
(`README.md`), под git-ревью.

Когда продукт спроектирован, следующий шаг — реализация из той же сессии корня
проекта: `/init-project` в `<org>/infra` читает strategy и проектирует инфру,
сквозная задача ведётся программой в `.claude/plans/` хаба `<org>/infra`, её фазы
сессия корня ведёт по репо сама или фоновыми агентами, а соседние форки
(`<org>/{backend,frontend,site,mobile,infra}` и `<org>/<bot>`) читают
stable-артефакты как upstream (`docs/README.md`). Изменение дизайна по ходу —
здесь, скиллами этого репо из той же сессии корня.

## Когда что-то идёт не так

- **Артефакт не `stable`** → доведи через соответствующий deep-dive того же слоя.
- **Подозрение на рассинхрон внутри слоя** → узкий аудит
  (`/project-audit`, `/interface-audit`, `/screen-audit`, `/fsd-audit`,
  `/design-audit`, `/telegram-bot-flow-audit`, `/mobile-audit`, `/service-audit`,
  `/infrastructure-audit`,
  `/swot-audit`, `/hypothesis-map-audit`, `/ajtbd-audit`).
